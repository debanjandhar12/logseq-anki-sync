## 2. Final Requirement After Discussion With User

### 2.1 Clarification Q&A

- **Question:** Should the fallback simply render every `requires-action` call as running?
  - **Initial answer:** Yes, as a possible small fix.
  - **Clarification:** Official assistant-ui semantics reserve tool-part `requires-action` for unresolved user/UI input, approval, or interruption. Automatically executing tools should be `running`.
  - **Final direction:** Fix the custom adapter's lifecycle rather than weakening `ToolFallbackImpl` semantics. Match the installed assistant-ui AI SDK integration as closely as LocalRuntime permits, and correct related consumers that conflate running work with required user action.
- **Question:** Is inline frontend execution the standard assistant-ui architecture?
  - **Answer after source inspection:** No. Canonical `useChatRuntime`/`useAISDKRuntime` uses `ExternalStoreRuntime`; its `ToolInvocationTracker` executes browser tools outside a `ChatModelAdapter`, keeps the message running while any executor is active, writes results through AI SDK `addToolOutput`, and relies on `sendAutomaticallyWhen` for another request. This project intentionally uses branch-aware `LocalRuntime`, whose installed core does not wire that tracker, so inline adapter execution is a project-specific compatibility layer. It should emulate the canonical status lifecycle while retaining LocalRuntime continuation.

### 2.2 Final Summarized Requirements

- Keep automatic frontend tool calls in assistant-ui's native `running` state while model streaming or inline execution is active, so the existing circular loader and shimmer appear.
- Emit final `requires-action/tool-calls` only when LocalRuntime needs to continue after recorded tool results or when an unresolved human/approval call genuinely needs action.
- Keep genuine human tools, approvals, and interrupts visually distinct and actionable without a running animation.
- Preserve branch-aware LocalRuntime, sequential frontend execution, model roundtrips, persistence, custom tool renderers, provider-executed tools, and cancellation behavior.
- Treat multiple tool calls emitted in one model step as an ordered batch: call N+1 must not start until call N has settled, its result has been merged into current content, and that update has been yielded. Do not adopt `ToolInvocationTracker`'s independent/concurrent execution behavior.
- Audit and fix directly related status consumers, especially chain-of-thought activity and action-required visibility.
- Add focused regression tests for the custom adapter lifecycle and affected UI.

## 3. Existing System

### 3.1 Canonical assistant-ui AI SDK behavior

- Installed versions are `@assistant-ui/core@0.2.21`, `@assistant-ui/react@0.14.27`, `@assistant-ui/react-ai-sdk@1.3.41`, and AI SDK `ai@7.0.31`. Installed source is authoritative; current docs/upstream may be newer.
- `@assistant-ui/react-ai-sdk/src/ui/use-chat/useAISDKRuntime.ts` builds an `ExternalStoreRuntime` with tool invocations enabled.
- `@assistant-ui/core/src/runtimes/tool-invocations/ToolInvocationTracker.ts` invokes registered frontend `execute`/`streamCall` callbacks as soon as complete arguments are available. `frontendTools()` only exposes schemas to the model and does not execute browser tools on the server.
- The AI SDK runtime considers a thread running while the request is submitted/streaming **or** any frontend tool tracker is executing. Its external-message auto-status then yields:
  - `running` while streaming/execution is active;
  - `requires-action/interrupt` for unresolved human interruption;
  - `requires-action/tool-calls` for another unresolved call after active execution stops;
  - `complete` when everything is resolved.
- Tool parts without results inherit message status; parts with results become complete. Thus canonical frontend tools render `running` while executing and genuine pauses render `requires-action`.
- Tool results are recorded through `addToolOutput`. A subsequent model request is automatic only when the application configures AI SDK `sendAutomaticallyWhen` (commonly `lastAssistantMessageIsCompleteWithToolCalls`).
- Canonical AI SDK integration tracks message-level streaming timing, extended through frontend execution. It does not automatically assign per-tool `timing`; `useToolCallElapsed()` only displays when a host/runtime supplies part timing.

### 3.2 This project's LocalRuntime adapter

- `src/chat-app/runtime/LocalChatModelAdapter/LocalAISDKChatModelAdapter.ts` intentionally uses `LocalRuntime` because the AI SDK external-store runtime does not provide the required message branching behavior.
- Installed LocalRuntime does not instantiate `ToolInvocationTracker`; therefore the adapter must execute frontend tools itself.
- The adapter currently yields `{type: "requires-action", reason: "tool-calls"}` immediately when a frontend call arrives, waits for the stream to finish, then executes queued non-human calls sequentially and keeps yielding the same status.
- `src/chat-app/runtime/LocalChatModelAdapter/tool-execution.ts` performs the actual `tool.execute(...)` await.
- LocalRuntime's `shouldContinue` loop requires the adapter's **final** status to be `requires-action/tool-calls`. Once non-human results are present and human/approval gates are resolved as required, LocalRuntime invokes the adapter again for the next LLM step. Intermediate yields do not need to use that final continuation status.
- This premature status transition is the root cause: unresolved automatic parts inherit `requires-action`, so `ToolFallbackImpl` correctly renders its alert icon instead of `LoaderCircleIcon`.

### 3.3 Related UI behavior

- `src/chat-app/components/ToolFallback.tsx` already follows documented assistant-ui status semantics:
  - `running` -> circular loader, `animate-spin`, shimmer;
  - `requires-action` -> alert and expanded details;
  - terminal statuses -> success/failure/cancellation presentation.
- Therefore the primary fix should not reinterpret `requires-action` inside this component.
- `useToolCallElapsed()` currently returns nothing because the custom adapter supplies no part timing. This is a separate missing lifecycle feature discovered during the audit; adding supported per-tool timing is appropriate if done at actual execution start/completion.
- `src/chat-app/components/AssistantMessage.tsx` treats both `running` and `requires-action` groups as actively streaming, incorrectly applying spinner/shimmer/preview/`aria-busy` semantics to genuine human action.
- `LogseqCommitChangesTool` is deliberately standalone. Other genuinely unresolved human/approval calls may still be grouped inside a collapsed chain-of-thought section.

### 3.4 Other findings and constraints

- A registered non-human tool without `execute` is currently not queued, despite `executeFrontendTool()` having an explicit missing-executor error response; it can remain unresolved.
- Cancellation is currently converted by `executeFrontendTool()` into a tool error response before project stop logic terminates the turn. This behavior has existing tests and should only change if adapter lifecycle tests demonstrate a continuation or stale-running bug.
- Installed assistant-ui has falsey-result checks (`!part.result`) in some LocalRuntime/part-status paths. The project should consistently produce defined result envelopes such as `ChatToolResponse`, and regression tests should expose any locally actionable falsey-result mismatch without editing dependencies.
- Message-level consumers in `Composer.tsx`, `ComposerAction.tsx`, `stopThread.ts`, `terminateToolTurn.ts`, and `recoverInterruptedMessages.ts` intentionally treat active execution and paused action states as non-sendable/stoppable/recoverable turns. They should remain unchanged unless tests identify a regression.
- Customized assistant-ui files live under `src/chat-app/components`; original registry files under `src/shadcn` and `node_modules` must not be edited. Changes to copied components require updates to their `Changes:` comments.
- Vitest only includes `*.test.ts`; React tests use jsdom with `createRoot`/`act`.

## 4. Solution

### 4.1 Correct status transitions in `LocalAISDKChatModelAdapter`

Update `LocalAISDKChatModelAdapter.run` in `src/chat-app/runtime/LocalChatModelAdapter/LocalAISDKChatModelAdapter.ts` to emulate canonical assistant-ui behavior while preserving LocalRuntime's final handshake:

1. When a non-provider tool call arrives, append/yield it without changing the active assistant message to `requires-action`; LocalRuntime's default/current run status remains `running`.
2. Classify the registered tool:
   - non-human frontend tool: queue it for automatic execution;
   - human tool or pending approval/interrupt: leave it unresolved for user action;
   - provider-executed tool: retain its existing provider stream/result path.
3. Continue yielding cumulative current-step content as `running` through the rest of model streaming.
4. Execute queued frontend tools sequentially as today. Immediately before each await, yield running content if needed so the UI has committed the unresolved call before execution begins.
5. After each automatic result, merge it into content and yield while the adapter run is still active before starting the next queued call. Resolved calls become complete at part level; any remaining automatic call stays running.
6. After all inline work settles, make the **final** yield `{type: "requires-action", reason: "tool-calls"}` whenever client tool calls occurred. This preserves LocalRuntime `shouldContinue`: it immediately starts the next model step when non-human results are ready, or remains paused when a human/approval call is unresolved.
7. Keep ordinary no-tool completion and provider-only finish handling unchanged.
8. Queue non-human tools even when `execute` is absent so the existing defensive path records an error result instead of leaving an unresolved call.
9. Update the adapter's architecture comment to distinguish intermediate execution status from the final LocalRuntime continuation signal.

Important edge cases:

- Multiple automatic calls remain strictly sequential to avoid reordering Logseq mutations: call N+1 starts only after call N settles and its result update is yielded. While the adapter run is active, unresolved queued calls may inherit message-level `running`, matching assistant-ui's message-scoped status model, but that presentation must not imply concurrent execution.
- If automatic and human calls coexist, the message remains running until automatic work completes, then the final `requires-action` state exposes the unresolved human call. This matches canonical auto-status precedence: active execution wins over pending action.
- Abort must stop subsequent queued execution and must not leave a persisted running message. Preserve current stop/termination integration; alter `executeFrontendTool()` abort propagation only if the new test demonstrates that the current error conversion permits unwanted continuation.

### 4.2 Add supported per-tool timing without replacing status

Use assistant-ui's existing `ToolCallMessagePart.timing` field in the same adapter:

- Set `startedAt` immediately before an automatic tool's `execute` begins, not when it is merely emitted/queued.
- Yield the updated part before awaiting execution so `useToolCallElapsed()` can begin ticking for the actually executing call.
- On success or ordinary tool error, preserve `startedAt` and set `completedAt` when the await settles.
- Do not add execution timing to human or provider-executed calls; provider timing remains owned by its stream/runtime.
- On cancellation, ensure the message becomes incomplete/cancelled through existing stop handling and that no live timing remains presented. A missing `completedAt` on an incomplete call intentionally means duration is unknown.

This uses a documented host-tracked field and allows the existing `ToolFallbackDuration`/`useToolCallElapsed()` implementation to work without a parallel execution-state store or custom timer.

### 4.3 Keep `ToolFallbackImpl` semantic and make only necessary refinements

In `src/chat-app/components/ToolFallback.tsx`:

- Do not treat `requires-action` as running and do not add a custom execution classifier.
- Retain the existing icon map, `animate-spin`, shimmer, `useToolCallElapsed()`, cancellation behavior, and action-state expansion.
- If regression tests expose accessibility ambiguity, replace raw status labels with explicit labels (“Tool is running”, “Tool requires user action”, etc.) without changing state behavior.
- Update the copied-component `Changes:` comment only if this file is modified.

With corrected adapter yields, the existing running branch is the direct fix for the missing circular animation.

### 4.4 Correct grouped execution versus action semantics

Update `src/chat-app/components/AssistantMessage.tsx`:

- Treat a chain-of-thought group as actively streaming only when `part.status.type === "running"`; generic `requires-action` must not set `ReasoningRoot.streaming`, `ReasoningTrigger.active`, or `aria-busy`.
- Keep automatic tool calls grouped during running and completion.
- Extend `groupMessagePart` so an unresolved tool part whose derived status is genuinely `requires-action` renders standalone. This makes human/approval UI visible rather than hiding it inside a collapsed reasoning group.
- Preserve the existing standalone rule for `LogseqCommitChangesTool` and custom renderer precedence (`part.toolUI ?? <ToolFallback ... />`).
- Update the file's `Changes:` comment to document the corrected activity and grouping behavior.

Because the adapter now uses native statuses, this logic does not need a project-owned lifecycle registry or indexed group inspection.

### 4.5 Preserve intentional message-level controls

Do not change these unless regression tests fail:

- `src/chat-app/components/Composer.tsx`
- `src/chat-app/components/ComposerAction.tsx`
- `src/chat-app/runtime/stopThread.ts`
- `src/chat-app/runtime/terminateToolTurn.ts`
- `src/chat-app/runtime/recoverInterruptedMessages.ts`

The composer should remain blocked and the stop action available both during active execution and while the current turn genuinely awaits required action. Recovery should still cancel interrupted automatic turns while retaining actionable human tools.

### 4.6 Regression tests

Add `tests/src/chat-app/runtime/LocalChatModelAdapter/LocalAISDKChatModelAdapter.test.ts`, mocking AI SDK streaming, registered tools, and the clock. Verify:

1. An automatic call is yielded with message status `running` before and during its executor.
2. `timing.startedAt` appears immediately before execution and `completedAt` appears with the result.
3. The adapter's final yield is `requires-action/tool-calls`, allowing LocalRuntime continuation after results.
4. A human tool is never executed and ends in genuine `requires-action` without automatic timing.
5. Mixed automatic/human calls remain running during automatic work, then end action-required for the human call.
6. Multiple automatic calls execute sequentially in emitted order; deferred promises/spies prove call N+1 is not invoked until call N resolves and its result-bearing yield has occurred. Timing starts only when each call actually begins, so queued calls do not accrue execution duration.
7. Missing executor and ordinary exceptions become defined error results and do not leave unresolved running parts.
8. Provider-executed calls retain existing stream status/result handling and receive no frontend timing.
9. Cancellation prevents later queued calls and leaves the turn cancelled rather than persistently running or continuing to another model step.

Extend `tests/src/chat-app/runtime/LocalChatModelAdapter/tool-execution.test.ts` only if abort propagation must change.

Add `tests/src/chat-app/components/ToolFallback.test.ts` using the existing `createRoot`/`act` pattern to verify:

- native `running` renders `LoaderCircleIcon` through its accessible label/data slot, `animate-spin`, and shimmer;
- supplied active timing displays and advances, then freezes at completion;
- `requires-action` renders an alert, does not spin/shimmer, and opens its details;
- complete, error, and cancelled states remain terminal and distinct.

Add focused `AssistantMessage`/`groupMessagePart` coverage to verify running groups are busy, action-required tools are standalone and non-animated, and custom tool UIs retain precedence.

Avoid assertions on Lucide SVG internals; assert accessible labels, `data-slot`, classes, disclosure state, and `aria-busy`.
