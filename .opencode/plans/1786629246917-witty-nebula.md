# Refactor Frontend Tool Execution Around assistant-ui Conventions

## 1. User Requirement

> Any way to make this cleaner and more maintainable while also following assistant ui conventions?

## 2. Final Requirement After Discussion With User

### 2.1 Clarification Q&A

- **Question:** How broad should the maintainability refactor be?
- **Answer:** Full cleanup.

### 2.2 Final Summarized Requirements

- Preserve the working behavior: branch-aware assistant-ui `LocalRuntime`, native `running`/`requires-action` status semantics, strict sequential project-managed frontend execution, per-tool timing, human-action safety, provider tools, result truncation/artifacts, persistence, and cancellation.
- Make `LocalAISDKChatModelAdapter` a thin orchestration boundary rather than the owner of model streaming, planning, execution, normalization, storage, and continuation policy.
- Introduce a pure, ordered tool-call planner and a dedicated sequential executor; do not adopt `ToolInvocationTracker`, `useChatRuntime`, parallel execution, or a generic queue/state-machine framework.
- Represent cancellation as terminal control flow rather than an ordinary tool error.
- Resolve unknown and malformed tool calls deterministically instead of leaving them unresolved.
- Build `ChatToolRegistry` once per mounted chat app and derive the toolkit, human names, and display metadata from that same instance.
- Use assistant-ui toolkit `display: "standalone"` and human-tool defaults instead of tool-name/status grouping exceptions.
- Decompose raw invocation, response normalization, model-output projection, and oversized-result storage into testable boundaries.
- Add planner, executor, adapter, registry/UI, and real LocalRuntime integration coverage, including branch isolation and continuation.
- Update relevant Docusaurus documentation for the custom LocalRuntime frontend-tool lifecycle.

## 3. Existing System

### 3.1 Behavior that must remain

- `src/chat-app/runtime/LocalChatModelAdapter/LocalAISDKChatModelAdapter.ts` uses `LocalRuntime` because the AI SDK/ExternalStore runtime does not satisfy the project’s message-branching requirements.
- Project-managed frontend tools execute inline after the AI SDK model stream and in strict emitted order. Call N+1 cannot start until call N settles and its result update has been yielded.
- Intermediate assistant/tool state is `running`; the final `{type: "requires-action", reason: "tool-calls"}` is LocalRuntime’s continuation handshake. LocalRuntime immediately continues when automatic calls are resolved, or remains paused for unresolved human tools/approvals.
- Automatic calls after the first human-action boundary are not executed. They receive a defined blocked error so they cannot bypass user authorization or leave LocalRuntime in an unresolved loop.
- `ToolCallMessagePart.timing` supplies `startedAt`/`completedAt` to assistant-ui’s `useToolCallElapsed()`.
- Provider-executed tools are owned by the provider/AI SDK stream and must remain outside the project frontend planner.
- `tool-execution.ts` supplies branch-aware messages, cancellation, `ToolResponse` normalization, artifacts, `toModelOutput`, and oversized-result storage/truncation.

### 3.2 Maintainability issues

- `LocalAISDKChatModelAdapter.run` owns model lookup, branch reconstruction, request conversion, stream parsing, provider calls, frontend policy, sequential execution, timing, usage metadata, errors, and LocalRuntime continuation.
- Human-boundary policy is embedded as a boolean inside the stream switch rather than expressed as a pure, exhaustive plan.
- Unknown emitted tool names can remain unresolved because they are neither human nor executable.
- Missing executors are discovered late inside execution rather than classified by the planner.
- `executeFrontendTool` mixes invocation, cancellation race, normalization, persistence/truncation, model-output conversion, and ordinary error conversion.
- Cancellation is currently caught as an ordinary tool failure; correctness relies partly on LocalRuntime noticing the aborted signal before applying a later yield.
- `ChatToolRegistry.build()` runs independently in `AppContent.tsx` and `useThreadBoundLocalAISDKChat.ts`, allowing the registered toolkit and runtime human-name list to drift.
- `AssistantMessage.groupMessagePart` contains project-specific tool-name/status conditions even though installed assistant-ui supports human-default and explicit `display: "standalone"` toolkit metadata.
- Existing adapter tests directly consume the generator but do not fully prove LocalRuntime continuation, branch ancestry, persistence, or cancellation end-to-end.

### 3.3 assistant-ui conventions and constraints

- Keep installed `@assistant-ui/react@0.14.27`, `@assistant-ui/react-ai-sdk@1.3.41`, `assistant-stream@0.3.26`, and `ai@7.0.31`; no new dependency is needed.
- The installed `ToolInvocationTracker` belongs to ExternalStoreRuntime, starts calls as arguments complete, and supports independent/parallel execution. Reusing or forking it would conflict with LocalRuntime, strict serial ordering, branch messages, human boundaries, and project result storage.
- Continue using schema-only `frontendTools(toToolsJSONSchema(...))`; do not give AI SDK real project frontend executors.
- Installed assistant-ui’s `groupPartByType` recognizes `"standalone-tool-call"` through toolkit registration. Human tools default to standalone; explicit `display` overrides the default.
- Keep custom components under `src/chat-app/components`; do not edit registry copies under `src/shadcn` or installed dependencies. Update copied-component `Changes:` comments when behavior changes.
- Settings must continue through `LogseqSettingAccessor`; no module-global tool registry because settings are sampled at chat-app mount.

## 4. Solution

- Build one `ChatToolRegistry` with `useMemo` per mounted chat app.
- Expose `useChatToolRegistry()` through React context and fail clearly outside the provider.
- Expose stable snapshots for the assistant-ui toolkit and readonly human-tool names, either from the provider value or memoized registry getters.
- Do not use a global singleton or make settings reactive as part of this refactor.

- `src/chat-app/components/AppContent.tsx`: remove its `ChatToolRegistry.build()` and consume the shared toolkit for `Tools({toolkit})`.

### 4.3 Separate tool-call message transforms

Create `src/chat-app/runtime/LocalChatModelAdapter/tool-call-message-part.ts` containing pure message concerns:

- `ToolCallMessagePart` type.
- `createToolCallMessagePart`.
- `updateToolCall`.
- `updateProviderToolCall` if keeping provider updates beside generic content transforms is clearer.

Update imports in the adapter, message conversion, planner/executor, and tests. This prevents conversion code from depending on an execution module merely for a type.

### 4.4 Add a pure ordered planner

Create `src/chat-app/runtime/LocalChatModelAdapter/frontend-tool-planner.ts` with:

```ts
type FrontendToolPlanItem =
    | {kind: "execute"; toolCall: ToolCallMessagePart; tool: Tool}
    | {kind: "await-human"; toolCall: ToolCallMessagePart}
    | {
          kind: "final-error";
          reason: "unknown-tool" | "missing-executor" | "blocked-by-human";
          toolCall: ToolCallMessagePart;
          message: string;
      };
```

Export a pure `planFrontendToolCalls(emittedCalls, tools)` that preserves model order and applies these rules:

1. Registered human tool -> `await-human` and establish the human-action boundary.
2. Any later registered automatic frontend tool -> `final-error/blocked-by-human`; never execute it.
3. Unknown name -> `final-error/unknown-tool` with a deterministic result.
4. Registered non-human tool without executor -> `final-error/missing-executor`.
5. Otherwise -> `execute`.

Unknown/missing calls do not establish a human boundary. Do not mutate inputs, access clocks/runtime state, or use a queue class.

### 4.5 Decompose invocation and response processing

Refactor `src/chat-app/runtime/LocalChatModelAdapter/tool-execution.ts` into narrow operations:

- `invokeFrontendTool`: invoke the executor with `toolCallId`, `abortSignal`, current branch messages, and a defensive throwing `human()`; race with abort; return raw output; surface cancellation distinctly.
- Replace the current `as any` context cast with a documented local intersection type at the assistant-stream integration boundary.
- `normalizeFrontendToolOutput`: apply `ToolResponse.toResponse` and return normalized result/artifact/error/explicit model content without persistence.
- `createFrontendToolErrorPatch`: consistently convert ordinary invocation, normalization, projection, or storage errors into project tool error results.
- Keep `storeAndTruncateOversizedToolResult` as the sole persistence/truncation boundary. Preserve existing result wording, paths, artifact behavior, and suppression of model content after truncation.
- Compute `tool.toModelOutput` only when the response is successful, no explicit model content exists, and truncation did not occur.
- Keep the prompt-settling abort race for tools that ignore their signal, but do not normalize `AbortError` as an ordinary model-visible tool error.

### 4.6 Add a strict sequential executor

Create `src/chat-app/runtime/LocalChatModelAdapter/frontend-tool-executor.ts`:

```ts
type FrontendToolExecutionEvent =
    | {type: "started"; toolCallId: string; startedAt: number}
    | {
          type: "finished";
          toolCallId: string;
          patch: ToolCallResultPatch;
          startedAt?: number;
          completedAt?: number;
      }
    | {type: "cancelled"; toolCallId?: string; completedAt: number};
```

Implement `executeFrontendToolPlan(plan, options)` as an async generator:

- Iterate with `for...of`; never use `Promise.all`, parallel maps, background tasks, or assistant-ui `ToolInvocationTracker`.
- `await-human`: emit nothing and leave the part unresolved.
- `final-error`: emit a terminal error patch without execution timing.
- `execute`:
  1. Check cancellation.
  2. Capture/inject `now()` and emit `started`.
  3. Only after that event is consumed, invoke the executor.
  4. Await completion before advancing.
  5. Normalize, truncate/project, and emit `finished` with completion timing.
  6. Only after that result event is consumed may the next call begin.
- Ordinary tool failures produce error patches and do not prevent the next pre-human automatic call from executing.
- Cancellation emits `cancelled`, terminates iteration immediately, and never starts later calls.
- Inject `now?: () => number` only at this boundary for deterministic tests; default to `Date.now`.

### 4.7 Make the model adapter thin

Create `src/chat-app/runtime/LocalChatModelAdapter/runLocalAISDKChatModel.ts` and move orchestration from `LocalAISDKChatModelAdapter.ts`:

- Model/provider-tool lookup and AI SDK tool construction.
- Branch-aware conversation reconstruction through `unstable_getMessage()`.
- `streamText` invocation.
- Translation of text, reasoning, source, file, provider call/result/error, finish, and abort parts.
- Collection of ordered non-provider tool calls.
- Invocation of the planner after the model step is consumed.
- Application of executor events to cumulative current-step content.
- Usage metadata and finish-reason mapping.

Status/event translation:

- Emitted/queued call -> `running`.
- `started` -> add `timing.startedAt`, yield `running`.
- `finished` -> add result/error/artifact/model content and optional completed timing, yield `running`.
- Planner `final-error` -> defined error result, yield `running`, no timing.
- `cancelled` -> yield `incomplete/cancelled` and return without continuation status.
- Non-cancelled step with project client calls -> one final `requires-action/tool-calls` yield.
- No project client calls -> preserve existing finish-status behavior.
- Provider-executed tools never enter the frontend plan.

Reduce `LocalAISDKChatModelAdapter.ts` to the exported adapter delegating to `runLocalAISDKChatModel`, plus the architecture comment documenting:

- why LocalRuntime is required;
- why `unstable_getMessage()` is required;
- why yields contain only the current roundtrip step;
- why the final action-required status is a continuation handshake;
- why project frontend execution is deliberately serial.

### 4.8 Preserve stop, recovery, and persistence contracts

Do not redesign these modules unless integration tests expose a required compatibility adjustment:

- `src/chat-app/runtime/stopThread.ts`
- `src/chat-app/runtime/terminateToolTurn.ts`
- `src/chat-app/runtime/recoverInterruptedMessages.ts`

Ensure cancellation from the executor becomes `incomplete/cancelled`, later calls do not run, no final continuation status is emitted, and project stop persistence can still add its durable termination result/reason.
