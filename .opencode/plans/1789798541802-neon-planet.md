## 1. User Requirement

- Is it possible to modify setupLogseqProxy.ts and build a queue to throttle requests to logseq at 1 request per 100ms? Logseq can misbehave when too many requests are made parallelly.

## 2. Final Requirement After Discussion With User

The user additionally requires upgrading the test stack to Vitest 5 before implementing the test-runner and proxy changes.

The user additionally clarified: "I don't like your vite plugin approach for logseq proxy. Either implement entire setupLogseqProxy inside the vite plugin or do not use vite plugin...."

### Clarification Q&A

Q: Should the implementation use one Chromium project for every test, including Node-oriented utility tests, or allow a mixed Node/Chromium setup?

A: Use all Chromium.

Q: Should tests be sequential within each file while test files remain parallel, or should Logseq-backed files also be serialized globally?

A: Enforce sequential tests within each file and preserve parallel test files.

Q: Should throttling apply globally to every request, per worker, or only to mutations?

A: Use a global FIFO throttle for every Logseq proxy request, with at most one request starting every 100 ms.

### Final Summarized Requirements

- Keep the default test command on Chromium through Vitest and Playwright.
- Make browser incompatibilities in currently included tests explicit and fix them so the suite can execute in Chromium rather than introducing a Node test project.
- Configure Vitest so tests in a file execute serially, while independent files remain eligible for parallel execution.
- Add a process-wide FIFO coordinator for all Logseq API proxy calls. The coordinator must limit request start times to one per 100 ms, preserve FIFO order, release the next request after both success and failure, and avoid changing application behavior outside tests.
- Do not implement the Logseq proxy through a Vite plugin or middleware. Replace `logseq-proxy` inside `tests/helpers/setupLogseqProxy.ts`; use a Vitest 5 browser custom command only as the shared Node-side HTTP transport needed for a process-wide queue.
- Preserve the existing expected `generateTitle` failure as an explicitly excluded/pre-existing issue rather than masking it with unrelated changes.
- Upgrade `vitest`, `@vitest/browser`, `@vitest/browser-playwright`, and `@vitest/ui` from 4.1.11 to the compatible Vitest 5 release line, keeping their versions aligned. Upgrade or confirm the compatible Playwright version as required by the provider.

## 3. Existing System

- `vite.config.ts` currently includes `**/*.test.{ts,tsx}`, enables one headless Chromium instance through `@vitest/browser-playwright`, and uses `tests/setup.ts` as a setup file.
- Commit `4ea91690` removed the former jsdom/fork settings: `environment: "jsdom"`, `pool: "forks"`, `singleFork: true`, `fileParallelism: false`, and `sequence.concurrent: false`. It did not add replacement ordering settings. Therefore the current configuration does not guarantee serial tests within a file, and Vitest may schedule files in parallel according to its browser worker behavior.
- `tests/setup.ts` calls `setupLogseqProxy()` during module setup, probes Logseq availability, and initializes `LogseqPluginStorageManager` in `beforeAll`.
- `tests/helpers/setupLogseqProxy.ts` delegates all API methods to `logseq-proxy`. The dependency creates async methods that call `fetch(`${apiServer}/api`, ...)` directly. It has no queue or rate limiter.
- The proxy package is imported statically and owns its internal `fetchLogseqApi` closure, so wrapping calls at individual test sites would be incomplete. A queue added only to a browser realm would also be scoped to that realm/worker and would not guarantee a process-wide limit when files run in parallel.
- Vitest 5 supports Node-side custom browser commands through `test.browser.commands` and browser-side calls through `commands` from `vitest/browser`. Commands execute in the shared Vitest Node process, so a command module can own one queue across parallel Chromium test files without adding a Vite plugin.
- `tests/vite-plugins/bundleJSStringPlugin.test.ts` imports `node:buffer` and `node:util` and mutates globals. This is the clearest known Chromium incompatibility. The tested plugin itself imports `node:path` and `esbuild`, so the browser test needs a browser-compatible test seam or a Chromium-compatible harness that invokes the Vite plugin through a Node-side service/module boundary.
- The repository already satisfies Vitest 5's documented prerequisites: `package.json` requires Node `>=22.12 <23` and uses Vite 8.2.1. The lockfile currently pins Vitest and browser packages to 4.1.11.
- The test suite contains both pure unit tests and tests that make real calls to the Logseq API. Several Logseq-backed tests create/delete pages and blocks and rely on unique names and cleanup. Parallel files therefore remain useful, but requests must be rate limited; request throttling alone does not make conflicting shared graph mutations deterministic.
- The existing working tree contains untracked Vitest screenshots/traces. They are unrelated test artifacts and must not be included in the implementation changes.

## 4. Solution

### 4.0 Upgrade to Vitest 5 first

Perform the dependency and compatibility migration before interpreting the remaining test failures:

- Update the four Vitest packages in `package.json` to the same Vitest 5 release line and update `pnpm-lock.yaml` with pnpm. Keep `@vitest/browser-playwright` aligned with `vitest` and verify the installed Playwright peer compatibility rather than independently selecting unrelated major versions.
- Read the Vitest 5 migration behavior into the test audit. Vitest 5 enables `clearMocks` by default, so tests that intentionally depend on mock call history crossing test boundaries must be corrected or made self-contained. Browser automock serialization behavior also changed; inspect any browser tests that use `vi.mock` without a factory.
- Replace any deprecated `test.sequential`, `describe.sequential`, or sequential option usage discovered during the audit with Vitest 5's supported `{concurrent: false}` form. The global file/test sequencing configuration should use the Vitest 5-supported `sequence.concurrent` setting, validated against the installed type definitions.
- Run the focused suite immediately after the package upgrade and capture the baseline failure set. Do not conflate dependency-migration failures with the known pre-existing `generateTitle` failure.
- Keep the upgrade in the same implementation scope as the runner changes so the final lockfile, config, and test behavior are verified together.

### 4.1 Test configuration and ordering

Modify `vite.config.ts` test configuration to make the intended scheduling explicit:

- Keep the existing Chromium provider and `instances: [{browser: "chromium"}]` as the single default project.
- Set `fileParallelism: true` so separate files can run concurrently.
- Set `sequence.concurrent: false` so tests in each file run serially. Confirm the Vitest 5 type/API spelling during implementation; do not use removed `sequential` modifiers/options.
- Do not set `singleFork` or a globally serial pool; those would defeat parallel file execution.
- Keep `trace: "on"` only if the generated trace volume is intentional. The test command’s HTML reporter/output should remain unchanged unless it contributes to a failure.

The implementation should validate the behavior with a dedicated small scheduling test or an existing Vitest scheduling probe: record test start/end events in one file and assert no overlap, while two separate files record overlapping execution. Do not rely only on configuration inspection.

### 4.2 Make the entire suite Chromium-compatible

Audit the first failing files after applying the ordering configuration, then fix incompatibilities at their test boundary rather than adding a Node project. In particular:

- Refactor `tests/vite-plugins/bundleJSStringPlugin.test.ts` so its assertions run through a browser-safe exported test helper or a Vite plugin test adapter. Avoid importing `node:*` modules into the browser bundle. If the plugin’s actual `node:path`/`esbuild` implementation cannot execute in Chromium, expose a narrow injectable bundler/path seam in `vite-plugins/bundleJSStringPlugin.ts`, provide the real implementation for production, and provide a deterministic browser test double that still verifies mode/environment replacement and transform contract.
- Review failures caused by browser-global differences (`process`, `Buffer`, filesystem access, workers, WASM, or package exports). Prefer existing Vite polyfills and project test helpers; do not add broad global shims that conceal production browser incompatibility.
- Keep tests that require Logseq behind their existing availability/database guards. Ensure `tests/setup.ts` initializes the proxy before the availability probe and that setup failures are represented as skipped integration tests rather than unrelated suite crashes.
- Treat `generateTitle` as an existing known failure. Record it in verification results and do not alter its implementation as part of this work.

### 4.3 Replace `logseq-proxy` in `setupLogseqProxy.ts`

Implement the complete browser-side Logseq facade in `tests/helpers/setupLogseqProxy.ts`; do not add a Vite plugin or HTTP middleware:

- Remove the `logseq-proxy` import and dependency after confirming it has no other call sites.
- Define the supported namespace allowlist matching the dependency's current behavior: `App`, `Editor`, `DB`, `Git`, `UI`, `Assets`, and `FileStorage`.
- Replace each `window.logseq[namespace]` with a dynamic proxy. A method call builds one structured request object `{method: `logseq.${namespace}.${property}`, args}` and calls the typed `logseqApiCall` command imported from `vitest/browser`.
- Return the command response body to callers so current tests continue to observe parsed JSON values or plain text. If the body contains the API's existing `{error}` shape, preserve the current behavior of returning it; do not turn Logseq application errors into a new exception contract.
- Preserve test-only local properties and stubs currently established after proxy setup: settings, `baseInfo`, `showMainUI`, `hideMainUI`, and no-op unsubscribe functions for `App.onThemeChanged` and `App.onThemeModeChanged`.
- Keep API server/token configuration out of the browser helper. Credentials are read only by the Node-side command factory from the environment loaded in `vite.config.ts`.

### 4.4 Process-wide queued browser command

Add a Node-only helper such as `tests/helpers/logseqApiBrowserCommand.ts` and register its command directly in `vite.config.ts` under `test.browser.commands`:

- Export `createLogseqApiCommand({apiServer, apiToken, minimumStartIntervalMs: 100})`, returning a typed Vitest `BrowserCommand`. Register it as `logseqApiCall`; do not register it through a plugin.
- Validate browser-provided input before network access. Accept one object argument to avoid positional argument serialization issues, require `args` to be an array, and allow only methods matching the known Logseq namespace/method shape. Pre-serialize `{method, args}` before entering the queue so invalid/circular/BigInt payloads fail without consuming a request slot.
- Keep one FIFO start gate in the command module. For each queued request, wait until the previous reserved start time plus 100 ms, update the next permitted start time, and then begin the HTTP request. The gate advances on request start, not response completion, so slow requests may overlap while no more than one starts in any 100 ms interval.
- Chain the gate with rejection handling so validation, timers, network failures, non-2xx responses, and response parsing failures cannot permanently block later queued calls.
- POST the serialized request to `${apiServer}/api` with JSON content type and the bearer token. Parse JSON when indicated by `Content-Type`, otherwise return text. Return a serializable envelope containing `ok`, `status`, response type, and body; throw only for transport/parsing failures, preserving the former proxy's handling of API error payloads.
- Keep the queue singleton scoped to the Vitest process. If module duplication is possible, store its state under a `Symbol.for(...)` key on Node `globalThis`. Document that separate Vitest processes/CI shards cannot share this in-memory throttle.
- Add a `vitest/browser` module augmentation in `tests/global.d.ts` for the exact `logseqApiCall` request/response types.

### 4.5 Queue tests and edge cases

Add focused Chromium tests that invoke Node-side test commands backed by an injected fake clock/fetch or a local fixture handler. The production command must not expose arbitrary URLs or credentials supplied by browser code:

- Multiple simultaneous calls execute in FIFO order.
- Start timestamps are at least 100 ms apart, allowing normal timer jitter with a non-flaky lower-bound assertion strategy.
- A rejected request does not block later requests, and slow requests may overlap while their start times remain spaced.
- A non-JSON response is forwarded as text, and JSON responses/errors retain expected status/content type behavior.
- The queue does not leak the API token.
- Empty queues do not leave timers or an active drain loop behind.

Use an injected clock/sleep implementation for deterministic queue tests rather than browser fake timers, because the queue runs in Node. Run one real integration smoke test through `setupLogseqProxy.ts` to confirm Chromium proxy -> Vitest command -> queued Logseq HTTP routing.

### 4.6 Documentation and scope

Update the relevant `docusaurus/` testing/development documentation if an existing page documents test execution. Document the default Chromium command, sequential-within-file/parallel-files semantics, the requirement for a running Logseq API server for integration tests, and the intentional 100 ms global throttle. Do not document `generateTitle` as fixed.
