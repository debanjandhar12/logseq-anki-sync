## 2. Final Requirement After Discussion With User

### 2.1 Clarification Q&A

1. **Q:** How should existing flat user skills with invalid legacy names migrate?
   **A:** “Migration not required... Plugin is not released yet.” No migration, compatibility aliases, or legacy tool arguments.
2. **Q:** Should the editor manage references/scripts or only SKILL.md?
   **A:** “SKILL.md only (Recommended)”. Preserve resources during content edits and folder renames; deletion removes the complete skill.
3. **Q:** Add safe nesting to the shared storage facade, or keep it flat with encoded skill keys?
   **A:** Initially requested an explanation. After comparing both designs, selected “A: Safe nesting (Recommended)”. Expand validated relative paths in the existing facade and extend the generic filesystem adapter; do not redesign backends or introduce inheritance/encoded keys.
4. **Q:** Preserve the invocation preference when bundled instructions/resources change?
   **A:** “Reset on content changes is recommended if it means less code”. Retain current semantics: ignore preference-only differences, but install bundled defaults when other folder content changes.

### 2.2 Final Summarized Requirements

- One skill is a directory named exactly like its frontmatter `name`, containing the fixed file `SKILL.md`; the filename is not `<name>.md`.
- Enforce ASCII lowercase kebab-case names, 1–64 characters, no leading/trailing/consecutive hyphens, and nonempty descriptions of at most 1024 characters. Preserve existing plugin boolean fields and unknown frontmatter.
- Support text resources in `references/` and `scripts/`, including safe nested relative paths. Resource editing UI, binary assets, general asset uploading, and new script runtimes are out of scope.
- Expose one read-only Bash mount at `/home/user/skills`. Every path advertised by the skill tool must be an actual path within that mount, never a host storage path.
- Match OpenCode's wrapper and bounded file disclosure: at most 10 non-SKILL.md file paths. Keep the plugin's existing success/error response envelope.
- Add a folder-based `SkillStore`; retain the explicitly requested `saveSkillFile(content, {references?, scripts?})` API. Compare whole folders through store hash methods.
- Include only the two requested `.ds` references in `logseq-datascript-queries`.
- Deliver in two parts: foundations first, then consumer integration. Part 1 is a preparatory change, not a separately released feature.

## 3. Existing System

### 3.1 Storage and skill flow

- `src/logseq/LogseqPluginStorageManager/LogseqPluginStorageManager.ts` is a static facade over `IAsyncStorage`. Its methods compose `${group}/${fileName}`; `getFiles(group)` returns all suffixes under that prefix. Both arguments currently reject `/`.
- `StorageBackendFactory.ts` selects `InMemoryStore`, `LocalStorageStore`, or `logseq.Assets.makeSandboxStorage()`. All accept opaque nested keys; Logseq's installed storage types explicitly support nested directories. No backend changes are necessary.
- `src/core/stores/skill-file-store/SkillFileStore.ts` writes `skills/<name>.md`, parses every enumerated file, sorts built-ins first, collapses missing/invalid reads to null, and swallows delete errors.
- `src/core/skill-parser/validateSkillFileContent.ts` uses gray-matter and field definitions from `constants.ts`, returning editor line ranges. It validates required strings/boolean types but not harness name rules or description length. String extraction trims values.
- `renderSkillFileTemplate.ts` preserves frontmatter and renders only the body through the existing template engine. Keep this behavior.
- `initBuiltInSkillFiles.ts` bundles seven raw strings via `?inlineSkill`, removes obsolete parsed built-ins, preserves malformed/same-name user files, and compares SKILL.md with gray-matter after removing only `disable-model-invocation`.
- `src/index.ts` initializes plugin storage before built-in installation. Keep that ordering and the public `initBuiltInSkillFiles` entry point.

### 3.2 Tool and UI

- `src/chat-app/tools/impl/SkillTool.tsx` accepts `{fileName}`, reads one skill, renders it, and returns `{success: true, skillFileContent}` through `ChatToolResponse`. Errors use the standard error envelope.
- `getModelInvokableSkillListString.ts` advertises `* <name>.md - <description>` and excludes only `disableModelInvocation === true`.
- `SkillEditorModal.tsx` keeps `{id, content, originalFileName}`, derives renames from frontmatter, and deletes old files before saving new files. Resources are not modeled. Built-ins are read-only, except the controllable invocation checkbox.
- Editor extensions already reuse core validation for inline diagnostics. Save validation also checks templates and duplicates, but owns a separate filename policy.
- Skill Creator currently says nested resources are unsupported. This must change without granting the model permission to mutate storage directly.

### 3.3 Bash constraints

- `JustBashAdapterFS.ts` mounts one storage group under `/home/user/<group>`, supports only flat files, and reports all directory entries as files. `fsPaths.ts` rejects nested filenames.
- `JustBashWrapper.getInstance()` is synchronous, snapshots mount configs once, and returns a shared Bash instance. Existing tool-result and parsed-PDF mounts are read-only.
- just-bash glob expansion uses synchronous `getAllPaths()`; directory traversal uses async `readdir`/`readdirWithFileTypes`. An initially empty/stale filename cache cannot correctly support nested globbing.
- MountableFs forbids overlapping mounts. Mount `skills` once; do not register one mount per skill.

### 3.4 Libraries and external conventions

- Reuse installed `gray-matter`, `zod`, and `path-browserify`. Use `@noble/hashes` as a direct dependency for browser-compatible skill SHA-256 hashing; existing PDF hashing is outside this task.
- Agent Skills specification: https://agentskills.io/specification. Its prose has an ambiguous Unicode wording, but its explicit `a-z`/`0-9` constraints and harness compatibility justify ASCII names here.
- Official validator `skills-ref` is Python 3.11+ with strictyaml, unsuitable for browser runtime loading. Implement the small name/description constraints with existing Zod and preserve the plugin's diagnostics/template support instead of importing a filesystem-oriented harness loader.
- Follow-up exploration requested by the user also evaluated JavaScript equivalents. The third-party npm `skills-ref` package exposes path-based validation and imports Node fs/path; it also rejects plugin-specific unknown metadata. `@skillscraft/core` is likewise filesystem-oriented; `@skillscraft/spec` supplies only schemas/constants. `@skill-tools/core` offers `parseSkillContent`, but its published entry imports Node filesystem modules, adds token/reference validation, and treats folder/name mismatch as a warning. `load-skills` is a Node directory loader without the required complete naming/length validation. None offers sufficient browser-compatible simplification over the installed libraries; retain gray-matter + Zod. Candidate sources: https://registry.npmjs.org/skills-ref, https://www.npmjs.com/package/@skillscraft/core, https://www.npmjs.com/package/@skillscraft/spec, https://www.npmjs.com/package/@skill-tools/core, https://www.npmjs.com/package/load-skills. No packages were installed during planning.
- OpenCode source inspected: https://raw.githubusercontent.com/anomalyco/opencode/dev/packages/opencode/src/tool/skill.ts. It uses `name`, excludes `**/SKILL.md`, lists hidden files without following symlinks, limits discovery to 10 files, and returns `<skill_content>`, a base directory, the sampled-file note, and `<skill_files>`. Use deterministic sorted sampling rather than depending on filesystem enumeration order.

### 4.1 Safe relative storage paths

**Change:** `src/logseq/LogseqPluginStorageManager/LogseqPluginStorageManager.ts`.
**Add:** `src/logseq/LogseqPluginStorageManager/relativeStoragePath.ts` and focused tests.

Replace slash rejection with a reusable assertion for canonical relative POSIX paths, applied to both group and file arguments when provided:

Library follow-up requested by the user: exploration evaluated `path-sanitizer`, `valid-path`, `is-valid-path`, `resolve-path`, `sanitize-filename`, and `filename-reserved-regex`. None fits this canonical opaque-key contract: sanitizers mutate/decode input, filesystem resolvers normalize traversal, filename validators lack segment rules or disallow nesting, and several depend on Node/platform behavior. Preserve legitimate spaces and Unicode in generic storage keys (skill names have their separate stricter schema). ### 4.2 Folder-based store and shared validation

**Add:** `src/core/stores/skill-store/SkillStore.ts`, `types.ts`, and `hashSkillFileSnapshot.ts`.
**Add:** `src/core/skill-parser/skillMetadataSchema.ts`, exporting shared Zod name/description constraints.

In Part 1, leave the old store and its consumers temporarily intact so the preparatory change stays buildable. Part 2 removes them and enables stricter parser/editor integration. Do not keep an alias in the final implementation.

Name schema: `z.string().min(1).max(64).regex(/^[a-z0-9]+(?:-[a-z0-9]+)*$/)`; validate the raw YAML string, not a trimmed or slugified version. Description must be a nonempty string after trimming and no more than 1024 characters; use the untrimmed value for its upper bound. Never automatically fix names during save.

Use explicit domain types:

```ts
type SkillResourceFiles = Record<string, string>;
interface SaveSkillFileOptions {
    references?: SkillResourceFiles;
    scripts?: SkillResourceFiles;
}
interface StoredSkill extends SkillFileData {
    folderName: string; // actual persisted folder identity
}
type SkillFolderFiles = Record<string, string>; // keys relative to skill root
```

Final store APIs:

```ts
getSkill(name: string): Promise<StoredSkill | null>
getAllSkills(): Promise<StoredSkill[]>
skillExists(name: string): Promise<boolean> // physical SKILL.md existence
getSkillFiles(name: string): Promise<SkillFolderFiles>
listSkillFiles(name: string): Promise<string[]>
saveSkillFile(content: string, options?: SaveSkillFileOptions): Promise<void>
deleteSkill(name: string): Promise<void>
hashSkillFiles(name: string, options?: HashOptions): Promise<string>
saveEditedSkills(entries: EditedSkill[], originalNames: readonly string[]): Promise<void>
```

`groupName` remains `skills`. Main layout is `skills/<name>/SKILL.md`; resources use `skills/<name>/references/<path>` and `skills/<name>/scripts/<path>`. Use a folder group and resource-relative filename through the shared facade.

- `getAllSkills` discovers only exactly `<folder>/SKILL.md`, never attempts to parse resources or legacy flat files. Validate folder name and equality with frontmatter name; log malformed/mismatched entries and skip them. Keep built-in-first/name ordering.
- `getSkill` returns null only for missing or invalid content; propagate unrelated storage failures so callers can report them accurately.
- Resource map values must be strings; keys must pass shared path validation. Allow nested files and dotfiles; reject file/directory prefix collisions, including conflicts with existing preserved files. Do not permit reference/script input to overwrite `SKILL.md` or escape its category.
- Ordinary `saveSkillFile(content)` changes only SKILL.md and preserves all resources. An omitted category preserves it; a supplied category is the complete replacement for that category; `{}` explicitly clears it. Preflight all metadata/paths/content before writes, write new contents first, then delete obsolete category files.
- `deleteSkill` enumerates and removes all descendant files. Propagate failures; do not claim successful deletion after swallowed errors.
- Folder identity is its compliant name, not a name hash or content hash. Resources remain text-only, matching current storage capabilities.

### 4.3 Canonical folder hash

The store owns recursive persisted-folder hashing. Its single public hash API is `hashSkillFiles(name, options?)`: callers supply the skill name, never a file list. Initialization uses this API for stored skills and an internal complete-snapshot comparison path for incoming bundles, not its own comparable-content function. Do not expose a second public `hashSkillFolder` or `getSkillFolderHash` method.

- Read every file inside the skill folder, including unexpected additional text files; include file paths, additions, removals, and contents in the hash.
- Compute a resource digest from **every descendant file except the root `SKILL.md`**, regardless of directory/category/depth. Sort root-relative paths lexicographically and hash UTF-8 `JSON.stringify(sortedEntries)` where each entry is `[relativePath, exactContent]`. JSON framing avoids concatenation ambiguity; an empty resource set has a deterministic digest. A nested file named `SKILL.md` is an ordinary resource and remains included.
- Compute a separate instruction digest for the root `SKILL.md`. Normally preserve its exact content. With `{ignoreDisableModelInvocation: true}`, canonicalize its frontmatter via gray-matter, removing only `disable-model-invocation` before serialization, matching today's comparison semantics. Sort frontmatter object keys recursively for deterministic canonical serialization while retaining values and body. No frontmatter processing is applied to resource files.
- Return a combined SHA-256 digest of a versioned/domain-tagged JSON tuple such as `["skill-files-v1", instructionDigest, resourceDigest]`. Separate digest roles prevent ambiguity. Keep the internal component hashes implementation details; callers receive one complete-folder hash.
- Return lowercase SHA-256 hex through the browser-compatible `@noble/hashes` SHA-256 implementation and hex utility. Do not rely on `crypto.subtle` availability in plugin iframe contexts. The snapshot helper file is named `hashSkillFileSnapshot.ts`. Missing/corrupt folder reads throw for hashing; no sentinel hash, sidecar file, persisted cache, or content-based folder ID.
- Stored and incoming files use the exact same private snapshot hashing helper. The public `hashSkillFiles(name, options?)` enumerates and reads the complete persisted folder, then delegates internally. The built-in reconciliation path builds its complete incoming snapshot and delegates internally too; expose bundle comparison through a store operation when Part 2 is implemented rather than restoring a public file-map hashing overload. Toggling invocation alone has equal hashes; changing any other metadata, body, path, resource content, or file count has unequal hashes.
- Explicit regression tests must modify persisted files at multiple nesting depths, including auxiliary directories outside references/scripts: edits, additions, removals, and renames each change the hash. Unrelated sibling skill folders do not affect it. Test root SKILL.md preference normalization separately and verify nested SKILL.md changes affect the resource digest.

### 4.4 Generic nested JustBashAdapterFS

**Change:** `JustBashAdapterFS.ts`, `utils/fsPaths.ts`, `utils/fsErrors.ts`, `JustBashWrapper.ts`, and its callers/tests.

- Remove flat-path rejection. Convert normalized mount-relative absolute paths to safe storage-relative paths through the shared validator. Keep POSIX shell normalization within the mount; backend paths never use raw `..`, absolute paths, or backslashes. MountableFs routing remains the permission boundary.
- Maintain persisted file paths and ephemeral empty directories. Infer every ancestor directory from descendant files; do not persist directory-marker files.
- `refresh()` scans the group, filters/validates returned keys, reconstructs file and directory caches, and detects malformed file/directory collisions. All traversal uses immediate children, sorted deterministically.
- Implement nested `exists`, directory/file `stat`/`lstat`, `realpath`, `readdir`, `readdirWithFileTypes`, and `getAllPaths` (root plus all ancestors/files). Directory reads fail EISDIR; missing entries fail ENOENT; traversal through files fails ENOTDIR. File size remains UTF-8 byte length and timestamps remain synthetic.
- Keep permissions and read-only rejection for every mutating method. Add ENOTEMPTY error support for nonrecursive directory removal.
- For generic readwrite adapters: implement recursive/nonrecursive `mkdir`, nested write/append with existing-parent checks, file/directory `rm`, recursive `cp` when requested, and directory `mv` through write-first/delete-last logic. Reject moving/copying a directory into itself; preserve current flat-file behavior. Empty directories exist only for the adapter lifetime. No links, persistent chmod/mtime metadata, or binary backend redesign.
- Refresh before directory enumeration; after successful adapter mutations update cached files/directories. Before each Bash tool execution refresh all mounted adapters so synchronous glob expansion sees persisted UI/store updates, even when no prior `ls` occurred.

**Initialization design:** make `JustBashWrapper.getInstance()` asynchronous, caching an initialization promise and the created adapters. Await initial `refresh()` before constructing Bash. On subsequent access await adapter refresh before returning Bash. Clear failed initialization promises so a later call can retry. `resetInstanceForTesting()` clears adapters and promise. Update `BashTool.execute` to `const bash = await JustBashWrapper.getInstance(); await bash.exec(...)`, including relevant mocks/callers. Do not add a second global storage cache or observer system solely for globbing.

Register one `/home/user/skills` read-only mount using the new store's group. Other mounts retain their permissions. Scripts may be read or invoked via interpreters already supported in the sandbox; neither host execution nor arbitrary new language runtimes are implied. Dynamic skill folders require no mount re-registration.

### 4.7 Built-in initialization via folder hashes

**Change:** `src/core/skill-init/initBuiltInSkillFiles.ts`.

Represent each bundle as `{content, references: {}, scripts: {}}`, with only the query skill receiving the two references. Build the same root-relative file map used by SkillStore hashing.

```ts
for (const bundled of builtIns) {
    const name = parseSkillFile(bundled.content).name;
    const exists = await SkillStore.skillExists(name);
    const existing = await SkillStore.getSkill(name);
    if (exists && !existing) continue; // preserve malformed occupied folder
    if (existing && !existing.builtInSkill) continue; // preserve user skill
    if (existing && await SkillStore.matchesBundledSkill(bundled, hashOptions)) continue;
    // A changed bundle is authoritative for its entire built-in folder.
    await replaceBundledFolder(name, bundled);
}
```

- `hashOptions` ignores only `disable-model-invocation`; delete `getComparableSkillContent` and initializer gray-matter dependency.
- `matchesBundledSkill` is a store comparison operation: derive the bundled name, get the stored digest through `hashSkillFiles(name, hashOptions)`, compute the incoming digest through the same private two-component snapshot helper, and compare them. The initializer does not pass file lists into the public hash API or duplicate canonicalization.
- Add store `replaceSkillFolder(content, options)` for privileged built-in synchronization: validate/preflight, write the complete bundle, then remove every file absent from the bundle, including unexpected files. This differs intentionally from preserve-by-default `saveSkillFile`.
- Remove obsolete parsed built-in folders recursively, not just SKILL.md. Keep malformed same-name and non-built-in collision safeguards and centralized logging. Hash/read/write errors propagate rather than masquerading as unchanged content.
- Preference-only changes skip all writes. Any instruction/resource change installs raw bundled content and resets invocation to its default, as requested. No preference-merge code.

### 4.10 SKILL.md-only editor and safe resource-preserving saves

**Change:** `src/ui/pages/SkillEditorModal/SkillEditorModal.tsx`, `types.ts`, `createSkillEditorExtensions.ts`, and relevant `utils/`.

- State retains `originalSkillName` (actual loaded folder name), not reconstructed `<name>.md`; retain original metadata/content for built-in permissions. Sidebar labels refer to skills; show `<name>/SKILL.md` and a short naming-rules hint.
- Generate a valid unused `new-skill`, `new-skill-2`, etc. frontmatter name when adding an entry. Use the same constraints for live diagnostics and save validation. Remove the separate filesystem-filename rule and keep duplicate-name/template checks.
- Built-ins remain non-renamable, non-deletable, body-read-only; allow only existing user-controllable invocation toggles. Store editor batch preflight verifies these against persisted originals, not merely edited metadata. This guards alternate callers without restricting privileged built-in initialization.
- Resources are not loaded into editable UI state; capture full source folder snapshots immediately before a save so current resources are preserved.

`SkillStore.saveEditedSkills` owns persistence, rename, and deletion sequencing:

1. Validate all entries/templates (UI template validation remains shared), source identities, destination uniqueness, built-in permissions, and collisions with unrelated stored folders. Reject occupied malformed destinations too; don't overwrite unseen data.
2. Snapshot every source and destination folder before any write. Associate resource files with editor entry identity, not destination name; this supports `alpha <-> beta` swaps and rename-into-deleted-name safely.
3. Build complete desired folder snapshots by replacing only SKILL.md of each source snapshot. New entries have no resources. Preserve even safe auxiliary files outside references/scripts if already present.
4. Write all desired destination snapshots, then clean stale destination files to match those snapshots. Delete only `originalNames - finalNames`, and only after every destination was written successfully.
