# Built-in skill persistence and user control

## 1. User Requirement

Currently in initDefaultInstalledSkillFiles, we overwrite all skill files. Instead we should only overwrite skill files which actual content (excluding frontmatter) somehow has become different.

The above change is needed because: I aditionally need you to introduce a new built-in-skill-user-controlable. When that is true, user should be able to control the disable-model-invocation through Enabled checkbox in the SkillEditorModalComponent. (like non default skills)
Note: User still shouldnt be able to edit the actual content directly through codemirror.

## 2. Final Requirement After Discussion With User

### 2.1 Clarification Q&A

- **Q: Which packaged built-in skills should be user-controllable?**  
  **A:** All five current built-in skills.
- **Q: If bundled body content changes, should initialization preserve the user's Enabled value or reset it to the bundled value?**  
  **A:** Choose whichever implementation is less code and more maintainable. The selected design performs a full bundled-file overwrite only in this case, resetting metadata to bundled defaults.
- **Q: Should the new key retain the requested `controlable` spelling?**  
  **A:** No. Use the standard spelling: `built-in-skill-user-controllable` and `builtInSkillUserControllable`.
- **Q: How should the Enabled checkbox appear for a non-controllable built-in?**  
  **A:** Keep it visible but disabled, matching current behavior.

### 2.2 Final Summarized Requirements

- Rename the frontmatter flag `default-installed-skill` to `built-in-skill` throughout metadata, TypeScript fields, filenames, functions, variables, comments, imports, exports, and tests. Do not retain compatibility aliases or add migration logic.
- Add optional boolean metadata `built-in-skill-user-controllable`, represented as `builtInSkillUserControllable` in TypeScript, with parser validation.
- Mark all five bundled skills as built-in and user-controllable.
- During startup, install missing built-ins, retain stale-built-in cleanup and same-name user-file protection, and compare the complete skill source except for `disable-model-invocation`. Do not rewrite when that invocation flag is the only difference; overwrite when the body or any other frontmatter differs.
- Compare canonicalized sources exactly after substituting/removing only `disable-model-invocation` from the comparison. Any other difference, including body whitespace, line endings, or other metadata, causes a complete overwrite with bundled content; this intentionally resets `disable-model-invocation` to the bundled value when another update exists.
- In `SkillEditorModalComponent`, every built-in remains read-only in CodeMirror and undeletable. A controllable built-in may toggle Enabled, which updates only `disable-model-invocation`; a non-controllable built-in keeps a visible disabled checkbox. Non-built-in behavior remains unchanged.

## 3. Existing System

- `src/index.ts` initializes storage and then calls `initDefaultInstalledSkillFiles` through the `src/core/chat-interop/index.ts` barrel.
- `src/core/chat-interop/initDefaultInstalledSkillFiles.ts` embeds five Markdown skill definitions. It deletes stored files marked `default-installed-skill: true` when no longer bundled, preserves same-name user-owned files, but currently saves every existing bundled built-in on every startup.
- `src/core/skill-parser/parseSkillFile.ts` uses `gray-matter`, requires `name` and `description`, validates `default-installed-skill` and `disable-model-invocation`, and returns the complete source in `SkillFileData.content`.
- `src/core/stores/skill-file-store/types.ts` currently exposes `defaultInstalledSkill?: boolean` and `disableModelInvocation?: boolean`. `SkillFileStore` persists the complete raw Markdown source under a filename derived from `name`.
- `gray-matter` already parses body and frontmatter independently and can reconstruct a comparison representation after neutralizing `disable-model-invocation`.
- `../../src/ui/pages/SkillEditorModal/SkillEditorModal.tsx` reparses permissive metadata from the editor source. `defaultInstalledSkill === true` currently disables CodeMirror, deletion, and Enabled. Toggling Enabled uses `matter.stringify` to preserve existing metadata/body while changing `disable-model-invocation`; Save persists the resulting complete source.
- `src/core/template-engine/getModelInvokableSkillListString.ts` already filters solely on `disableModelInvocation`; no change is required there.
- Existing direct coverage is limited to `tests/src/core/skill-parser/parseSkillFile.test.ts`; there are no initializer or skill-editor tests. UI tests use Vitest/jsdom with manual React roots, while storage tests can inject `InMemoryStore` into `LogseqPluginStorageManager.store`.
- The five bundled definitions are the `src/chat-app/prompts/SKILL_LOGSEQ_*.md` files imported by the initializer. No Docusaurus documentation currently describes this metadata.

## 4. Solution

### 4.1 Rename and extend the metadata model

Update `src/core/stores/skill-file-store/types.ts`:

- Rename `defaultInstalledSkill?: boolean` to `builtInSkill?: boolean`.
- Add `builtInSkillUserControllable?: boolean`.
- Keep both optional so user-created skill files require neither field.

Update `src/core/skill-parser/parseSkillFile.ts`:

- Replace parsing and validation of `default-installed-skill` with `built-in-skill` / `builtInSkill`.
- Parse `built-in-skill-user-controllable` into `builtInSkillUserControllable` and reject a present non-boolean value.
- Use clear errors ending in `built-in-skill must be a boolean` and `built-in-skill-user-controllable must be a boolean`.
- Continue returning the original full source as `content`; comparison parsing remains local to initialization rather than expanding the general data model solely for one comparison.
- Do not recognize the old metadata key, because the plugin is unreleased and migration was explicitly excluded.

No cross-field parser restriction is needed: controllability only has behavioral meaning when `builtInSkill === true`; keeping parsing independent makes the metadata model simple and tolerant.

### 4.2 Rename and revise built-in initialization

Rename `src/core/chat-interop/initDefaultInstalledSkillFiles.ts` to `src/core/chat-interop/initBuiltInSkillFiles.ts` and update:

- `initDefaultInstalledSkillFiles` -> `initBuiltInSkillFiles`.
- `DEFAULT_SKILL_FILES` -> `BUILT_IN_SKILL_FILES`.
- `defaultSkillFileNames` and all default-installed comments/locals -> built-in terminology.
- The barrel export in `src/core/chat-interop/index.ts`.
- The import and startup call in `src/index.ts`.

Use `gray-matter` in the initializer to compare the complete skill while ignoring only `disable-model-invocation`. A small local helper should parse the source, remove that one key from copied metadata, and serialize the remaining metadata with the unchanged parsed body:

```ts
function getComparableSkillContent(content: string): string {
    const parsed = matter(content);
    const metadata = {...parsed.data};
    delete metadata["disable-model-invocation"];
    return matter.stringify(parsed.content, metadata);
}
```

An equivalent helper that replaces the invocation value with a fixed sentinel is acceptable if it more reliably preserves field presence; the key requirement is that changing only this field cannot change the comparison result, while every other metadata/body change can.

Preserve the current stale cleanup and per-bundle loop, with this decision table:

```text
No stored file                         -> save bundled source
Stored same-name non-built-in file     -> preserve it
Stored built-in, differs only in invocation flag -> do not write
Stored built-in, any other difference           -> save complete bundled source
Stored stale built-in                   -> delete
Stored stale non-built-in               -> preserve
```

Compare the neutralized representations directly. Do not trim or normalize body line endings/whitespace. The helper's deterministic `gray-matter` serialization makes metadata ordering/formatting non-semantic, while metadata values other than `disable-model-invocation` remain part of equality. This means a user-only invocation change survives startup. When the body or another metadata value changes, full overwrite is the chosen minimal, maintainable policy and resets Enabled to the bundled default.

Keep existing malformed-file behavior unchanged: store reads that cannot be parsed may appear missing and be replaced at a current bundled filename; malformed files omitted from `getAllSkillFile()` are not candidates for stale cleanup.

### 4.3 Update bundled skill definitions

In each file below, replace `default-installed-skill: true` with `built-in-skill: true` and add `built-in-skill-user-controllable: true`, retaining `disable-model-invocation: false`:

- `src/chat-app/prompts/SKILL_LOGSEQ_DATASCRIPT_QUERY.md`
- `src/chat-app/prompts/SKILL_LOGSEQ_DATASCRIPT_QUERY_PITFALLS.md`
- `src/chat-app/prompts/SKILL_LOGSEQ_PROPERTIES_AND_TAGS.md`
- `src/chat-app/prompts/SKILL_LOGSEQ_TOOLS_GUIDE.md`
- `src/chat-app/prompts/SKILL_LOGSEQ_WORKING_WITH_VIDEO_AND_WEB_EMBEDS.md`

The Vite `?inlineSkill` pipeline needs no changes because it embeds source without interpreting metadata.

### 4.4 Apply independent editor capabilities

Update `../../src/ui/pages/SkillEditorModal/SkillEditorModal.tsx` so built-in ownership and invocation controllability are separate capabilities:

- Extend `getSkillFileMetadata` to return/read `builtInSkill`, `builtInSkillUserControllable`, and `disableModelInvocation` from the renamed keys.
- Rename `isActiveFileDefault` and related callback dependencies to `isActiveFileBuiltIn`.
- Derive controllability only for a built-in, for example:

```ts
const isActiveFileBuiltIn = activeFileMetadata?.builtInSkill === true;
const isActiveFileBuiltInUserControllable =
    isActiveFileBuiltIn && activeFileMetadata?.builtInSkillUserControllable === true;
```

- Keep CodeMirror `editable={!isActiveFileBuiltIn}`. The controllability flag must never unlock direct source editing.
- Keep deletion guarded and disabled for every built-in.
- Disable Enabled only when the active skill is a built-in that is not user-controllable. User-created skills remain enabled regardless of the optional controllability key.
- Change the toggle handler guard to permit normal skills as well as controllable built-ins, while rejecting non-controllable built-ins:

```ts
if (!activeFile || (isActiveFileBuiltIn && !isActiveFileBuiltInUserControllable)) return;
```

- Continue using `updateDisableModelInvocation`; its `matter.stringify` path preserves `built-in-skill` and `built-in-skill-user-controllable`, changes only `disable-model-invocation`, and leaves the body unchanged.
- Do not add a built-in guard to shared `handleContentChange`, because the dedicated checkbox must programmatically update the controlled source even while CodeMirror is read-only.

Expected matrix:

| Skill | CodeMirror | Delete | Enabled |
|---|---|---|---|
| User skill | Editable | Allowed | Editable |
| Built-in, controllable | Read-only | Disabled | Editable |
| Built-in, not controllable | Read-only | Disabled | Visible and disabled |
