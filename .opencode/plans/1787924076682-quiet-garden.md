# Move Skill Editor Entry Point to Settings

## 1. User Requirement

Currently in LogseqAIChatToolbarMenu.tsx, the skill editor menu item is listed. This needs to be moved to settings.

Logseq has recently introduced a way to add buttons to the settings.ts page schema. For example:
```
logseq.provideModel({
        showToolbarMenu: () => {
            console.log('Settings button clicker');
        }
});

logseq.useSettingsSchema([
  {
    key: 'open-toolbar',
    type: 'button',
    title: 'Toolbar',
    text: 'Open Toolbar',
    action: 'showToolbarMenu',
    description: 'Open the toolbar menu.',
  },
])
```
Note: above may show typescript error currently as the plugin sdk with new typing is not release yet but functionality wise this should work.

Similar to above, we need to add a button for skill editor in settings.ts page. The button should be named "Open Skill Editor" and on click it should open the skill editor page.

Remove from LogseqAIChatToolbarMenu.

## 2. Final Requirement After Discussion With User

### 2.1 Clarification Q&A

- Q: Where should the new settings button appear?
- A: Create a new section called `💬 Main` above `webToolsHeading`.

### 2.2 Final Summarized Requirements

- Add a `💬 Main` settings heading immediately before the existing Web Tools section.
- Add an `Open Skill Editor` settings button in that section.
- Wire the button through a Logseq provided model action to the existing skill editor modal launcher.
- Accommodate the installed SDK's temporarily stale `SettingSchemaDesc` typing without broadly weakening project types.
- Remove the Skills Editor item from the toolbar dropdown, leaving the other entries and separators functional.
- Target the newly introduced Logseq runtime behavior requested by the user; do not retain an older-host toolbar fallback.

## 3. Existing System

- `src/settings.ts` builds a `SettingSchemaDesc[]` in `addSettingsToLogseq()` and registers it through `LogseqSettingAccessor.useSettingsSchema()`. The requested insertion point is after `globalAgentInstruction` and before `webToolsHeading`.
- `src/index.ts` invokes `addSettingsToLogseq()` during plugin startup after toolbar registration. This is early enough to register both the model action and settings schema; the existing editor entry point has the same brief startup dependency on UI/storage initialization.
- `src/ui/pages/LogseqAIChatToolbarMenu.tsx` currently imports `showSkillEditorModal` and exposes a `skills-editor` menu item whose callback invokes it. Removing the item does not leave adjacent separators: the post-change grouping remains Open Chat, separator, Storage Info and Settings, separator, links.
- `src/ui/launchers/showSkillEditorModal.ts` is the established entry point. It mounts `SkillEditorModalComponent` through `createModalPromise()` and reports modal-opening errors.
- Existing host callback registration uses `logseq.provideModel()` in `src/registerToolbar.ts` and other modules.
- The installed `@logseq/libs@0.3.3` does not yet type settings buttons. The upstream Logseq implementation added `type: "button"` with optional `buttonText` and `buttonAction` fields; these are the actual runtime field names (rather than the illustrative `text`/`action` names in the request).
- `PluginSettings` models persisted values only. A heading and action button are schema presentation entries and must not be added to it.
- There is no existing settings-schema test or toolbar-menu test. Existing Vitest tests use jsdom and module mocks; global setup may print an expected warning when a live Logseq API server is absent.

## 4. Solution

### 4.1 Register the skill editor action and button schema

Modify `src/settings.ts`:

1. Import `showSkillEditorModal` directly from `./ui/launchers/showSkillEditorModal`.
2. Define a collision-resistant action-name constant, such as `OPEN_SKILL_EDITOR_SETTINGS_ACTION = "openSkillEditorFromSettings"`, so the schema and provided model cannot drift apart.
3. Add a narrow local compatibility type for the unreleased SDK shape. It should preserve normal `SettingSchemaDesc` fields while allowing:

   ```ts
   type SettingsButtonSchemaDesc = Omit<SettingSchemaDesc, "type"> & {
       type: "button";
       buttonText: string;
       buttonAction: string;
   };
   ```

   Include a short comment that this can be removed once the installed Logseq SDK publishes the new fields.
4. At the start of `addSettingsToLogseq()`, register the model action before registering the schema:

   ```ts
   logseq.provideModel({
       [OPEN_SKILL_EDITOR_SETTINGS_ACTION]: () => {
           void showSkillEditorModal().catch(() => undefined);
       }
   });
   ```

   Treat modal launch as fire-and-forget so Logseq's model RPC does not remain pending until the editor closes. The launcher already reports opening failures, so consume its rejection without emitting a duplicate error.
5. Type the local schema as `Array<SettingSchemaDesc | SettingsButtonSchemaDesc>` and add these entries directly before `webToolsHeading`:
   - A non-persisted heading with a unique key (for example `mainSettingsHeading`), `title: "💬 Main"`, `type: "heading"`, empty description, and `default: null`.
   - A non-persisted button with a unique key (for example `openSkillEditorButton`), `type: "button"`, a clear `Skill Editor` title/description, `buttonText: "Open Skill Editor"`, `buttonAction: OPEN_SKILL_EDITOR_SETTINGS_ACTION`, and `default: null`.
6. Cast the mixed schema to `SettingSchemaDesc[]` only at the `LogseqSettingAccessor.useSettingsSchema(...)` boundary. Do not alter `LogseqSettingAccessor`, use `any`, or add the presentation keys to `PluginSettings`.

### 4.2 Remove the toolbar entry

Modify `src/ui/pages/LogseqAIChatToolbarMenu.tsx`:

- Remove the `showSkillEditorModal` import.
- Remove the complete item with key `skills-editor` from the `items` array.
- Keep `SETTINGS_ICON`, because the remaining Settings menu item still uses it.
- Keep `chat-separator`; it continues to separate Open Chat from Storage Info and Settings and does not produce an empty or doubled separator.

### 4.3 Add focused regression coverage

Add `tests/src/settings.test.ts` with isolated mocks for the launcher, `LogseqSettingAccessor`, and required `logseq` host functions. Reset module/mock state between tests because `addSettingsToLogseq()` registers listeners and styles.

Verify that:

- `addSettingsToLogseq()` provides `openSkillEditorFromSettings` before the schema is registered.
- The schema order is `mainSettingsHeading`, `openSkillEditorButton`, then `webToolsHeading`.
- The heading and button contain the exact runtime fields and requested labels, especially `type: "button"`, `buttonText: "Open Skill Editor"`, and matching `buttonAction`.
- Invoking the supplied model action calls `showSkillEditorModal()` once.
- A rejected launcher promise is consumed rather than becoming an unhandled rejection or producing an additional settings-layer notification.

No new React toolbar test is needed solely to assert deletion of a static item; type checking, linting, and manual toolbar validation cover the uncomplicated removal.

### 4.4 Scope and compatibility

- Do not update documentation: the repository has no current user-facing page that identifies the toolbar as the Skill Editor location, and this is a small navigation relocation.
- Do not add an old-Logseq fallback. The stale SDK typing is handled locally, while runtime support intentionally depends on the newly introduced Logseq settings-button feature specified in the request.
- Do not reorder plugin initialization as part of this change. A click during the narrow pre-initialization window was already possible through the toolbar and solving application-wide readiness is outside this relocation.
