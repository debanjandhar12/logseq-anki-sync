# Commit review cancel-and-continue plan

## 1. User Requirement

Currently in CommitTool / AIChangesReviewModalComponent, there is a button to reject changes. However, there is no button to cancel and continue with changes. We need to introduce that feature. Keep the button as ghost and to left side of footer.

When the tool is terminated (by click the stop button),it should behave same as cancel and continue with changes. Aditionally, currently, it seems like the stop button is disabled when we need to review changes: `disabled={requiresActionState}` at `ComposerAction.tsx:58`. This needs to be changed to not be disabled. When it is click, the current tool call should go for abort.

## 2. Final Requirement After Discussion With User

### 2.1 Clarification Q&A

- Q: Should “Cancel and continue with changes” merely close the modal, or end the pending CommitTool call while retaining changes and unblocking chat?
  - A: **Abort and retain**. Terminate the current tool/turn, retain the reversible tracker and all uncommitted changes, and allow the user to continue chatting.
- Q: What exact label should the new footer action use?
  - A: **Cancel and continue**.

### 2.2 Final Summarized Requirements

- Add a left-aligned ghost action labeled **Cancel and continue** to the AI changes review modal.
- The new action must abort the pending `logseq_commit_changes` call and terminally cancel its assistant turn without asking the model to continue that turn.
- Preserve the reversible transaction tracker and queued uncommitted changes; do not clear/discard them.
- After cancellation, change the pending assistant message out of `requires-action` so the composer is immediately usable for a new message.
- Make the composer stop button enabled while the commit tool requires review. In that state, stop must invoke the same abort-and-retain operation as the modal action.
- Keep existing behavior for **Commit changes**, **Discard uncommitted changes**, header close, and Escape. Close/Escape continue to defer review and leave the tool pending.
- Make cancellation safe while diff preparation, modal review, or final commit execution is in progress: temporary graph mutations must be cleaned up and late async callbacks must not commit, discard, resume, or overwrite cancellation.

## 3. Existing System

### Commit review flow

- `src/chat-app/tools/impl/LogseqCommitChangesTool.tsx` defines the human tool `logseq_commit_changes`.
- Its renderer locates the latest reversible transaction tracker, prepares a diff by executing then reverting queued commands, persists the tracker, and opens `showAIChangesReviewModal`.
- The modal currently returns `true` (commit), `false` (discard), or `null` (defer). Discard calls `executeCancel`, which clears the tracker. Defer adds no tool result and leaves the turn in `requires-action`.
- Review work is launched from a React callback, not from a frontend tool `execute` context, so it has no assistant-ui `AbortSignal`. `executeApprove` accepts a signal, but renderer calls do not supply one; `prepareReview` supplies none.
- `LogseqReversibleTransactionTracker.execute` and `revertAppliedCommands` support cooperative abort checks between commands. Individual Logseq command operations and page printing are not interruptible, so cancellation must check immediately after each awaited boundary and perform un-aborted cleanup.

### Modal and footer

- `src/ui/pages/AIChangesReviewModal.tsx` renders `ModalFooter` with Commit and destructive Discard actions.
- `src/ui/launchers/showAIChangesReviewModal.ts` exposes `Promise<boolean | null>`.
- `src/ui/modals/core/ModalFooter.tsx` uses `sm:flex-row-reverse`; its existing `children` position does not provide a reliable left-side leading slot. `LogseqButton` already supports `color="ghost"`.
- Header close and Escape use `handleCancel`; Enter currently resolves the default discard result. Outside-click is disabled by the component.

### Composer and runtime cancellation

- `src/chat-app/components/ComposerAction.tsx` displays stop for both running and `requires-action` states, but explicitly sets `disabled={requiresActionState}`.
- `ComposerPrimitive.Cancel` delegates to `runtime.cancelRun()`. Once LocalRuntime has settled into a human-tool `requires-action` state, its roundtrip abort controller is normally gone, so merely removing `disabled` would leave the pending tool unresolved.
- `src/chat-app/runtime/cancelPendingToolCallsInThread.ts` already patches unresolved calls with an error result and marks the assistant message `{type: "incomplete", reason: "cancelled"}` in both runtime and `ThreadStore`. This does not restart the model, unlike renderer `addResult`, but it currently targets only the latest required-action turn and has no exact-call option.
- Review callbacks can continue after repository cancellation and later call `addResult` or mutate/persist the tracker. A shared cancellation session is therefore required, not only a message-state patch.

### Existing tests and documentation

- Relevant tests are in:
  - `tests/src/chat-app/tools/impl/LogseqCommitChangesTool.test.ts`
  - `tests/src/chat-app/runtime/cancelPendingToolCallsInThread.test.ts`
  - `tests/src/ui/pages/AIChangesReviewModal.test.ts`
- There is no existing `ComposerAction` coverage and no component-level review-modal action coverage.
- No matching user documentation for this review UI was found under `docusaurus/`; no documentation change is required for this targeted behavior.

## 4. Solution

### 4.1 Add targeted pending-tool cancellation

Modify `src/chat-app/runtime/cancelPendingToolCallsInThread.ts`:

- Add an optional target containing `messageId`, `toolCallId`, and optional `toolName` to both repository and thread-level cancellation APIs.
- Validate that the target message belongs to the active branch, is in `requires-action`, and contains the matching unresolved tool call.
- When targeted, cancel all unresolved calls in that same assistant turn so an `incomplete/cancelled` turn cannot retain structurally unresolved siblings, while leaving older turns, inactive branches, and other threads untouched.
- Preserve existing artifacts and already-resolved results.
- Return a changed/not-found result so stale clicks cannot report success or mutate an unrelated call.
- Preserve the current untargeted behavior for `ReviewChangesDisplay` compatibility.

The terminal patch remains:

```ts
result: {success: false, error: "User canceled operation"},
isError: true,
status: {type: "incomplete", reason: "cancelled"}
```

This repository import is intentionally used instead of `addResult`: LocalRuntime resumes the model after the last human tool receives `addResult`, whereas cancel-and-continue must end the current turn and unblock a new user message.

### 4.2 Add shared CommitTool abort orchestration

Add `src/chat-app/runtime/abortPendingCommitToolCall.ts` as the single operation used by the modal flow and composer stop action.

- Identify a pending commit call by `{threadId, messageId, toolCallId, toolName}`. The tool renderer supplies its exact `toolCallId` and containing message ID; the composer path locates the unresolved `LogseqCommitChangesTool.NAME` call on the current active required-action turn.
- Maintain a module-local active review-session registry keyed by thread/message/tool-call identity. A session stores:
  - its own `AbortController`;
  - the captured tracker and original artifact location;
  - a promise resolved when the renderer’s async review callback reaches `finally`;
  - one idempotent abort/finalization promise.
- `abortPendingCommitToolCall` must:
  1. validate and capture the exact pending call before asynchronous work;
  2. abort a registered review session immediately, if present;
  3. wait for that review callback to quiesce;
  4. ensure commands temporarily applied by review/commit cancellation are reverted without passing the already-aborted signal;
  5. persist the retained tracker at its existing artifact location using `persistLogseqReversibleTransactionTrackerArtifact`;
  6. invoke targeted `cancelPendingToolCallsInThread` to terminally cancel the turn.
- If stop is clicked before review is opened, use the current tracker/location without a registered session, retain its existing safe state, persist if cleanup was needed, and patch the pending commit turn.
- Make repeated stop/modal requests share the same finalization promise. Never clear the tracker or append a synthetic tool result.
- Log failures through the centralized logger. Even if tracker persistence fails, still move the tool turn out of `requires-action` so the composer is not permanently blocked; notify the user that retained state could not be persisted.

Ordering is important: settle graph work and persist the tracker first, then patch runtime/store cancellation, so a late tracker persistence import cannot overwrite the terminal tool-call state.

### 4.3 Make commit review async work abort-safe

Modify `src/chat-app/tools/impl/LogseqCommitChangesTool.tsx`:

- Read `toolCallId`, determine its containing assistant message, and acquire the current thread ID/runtime using the established local-ID/remote-ID and `assistantRuntime.threads.getById(threadId)` pattern.
- At the start of `reviewAndCommit`, create and register an active review session with the exact tracker instance and artifact location.
- Extend `prepareReview` to accept `{signal?: AbortSignal}` and:
  - pass the signal into tracker execution;
  - check it before and after each printer, execute, revert, persistence, and diff-construction boundary;
  - on abort, use an un-aborted cleanup reversion so temporary applied commands do not remain partially applied;
  - retain the command queue and propagate an abort outcome rather than a normal tool error.
- Pass the same session signal to the modal launcher and final commit path.
- Add a review-specific abort-safe commit helper (or extend `executeApprove` without changing its existing public behavior) that checks the signal before execution and after execution but before `tracker.clear()`. If aborted during cooperative execution, revert newly applied commands, retain the queue, and do not produce a normal result.
- Before every `addResult`, tracker clear, normal persistence, and user notification, verify that the session has not been aborted. Catch abort separately from ordinary failures and suppress normal result/error handling.
- Resolve and unregister the session in `finally`; this lets the shared abort operation safely wait until no late callback can overwrite cancellation.

Result routing after the modal becomes:

```ts
switch (reviewResult) {
    case "commit":
        // abort-safe execute, then add success result
        break;
    case "discard":
        // existing clear-and-error behavior
        break;
    case "abort":
        // start shared abort finalization, return, then settle session in finally
        break;
    case "defer":
        // preserve existing pending-tool behavior
        return;
}
```

The modal path must not await a finalizer that is itself waiting for the renderer session’s `finally`; it starts the idempotent abort request and returns so session completion can resolve. The composer path may await the same finalizer.

### 4.4 Give the modal explicit outcomes and a leading ghost action

Modify:

- `src/ui/pages/AIChangesReviewModal.tsx`
- `src/ui/launchers/showAIChangesReviewModal.ts`
- `src/ui/modals/core/ModalFooter.tsx`

Define and use a discriminated result:

```ts
type AIChangesReviewResult = "commit" | "discard" | "abort" | "defer";
```

- Map Commit to `"commit"`, Discard to `"discard"`, and the new action to `"abort"`.
- Map header close/Escape to `"defer"`, preserving current semantics. Preserve Enter’s existing discard default.
- Allow `showAIChangesReviewModal` to accept the review session’s optional `AbortSignal`. While mounted, listen for external abort (composer stop), resolve `"abort"`, and close the modal; remove the listener on cleanup and guard against duplicate resolution.
- Add a narrowly scoped `leadingAction` slot to `ModalFooter`, rendered after the standard buttons in DOM order so `sm:flex-row-reverse` places it visually at the far left without changing existing modal ordering.
- Render a `LogseqButton color="ghost"` in that slot with exact text **Cancel and continue**. Keep Commit primary and Discard failed/red.
- Keep the existing responsive footer behavior and do not enable outside-click closure.

### 4.5 Enable stop for required CommitTool action

Modify `src/chat-app/components/ComposerAction.tsx`:

- Keep `ComposerPrimitive.Cancel` for a genuinely running model/tool roundtrip.
- For a `requires-action` turn containing an unresolved `logseq_commit_changes` call, render the same square stop button as a project-owned button whose click invokes `abortPendingCommitToolCall` with the current thread runtime.
- Do not set `disabled={requiresActionState}`. Disable only while the idempotent abort operation is finalizing, to prevent duplicate interaction.
- Preserve the existing icon, classes, tooltip/ARIA label, model selector, idle Send behavior, and normal running cancellation.
- If a required-action state does not belong to CommitTool, avoid targeting an unrelated tool; retain the appropriate existing generic cancellation behavior rather than silently patching it as a commit abort.
- Update the component’s required “Changes” comment to document the project-specific required-action stop behavior.

Once cancellation changes the last message to `incomplete/cancelled`, the existing send-button predicate and composer keyboard logic naturally allow the next user message; no `Composer.tsx` change is needed.
