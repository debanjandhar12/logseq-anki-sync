# Share the just-bash filesystem and virtual identity with Pyodide

## 1. User Requirement

> Review for e486f9f6 / 46a25c89:

It was my expectation that a python script should be able to read / write to JustBashAdapterFS.ts based on permissions. Interoperability should have been seemless.
> - Network access does not have same problem since pythonCommand.ts currently passes the allow list fetch.
> - OS paths and username needs to be same as just-bash so that pyodide does not appear to be virtualized differently. (user from VIR_ENV_USER_PATH should have been used... I am also open to renaming VIR_ENV_USER_PATH to VIR_ENV_USER = 'user' if required... basic idea is constant for both should be centralized.. changing one constant should impact both).
>

However in future, write stores might be added as well. Hence, the bridge needs to support both read and write from pyodide (similar to JustBashAdapterFS which supports both..)

## 2. Final Requirement After Discussion With User

### 2.1 Clarification Q&A

**Is a live bridge possible?** The user ran a probe in the Logseq plugin iframe (`lsp://logseq.com/external/...`, Electron 42 / Chrome 148):

```
crossOriginIsolated: false
sabConstructorExposed: false
worker.error: "postMessage threw: DataCloneError: ... SharedArrayBuffer transfer requires self.crossOriginIsolated."
coep/coop/corp headers on plugin assets: null
```

Conclusion: a live, blocking host<->worker filesystem bridge (the `Atomics.wait` design just-bash uses for its Node-only `python3`) is **not possible** in Logseq. Logseq's main process strips CSP/X-Frame-Options but never adds COOP/COEP. Running Pyodide on the main thread would not help either: Emscripten FS `node_ops` are synchronous while `IFileSystem` / `LogseqPluginStorageManager` are Promise-based. The only seamless option is a **snapshot bridge**: copy the just-bash tree into Pyodide's MEMFS before the script runs, diff MEMFS afterwards, and write changes back through `IFileSystem` (where `JustBashAdapterFS` enforces permissions).

| Question | Answer |
|---|---|
| Write-back failures when script exits 0 (e.g. chmod-bypassed read-only mount, write into read-only base)? | **stderr + force exit code 1** |
| Snapshot size budget exceeded (per-file / total)? | **Fail the command** with a clear message naming the limit |
| Share `/tmp` too (possibly a new persistent tmp store for pip cache)? | Open to it, but **keep `/tmp` Python-private if it adds a lot of complexity** -> decision: keep private (see 4.9) |
| Identity centralization? | **`VIR_ENV_USER` + derived path + hostname**; bash and Pyodide both read the same constants |
| Propagate Python deletions back? | **Yes, full diff** (created / modified / deleted files and directories) |

### 2.2 Final Summarized Requirements

1. A Python script run via `python` / `python3` / `py` sees the just-bash `/home/user` subtree (all `JustBashAdapterFS` mounts and the base) as ordinary files: `open()`, `os.listdir()`, `json.load()`, `pathlib` etc. work without any special API.
2. Files/directories the script creates, modifies or deletes under `/home/user` are written back to just-bash through `IFileSystem`, so `JustBashAdapterFS` permissions (`read` / `readexecute` / `readwrite`) are the authoritative check. Future `readwrite` mounts work with no bridge changes.
3. Read-only locations are presented read-only inside Python (mode bits), so the common path raises `PermissionError` immediately; bypasses are caught at write-back and reported (stderr + exit 1).
4. Snapshot and write-back are bounded by byte budgets; exceeding them fails the command.
5. `HOME`, `USER`, `LOGNAME`, `HOSTNAME`, uid/gid, `whoami`, `hostname`, `~`, `socket.gethostname()`, `os.getuid()` etc. are identical between bash and Python and derived from a single set of constants in `src/constants.ts`.
6. Documentation and the `working-with-bash` skill are updated to describe the shared filesystem.

## 4. Solution

### 4.1 Overview / data flow

```
createPythonCommand (host, inside just-bash command)
  1. captureSandboxSnapshot(context.fs, VIR_ENV_USER_PATH)      -> SandboxSnapshot   (budget-checked)
  2. executePython({..., snapshot})                              -> worker
       worker: materializeSnapshot(FS, snapshot)                 (mkdir/write/chmod/utime)
               run bootstrap + user code
               collectSandboxChanges(FS, snapshot)               -> SandboxChanges    (budget-checked)
       returns PythonExecutionResult + changes
  3. applySandboxChanges(context.fs, changes)                    -> WriteBackFailure[]
  4. merge failures into stderr / exit code                      -> ExecResult
```

Scope is exactly the `VIR_ENV_USER_PATH` subtree. Python's `/tmp`, `/lib`, site-packages etc. stay private and ephemeral. MEMFS mode bits are a *hint*; `IFileSystem` is the authority.

### 4.2 Constants (`src/constants.ts`)

```ts
/** Virtual identity shared by the Bash sandbox and the Python runtime. Change here only. */
export const VIR_ENV_USER = "user";                 // must equal just-bash's built-in `whoami`
export const VIR_ENV_HOSTNAME = "localhost";        // must equal just-bash's built-in `hostname`
export const VIR_ENV_UID = 1000;
export const VIR_ENV_GID = 1000;
export const VIR_ENV_USER_PATH = `/home/${VIR_ENV_USER}`;
```

Keep `VIR_ENV_USER_PATH` (all existing imports stay valid). Add to `src/core/just-bash-wrapper/pyodide/fs-bridge/sandboxFsLimits.ts`:

```ts
export const MAX_SANDBOX_SNAPSHOT_FILE_BYTES = 16 * 1024 * 1024;
export const MAX_SANDBOX_SNAPSHOT_TOTAL_BYTES = 128 * 1024 * 1024;
```

Both limits apply to the inbound snapshot and to the outbound change set.

### 4.3 Protocol types (`pyodide/workerProtocol.ts`)

```ts
export interface SandboxSnapshotDirectory { path: string; mode: number }           // absolute, mode & 0o777
export interface SandboxSnapshotFile { path: string; mode: number; content: Uint8Array }
export interface SandboxSnapshot {
    root: string;                                   // VIR_ENV_USER_PATH
    directories: SandboxSnapshotDirectory[];        // includes root, sorted by depth asc
    files: SandboxSnapshotFile[];
}
export interface SandboxChanges {
    createdDirectories: string[];                   // depth asc
    writtenFiles: Array<{path: string; content: Uint8Array}>;   // created + modified
    deletedFiles: string[];
    deletedDirectories: string[];                   // depth desc
    unsupported: Array<{path: string; reason: string}>;         // e.g. symlinks
}
export interface PythonWorkerExecution { ...existing; snapshot: SandboxSnapshot }
export type PythonExecutionResult = { stdout; stderr; exitCode; changes?: SandboxChanges }
```

`changes` is `undefined` when the worker failed before/while collecting (and when the budget was exceeded) so the host never applies a partial diff. Payloads cross comlink by structured clone (no `transfer()`): `InMemoryFs.readFileBuffer` may return a view onto the filesystem's own buffer, and transferring would detach it.

### 4.4 Host: `pyodide/fs-bridge/captureSandboxSnapshot.ts`

```ts
export async function captureSandboxSnapshot(fs: IFileSystem, root: string): Promise<SandboxSnapshot>
```

- Recursive walk starting at `root`: `fs.stat(root)` (must be a directory, else throw), `fs.readdir(dir)` sorted, then per child `fs.stat(child)`; directory -> recurse, file -> `fs.readFileBuffer(child)`; `isSymbolicLink` -> throw `SandboxSnapshotError("symbolic links are not supported: <path>")`.
- Mode: `stat.mode & 0o777`. (After 4.8 the read-only base reports `0o555`/`0o444`.)
- Budgets: per file `content.byteLength > MAX_SANDBOX_SNAPSHOT_FILE_BYTES` -> throw `SandboxSnapshotError("'<path>' exceeds the 16 MiB per-file limit")`; running total over `MAX_SANDBOX_SNAPSHOT_TOTAL_BYTES` -> throw with total-limit message. Check before reading the next file so the walk stops early.
- Known cost: `JustBashAdapterFS.stat()` on a file reads its content, so adapter files are read twice (stat + readFileBuffer). Acceptable for now; noted as a follow-up (expose `readdirWithFileTypes` through the mountable layer).
- Export a small `SandboxSnapshotError extends Error` so the command can produce `python: cannot snapshot sandbox filesystem: <message>`.

### 4.5 Host: `pyodide/fs-bridge/applySandboxChanges.ts`

```ts
export interface WriteBackFailure { path: string; message: string }
export async function applySandboxChanges(fs: IFileSystem, changes: SandboxChanges): Promise<WriteBackFailure[]>
```

Sequential, each step individually try/caught (an EROFS on one path must not stop the others):

1. `unsupported` -> straight to failures.
2. `createdDirectories` (depth asc) -> `fs.mkdir(path, {recursive: true})`.
3. `writtenFiles` -> `fs.writeFile(path, content)` (Uint8Array; `JustBashAdapterFS.toStorableText` decodes UTF-8, `InMemoryFs` keeps bytes).
4. `deletedFiles` -> `fs.rm(path)`.
5. `deletedDirectories` (depth desc) -> `fs.rm(path)` (non-recursive; if a child deletion failed above, this reports ENOTEMPTY/EROFS for the dir too, which is the truth).

Failure message = `error.message` from the fs (already Node-style, e.g. `EROFS: read-only file system, open '/x.txt'`).

### 4.6 Host: `pyodide/createPythonCommands.ts`

After computing `code`/`scriptArgs` and before `executePython`:

```ts
let snapshot: SandboxSnapshot;
try { snapshot = await captureSandboxSnapshot(context.fs, VIR_ENV_USER_PATH); }
catch (cause) { return error(commandName, `cannot snapshot sandbox filesystem: ${message(cause)}`, 1); }

const result = await executePython({..., snapshot});
if (!result.changes) return result;                       // aborted / timed out / worker failure / budget exceeded

const failures = await applySandboxChanges(context.fs, result.changes);
if (failures.length === 0) return stripChanges(result);
const lines = failures.map(f => `${commandName}: cannot write back '${f.path}': ${f.message}\n`).join("");
return { stdout: result.stdout, stderr: result.stderr + lines, exitCode: result.exitCode === 0 ? 1 : result.exitCode };
```

`error()` gains an optional exit code parameter (keep default 2 for usage errors; snapshot failure uses 1). `ExecResult` must not carry `changes` -> return `{stdout, stderr, exitCode}` only.

### 4.7 Runtime plumbing (`pyodide/pyodideRuntime.ts`)

- `ExecutionOptions extends PythonWorkerExecution` already; `createExecution()` adds `snapshot`.
- Timeout/abort/failure branches return results **without** `changes` (nothing is written back), which is the desired semantics: a killed worker's partial writes are lost, like a killed process whose fs was tmpfs-backed.

### 4.8 `ReadOnlyFileSystem.ts`: report read-only modes

`stat` and `lstat` return `{...stat, mode: stat.mode & ~0o222}`. Effect: `ls -ld /home/user` shows `dr-xr-xr-x`, matching the EROFS behaviour it already has, and the snapshot carries correct modes for base paths. Add a focused test.

### 4.9 Decision on `/tmp` and a pip cache

Keep `/tmp` Python-private. Reasons: micropip installs into `/lib/python3.14/site-packages`, not `/tmp`, so sharing `/tmp` would not cache wheels; wheels are binary while `LogseqPluginStorageManager`/`JustBashAdapterFS` are text-only (would need base64 + ~33% bloat and tens of MB per SciPy-class wheel per `python` call under the snapshot model). A wheel cache is a separate feature best done in the worker with the Cache API keyed by the pinned jsDelivr URL (does not touch the fs bridge). Record as follow-up in the docs section, not implemented here.

### 4.10 Worker: `pyodide/worker/materializeSnapshot.ts`

```ts
export const SNAPSHOT_MTIME_SECONDS = 0;   // matches JustBashAdapterFS epoch-0 mtimes
export function materializeSnapshot(FS: PyodideFS, snapshot: SandboxSnapshot): void
```

1. If `snapshot.root` exists in MEMFS (Pyodide creates `HOME`), remove its contents first (`FS.readdir`, recursive `unlink`/`rmdir`) so the view is exact.
2. `FS.mkdirTree(dir.path)` for every directory (depth asc). Modes are applied **after** files are written (a `0o555` directory would block `writeFile` into it).
3. `FS.writeFile(file.path, file.content)` then `FS.utime(path, SNAPSHOT_MTIME_SECONDS * 1000, SNAPSHOT_MTIME_SECONDS * 1000)`.
4. `FS.chmod(path, mode)` for files (`0o444` / `0o644` / `0o666`...), then directories deepest-first.

Type `PyodideFS = PyodideInterface["FS"]` (declared once in `worker/pyodideFs.ts` with the handful of members we use, since the shipped d.ts types `FS` loosely).

### 4.11 Worker: `pyodide/worker/collectSandboxChanges.ts`

```ts
export function collectSandboxChanges(FS: PyodideFS, snapshot: SandboxSnapshot): SandboxChanges   // throws SandboxBudgetError
```

- Index snapshot: `Map<path, Uint8Array>` for files, `Set<path>` for directories.
- Walk MEMFS from `snapshot.root` with `FS.readdir` (skip `.`/`..`) and `FS.lstat`:
  - symlink -> `unsupported.push({path, reason: "symbolic links are not supported"})`, do not descend.
  - directory -> if not in snapshot dirs -> `createdDirectories`; recurse.
  - file -> `content = FS.readFile(path)`; not in snapshot files -> written; else compare `byteLength` then bytes (`indexOf`-free loop or `every`) -> written if different.
  - Type changes (file -> dir or dir -> file) fall out naturally: old entry lands in deleted*, new one in created*/written.
- `deletedFiles` = snapshot files not seen; `deletedDirectories` = snapshot dirs not seen (never the root).
- Budget: per written file and total over `MAX_SANDBOX_SNAPSHOT_*` -> throw `SandboxBudgetError` with the same wording as 4.4.
- Byte comparison is used instead of trusting mtime so a script's `os.utime()` cannot hide changes.

### 4.12 Worker: `executePythonInWorker.ts`

```ts
materializeSnapshot(pyodide.FS, execution.snapshot);        // before loadPackage/bootstrap; failure -> io.result(1, error)
... existing run ...
const result = io.result(exitCode | 1-on-error);            // existing
try { result.changes = collectSandboxChanges(pyodide.FS, execution.snapshot); }
catch (error) { return {...result, exitCode: 1, stderr: result.stderr + `python: ${message}\n`, changes: undefined}; }
```

Changes are collected on both success and uncaught-exception paths (files written before a crash persist, like a real process), but **not** when materialization itself failed.

Unit-test seam: `executePythonInWorker.test.ts` mocks `./materializeSnapshot` and `./collectSandboxChanges` modules (`vi.mock`) since its fake `pyodide` has no `FS`.

### 4.13 Worker identity (`initializePyodideWorker.ts`, `createPythonExecution.ts`)

- `loadPyodide({..., env: {HOME: VIR_ENV_USER_PATH, USER: VIR_ENV_USER, LOGNAME: VIR_ENV_USER, HOSTNAME: VIR_ENV_HOSTNAME}})`. The worker imports `src/constants.ts` directly (pure module, already bundled).
- Bootstrap additions (values injected with `JSON.stringify`):

```python
import os, socket, platform
_uname = os.uname()
os.uname = lambda: os.uname_result((_uname.sysname, HOSTNAME, _uname.release, _uname.version, _uname.machine))

```

Plus the existing `os.environ.update(env)` — just-bash's `exportedEnv` now contains `HOME/USER/LOGNAME/HOSTNAME` (4.14), so `os.environ` matches bash. Keep `os.makedirs(cwd, exist_ok=True)` (cwd may be outside the snapshot, e.g. `/`). `getpass.getuser()` reads `LOGNAME`/`USER` and needs no patch.
