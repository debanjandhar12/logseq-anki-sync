# Centralize skill frontmatter schema, forbid Mustache in frontmatter, convert MustacheView to a class

## 1. User Requirement

> (a) can we centralize SKILL_FRONTMATTER_FIELDS? across validation (validateSkillFileContent.ts) and createSkillEditorExtensions.ts?
> (b) Is mustache variables currently supported in frontmatter (for codemirror extension, skill parsing)? it should not be supported there...
> (c) In MustacheView.ts, can we derive from createMustacheView, instead of creating EMPTY_MUSTACHE_VIEW_VALUES etc separately?  Also, we should make MustacheView into a class (static / non-static, either is fine). We might need to make the method async, if required, make it async.

## 2. Final Requirement After Discussion With User

### 2.1 Clarification Q&A

1. **Where should the centralized field schema live, and how far should de-duplication go?**
   → *Core table drives validation + editor + metadata reads.* New module under `src/core/skill-parser/`; consumed by `validateSkillFileContent.ts`, `createSkillEditorExtensions.ts`, `SkillEditorModal/utils/skillFileFrontmatter.ts` and `initBuiltInSkillFiles.ts`.
2. **A single ordered table forces one order for autocomplete and validation diagnostics. Which order wins?**
   → *Autocomplete order everywhere*: `name`, `description`, `disable-model-invocation`, `built-in-skill`, `built-in-skill-user-controllable`. The validator's diagnostic order changes accordingly and its test assertion is updated.
3. **How should Mustache inside skill-file frontmatter be rejected?**
   → *Lint error + suppress completion + render body only.* Any `<% ... %>` in the frontmatter block is an error in the editor and blocks save; Mustache autocomplete is suppressed inside frontmatter; `SkillTool` renders only the body and leaves frontmatter verbatim.
4. **`MustacheView` shape, given that deriving names from `create()` requires async Logseq lookups?**
   → *Static class with async `getVariableNames()` derived from `create()`.* Async propagates into `validateMustacheTemplate`, the skill save-time validation, the CodeMirror linter, and their tests.

### 2.2 Final Summarized Requirements

- One ordered, typed skill-frontmatter field table in core, used for runtime validation, editor autocomplete, permissive metadata reads, and frontmatter writes.
- Mustache tags are body-only in skill files: rejected by the editor linter, rejected at save, never rendered in frontmatter.
- `MustacheView` becomes a static class whose supported-variable list is derived from the real view produced by `create()`; `EMPTY_MUSTACHE_VIEW_VALUES`, `MustacheViewValues` and `createMustacheViewFromValues` are deleted.
- Behavior preserved elsewhere: unknown frontmatter fields stay allowed, existing validation messages stay identical (only their order changes), case-insensitive Mustache lookups keep working.

## 3. Existing System

### 3.1 Skill frontmatter field names are hard-coded in four production sites

| Site | Duplication |
| --- | --- |
| `src/core/skill-parser/validateSkillFileContent.ts` | Reads `name`, `description`, `built-in-skill`, `built-in-skill-user-controllable`, `disable-model-invocation` with five near-identical `if` blocks; each key literal appears twice (read + message). |
| `src/ui/pages/SkillEditorModal/createSkillEditorExtensions.ts` | Module-private `SKILL_FRONTMATTER_FIELDS: readonly FrontmatterFieldDefinition[]` used only for autocomplete. |
| `src/ui/pages/SkillEditorModal/utils/skillFileFrontmatter.ts` | `getSkillFileMetadata()` re-reads four keys permissively; `updateDisableModelInvocation()` writes `"disable-model-invocation"`. |
| `src/core/chat-interop/initBuiltInSkillFiles.ts` | `delete metadata["disable-model-invocation"]` in `getComparableSkillContent()`. |

`tests/src/ui/components/LogseqCodeEditor/extensions/yamlFrontmatter.test.ts` redeclares the same five-field array locally. `SkillFileData` (`src/core/stores/skill-file-store/types.ts`) is the camelCase mirror; `FrontmatterFieldDefinition` (`src/ui/components/LogseqCodeEditor/extensions/yamlFrontmatter.ts`) is the CodeMirror-side shape `{key, valueType, required?}`.

Validation call graph: `SkillFileStore` → `parseSkillFile` → `validateSkillFileContent`; the editor additionally calls `validateSkillFileContent(source).issues` through `createFrontmatterLinter`.

### 3.2 Mustache is currently fully supported inside frontmatter (three layers)

- **Editor:** `createMustacheLinter(validateMustacheTemplate)` lints `view.state.doc.toString()` with no region restriction; `createMustacheCompletionSource` has no region restriction either, and both `createFrontmatterCompletionSource` and `createMarkdownCompletionSource` explicitly *yield* to an open Mustache tag via `isInsideOpenTag`.
- **Save gate:** `getFirstInvalidSkillTemplate()` in `src/ui/pages/SkillEditorModal/utils/validateSkillFiles.ts` runs `validateMustacheTemplate(file.content)` over the whole file, so `name: <% today %>` passes.
- **Runtime:** `SkillTool.execute()` renders `skillFile.content` (whole file, frontmatter included) through `parseTemplateString`.

Existing tests lock this in: `validateMustacheTemplate.test.ts` → "validates variables in frontmatter and fenced code"; `SkillTool.test.ts` → `expect(render).toHaveBeenCalledWith(source)` where the fixture has `name: <% today %>`.

A latent bug follows from it: a rendered frontmatter value can break YAML, after which `SkillFileStore.getSkillFile` swallows the parse error and the tool reports "Skill file not found".

Two frontmatter-range helpers matter: `getFrontmatterRange()` in `yamlFrontmatter.ts` returns the **body** range (between the `---` delimiters) and is used by markdown/frontmatter completion; `validateSkillFileContent` computes its own `getMatterFrom` offsets for diagnostics.

### 3.3 `MustacheView.ts` derives names from a parallel empty-values constant

`createMustacheViewFromValues(values)` builds the view and wraps it in a case-insensitive `Proxy`; `EMPTY_MUSTACHE_VIEW_VALUES` is a second full listing of the same 10 fields (+ 7 weekday aliases) whose only purpose is `MUSTACHE_TEMPLATE_VARIABLE_NAMES = Object.keys(createMustacheViewFromValues(EMPTY_MUSTACHE_VIEW_VALUES))`. `createMustacheView(date?)` is async because it awaits Logseq settings, current page/block, `preferredDateFormat` and the model-invokable skill list.

Consumers: `validateMustacheTemplate.ts` (module-level `SUPPORTED_VARIABLE_NAMES` set), `parseTemplateString.ts`, `createSkillEditorExtensions.ts` (autocomplete), the `template-engine` barrel, and three test files.

Relevant constraints:
- `linter()` accepts `(view) => Diagnostic[] | Promise<Diagnostic[]>`, and a `CompletionSource` may return a promise, so async validation/completion needs no CodeMirror workaround.
- `SkillEditorModal.tsx` builds extensions once at module scope (`const SKILL_EDITOR_EXTENSIONS = createSkillEditorExtensions();`), so nothing may touch Logseq APIs during extension construction.
- `tsconfig.json` has `"strict": false`; tests run under vitest/jsdom with `tests/setup.ts` proxying `@logseq/libs` to a live Logseq HTTP API, so suites that must run without Logseq have to stub their dependencies (existing precedent: `MustacheView.test.ts` spies the four dependency modules).
- Bundled skills use `<% #includeFile %>` in the **body** only and have clean frontmatter, so the new rule breaks no shipped file. `MAIN_SYSTEM_MESSAGE.md` has no frontmatter.

## 4. Solution

### 4.1 New core module: skill frontmatter schema

**`src/core/skill-parser/skillFrontmatterFields.ts` (new)**

```ts
import type {SkillFileData} from "../stores/skill-file-store/types";

export type SkillFrontmatterDataKey = Exclude<keyof SkillFileData, "content">;

/**
 * Mapped union keeps each dataKey paired with the value type of the corresponding
 * SkillFileData property; e.g. name cannot accidentally be declared boolean.
 */
export type SkillFrontmatterFieldDefinition = {
    [K in SkillFrontmatterDataKey]: {
        key: string;
        dataKey: K;
        valueType: NonNullable<SkillFileData[K]> extends boolean ? "boolean" : "string";
        required?: boolean;
    };
}[SkillFrontmatterDataKey];

/** Single source of truth: drives validation, editor autocomplete and metadata reads. */
export const SKILL_FRONTMATTER_FIELDS = [
    {key: "name", dataKey: "name", valueType: "string", required: true},
    {key: "description", dataKey: "description", valueType: "string", required: true},
    {key: "disable-model-invocation", dataKey: "disableModelInvocation", valueType: "boolean"},
    {key: "built-in-skill", dataKey: "builtInSkill", valueType: "boolean"},
    {
        key: "built-in-skill-user-controllable",
        dataKey: "builtInSkillUserControllable",
        valueType: "boolean"
    }
] as const satisfies readonly SkillFrontmatterFieldDefinition[];

/** YAML key lookup for read/write sites that need a single field, e.g. disable-model-invocation. */
export const SKILL_FRONTMATTER_KEYS = Object.freeze(
    Object.fromEntries(SKILL_FRONTMATTER_FIELDS.map((field) => [field.dataKey, field.key]))
) as {
    readonly [K in (typeof SKILL_FRONTMATTER_FIELDS)[number] as K["dataKey"]]: K["key"];
};

export type SkillFrontmatterValues = Partial<Pick<SkillFileData, SkillFrontmatterDataKey>>;

/** Permissive read: strings are trimmed, values with an unexpected type are dropped. */
export function readSkillFrontmatterValues(data: Record<string, unknown>): SkillFrontmatterValues {
    const values: SkillFrontmatterValues = {};
    for (const field of SKILL_FRONTMATTER_FIELDS) {
        const value = data[field.key];
        if (field.valueType === "string" && typeof value === "string") {
            Object.assign(values, {[field.dataKey]: value.trim()});
        } else if (field.valueType === "boolean" && typeof value === "boolean") {
            Object.assign(values, {[field.dataKey]: value});
        }
    }
    return values;
}
```

`SKILL_FRONTMATTER_FIELDS` is structurally assignable to `readonly FrontmatterFieldDefinition[]` (extra `dataKey` is fine for a non-fresh value), so the CodeMirror extension needs no type change.

The mapped union prevents mismatched `dataKey` / `valueType` entries. The table itself cannot prove exhaustiveness or uniqueness, so a focused test will assert that every `SkillFileData` metadata property occurs exactly once.

### 4.2 New core module: gray-matter-compatible lexical split

**`src/core/skill-parser/skillFileFrontmatter.ts` (new)**

```ts
export interface SkillFileFrontmatterSplit {
    /** Exact bytes gray-matter removes before exposing parsed.content. */
    prefix: string;
    /** Exactly equivalent to matter(source, {}).content for parseable input. */
    body: string;
    /** Raw YAML matter only; half-open and excludes delimiters. */
    matterRange: {from: number; to: number} | null;
}

export function splitSkillFileFrontmatter(source: string): SkillFileFrontmatterSplit {
    const delimiter = "---";
    if (!source.startsWith(delimiter) || source[delimiter.length] === "-") {
        return {prefix: "", body: source, matterRange: null};
    }

    // Mirror matter.language() exactly, including String#slice's -1 behavior when
    // there is no line break after the opening delimiter.
    let remaining = source.slice(delimiter.length);
    const initialRemainingLength = remaining.length;
    const languageRaw = remaining.slice(0, remaining.search(/\r?\n/));
    let matterFrom = delimiter.length;
    if (languageRaw.trim()) {
        remaining = remaining.slice(languageRaw.length);
        matterFrom += languageRaw.length;
    }

    // gray-matter closes at the first literal "\n---", not a delimiter-only line.
    const closingToken = "\n---";
    let closingIndex = remaining.indexOf(closingToken);
    if (closingIndex < 0) closingIndex = initialRemainingLength;
    if (closingIndex === initialRemainingLength) {
        return {
            prefix: source,
            body: "",
            matterRange: {from: matterFrom, to: matterFrom + remaining.length}
        };
    }

    const matterTo = matterFrom + closingIndex;
    let bodyFrom = matterTo + closingToken.length;
    if (source[bodyFrom] === "\r") bodyFrom += 1;
    if (source[bodyFrom] === "\n") bodyFrom += 1;

    return {
        prefix: source.slice(0, bodyFrom),
        body: source.slice(bodyFrom),
        matterRange: {from: matterFrom, to: matterTo}
    };
}
```

This intentionally mirrors `node_modules/gray-matter/index.js:57-123` and `matter.language()` at lines 205-217, including its unusual no-newline `String#slice(0, -1)` behavior. `----` is not frontmatter; an optional language suffix after the opening `---` is removed before searching; the first literal `\n---` closes the block; exactly three closing hyphens are consumed; at most one following `\r` and one `\n` are consumed; any other suffix is body. Thus `--- trailing` yields body beginning at ` trailing`, and `---Body` yields body beginning at `Body`. For no recognized block, body is the whole source; for an unclosed block, prefix is the whole source and body is empty. Implementation should stay deliberately close to the dependency algorithm rather than “cleaning up” these semantics.

All consumers use half-open ranges (`from <= position && position < to`), so the first byte of `body` is never classified as frontmatter.

**`src/ui/components/LogseqCodeEditor/extensions/yamlFrontmatter.ts`** — implement its existing `getFrontmatterRange()` in terms of `splitSkillFileFrontmatter(source).matterRange` instead of retaining the stricter delimiter-line regex. This keeps YAML completion, Markdown completion, Mustache completion, save validation and runtime rendering aligned for `--- trailing`, `---Body`, CRLF and unclosed blocks. Keep the existing export/API.

```ts
function getInvalidFieldMessage(
    field: SkillFrontmatterFieldDefinition,
    value: unknown
): string | null {
    if (field.valueType === "boolean") {
        return value === undefined || typeof value === "boolean"
            ? null
            : `Invalid skill file metadata: ${field.key} must be a boolean`;
    }
    if (typeof value === "string" && value.trim().length > 0) return null;
    if (!field.required && value === undefined) return null;
    return field.required
        ? `Invalid skill file metadata: ${field.key} is required`
        : `Invalid skill file metadata: ${field.key} must be a non-empty string`;
}
```

Behavior notes:
- Messages are byte-identical to today's; only diagnostic order changes (`disable-model-invocation` now precedes `built-in-skill`).
- `locateKey` is unified to `Object.hasOwn(parsed.data, field.key)`, which is equivalent to the current mixed usage (booleans only produce an issue when the key is present).
- Strings are trimmed by `readSkillFrontmatterValues`, replacing the inline `.trim()` calls.

### 4.4 `MustacheView` becomes a static class deriving its names from `create()`

**`src/core/template-engine/MustacheView.ts`** — delete `MustacheViewValues`, `createMustacheViewFromValues`, `EMPTY_MUSTACHE_VIEW_VALUES`, `MUSTACHE_TEMPLATE_VARIABLE_NAMES`, `getMustacheTemplateVariableNames`, `createCaseInsensitiveMustacheView`. Keep `MustacheTemplateView` and the `WEEKDAYS` table.

```ts
export class MustacheView {
    private static variableNamesPromise: Promise<readonly string[]> | null = null;

    /** Builds the live view; every supported variable is produced here exactly once. */
    static async create(date: Date = new Date()): Promise<MustacheTemplateView> {
        const now = dayjs(date);
        const dayjsFormat = await getUserPreferredDayjsFormat();
        const currentPage = await LogseqEditor.getCurrentPage();
        const currentEditingBlock = await LogseqEditor.getCurrentEditingBlock();
        const modelInvokableSkillList = await getModelInvokableSkillListString();

        const view: MustacheTemplateView = {
            globalAgentInstruction:
                LogseqSettingAccessor.getPluginSettings().globalAgentInstruction?.trim() ?? "",
            currentPage: currentPage?.uuid ?? "No current page",
            currentEditingBlock: currentEditingBlock?.uuid ?? "No current editing block",
            modelInvokableSkillList,
            chatAppAgentToolResultMaxChar: String(CHAT_APP_AGENT_TOOL_RESULT_MAX_CHAR),
            time: now.format("HH:mm"),
            today: now.format(dayjsFormat),
            tomorrow: now.add(1, "day").format(dayjsFormat),
            yesterday: now.subtract(1, "day").format(dayjsFormat),
            userTimeZone: getUserTimeZone()
        };

        for (const [weekday, weekdayIndex] of WEEKDAYS) {
            view[`last ${weekday.toLowerCase()}`] = MustacheView.getLastWeekday(
                now,
                weekdayIndex
            ).format(dayjsFormat);
        }

        return MustacheView.createCaseInsensitive(view);
    }

    /**
     * Supported variable names, derived from the real view so the two cannot drift.
     * Memoized because the shape is static; a failed lookup is not cached.
     */
    static async getVariableNames(): Promise<readonly string[]> {
        if (!MustacheView.variableNamesPromise) {
            const variableNamesPromise = MustacheView.create().then(
                (view) => Object.freeze(Object.keys(view)) as readonly string[]
            );
            MustacheView.variableNamesPromise = variableNamesPromise;
            variableNamesPromise.catch(() => {
                // Do not let a stale rejection clear a newer retry.
                if (MustacheView.variableNamesPromise === variableNamesPromise) {
                    MustacheView.variableNamesPromise = null;
                }
            });
        }
        return MustacheView.variableNamesPromise;
    }

    /** Wraps a caller-supplied view so `<% TODAY %>` and `<% today %>` both resolve. */
    static createCaseInsensitive(view: MustacheTemplateView): MustacheTemplateView { /* current Proxy body */ }

    private static getLastWeekday(date: dayjs.Dayjs, weekdayIndex: number): dayjs.Dayjs { /* unchanged */ }
}
```

`Object.keys` on the returned Proxy yields the canonical target keys (no `ownKeys` trap), i.e. exactly the list produced today.

### 4.5 Mustache is body-only in skill files

**`src/core/skill-parser/validateSkillFileTemplate.ts` (new)** — the single template validator for skill files, used by both the editor linter and the save gate.

```ts
export const FRONTMATTER_MUSTACHE_MESSAGE =
    "Mustache templates are not supported in skill file frontmatter.";

export async function validateSkillFileTemplate(
    content: string
): Promise<MustacheTemplateIssue[]> {
    const {prefix} = splitSkillFileFrontmatter(content);
    if (!prefix) return validateMustacheTemplate(content);

    return [
        ...collectFrontmatterTagIssues(prefix),
        // Mask the block (offsets and line breaks preserved) so body offsets stay exact
        // and an unclosed tag in frontmatter cannot mask body issues.
        ...(await validateMustacheTemplate(maskPrefix(content, prefix.length)))
    ];
}

function maskPrefix(content: string, prefixLength: number): string {
    return content.slice(0, prefixLength).replace(/[^\n]/g, " ") + content.slice(prefixLength);
}
```

`collectFrontmatterTagIssues` scans only `prefix` for every `MUSTACHE_TEMPLATE_TAGS[0]`, ending an issue after its matching closing tag when present, otherwise at end of line (excluding a trailing `\r`), and always advances so adjacent/malformed tags cannot loop. Because suffix text after closing `---` belongs to `body`, a tag in `--- <% today %>` is valid body Mustache and is not reported as frontmatter.

**`src/core/skill-parser/renderSkillFileTemplate.ts` (new)** — frontmatter is returned verbatim.

```ts
export async function renderSkillFileTemplate(content: string): Promise<string> {
    const {prefix, body} = splitSkillFileFrontmatter(content);
    return prefix + (await parseTemplateString(body));
}
```

### 5.2 Commands

```bash
pnpm test --run --reporter=dot --silent          # full suite (some suites need Logseq API on 127.0.0.1:12315)
npx tsc --noEmit                                 # type check
pnpm run check:fix <modified files> --reporter=summary   # biome lint + format, modified files only
pnpm build                                       # confirms the vite bundle still builds
```

Targeted runs while iterating: `pnpm test skillFileFrontmatter.test.ts --run --reporter=dot --silent`, same for `validateSkillFileTemplate`, `MustacheView`, `validateSkillFileContent`, `mustache`, `yamlFrontmatter`, `validateSkillFiles`, `SkillTool`.

All tests other than the single cache-owning `MustacheView.test.ts` case must stub `MustacheView.getVariableNames()` directly. This keeps template, lint and save tests independent of Logseq APIs and prevents the real static cache from leaking state across the single-fork suite.

### 5.3 Manual validation (`pnpm dev` in Logseq)

1. Open the Skills Editor. In frontmatter type `name: <% today %>` → red diagnostic "Mustache templates are not supported in skill file frontmatter."; typing `<% ` there offers no variable completions.
2. In the body, `<% tod` still autocompletes to `<% today %>` and `<% unknown %>` still reports "Unknown Mustache variable"; the lint gutter shows both frontmatter and Mustache diagnostics.
3. Frontmatter key autocomplete still offers the five fields in order `name, description, disable-model-invocation, built-in-skill, built-in-skill-user-controllable`, suppressing already-present keys, with `true`/`false` value completion.
4. Save with a frontmatter tag → error toast "Validation failed in <file>: Mustache templates are not supported…", save blocked; remove the tag → save succeeds.
5. Ask the chat agent to load a skill whose body uses `<% today %>` → the returned content shows rendered body values and untouched frontmatter; the "Enabled" checkbox still toggles `disable-model-invocation`; restarting the plugin does not rewrite unchanged built-in skills.
