# Centralize skill frontmatter schema, forbid Mustache in frontmatter, convert MustacheView to a class

## 1. User Requirement

> (a) can we centralize SKILL_FRONTMATTER_FIELDS? across validation (validateSkillFileContent.ts) and createSkillEditorExtensions.ts?
> (b) Is mustache variables currently supported in frontmatter (for codemirror extension, skill parsing)? it should not be supported there...
> (c) In MustacheView.ts, can we derive from createMustacheView, instead of creating EMPTY_MUSTACHE_VIEW_VALUES etc separately?  Also, we should make MustacheView into a class (static / non-static, either is fine). We might need to make the method async, if required, make it async.

## 2. Final Requirement After Discussion With User

### 2.1 Clarification Q&A

1. **Where should the centralized field schema live, and how far should de-duplication go?**
   → *Core table drives validation + editor + metadata reads.* New module under `src/core/skill-parser/`; consumed by `validateSkillFileContent.ts`, `createSkillEditorExtensions.ts`, `SkillEditorModal/utils/skillFileFrontmatter.ts` and `initBuiltInSkillFiles.ts`.
2. **A single ordered table forces one order for autocomplete and validation diagnostics. Which order wins?**
   → *Autocomplete order everywhere*: `name`, `description`, `disable-model-invocation`, `built-in-skill`, `built-in-skill-user-controllable`. The validator's diagnostic order changes accordingly and its test assertion is updated.
3. **How should Mustache inside skill-file frontmatter be rejected?**
   → *Lint error + suppress completion + render body only.* Any `<% ... %>` in the frontmatter block is an error in the editor and blocks save; Mustache autocomplete is suppressed inside frontmatter; `SkillTool` renders only the body and leaves frontmatter verbatim.
4. **`MustacheView` shape, given that deriving names from `create()` requires async Logseq lookups?**
   → *Static class with async `getVariableNames()` derived from `create()`.* Async propagates into `validateMustacheTemplate`, the skill save-time validation, the CodeMirror linter, and their tests.

### 2.2 Final Summarized Requirements

- One ordered, typed skill-frontmatter field table in core, used for runtime validation, editor autocomplete, permissive metadata reads, and frontmatter writes.
- Mustache tags are body-only in skill files: rejected by the editor linter, rejected at save, never rendered in frontmatter.
- `MustacheView` becomes a static class whose supported-variable list is derived from the real view produced by `create()`; `EMPTY_MUSTACHE_VIEW_VALUES`, `MustacheViewValues` and `createMustacheViewFromValues` are deleted.
- Behavior preserved elsewhere: unknown frontmatter fields stay allowed, existing validation messages stay identical (only their order changes), case-insensitive Mustache lookups keep working.

## 3. Existing System

### 3.1 Skill frontmatter field names are hard-coded in four production sites

| Site | Duplication |
| --- | --- |
| `src/core/skill-parser/validateSkillFileContent.ts` | Reads `name`, `description`, `built-in-skill`, `built-in-skill-user-controllable`, `disable-model-invocation` with five near-identical `if` blocks; each key literal appears twice (read + message). |
| `src/ui/pages/SkillEditorModal/createSkillEditorExtensions.ts` | Module-private `SKILL_FRONTMATTER_FIELDS: readonly FrontmatterFieldDefinition[]` used only for autocomplete. |
| `src/ui/pages/SkillEditorModal/utils/skillFileFrontmatter.ts` | `getSkillFileMetadata()` re-reads four keys permissively; `updateDisableModelInvocation()` writes `"disable-model-invocation"`. |
| `src/core/chat-interop/initBuiltInSkillFiles.ts` | `delete metadata["disable-model-invocation"]` in `getComparableSkillContent()`. |

`tests/src/ui/components/LogseqCodeEditor/extensions/yamlFrontmatter.test.ts` redeclares the same five-field array locally. `SkillFileData` (`src/core/stores/skill-file-store/types.ts`) is the camelCase mirror; `FrontmatterFieldDefinition` (`src/ui/components/LogseqCodeEditor/extensions/yamlFrontmatter.ts`) is the CodeMirror-side shape `{key, valueType, required?}`.

Validation call graph: `SkillFileStore` → `parseSkillFile` → `validateSkillFileContent`; the editor additionally calls `validateSkillFileContent(source).issues` through `createFrontmatterLinter`.

### 3.2 Mustache is currently fully supported inside frontmatter (three layers)

- **Editor:** `createMustacheLinter(validateMustacheTemplate)` lints `view.state.doc.toString()` with no region restriction; `createMustacheCompletionSource` has no region restriction either, and both `createFrontmatterCompletionSource` and `createMarkdownCompletionSource` explicitly *yield* to an open Mustache tag via `isInsideOpenTag`.
- **Save gate:** `getFirstInvalidSkillTemplate()` in `src/ui/pages/SkillEditorModal/utils/validateSkillFiles.ts` runs `validateMustacheTemplate(file.content)` over the whole file, so `name: <% today %>` passes.
- **Runtime:** `SkillTool.execute()` renders `skillFile.content` (whole file, frontmatter included) through `parseTemplateString`.

Existing tests lock this in: `validateMustacheTemplate.test.ts` → "validates variables in frontmatter and fenced code"; `SkillTool.test.ts` → `expect(render).toHaveBeenCalledWith(source)` where the fixture has `name: <% today %>`.

A latent bug follows from it: a rendered frontmatter value can break YAML, after which `SkillFileStore.getSkillFile` swallows the parse error and the tool reports "Skill file not found".

Two frontmatter-range helpers matter: `getFrontmatterRange()` in `yamlFrontmatter.ts` returns the **body** range (between the `---` delimiters) and is used by markdown/frontmatter completion; `validateSkillFileContent` computes its own `getMatterFrom` offsets for diagnostics.

### 3.3 `MustacheView.ts` derives names from a parallel empty-values constant

`createMustacheViewFromValues(values)` builds the view and wraps it in a case-insensitive `Proxy`; `EMPTY_MUSTACHE_VIEW_VALUES` is a second full listing of the same 10 fields (+ 7 weekday aliases) whose only purpose is `MUSTACHE_TEMPLATE_VARIABLE_NAMES = Object.keys(createMustacheViewFromValues(EMPTY_MUSTACHE_VIEW_VALUES))`. `createMustacheView(date?)` is async because it awaits Logseq settings, current page/block, `preferredDateFormat` and the model-invokable skill list.

Consumers: `validateMustacheTemplate.ts` (module-level `SUPPORTED_VARIABLE_NAMES` set), `parseTemplateString.ts`, `createSkillEditorExtensions.ts` (autocomplete), the `template-engine` barrel, and three test files.

Relevant constraints:
- `linter()` accepts `(view) => Diagnostic[] | Promise<Diagnostic[]>`, and a `CompletionSource` may return a promise, so async validation/completion needs no CodeMirror workaround.
- `SkillEditorModal.tsx` builds extensions once at module scope (`const SKILL_EDITOR_EXTENSIONS = createSkillEditorExtensions();`), so nothing may touch Logseq APIs during extension construction.
- `tsconfig.json` has `"strict": false`; tests run under vitest/jsdom with `tests/setup.ts` proxying `@logseq/libs` to a live Logseq HTTP API, so suites that must run without Logseq have to stub their dependencies (existing precedent: `MustacheView.test.ts` spies the four dependency modules).
- Bundled skills use `<% #includeFile %>` in the **body** only and have clean frontmatter, so the new rule breaks no shipped file. `MAIN_SYSTEM_MESSAGE.md` has no frontmatter.

## 4. Solution: Follow-up Module Reorganization

The implementation in the current worktree already satisfies the original behavior goals. This follow-up addresses the requested module-boundary review without changing runtime behavior, except for file/API locations.

### 4.1 Make `skill-parser` a real module

Replace `src/core/skill-parser/skillFrontmatterFields.ts` with:

- `src/core/skill-parser/types.ts`
  - `SkillFrontmatterDataKey`
  - `SkillFrontmatterFieldDefinition`
  - `SkillFrontmatterValues`
  - Optionally move `SkillFileValidationIssue` and `SkillFileValidationResult` here from `validateSkillFileContent.ts` if that does not create circular imports; otherwise leave those two beside their producer and export them through the barrel.
- `src/core/skill-parser/constants.ts`
  - `SKILL_FRONTMATTER_FIELDS`
  - `SKILL_FRONTMATTER_KEYS`
  - `FRONTMATTER_MUSTACHE_MESSAGE` (moved out of `validateSkillFileTemplate.ts`)
- `src/core/skill-parser/readSkillFrontmatterValues.ts`
  - only `readSkillFrontmatterValues()`
- `src/core/skill-parser/index.ts`

Export the public skill API from the barrel:

```ts
export {parseSkillFile} from "./parseSkillFile";
export {readSkillFrontmatterValues} from "./readSkillFrontmatterValues";
export {renderSkillFileTemplate} from "./renderSkillFileTemplate";
export {validateSkillFileContent} from "./validateSkillFileContent";
export {validateSkillFileTemplate} from "./validateSkillFileTemplate";
export type {
    SkillFileValidationIssue,
    SkillFileValidationResult
} from "./validateSkillFileContent";
export {
    FRONTMATTER_MUSTACHE_MESSAGE,
    SKILL_FRONTMATTER_FIELDS,
    SKILL_FRONTMATTER_KEYS
} from "./constants";
export type {
    SkillFrontmatterDataKey,
    SkillFrontmatterFieldDefinition,
    SkillFrontmatterValues
} from "./types";
```

Use relative imports inside the module. External consumers use `src/core/skill-parser` rather than deep paths.

### 4.2 Create the generic frontmatter module

Move and rename `src/core/skill-parser/skillFileFrontmatter.ts` to:

- `src/core/frontmatter/splitFrontmatter.ts`
- `src/core/frontmatter/types.ts` containing `FrontmatterSplit`
- `src/core/frontmatter/index.ts`

Rename the API from skill-specific to generic:

```ts
export interface FrontmatterSplit {
    prefix: string;
    body: string;
    matterRange: {from: number; to: number} | null;
}

export function splitFrontmatter(source: string): FrontmatterSplit;
```

Keep the implementation byte-for-byte compatible with the current splitter. This module owns generic Markdown frontmatter boundaries and will later support command Markdown files with a different schema. Do not put it in `template-engine`: future command files need frontmatter splitting without depending on Mustache.

Move `tests/src/core/skill-parser/skillFileFrontmatter.test.ts` to `tests/src/core/frontmatter/splitFrontmatter.test.ts` and update names/imports.

### 4.3 Keep skill policy in `skill-parser`

Keep `validateSkillFileTemplate.ts` and `renderSkillFileTemplate.ts` in `skill-parser`. They implement the skill-file policy that Mustache is body-only; that policy is not generic to all frontmatter Markdown files.

Update their imports from the old splitter to the generic barrel:

```ts
import {splitFrontmatter} from "../frontmatter";
```

Also update `src/ui/components/LogseqCodeEditor/extensions/yamlFrontmatter.ts` and `src/ui/pages/SkillEditorModal/createSkillEditorExtensions.ts` to import `splitFrontmatter` from `src/core/frontmatter`.

### 4.4 Split the Skill Editor utility by operation

Delete `src/ui/pages/SkillEditorModal/utils/skillFileFrontmatter.ts` after moving its functions:

- `utils/getSkillFileMetadata.ts`
  - `getSkillFileMetadata()`
- `utils/getSkillFileDisplayName.ts`
  - `getSkillFileDisplayName()` (rename from `getDisplayFileName` for consistency)
  - `UNTITLED_FILE_NAME` remains local
- `utils/getSkillFileName.ts`
  - `getSkillFileName()`
- `utils/updateDisableModelInvocation.ts`
  - `updateDisableModelInvocation()`

`getSkillFileDisplayName` imports `getSkillFileMetadata`. Update `SkillEditorModal.tsx` and `utils/validateSkillFiles.ts` imports.

### 4.5 Additional logic to move

- Move `FRONTMATTER_MUSTACHE_MESSAGE` to `skill-parser/constants.ts` because messages are module constants.
- Keep `validateSkillFileTemplate()` and `renderSkillFileTemplate()` in `skill-parser`; do not broaden `template-engine` into a policy owner.
- Keep `parseSkillFile()` in `skill-parser`.
- Keep generic Mustache parsing, variable view creation, and `parseTemplateString()` in `template-engine`.
- Do not create a new template/frontmatter umbrella module. `frontmatter` is syntax extraction, `template-engine` is Mustache rendering, and `skill-parser` is skill schema/policy.

Update source consumers:

  - skill constants/validators from `src/core/skill-parser`
- `src/ui/pages/SkillEditorModal/utils/validateSkillFiles.ts`
  - `parseSkillFile` and `validateSkillFileTemplate` from `src/core/skill-parser`
  - split display/name utilities from their new operation files
- `src/ui/pages/SkillEditorModal/SkillEditorModal.tsx`
  - new operation-file imports

Update tests under `tests/src/core/skill-parser`, `tests/src/core/frontmatter`, `tests/src/ui/components/LogseqCodeEditor/extensions`, `tests/src/ui/pages/SkillEditorModal`, and `tests/src/chat-app/tools/impl` to match renamed modules/functions. Rename tests consistently:

- `skillFrontmatterFields.test.ts` → `skillFrontmatter.test.ts` or split into `constants.test.ts` and `readSkillFrontmatterValues.test.ts`; prefer `readSkillFrontmatterValues.test.ts` plus constants assertions in it.
- `skillFileFrontmatter.test.ts` → `splitFrontmatter.test.ts` under `tests/src/core/frontmatter`.

### 4.7 Design rationale

- `src/core/frontmatter` is the reusable, property-schema-independent extraction layer needed by the future command feature.
- `src/core/skill-parser` owns skill schema, skill validation, and body-only template policy.
- `src/core/template-engine` remains Mustache-specific and keeps its established public API; no rename or repurposing is needed.
- Splitting UI utilities by operation avoids reviving a mixed “frontmatter” utility that reads metadata, formats names, and mutates YAML in one file.
