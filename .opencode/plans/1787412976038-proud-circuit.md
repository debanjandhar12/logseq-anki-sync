## 2. Final Requirement After Discussion With User

### 2.1 Clarification Q&A

- Render the entire stored skill file, including YAML frontmatter, when `SkillTool` reads it.
- Insert complete Mustache tags from autocomplete and consume an existing closing `%>`.
- Validate malformed Mustache and unknown interpolated variables only; ignore section/control names such as `includeFile`.
- Show inline diagnostics and block Save if any active or inactive skill is invalid.
- Add real YAML frontmatter support using `@codemirror/lang-yaml`.
- Frontmatter completion includes all five supported fields: `name`, `description`, `disable-model-invocation`, `built-in-skill`, and `built-in-skill-user-controllable`.
- Mustache supported names must be derived from a synchronous view-building helper, not maintained in a separate metadata/description registry.
- Read-only built-in skill errors also block all saves.
- Remove the test-only `mode` frontmatter field and generic enum completion test; the implemented Skill Editor contract contains only the five real string/boolean skill fields.

### 2.2 Final Summarized Requirements

- Preserve the implemented whole-file runtime rendering in `SkillTool` and the `globalAgentInstruction` compatibility fix.
- Refactor `template-engine` into a barrel-exported module, rename its constants file, remove the standalone variable metadata file, and derive supported names from the actual view shape.
- Retain parser-based Mustache validation while simplifying its implementation where possible.
- Turn `LogseqCodeEditor` into a directory module with generic, separately testable Markdown, Mustache, and YAML-frontmatter extensions.
- Compose those generic sources for the Skill Editor with exactly one autocomplete engine, inline Mustache linting, and authoritative all-file save validation.
- Disable HTML completion, retain Markdown language behavior, offer local Markdown syntax snippets, and insert fenced code as `````language`` without a space.
- Add focused regression tests and synchronized skill-authoring documentation.

## 3. Existing System

- The current implementation already renders `skillFile.content` through `parseTemplateString()` in `src/chat-app/tools/impl/SkillTool.tsx` and returns the rendered complete source without persisting it.
- `src/core/template-engine/MustacheView.ts` currently builds canonical variables and compatibility aliases through a separate `mustacheTemplateVariables.ts` registry. The registry also supplies editor descriptions, which are not required.
- `src/core/template-engine/validateMustacheTemplate.ts` correctly uses `Mustache.parse()` token offsets to detect unknown escaped/unescaped variables, malformed syntax, and unsupported delimiter changes. It ignores section/control names and recursively checks variables inside sections.
- `src/core/template-engine` has no `index.ts`; application code deep-imports individual files.
- `src/ui/components/LogseqCodeEditor.tsx` is a generic wrapper, while `../../src/ui/pages/SkillEditorModal/createSkillEditorExtensions.ts` currently combines Markdown language support, snippets, Mustache completion, and Mustache linting.
- `@codemirror/lang-markdown` provides Markdown parsing and editing commands but not general Markdown syntax snippets. A small reusable local snippet source remains appropriate.
- `@codemirror/lang-yaml` provides YAML parsing and `yamlFrontmatter({content})`, but schema-aware field/value completion still requires a generic local completion source.
- Current completion context code needs hardening for trailing whitespace in Mustache tags, unfinished inline code, and CRLF frontmatter.
- Save-time validation currently exempts built-in skills; final requirements remove that exemption.

## 4. Solution

### 4.1 Make `template-engine` a cohesive module

1. Rename `src/core/template-engine/mustacheTemplateConstants.ts` to `src/core/template-engine/constants.ts` and keep a readonly `MUSTACHE_TEMPLATE_TAGS` tuple.
2. Delete `src/core/template-engine/mustacheTemplateVariables.ts`.
3. Refactor `src/core/template-engine/MustacheView.ts` around two layers:
   - `createMustacheView()` remains asynchronous and resolves live settings, Logseq context, skill list, dates, and timezone.
   - Add an exported synchronous `createMustacheViewFromValues(values)` helper. Its typed input contains all resolved semantic values, including a seven-entry previous-weekday value map. The helper creates the concrete canonical keys and compatibility aliases and wraps the result with `createCaseInsensitiveMustacheView()`.
4. Add `getMustacheTemplateVariableNames()` in `MustacheView.ts`. It calls `createMustacheViewFromValues()` with inert empty values and returns the resulting own keys. It must not call settings, Logseq, storage, dates, or other asynchronous APIs. Cache/freeze the derived names and use them for validation and completion.
5. The synchronous helper must produce:
   - canonical keys `globalAgentInstruction`, `currentPage`, `currentEditingBlock`, `modelInvokableSkillList`, `chatAppAgentToolResultMaxChar`, `time`, `today`, `tomorrow`, `yesterday`, `userTimeZone`, and `lastSunday` through `lastSaturday`;
   - existing aliases `additionalSystemMessage`, `additional system message`, `current page`, `current editing block`, `model invokable skill list`, and spaced weekday forms;
   - case-only compatibility through the existing case-insensitive proxy.
6. Add `src/core/template-engine/index.ts` exporting the public renderer, view helpers/types, variable-name getter, validator/types, date/time helpers, skill-list helper, and delimiter constant. Internal implementation files may use relative imports to avoid barrel cycles; all consumers outside `template-engine` must import from the barrel.
7. Keep `MAIN_SYSTEM_MESSAGE.md` unchanged because `globalAgentInstruction` is the intended canonical key.

### 4.2 Simplify but preserve Mustache validation behavior

Update `src/core/template-engine/validateMustacheTemplate.ts` to import names from `getMustacheTemplateVariableNames()` and delimiters from `constants.ts`.

- Use the typed `Mustache.parse(source, MUSTACHE_TEMPLATE_TAGS)` API directly where the installed types permit, removing unnecessary wrapper casts/custom declarations.
- Normalize the derived view keys once into a case-insensitive `ReadonlySet`.
- Retain recursive token traversal because Mustache itself does not reject unknown variables.
- Validate only escaped `name` and unescaped `&` interpolation tokens; dotted paths and `.` remain unsupported because the view is flat.
- Ignore section, inverted-section, close, comment, and partial names, including `includeFile`, while still walking nested interpolation tokens.
- Continue rejecting delimiter-change tokens so Logseq `{{...}}` macros remain literal.
- Keep syntax-error-to-range conversion. Isolate parser-offset extraction/clamping in one small helper and provide a safe unmatched-opener fallback; do not replace this with regex-only parsing.

### 4.3 Preserve whole-file skill rendering and enforce all-file validation

- Keep `SkillTool.execute()` rendering the exact stored `skillFile.content` through the template-engine barrel before constructing `skillFileContent`.
- Preserve filename lookup, response shape, error behavior, and the rule that rendered output is never reparsed or stored.
- In `SkillEditorModal.handleSave`, validate every parsed skill, including read-only built-ins, before any delete/save operation. Remove the built-in exemption.
- On the first issue, select that file, show its filename and validation message, and return without any persistence. Inline diagnostics and save validation must use the same pure validator.

### 4.4 Convert `LogseqCodeEditor` into a generic directory module

Move the current wrapper without behavior changes:

```text
src/ui/components/LogseqCodeEditor/
  LogseqCodeEditor.tsx
  index.ts
  extensions/
    index.ts
    markdown.ts
    mustache.ts
    yamlFrontmatter.ts
```

- `LogseqCodeEditor/index.ts` exports the component/props and generic extension APIs.
- Update existing consumers to import the directory barrel. Do not retain a conflicting same-name flat file unless a compatibility shim is proven necessary.
- Extension modules expose completion sources/language supports rather than each installing competing global autocomplete overrides.

#### Markdown extension

`extensions/markdown.ts` will:

- expose Markdown support configured with `completeHTMLTags: false`;
- expose a reusable Markdown syntax `CompletionSource` using CodeMirror `snippetCompletion()` for headings, bullet/number/task lists, blockquotes, links/images, fenced/inline code, bold, italic, and horizontal rules;
- support explicit completion and context-specific trigger completion;
- suppress snippets inside YAML frontmatter, fenced/unfinished inline code, and unfinished Mustache tags;
- correctly support LF and CRLF boundaries;
- insert fenced code as `````language\nCode\n``` `` with no space between the opening fence and language.

No third-party Markdown snippet package will be added because the installed first-party Markdown package does not include snippets and available third-party packages are not suitable generic CodeMirror extensions.

#### Generic Mustache extension

`extensions/mustache.ts` will accept options rather than import skill/template-engine internals directly:

- delimiter tuple;
- readonly variable-name list;
- validator callback for linting.

It will expose a completion-source factory and lint-extension factory. Completion will:

- find the nearest still-open delimiter on the current line;
- reject control prefixes and a close delimiter occurring before the cursor;
- trim both leading and trailing query whitespace for matching;
- consume whitespace and a close delimiter after the cursor when applying a full tag;
- support frontmatter and fenced code because runtime Mustache does too.

The lint adapter maps generic `{from,to,message}` issues to CodeMirror diagnostics and installs `linter()`/`lintGutter()` without embedding Logseq-specific logic.

#### Generic YAML-frontmatter extension

Add direct dependency `@codemirror/lang-yaml` and use `yamlFrontmatter({content: markdownSupport})` so the initial YAML block has real parsing/highlighting and the body remains Markdown.

`extensions/yamlFrontmatter.ts` will expose a generic schema-driven completion source. Its field definition accepts a key, value kind, required flag, and optional enum values. The source will:

- operate only inside the initial `---` frontmatter block, supporting LF/CRLF and temporarily incomplete YAML;
- offer partial/missing keys while suppressing duplicate keys already present;
- insert key syntax suitable for continued value entry;
- offer `true`/`false` for boolean fields and configured values for enum fields;
- offer `true`/`false` for boolean fields. Enum completion is outside the current Skill Editor requirement and should not be represented by a fictitious skill field in tests;
- avoid triggering inside an unfinished Mustache tag.

### 4.5 Compose generic extensions for the Skill Editor

Keep `../../src/ui/pages/SkillEditorModal/createSkillEditorExtensions.ts` only as a thin skill-specific composition/configuration module:

- define the five-field schema: required string `name` and `description`; optional booleans `disable-model-invocation`, `built-in-skill`, and `built-in-skill-user-controllable`;
- obtain template names from the template-engine barrel;
- create Markdown-body/YAML-frontmatter language support;
- create Mustache, frontmatter, and Markdown completion sources;
- install exactly one `autocompletion({override: [...]})` with source precedence Mustache, frontmatter, then Markdown;
- add the generic Mustache lint extension using `validateMustacheTemplate`;
- return a stable extension array used by `SkillEditorModal`.

`SkillEditorModal` continues passing `basicSetup={{autocompletion: false}}` so the wrapper does not install a second autocomplete engine.
