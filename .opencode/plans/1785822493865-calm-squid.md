# Plan: Clarify Commit Tool Temporary-Change Outcomes

## 1. User Requirement

> Please check and enhance ChatToolResponse returned from LogseqCommitChangesTool. Make changes to clearly mention whether temporary changes were discarded or not.

> Also, need to make changes so that when user rejects, tempory changes are cleared.

## 2. Final Requirement After Discussion With User

### Clarification Q&A

- Q: Should the enhanced status cover every `LogseqCommitChangesTool` result path, including approval success, cancel/reject, no-op, and error/review failures?
- A: All paths.
- Q: For exceptional review failures where Logseq reversion fails, should the response distinguish unapplied graph changes from tracker cleanup?
- A: Treat clearing the tracker as sufficient to report the temporary changes discarded.

### Final Summarized Requirements

- Make every `ChatToolResponse` produced by `LogseqCommitChangesTool` explicitly communicate whether temporary changes were discarded.
- When the user rejects the review modal, discard the pending temporary changes by clearing the reversible transaction tracker after preview has reverted its applied mutations.
- Preserve accurate wording for cases where committed changes remain in Logseq and pending changes remain available after a failure; report changes as discarded when the cleanup path clears the tracker, including after a failed preview reversion.
- Add focused automated coverage for the response status and rejection-discard behavior.

## 3. Solution

### Commit Tool Response Contract

- Modify `src/chat-app/tools/impl/LogseqCommitChangesTool.tsx` so its success result payload includes an explicit boolean status such as `temporaryChangesDiscarded`, alongside the existing human-readable `changes` text.
- Set the field and message truthfully for every response-producing path:
  - No queued mutation commands: `false`; nothing existed to discard.
  - Execution produces no applied graph mutations and the tracker is cleared: `true`; the temporary tracker state was discarded.
  - Commit succeeds: `false`; the Logseq mutations remain committed, even though the reversible tracker is cleared.
  - Commit execution fails: `false`; retain the error-provided tracker artifact so remaining temporary changes are not represented as discarded.
  - User rejection: clear the prepared tracker and return a response that explicitly confirms temporary changes were discarded.
  - Diff/review errors where the tracker remains available: explicitly report `false` in the response text.
  - Diff-revert failure: preserve the existing defensive tracker clear and explicitly report that the temporary changes were discarded because their tracking was cleared.
  - Unexpected outer render error: state that discard status is unknown/not confirmed rather than claiming either outcome.
- Keep the rejection result as an error-form `ChatToolResponse` if assistant-ui requires this to mark a declined human tool; ensure its artifact is the serialized cleared tracker so later tools cannot recover the rejected changes.

### Rejection Cleanup

- In `executeCancel()` in `src/chat-app/tools/impl/LogseqCommitChangesTool.tsx`, clear the supplied transaction tracker before creating its artifact.
- Make the response wording distinguish the intended lifecycle: preview restoration has already reverted applied graph mutations, and clearing the queue discards the pending changes so they cannot be committed later.
- Do not add a second revert operation in the rejection handler: normal `prepareReview()` completes the revert before opening the modal, and any failed revert exits through its dedicated error path before user approval/rejection is available.

### Focused Tests

- Add a direct unit test file under `tests/src/chat-app/tools/impl/` for `LogseqCommitChangesTool`.
- Test `executeApprove()` with an empty tracker, a tracker whose mutation commands apply successfully, a tracker with no applied graph mutations, and an execution failure, asserting both result text/status and serialized artifact state.
- Test `executeCancel()` with a prepared tracker containing queued changes, asserting the tracker and response artifact are cleared and the response explicitly reports discarded changes.
- Test error-response wording for retained temporary changes and for the diff-revert cleanup path where applicable. Keep UI/modal integration out of scope unless the existing test setup can render the custom human-tool component without extensive new harness code.
