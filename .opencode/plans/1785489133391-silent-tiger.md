# Plan: Add Toolkit/Grouping Support to ChatToolRegistry

## 1. User Requirement

> I need you to read 1785489133391-silent-tiger.md and improve the plan. Specifically, the typescript might be messed up.

Underlying feature: add toolkit grouping to `ChatToolRegistry` so tools can be organized into named toolkits (`logseq`, `web`, `pdf`, `misc`). Toolkits are defined in the registry only — no toolkit property is added to tool classes.

## 2. Final Requirement After Discussion With User

### 2.1 Clarification Q&A

**Q1 — Toolkit type modeling.** The original plan stored tools in `Map<ToolkitName, Toolkit>` using assistant-ui's `Toolkit` type. But `Toolkit` is `Record<string, ToolDefinition<any, any>>`, and `ToolDefinition` *requires* `render` (or `renderText`) for `frontend`/`human` tools (via the `WithRender` conditional in `@assistant-ui/core` `toolbox.d.ts`). The registry stores render-less `Tool<any, any>` from `BaseChatTool.getDefinition()` — render is registered separately through `toolUIs` + `aui.tools().setToolUI(...)`. A render-less `Tool` is **not** assignable to `ToolDefinition`, so the original `toolkitMap` typing is a compile error. Additionally, `ModelContext.tools` (`@assistant-ui/core` `model-context/types.d.ts`) is `Record<string, Tool<any, any>> | undefined` — **not** `Toolkit`.

**A1 (chosen):** Make `toolkitMap` the single source of truth, typed as `Map<ToolkitName, Record<string, Tool<any, any>>>` (matches `ModelContext.tools` exactly). Do **not** import or use assistant-ui's `Toolkit`/`ToolDefinition` types. `getTools()` aggregates all toolkits.

### 2.2 Final Summarized Requirements

- Define `ToolkitEnum` (const object) + `ToolkitName` type for 4 toolkits: `logseq`, `web`, `pdf`, `misc`, exported from `ToolRegistry.ts`.
- `registerTool(tool, toolkit)` — `toolkit` is mandatory; **preserve the existing generic constraints** `TArgs extends Record<string, unknown>, TResult extends ChatToolResult`. Writes tool definitions into `toolkitMap`.
- `toolkitMap` replaces the flat `tools` map as the single source of truth for tool definitions. All 4 toolkits are **pre-initialized to empty `{}`** so `getToolkits()` always returns a complete `Record<ToolkitName, …>` even when `web`/`pdf` are conditionally empty.
- `getTools(): Record<string, Tool<any, any>>` — unchanged signature; now aggregates all toolkits in `ToolkitEnum` order. Keeps `useAssistantModelContext.tsx` working with no changes.
- New `getToolkit(name): Record<string, Tool<any, any>>` and `getToolkits(): Record<ToolkitName, Record<string, Tool<any, any>>>` — both directly assignable to `ModelContext.tools`.
- `toolUIs` and `humanToolNames` remain **global**, keyed by unique tool name; they are NOT grouped by toolkit (tool names are unique across toolkits).
- `getToolUIs()`, `getHumanToolNames()`, `getInstance()`, `reset()` — unchanged.
- Tool classes (`BaseChatTool` and all `impl/*`) — unchanged.
- `useAssistantModelContext.tsx` — no changes now; `getToolkit()` is available for future toolkit-based filtering.

## 3. Solution

### 3.1 TypeScript corrections vs. the original plan

| # | Original plan defect | Fix |
|---|---|---|
| 1 | `toolkitMap: Map<ToolkitName, Toolkit>` — `Toolkit` requires `render`; registry holds render-less `Tool` -> type error. | Use `Map<ToolkitName, Record<string, Tool<any, any>>>`. Drop the `Toolkit`/`ToolDefinition` import. |
| 2 | `registerTool<TArgs, TResult>` dropped the generic constraints. | Restore `TArgs extends Record<string, unknown>, TResult extends ChatToolResult`. |
| 3 | `createDefault()` referenced an undefined `settings.` variable. | Use `const settings = LogseqSettingAccessor.getPluginSettings();` (already imported). |
| 4 | Target State named `getToolsForToolkit(name)` but Implementation defined `getToolkit(name)`/`getToolkits()`. | Standardize on `getToolkit(name)` + `getToolkits()`. |
| 5 | `getToolkits(): Record<ToolkitName, Toolkit>` would be missing keys when `web`/`pdf` are empty. | Pre-initialize all 4 toolkits to `{}`; return `Record<ToolkitName, Record<string, Tool<any,any>>>`. |
| 6 | Relationship between `toolkitMap` and existing `tools`/`toolUIs`/`humanToolNames` was unspecified. | `toolkitMap` is source of truth for definitions; `toolUIs`/`humanToolNames` stay global; `getTools()` aggregates. |

### 3.2 Phase 1 — Types and state (`src/chat-app/tools/ToolRegistry.ts`)

Module dependencies (unchanged — we do NOT add a `Toolkit` import):
- `import type {Tool} from "assistant-stream";` (already present — reuse)
- `import type {BaseChatTool} from "src/chat-app/tools/base/BaseChatTool";`
- `import type {ChatToolResult} from "src/chat-app/tools/base/ChatToolResponse";`

New exported constants (top of file, after imports):

```typescript
export const ToolkitEnum = {
    LOGSEQ: "logseq",
    WEB: "web",
    PDF: "pdf",
    MISC: "misc"
} as const;
export type ToolkitName = (typeof ToolkitEnum)[keyof typeof ToolkitEnum];
```

Class state — replace `private readonly tools = new Map<string, Tool<any, any>>();` with:

```typescript
private readonly toolkitMap = new Map<ToolkitName, Record<string, Tool<any, any>>>(
    (Object.values(ToolkitEnum) as ToolkitName[]).map(
        (name) => [name, {} as Record<string, Tool<any, any>>]
    )
);
```

Keep unchanged:
- `private readonly toolUIs = new Map<string, ToolCallMessagePartComponent>();`
- `private readonly humanToolNames = new Set<string>();`
- `static instance`, `getInstance()`, `reset()`.

### 3.3 Phase 2 — Accessors and `registerTool` (`src/chat-app/tools/ToolRegistry.ts`)

`registerTool` — preserve generic constraints, add mandatory `toolkit`, write into `toolkitMap`:

```typescript
private registerTool<TArgs extends Record<string, unknown>, TResult extends ChatToolResult>(
    tool: BaseChatTool<TArgs, TResult>,
    toolkit: ToolkitName
): void {
    const tools = this.toolkitMap.get(toolkit);
    if (tools) tools[tool.name] = tool.getDefinition(); // Tool<TArgs,TResult> -> Tool<any,any>
    if (tool.type === "human") this.humanToolNames.add(tool.name);
    if (tool.render) this.toolUIs.set(tool.name, tool.render);
}
```

Accessors:

```typescript
getTools(): Record<string, Tool<any, any>> {
    const all: Record<string, Tool<any, any>> = {};
    for (const name of Object.values(ToolkitEnum) as ToolkitName[]) {
        Object.assign(all, this.toolkitMap.get(name) ?? {});
    }
    return all;
}

getToolkit(name: ToolkitName): Record<string, Tool<any, any>> {
    return {...(this.toolkitMap.get(name) ?? {})}; // defensive copy, like getTools()
}

getToolkits(): Record<ToolkitName, Record<string, Tool<any, any>>> {
    return Object.fromEntries(
        (Object.values(ToolkitEnum) as ToolkitName[]).map(
            (name) => [name, {...(this.toolkitMap.get(name) ?? {})}]
        )
    ) as Record<ToolkitName, Record<string, Tool<any, any>>>;
}
```

`getToolUIs()` and `getHumanToolNames()` — unchanged.

Note: `getToolkit`/`getToolkits` return shallow copies to match `getTools()`'s defensive-copy behavior and prevent external mutation of internal state.

### 3.4 Phase 3 — Group tools in `createDefault()` (`src/chat-app/tools/ToolRegistry.ts`)

Fix the undefined `settings` reference and group by toolkit. Conditional registration for `web`/`pdf` stays here:

```typescript
private static createDefault(): ChatToolRegistry {
    const registry = new ChatToolRegistry();
    const settings = LogseqSettingAccessor.getPluginSettings(); // fixes undefined `settings.`

    // logseq toolkit (20 tools)
    registry.registerTool(new LogseqReadBlockTool(), ToolkitEnum.LOGSEQ);
    registry.registerTool(new LogseqDataScriptQueryTool(), ToolkitEnum.LOGSEQ);
    registry.registerTool(new LogseqInsertBlockTool(), ToolkitEnum.LOGSEQ);
    registry.registerTool(new LogseqCreatePageTool(), ToolkitEnum.LOGSEQ);
    registry.registerTool(new LogseqCreateTagPageTool(), ToolkitEnum.LOGSEQ);
    registry.registerTool(new LogseqDeletePageTool(), ToolkitEnum.LOGSEQ);
    registry.registerTool(new LogseqRenamePageTool(), ToolkitEnum.LOGSEQ);
    registry.registerTool(new LogseqRestorePageTool(), ToolkitEnum.LOGSEQ);
    registry.registerTool(new LogseqTextSearchTool(), ToolkitEnum.LOGSEQ);
    registry.registerTool(new LogseqUpdateBlockTool(), ToolkitEnum.LOGSEQ);
    registry.registerTool(new LogseqMoveBlockTool(), ToolkitEnum.LOGSEQ);
    registry.registerTool(new LogseqUpsertPropertyPageTool(), ToolkitEnum.LOGSEQ);
    registry.registerTool(new LogseqUpsertPropertyToBlockTool(), ToolkitEnum.LOGSEQ);
    registry.registerTool(new LogseqDeletePropertyFromBlockTool(), ToolkitEnum.LOGSEQ);
    registry.registerTool(new LogseqAddPropertyToTagPageTool(), ToolkitEnum.LOGSEQ);
    registry.registerTool(new LogseqRemovePropertyFromTagPageTool(), ToolkitEnum.LOGSEQ);
    registry.registerTool(new LogseqAddTagToBlockTool(), ToolkitEnum.LOGSEQ);
    registry.registerTool(new LogseqRemoveTagFromBlockTool(), ToolkitEnum.LOGSEQ);
    registry.registerTool(new LogseqClearChangesTool(), ToolkitEnum.LOGSEQ);
    registry.registerTool(new LogseqCommitChangesTool(), ToolkitEnum.LOGSEQ);

    // web toolkit (conditional)
    if (settings.webToolsProvider === WebToolsProviderEnum.JINA) {
        registry.registerTool(new WebSearchTool(), ToolkitEnum.WEB);
        registry.registerTool(new WebPageGetTool(), ToolkitEnum.WEB);
    }

    // pdf toolkit (conditional)
    if (settings.contentParsingProvider === ContentParsingProviderEnum.LLAMA_CLOUD) {
        registry.registerTool(new ReadPdfTool(), ToolkitEnum.PDF);
    }

    // misc toolkit
    registry.registerTool(new SkillTool(), ToolkitEnum.MISC);
    registry.registerTool(new GetUserInfoTool(), ToolkitEnum.MISC);

    return registry;
}
```

## Notes

- Tool classes remain unchanged (no toolkit property on `BaseChatTool`).
- `toolUIs` / `humanToolNames` stay global (keyed by tool name); only tool *definitions* are grouped by toolkit.
- Conditional registration (web/pdf) stays in `createDefault()` for now.
- Alternative to `Map`: a plain `Record<ToolkitName, Record<string, Tool<any, any>>>` object is an equivalent, cast-free form (all 4 keys guaranteed by construction). `Map` is used here per the chosen direction; either satisfies the "source of truth + aggregate" design.
- Future: toolkit-based filtering/enabling logic will be added when needed via `getToolkit()`/`getToolkits()`.
