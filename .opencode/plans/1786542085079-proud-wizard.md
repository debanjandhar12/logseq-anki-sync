## 2. Final Requirement After Discussion With User

### 2.1 Clarification Q&A

1. **For an explicit Commit Changes “Continue later” action, should the refactor keep the current stale-target guard (verify the expected tool call still exists), while clearly making termination turn-wide, or simplify it to target only the assistant message?**
   - **Answer:** Message ID only.

2. **When a user attempts to switch chat threads while the current thread has a live run or an open review action, should switching await a stop and remain on the current thread when stopping fails?**
   - **Answer:** Stop before switch.

### 2.2 Final Summarized Requirements

- Preserve the actual correctness guarantees introduced by the three race-fix commits: atomic in-process thread-file mutation, no late producer overwrite after Stop, and a durable terminal result for each unresolved tool call in a stopped assistant turn.
- Remove or encapsulate bespoke concurrency and storage-error plumbing. Use the established `await-lock` dependency behind a reusable keyed exclusive-operation abstraction; `ThreadStore` must no longer own `runSerialized` or lock-entry bookkeeping.
- Replace message-text detection of a missing Logseq storage file with a generic, typed optional-read contract at the storage boundary. An absent record may be initialized; corrupt, invalid, or unreadable existing data must fail without being overwritten.
- Keep `recoverInterruptedMessages` exclusively as load-time, in-memory crash/interruption recovery. Do not use it to implement Stop or persistence.
- Separate active run cancellation/waiting, pure assistant-turn termination, and persisted-history reconciliation into independently testable modules. Keep only a thin Stop orchestrator.
- Make termination explicitly assistant-message/turn scoped. Both ordinary Stop and Commit Changes “Continue later” use only `messageId`; every unresolved tool call in that selected assistant message receives the terminal user/caller error result. Resolved calls and artifacts remain unchanged.
- Simplify duplicate-stop/result-state machinery while retaining the essential cancellation-before-import ordering and failure reporting required to gate unsafe follow-up actions.
- Extract Review Changes selectors and workflows from `ReviewChangesDisplay.tsx`; the component should be presentation-focused. Destructive review actions must not proceed after failure to safely stop.
- Route every thread/new-thread switch through one stop-before-switch guard. Await cancellation and terminal persistence. If either fails, do not switch away.
- Update tests and the race-condition documentation to describe the resulting, maintainable architecture and invariants.

## 3. Existing System

### 3.1 Race-fix history and required retained behavior

`docusaurus/docs/chat/stop-tool-result-race.md` documents two separate races:

1. Independent full-thread read/modify/write paths could lose a concurrent update. For example, a continuation append based on an old file snapshot could overwrite Stop’s persisted synthetic tool results.
2. An assistant-ui roundtrip producer could still be alive while the public message state was `requires-action`. Importing the stopped state before that producer ended allowed a late yield to overwrite the stopped message and remove tool results.

The commit sequence addressed those issues:

- `c6d32387` introduced serialized thread mutations and made Stop update the latest stored state rather than blindly saving a stale runtime export.
- `813cdccd` added branch/ancestry reconciliation, missing-thread initialization for Stop-before-initial-persistence, and the brittle `isMissingFileError()` fallback.
- `465977ad` added true run tracking and abort-racing frontend tool execution so Stop can cancel and await an adapter producer even when `runtime.getState().isRunning` is false.

The refactor must preserve these invariants rather than revert to pre-fix behavior.

### 3.2 Thread storage

`src/core/stores/thread-store/ThreadStore.ts` currently has three incompatible read contracts:

- `loadRawThread()` reads raw content and throws if it is not a string. `ThreadTopToolBar` uses this to export a page.
- `loadThread()` broadly catches storage and JSON errors and returns `null`; `LocalThreadHistoryAdapter.load()` uses this for best-effort history load.
- private `loadThreadForMutation()` only treats null content and a specific error message (`"file not existed"`) as absent, propagating other failures so a mutation does not overwrite corrupt data.

`updateThread()` and `deleteThread()` call private `runSerialized()`. The implementation keeps a `Map<string, {lock: AwaitLock; users: number}>`, handles acquisition/release and map cleanup itself, and is deliberately non-reentrant. The atomic critical section correctly encompasses read, updater, and save, but this bookkeeping belongs in a reusable concurrency abstraction, not in the store.

`src/logseq/LogseqPluginStorageManager/LogseqPluginStorageManager.ts` currently exposes raw `getFileContent()` and `fileExists()` independently. It is the appropriate place to normalize backend-specific missing-file behavior into an optional read.

### 3.3 Run, termination, and persistence lifecycle

`src/chat-app/runtime/withRoundtripPersistence.ts` wraps every adapter `run()` with `trackThreadRun(threadId)` and finalizes it in `finally`. `ThreadRunLifecycle.ts` stores per-thread reference counts because assistant-ui’s public `isRunning` is false during some `requires-action` states even though the adapter generator can still yield later.

`src/chat-app/runtime/stopThread.ts` currently combines all of the following in 252 lines:

- target selection and duplicate-stop signature arbitration;
- active-run detection, `unstable_on("runEnd")`, timeout, `cancelRun()`, and run-end wait;
- terminating the runtime repository and importing it;
- serializing persistence;
- missing-thread creation;
- branch ancestry restoration and stored-result precedence reconciliation.

The existing cancellation ordering is essential: subscribe to `runEnd`, cancel, wait for producer cleanup, then transform/import/persist. Waiting prevents a live stale producer from overwriting Stop’s imported terminal state.

`terminateToolTurn.ts` names its target `ToolTurnTarget`, accepting `messageId`, `toolCallId`, and `toolName`. In reality `toolCallId`/`toolName` only validate one unresolved call; after validation the function terminalizes **every** unresolved tool call in the selected assistant message. This is correct for a thread-level Stop and must become the explicit public policy.

The persistence merge deliberately reads the newest stored repository inside `ThreadStore.updateThread`, retains newly persisted tool results and continuations, preserves the latest stored head/unrelated branches, and restores only target ancestry from the stopped runtime export. These are valid reconciliation invariants but are currently hidden in `stopThread.ts`.

### 3.4 Interrupted-message recovery

`src/chat-app/runtime/recoverInterruptedMessages.ts`, called only from `LocalThreadHistoryAdapter.load()`, maps persisted assistant `running` messages and non-human/non-approval `requires-action` messages to cancelled/incomplete for display after a crash/reload. It neither persists that projection nor creates missing tool results. It is therefore not a replacement for normal Stop; it remains a justified, separate crash-recovery operation.

### 3.5 Review Changes and switching paths

`src/chat-app/components/ReviewChangesDisplay.tsx` currently mixes pure message selectors, transaction rollback, artifact persistence, confirmation UI, stopping, discard-tool execution, synthetic response construction, notification, and popover state. Its first pre-confirmation stop relies on public `isRunning`, known to be insufficient during a tracked `requires-action` run; the post-confirmation stop is unconditional.

Thread switching is currently initiated directly by assistant-ui primitives or API calls:

- `src/chat-app/components/ThreadList.tsx`: `ThreadListItemPrimitive.Trigger` switches immediately.
- `src/chat-app/components/ThreadTopToolBar.tsx`: `ThreadListPrimitive.New` switches immediately.
- `src/chat-app/hooks/useChatCommandHandler.ts`: `NewThreadCommand` directly invokes `aui.threads().switchToNewThread()`.

None currently waits for the source thread to be safely stopped and persisted. Existing code sometimes captures a source runtime before an await, but it has no centralized operation ownership or switch gate.

### 3.6 Existing relevant tests

- `tests/src/core/stores/ThreadStore.test.ts`: same-thread serialization, different-thread concurrency, lock release after errors, and deletion serialization.
- `tests/src/chat-app/runtime/stopThread.test.ts`: run-end ordering, continuation preservation, ancestry recovery, branch behavior, missing-thread creation, tracked-run behavior, targets, and duplicate Stop behavior.
- `tests/src/chat-app/runtime/terminateToolTurn.test.ts`: content/status transformation rules.
- `tests/src/chat-app/runtime/LocalThreadHistoryAdapter.test.ts`: append and recovery behavior.
- `tests/src/chat-app/components/ReviewChangesDisplay.test.ts`: review action workflows.

Current gaps include source-thread switching while Stop/review work is pending and a clear test stating the intended message-wide termination policy for multiple unresolved tool calls with a message-only target.

## 4. Solution

### 4.1 Introduce reusable keyed exclusivity and explicit optional storage reads

1. Add `src/core/locking/KeyedExclusiveOperationLock.ts`.
   - Wrap the already installed `await-lock` dependency in a generic `runExclusive(key, operation)` API.
   - Move per-key lock allocation, reference counting, release, and idle-entry deletion from `ThreadStore.runSerialized()` into this class.
   - Keep distinct keys concurrent and document non-reentrancy. The lock must retain the exact current behavior: acquire before a mutation reads storage and release only after save/skip/error cleanup.
   - This is an intentional dependency encapsulation rather than adding a second locking package: `await-lock` is already present, tested in this project, and supplies the lock primitive while the project needs keyed lifecycle management.

2. Extend `src/logseq/LogseqPluginStorageManager/LogseqPluginStorageManager.ts` with a decoded optional-read API, e.g. `readOptionalFile(group, fileName, deserialize): Promise<T | undefined>`.
   - Read first; return `undefined` when the backend natively returns null/undefined.
   - If reading throws, call `fileExists()` only then. Normalize the failure to `undefined` only when the existence check proves the record is absent. Rethrow the original read error when the record exists; propagate/check-wrap an existence-check failure without turning it into absence.
   - Apply `deserialize` only to actual string content and propagate deserialization errors. Do not pre-check existence, which would introduce an avoidable race and extra I/O.
   - Retain `getFileContent()` as the raw API needed by page export. Make its return type explicit if TypeScript inference does not already represent optional content.

3. Refactor `ThreadStore`.
   - Replace `ThreadLockEntry`, `threadLocks`, `runSerialized()`, `loadThreadForMutation()`, and `isMissingFileError()` with a static `KeyedExclusiveOperationLock<string>` and the storage manager optional-read API.
   - Keep `updateThread(threadId, updater)` as the only thread-file transactional abstraction: under the keyed lock it reads the newest valid optional data, invokes the updater, and conditionally saves.
   - Serialize `deleteThread()` through the same keyed lock. Stop silently swallowing delete errors; absent deletion should be a clearly idempotent storage-manager contract if required, while real storage failures must remain visible.
   - Make `loadThread()` mean one explicit thing: return null/undefined only for an absent record and throw for invalid content, JSON corruption, and storage failures. If a caller truly needs best-effort behavior, add a deliberately named `tryLoadThread()` rather than concealing errors in `loadThread()`.
   - Keep `listThreads()` warning-and-skipping individual malformed thread files only if that existing UX is desired; do not classify backend read failure as a missing record.

### 4.2 Split Stop into lifecycle control, pure domain transformation, and persistence reconciliation

1. Add `src/chat-app/runtime/ThreadRunController.ts`.
   - Move true-run detection and cancellation/wait handling from `stopThread.ts` here.
   - `stopActiveThreadRun({threadId, runtime})` must use `isThreadRunActive(threadId) || runtime.getState().isRunning` to determine whether a producer may still write.
   - When active: subscribe to `runEnd` before `cancelRun()`, recheck the tracker to close the completion race, wait with the existing bounded timeout, and always unsubscribe/clear the timer.
   - Keep at most one simple per-thread pending cancellation promise so concurrent callers do not issue competing `cancelRun()` calls. Do not carry target/error-message signatures or general Stop arbitration into this module.
   - Continue using `ThreadRunLifecycle` with its reference count and `withRoundtripPersistence` `finally` cleanup. This tracker cannot be removed until assistant-ui offers an authoritative, stable run handle/lifecycle promise that covers the `requires-action` producer state. Isolate the unstable assistant-ui event in this controller.

2. Rename `src/chat-app/runtime/terminateToolTurn.ts` to `src/chat-app/runtime/terminateAssistantTurn.ts` and replace its public types/functions.
   - Define `AssistantTurnTarget` as `{messageId: string}` only and rename `getActiveAssistantMessageTarget()` to a clear latest-turn selector such as `getLatestAssistantTurnTarget()`.
   - `terminateAssistantTurn(repository, {target, errorMessage})` remains pure and idempotent. For the selected assistant message, terminalize every unresolved `tool-call` part, preserve all already resolved calls and artifacts, preserve completed approval metadata, and cancel only unresolved approval requests. Set the message to cancelled/incomplete only when a part changed.
   - Do not accept, validate, or infer `toolCallId`/`toolName`. The Commit Changes “Continue later” path will target the known message ID, and all unresolved calls in that same assistant turn will visibly become terminal. This is the selected low-complexity policy.
   - Permit explicit message-ID termination independently of currently selected head branch so persistence reconciliation can safely terminalize an old active turn after a branch/head change. Preserve unrelated branches.

3. Add `src/chat-app/runtime/persistTerminatedAssistantTurn.ts`.
   - Move `persistTerminatedToolTurn`, `mergeTargetAncestry`, and `mergeTerminatedMessageItem` out of `stopThread.ts`.
   - Inside `ThreadStore.updateThread()`, apply `terminateAssistantTurn()` to the newest stored repository, then reconcile only the target message’s runtime ancestry into it.
   - Name the graph routine by policy, e.g. `reconcileTerminatedAssistantTurnIntoStoredRepository()`, and document invariants next to it:
     - latest stored `headId` and unrelated messages win;
     - newer stored successful tool results win over synthetic terminal results;
     - newer persisted continuations are retained;
     - missing target ancestors are restored from the terminal runtime repository;
     - unrelated stale runtime branches are never imported;
     - an absent thread may be initialized with only the required terminated ancestry and current metadata.
   - Preserve parse/storage errors from the transactional read; never manufacture an empty thread in response to corruption/outage.

4. Reduce `src/chat-app/runtime/stopThread.ts` to a small orchestrator.
   - Snapshot/select the message target (explicit target or latest assistant message), await `ThreadRunController`, re-export runtime after the producer has stopped, run the pure termination, import only if it changed, and invoke persisted reconciliation.
   - Replace `pendingStops` target/signature machinery and the `kind`/`persistenceFailed` mixture with a small discriminated outcome such as `stopped`, `idle`, or `failed` with a real error. A failure to cancel/wait or to persist changed terminal state is unsafe and must be visible to callers.
   - A `stopped` result means either the live run was ended or an assistant turn was terminalized; `idle` means neither action was necessary. Do not swallow persistence failure after runtime import.
   - Retain the required ordering: **wait for producer end -> terminalize runtime repository -> import -> reconcile and persist current stored history**.

5. Update direct call sites.
   - `src/chat-app/hooks/useStopThread.ts`: expose the message-only target and return the complete result/failure to callers rather than reducing an unsafe failure to `undefined`; notifications must accurately distinguish cancellation versus persistence failure.
   - `src/chat-app/components/ComposerAction.tsx`: ordinary Stop passes no target and derives the latest assistant turn.
   - `src/chat-app/tools/impl/LogseqCommitChangesTool.tsx`: “Continue later” passes `{messageId}` and `COMMIT_LATER_MESSAGE`; remove `toolCallId`/`toolName` and block the follow-up workflow on a failed stop.

### 4.3 Preserve, document, and test crash recovery separately

1. Retain `src/chat-app/runtime/recoverInterruptedMessages.ts` as a pure load-time recovery projection. Optionally rename only if a clearer name is preferred, but do not merge it with termination or persistence.
2. Keep its sole production invocation in `LocalThreadHistoryAdapter.load()` and add a comment that it intentionally does not persist changes or synthesize tool results.
3. Confirm no Stop, review workflow, run controller, or switch path invokes recovery. A normal stop must persist actual failed tool results, while recovery makes stale persisted transient UI state renderable after a crash.

### 4.4 Extract Review Changes workflow logic

1. Add `src/chat-app/review-changes/reviewChangesSelectors.ts` and move the pure functions `getReviewChangesSummary`, `getReviewChangesCommandCount`, and `getReviewChangesLifecycleLabel` there.
2. Add `src/chat-app/review-changes/reviewChangesWorkflows.ts`.
   - Move `revertAndKeepReviewChanges()` and `revertAndDiscardReviewChanges()` plus their injected dependencies here.
   - Define explicit workflow outcomes for completed, confirmation-cancelled, blocked-by-safe-stop-failure, and the existing revert-failed/discarded fallback.
   - Replace the initial raw `runtime.getState().isRunning` check with the safe Stop/controller outcome. Before destructive actions, stop if there is a live or unresolved turn; after the confirmation modal closes, recheck quiescence because state may have changed while awaiting user input.
   - Do not execute the discard tool or mutate graph transactions when safe Stop fails. Keep source `threadId` and runtime captured for the workflow so an asynchronous completion cannot operate on a newly selected thread.
3. Optionally add `src/chat-app/review-changes/appendSyntheticToolResponse.ts` to isolate synthetic assistant tool-response construction from both workflow and component.
4. Reduce `ReviewChangesDisplay.tsx` to UI state, selector output, triggering workflows, and presentation/error display. Remove direct stop/tool/transaction/persistence/modal wiring from the component. Ensure busy/open state is tied to the captured operation so completion from a stale operation does not reset a different selected thread’s UI.

### 4.5 Gate every switch behind safe Stop

1. Add `src/chat-app/runtime/switchThreadSafely.ts`.
   - Accept the source thread ID/runtime and a deferred `switchTo()` operation.
   - Await the simplified Stop result. Invoke `switchTo()` only for `stopped` or `idle`; return a blocked/failure result for cancellation timeout, cancellation error, or termination persistence error.
   - Do not treat merely calling `cancelRun()` as safe. The source must have ended and persisted terminal state first.
   - Coalesce/reject rapid duplicate switch attempts with a simple busy guard; no target-signature protocol is needed.

2. Route each known switch entry point through that guard.
   - `src/chat-app/components/ThreadList.tsx`: replace `ThreadListItemPrimitive.Trigger`, whose built-in behavior switches immediately, with a project-owned trigger/button which resolves the current source runtime, awaits `switchThreadSafely`, then calls assistant-ui’s explicit `threads.switchToThread(targetId)`. Call `onThreadSelected` only after success; on failure leave the history/current thread view unchanged and notify the user.
   - `src/chat-app/components/ThreadTopToolBar.tsx`: replace `ThreadListPrimitive.New` with a project-owned new-thread button that safely stops the current thread before `threads.switchToNewThread()`, then invokes `onBackToThread()` only after success.
   - `src/chat-app/hooks/useChatCommandHandler.ts`: route `NewThreadCommand` through the same guard rather than calling `switchToNewThread()` directly.
   - Update the copied-component change comments required by `src/chat-app/AGENTS.md` when replacing assistant-ui primitives.

### 4.6 Documentation

Update `docusaurus/docs/chat/stop-tool-result-race.md` to retain its failure timeline while replacing descriptions of the current bespoke implementation. Document the final invariants and module boundaries: keyed atomic storage mutation, true producer lifecycle controller, assistant-turn-wide termination, persisted reconciliation, load-only interruption recovery, and stop-before-switch policy. State explicitly that the lock is in-process and not a cross-process storage transaction.

## 5. Verification

### 5.1 Focused unit and component coverage

1. Add tests for `KeyedExclusiveOperationLock` or retain equivalent store-level tests proving:
   - full same-thread read/mutate/save serialization;
   - independent keys proceed concurrently;
   - cleanup after updater, save, and acquisition-related failures;
   - delete and update cannot interleave for the same key.

2. Add storage-manager contract tests for optional reads:
   - native absent value returns absent;
   - thrown read plus proven absent key returns absent;
   - thrown read plus existing key rethrows;
   - parser failure propagates and causes no updater/save;
   - no eager existence check is performed before a successful read.

3. Update `ThreadStore` tests to prove corrupt/invalid thread content is never overwritten and initialization still works for an explicitly absent record.

4. Split current `stopThread` tests by module responsibility:
   - `ThreadRunController`: subscribe before cancel, wait for `runEnd`, tracker-overrides-public-state behavior, timeout/cancel error cleanup, one shared in-flight cancellation.
   - `terminateAssistantTurn`: selected message ID only; all unresolved sibling calls terminalize; resolved calls/artifacts/approval metadata remain correct; inactive-branch explicit target policy; idempotency and invalid targets.
   - `persistTerminatedAssistantTurn`: continuation retention, target-ancestry restoration, stored-head branch switch, absent-thread initialization, unrelated runtime branch exclusion, stored successful result precedence.
   - thin `stopThread`: producer completion precedes import/persist, idle behavior, and surfaced unsafe failure.

5. Extend `LocalThreadHistoryAdapter` tests to verify recovery is load-only, persists nothing, preserves human approval behavior, and is not relied on by normal Stop to create tool results.

6. Split `ReviewChangesDisplay` tests into selectors, workflows, and component presentation. Verify safe Stop happens before destructive work, safe-stop failure blocks confirmation/discard as specified, confirmation-time state changes trigger the second quiescence check, and synthetic response appends exactly once.

7. Add `switchThreadSafely` tests proving it awaits Stop, switches only on safe `stopped`/`idle`, blocks on cancellation/persistence failure, and surfaces a switching failure. Extend Thread List, toolbar, and command-handler tests to prove each entry point uses the gate and does not change visual/thread state on failure.

### 5.2 Commands and manual regression validation

After implementation, run targeted suites first, then:

```bash
pnpm test --run --reporter=dot --silent
npx tsc --noEmit
pnpm run check:fix <each-modified-file> --reporter=summary
```

Perform manual validation in a running Logseq instance:

1. Start a frontend tool that waits/ignores abort, press Stop during `requires-action`, and confirm all unresolved calls in that assistant turn show terminal user errors; confirm a late tool completion cannot erase them.
2. Stop a turn with multiple unresolved tool calls and verify every unresolved sibling receives a result while successful siblings remain unchanged; continue the conversation successfully afterward.
3. Trigger Commit Changes “Continue later” in a turn containing unresolved calls and verify message-wide terminalization with the custom continue-later message.
4. Trigger Stop while history/metadata persistence is active and verify no continuation, latest head, or resolved result is lost.
5. Start an active run, select another thread and create a new thread through the toolbar and external command; verify each waits for Stop, and force/observe a stop failure to verify switching is blocked.
6. Reload a thread containing an intentionally persisted transient assistant state and confirm the UI recovers it without rewriting its stored file.
