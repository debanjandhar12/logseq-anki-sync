## 3. Existing System

### Fixture modules

- `tests/helpers/chat-scenario/fixtures/` contains `aiChatScenarioFixture.ts`, `modelFixture.ts`, `storageFixture.ts`, and `withScenarioSettings.ts`, but no index.
- Seven files under `tests/scenario/ai-chat-modal/` import `test` from the implementation file. `basic-conversation.e2e.test.tsx` also imports `SCENARIO_TITLE`; `advanced-branching.e2e.test.tsx` imports `ModelFixture` and `StorageFixture` from leaf files.
- Chat fixtures compose isolated storage, a mock model, real chat mounting, and cleanup. `modelFixture.ts` includes hoisted title-generation mocking. Chat scenarios require a running Logseq API and DB graph.
- `tests/helpers/skill-and-command-editor/fixtures/editorFixture.ts` exports `test`, and privately defines `EditorKind`, `editorControls`, `createStorageFixture`, and `EditorFixture`. Four editor scenario files import it directly.
- Editor controls are role/title locators. Editor mounting unmounts the previous editor, then waits for its dialog and New button. Storage/UI mocking and command-save reload synchronization belong to fixture lifecycle, not the driver.

### Existing helper patterns

- `tests/helpers/chat-scenario/createChatDriver.ts` exposes locators and actions, with `ChatDriver = ReturnType<typeof createChatDriver>` beside the factory. Action-local assertions synchronize interactions.
- `tests/helpers/chat-scenario/assertions/index.ts` uses explicit named runtime exports and separate type exports. Chat does not enforce a strict query/assertion distinction, so follow its useful boundaries rather than copy its entire structure.
- Shared query helpers live in `tests/helpers/query/`.
- Editor `codeMirror.ts` contains only `codeMirrorView(content)` and `placeCursor(content, position)`. The query uses `EditorView.findFromDOM` and throws `CodeMirror has not mounted` if no view exists. The action dispatches selection, scrolls, focuses, and polls the selection head.
- Both CodeMirror suites repeat completion visibility, frontmatter suppression, and Markdown style assertions. Both basic suites repeat duplicate-name validation and unsaved-change confirmation checks.
- Completion UI and confirmation modals are queried through `page`; they must not be scoped to the content textbox.

### Test/tooling constraints

- Vitest browser e2e uses Chromium; keep file parallelism enabled and within-file tests nonconcurrent.
- Test setup defaults the Logseq HTTP API to `http://127.0.0.1:12315` (overridable through `LOGSEQ_API_SERVER`).
- TypeScript includes tests and uses bundler resolution, supporting directory index imports without config changes.
- Project instructions require tests, `npx tsc --noEmit`, and a final `pnpm run check:fix <filename> --reporter=summary` restricted to changed files.

## 4. Solution

### A. Explicit fixture entry points

Add `tests/helpers/chat-scenario/fixtures/index.ts`:

```ts
export {test} from "./aiChatScenarioFixture";
export {SCENARIO_TITLE} from "./modelFixture";
export type {ModelFixture} from "./modelFixture";
export type {StorageFixture} from "./storageFixture";
```

Expose the scenario-facing API, not unused implementation factories/settings helpers. Keep internal imports directed at sibling implementations, never back through the barrel. Do not move or modify hoisted mocks.

Add `tests/helpers/skill-and-command-editor/fixtures/index.ts`, explicitly exporting `test` and type-only `EditorKind`, `EditorControls`, and `EditorFixture`.

Update fixture imports in all eleven scenarios:

- Chat: `basic-branching`, `thread-list-ui`, `assistant-message-ui`, `advanced-branching`, `basic-conversation`, `composer-ui`, and `user-message-ui` (`.e2e.test.tsx` under `tests/scenario/ai-chat-modal/`). Consolidate title/type imports into the new fixture entry point, retaining type-only syntax.
- Editor: `basic-command-file-editor-operations`, `command-file-editor-codemirror-operations` under `tests/scenario/command-editor/`; `basic-skill-file-editor-operations`, `skill-file-editor-codemirror-operations` under `tests/scenario/skill-editor/`.

No combined parent barrel or compatibility re-exports are necessary: all consumers are internal and will migrate together.

### B. Editor types without extra factories

Add `tests/helpers/skill-and-command-editor/fixtures/types.ts` with type-only `Locator` import:

```ts
export type EditorKind = "skill" | "command";

export interface EditorControls {
    root: Locator;
    dialog: Locator;
    content: Locator;
    enabled: Locator;
    newButton: Locator;
    deleteButton: Locator;
    saveButton: Locator;
    cancelButton: Locator;
    file(displayName: string): Locator;
}

export interface EditorFixture {
    mount(kind: EditorKind): Promise<EditorControls>;
    unmount(): Promise<void>;
    result(): Promise<boolean | null>;
}
```

In `editorFixture.ts`, remove local type declarations, import these contracts directly from `./types`, and annotate `editorControls` with `EditorControls`. Keep this single-use locator factory private. Keep storage return-type inference and the inline Vitest context as-is; do not introduce extra named storage/context types merely for symmetry.

Preserve mount waits, storage disposal, UI namespace replacement/restoration, command reload accounting, and nested teardown `finally` blocks exactly. The extraction must not add calls to `editor.result()` (successful command results currently increment expected reload counts).

### C. Shared query and CodeMirror driver

Add `tests/helpers/query/getCodeMirrorView.ts`, exporting `getCodeMirrorView(content: Locator): EditorView`. Move the current lookup unchanged, including the cast and exact missing-view error. Do not add fallback DOM searches, caching, or new error recovery.

Add `tests/helpers/skill-and-command-editor/createCodeMirrorDriver.ts`:

```ts
createCodeMirrorDriver(content: Locator) => {
    content,
    view(): EditorView,
    text(): string,
    placeCursor(position: number): Promise<void>,
    completionOption(label: string): Locator,
    completionListbox: Locator
}
export type CodeMirrorDriver = ReturnType<typeof createCodeMirrorDriver>;
```

- `view()` delegates to `getCodeMirrorView(content)` each time. `text()` reads `view().state.doc.toString()`. Lazy view resolution avoids stale instances if the editor remounts while switching files.
- `placeCursor` preserves existing dispatch/focus/poll behavior. Resolve the view once for that action and poll that view's selection head. Do not clamp positions or change invalid-position behavior.
- `completionOption` uses page-level `getByRole("option", {name: label, exact: true})`; `completionListbox` uses page-level `getByRole("listbox")`.
- Keep editing through `content.fill`, browser keyboard input, and completion-option clicks. Do not implement document changes with CodeMirror dispatches.
- Do not wrap arbitrary commands/keyboard input or editor Save/Delete lifecycle in this driver.

In each CodeMirror scenario, retain the mounted controls and create the CodeMirror driver from their `content`, e.g. `const codeMirror = createCodeMirrorDriver(driver.content)`. Use `codeMirror.view()`, `text()`, `placeCursor()`, and popup locators instead of the old functions/page query duplication.

After migration, delete `tests/helpers/skill-and-command-editor/codeMirror.ts`.

### D. Assertion module

Only the CodeMirror-specific checks warrant extraction. Keep everything else inline in the suites.

Add `tests/helpers/skill-and-command-editor/assertions/expectCodeMirror.ts`:

1. `expectCompletionOptions(driver: CodeMirrorDriver, labels: readonly string[]): Promise<void>` checks each exact-name option is visible. This asserts presence, not an exclusive option set.
2. `expectFrontmatterCompletionSuppressed(driver: CodeMirrorDriver, position: number): Promise<void>` obtains the current view, polls `completionStatus(view.state)` (imported from `@codemirror/autocomplete`) to `null`, checks `view.state.doc.sliceString(position, position + 2) === "<%"`, then checks the completion listbox is not in the document.

Add `assertions/index.ts` with explicit exports of these two functions.

Deliberately not extracted (left inline, since the helpers would be thin wrappers or single-scenario concerns):

- Markdown heading style checks (small `getByText` + computed-style loop, only two call sites).
- Duplicate-name message/validation polling.
- Unsaved-changes confirmation dialog checks.
- Read-only document equality, saved-result checks, checkbox/file/delete state, and persisted-storage checks.

### E. Scenario migration and behavior preservation

- Replace only the repeated CodeMirror completion assertion blocks.
- Keep typing, explicit `startCompletion`, completion selection, heading style loops, duplicate-name and unsaved-change checks, Keep-editing/discard clicks, and persisted-storage checks visible in scenarios.
- Retain the positive body-completion control and Escape before frontmatter suppression. The helper only verifies the resulting state; it does not start completion or mutate the editor.
- Retain immediate document equality for read-only tests and polling for asynchronous insertion/fill checks. Express these using driver `text()` without adding one-line assertion wrappers.
- Leave checkbox states, file visibility, Save results, deletion, and DOM `textContent` assertions inline. DOM text and CodeMirror document text are not interchangeable.
- Remove imports made obsolete by extraction (`completionStatus`, `page`, old CodeMirror helpers) only where no remaining use exists.
