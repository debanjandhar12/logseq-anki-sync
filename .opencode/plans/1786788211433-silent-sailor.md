# Chat Page Export Refactor Plan

## 1. User Requirement

Currently, handleExportAsPage in ThreadTopToolBar.tsx handles a lot of logic. Most of which should have been abstracted out in ChatPageExporter.ts. Aditionally, I do not want title to be part of the exported page name. `_chat_export_${threadId}` is enough.

## 2. Final Requirement After Discussion With User

### 2.1 Clarification Q&A

**Question:** Which responsibilities should remain in `handleExportAsPage` versus move into `ChatPageExporter`?

**Answer:** Full workflow. `ChatPageExporter` should own export construction/reconciliation, navigation, and centralized export-failure logging. The toolbar should retain its UI busy/duplicate-click state and success/error notifications.

### 2.2 Final Summarized Requirements

- Replace title-dependent export naming with the stable, exact page name `_chat_export_${threadId}`.
- Remove title resolution and persisted-thread loading from the export path; titles no longer affect export behavior.
- Give `ChatPageExporter` one workflow-level API that builds the export tree, gets or creates and reconciles the page, navigates to it, logs failures once, and returns the page name.
- Reduce `ThreadTopToolBar.handleExportAsPage` to capturing the current thread data, guarding duplicate requests, invoking the exporter, and presenting success/error notifications.
- Preserve existing message-to-block conversion, deterministic page reconciliation, icon/collapse behavior, disabled-state rules, and retry behavior.
- Do not migrate, rename, merge, or delete pages previously exported with title-suffixed names; subsequent exports use the new canonical page.

## 3. Existing System

### Toolbar workflow

- `src/chat-app/components/ThreadTopToolBar.tsx` reads the active messages, remote thread ID, title, and status from assistant-ui state.
- `handleExportAsPage` currently loads and parses the persisted thread through `ThreadStore`, resolves an active/stored/generated title, builds the page name and desired tree, calls the exporter, navigates with `LogseqNavigator`, logs errors, and shows notifications.
- A synchronous ref plus React state prevents rapid duplicate exports and disables the action while work is pending. `isThreadPageExportEnabled` also requires a regular persisted thread with at least one message.
- Notification failures are independently caught and logged by the toolbar's `notify` helper. This UI-specific behavior should remain there.
- Because this component is a copied/modified assistant-ui component, its `Changes` comment must continue to describe project-specific modifications per `src/chat-app/AGENTS.md`.

### Exporter workflow

- `src/chat-app/export/ChatPageExporter.ts` currently exposes separate `resolveTitle`, `createPageName`, `createBlockTree`, and `exportPage` steps, forcing the component to orchestrate domain operations.
- `createBlockTree` exports each user message as a root block, groups subsequent assistant text/tool calls beneath it, ignores system and unsupported message parts, and rejects assistant content without a preceding user message.
- `exportPage` rejects an empty desired tree, gets or creates the target page through `LogseqEditor`, and reconciles the complete block tree by sibling position. Existing UUIDs are reused where possible; excess blocks are removed; missing blocks are inserted; icons and tool-call collapse state are applied.
- Reconciliation mutations already add page, parent, block, and positional context to errors. The operation is not transactional, but rerunning converges on the desired tree.
- Exporter dependencies are injectable, allowing unit tests to avoid a running Logseq instance.

### Naming and tests

- The current name is `_chat_export_${threadId}_${threadTitle.trim()}`. Title selection prefers the active title, then persisted title, then `generateTitle`.
- Loading persisted JSON is currently mandatory even when the active title is available, so missing/corrupt storage can unnecessarily block export.
- `tests/src/chat-app/export/ChatPageExporter.test.ts` thoroughly covers conversion and reconciliation but tests the low-level public steps independently.
- `tests/src/chat-app/components/ThreadTopToolBar.test.ts` covers export enablement and menu dismissal, but not the asynchronous export handler.
- Existing documentation does not describe Export as Page; the naming change is user-visible and should receive a concise feature document.

## 4. Solution

### 4.1 Introduce one exporter workflow API

Modify `src/chat-app/export/ChatPageExporter.ts`:

- Add a request type containing only the stable thread identity and active-branch message snapshot:

  ```ts
  interface ChatPageExportRequest {
      threadId: string;
      messages: readonly ThreadMessage[];
  }
  ```

- Add `ChatPageExporter.exportThread(request, dependencies?)`, returning `Promise<{pageName: string}>`.
- Have this method perform, in order:
  1. Construct the exact page name `_chat_export_${threadId}` without title lookup, trimming, suffixing, or sanitization.
  2. Convert the supplied active-branch messages into the desired block tree.
  3. Reject before page access if the conversion yields no user root blocks.
  4. Get or create the canonical page and reconcile its blocks with the existing algorithm.
  5. Navigate to the reconciled page UUID through `LogseqNavigator.goToBlock` only after all reconciliation work succeeds.
  6. Return the canonical page name for the toolbar's success notification.
- Wrap the complete workflow in a single error boundary. Log `Failed to export chat as Logseq page` once with `threadId`, `pageName`, and the original error, then rethrow so the toolbar can show failure feedback. Preserve existing contextual reconciliation errors and causes; do not add a custom error hierarchy.
- Remove `generateTitle`, `resolveTitle`, and all title parameters. Make page-name creation, block-tree creation, and the current low-level page reconciliation entry point private implementation details so callers cannot partially orchestrate the workflow again.
- Keep all existing message conversion and recursive reconciliation helpers behaviorally unchanged.

### 4.2 Extend dependencies for navigation and logging

In `ChatPageExporterDependencies`:

- Add an injectable navigation function backed by a bound `LogseqNavigator.goToBlock` default.
- Add an injectable error-logging callback backed by a module-level `createLogger(LoggerCategory.CHAT_UI)` default.
- Keep all existing bound `LogseqEditor` dependencies intact.
- Type logging context to accept the original `unknown` rejection value; logging must not replace or obscure the thrown reconciliation error.

This keeps host access behind existing wrappers and makes navigation/error paths unit-testable without Logseq.

### 4.3 Reduce toolbar responsibilities

Modify `src/chat-app/components/ThreadTopToolBar.tsx`:

- Remove imports and usage of `ThreadStore`, `ThreadFileData`, and `LogseqNavigator`.
- Stop selecting `threadListItem.title`; it is no longer part of export identity.
- Preserve the existing disabled-state calculation, ref-based immediate duplicate guard, and React busy state.
- At invocation, capture the current thread ID and a shallow snapshot of active messages, then call:

  ```ts
  const {pageName} = await ChatPageExporter.exportThread({
      threadId: capturedThreadId,
      messages: capturedMessages
  });
  ```

- On success, retain `Chat exported to page: ${pageName}`. On failure, retain the generic error notification but remove duplicate export-failure logging because the exporter owns it. Always reset both busy mechanisms in `finally`.
- Keep the toolbar logger for notification failures in `notify`.
- Update the component's `Changes` comment to record that page export delegates the export/navigation workflow to `ChatPageExporter`, while the toolbar owns action state and notifications.

### 4.4 Adapt exporter tests to the public workflow

Modify `tests/src/chat-app/export/ChatPageExporter.test.ts`:

- Extend the dependency fixture with navigation and logging spies.
- Drive conversion and reconciliation through `exportThread` using representative `ThreadMessage` fixtures rather than relying on the removed public construction methods.
- Replace title fallback/name tests with assertions that `thread-1` consistently reads, creates, reconciles, logs, returns, and navigates under exactly `_chat_export_thread-1`.
- Preserve existing coverage for:
  - user/assistant/tool hierarchy and omitted part types;
  - missing and unserializable tool results;
  - leading assistant and no-user-message failures;
  - existing-page reuse and nullable create/refetch behavior;
  - positional updates, reverse removals, inserts, icons, collapse ordering, and contextual mutation failures.
- Add workflow-boundary assertions that navigation happens after reconciliation, is skipped after earlier failures, and that navigation failures are logged and rethrown.
- Assert each failure is logged exactly once with the canonical page name and that existing `Error` identity/cause information is preserved.

### 4.5 Add focused toolbar integration coverage

Modify `tests/src/chat-app/components/ThreadTopToolBar.test.ts`:

- Retain current enablement and non-modal menu tests.
- Mock assistant-ui state and `ChatPageExporter.exportThread` to verify the toolbar passes only the captured thread ID/messages, not title or persisted data.
- Verify a second rapid invocation while the first promise is pending does not start another export and that the action becomes available again after resolve or reject.
- Verify success uses the returned canonical page name, failure shows the generic error notification, and the toolbar does not independently log the export failure.
- Keep tests at the component boundary; do not expose a production-only handler solely for testing.

### 4.6 Document canonical export behavior

- Add `docusaurus/docs/chat/export-as-page.md` describing how to invoke Export as Page, the canonical `_chat_export_${threadId}` name, re-export reconciliation/overwrite behavior, and that thread-title changes do not produce a new target page.
- State that existing legacy title-suffixed export pages are left untouched.
- Add the feature page to a concise Chat category in `docusaurus/sidebars.js` without restructuring unrelated provider documentation.

- Search the repository to confirm the export path has no remaining `resolveTitle` reference, no title argument in page-name construction, and no `ThreadStore`/`ThreadFileData` usage in `ThreadTopToolBar.tsx`.
- In Logseq, export a persisted regular thread and confirm navigation to `_chat_export_<threadId>` and the success notification's exact matching name.
- Rename that thread and export again; confirm the same canonical page is reconciled rather than a title-derived page being created.
- Export the same thread after changing messages; confirm existing page blocks are updated in place according to current reconciliation behavior.
- Trigger or simulate an export failure; confirm one centralized error log, one generic error notification, no navigation after pre-navigation failure, and that the menu action becomes usable again.
