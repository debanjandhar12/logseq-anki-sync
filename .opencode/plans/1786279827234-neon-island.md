# What happens when the commit tool is "terminated" (stream/run aborted)?

> This is an **explanation-only** document. The user asked for an explanation of current behavior — **no code changes are planned.**

## User Requirement
> What happens when commit tool is terminated? (not canceled)

## Clarification (resolved)
- **"Terminated"** = the AI SDK stream/run is **aborted** (stop button / programmatic abort of the `AbortSignal`), as opposed to an explicit cancel via the "Revert and discard" flow.
- **Goal** = explain only; no implementation.

## Terminology note
"Terminated" is **not** a defined state anywhere in `src/` or in `@assistant-ui` / `assistant-stream`. The real terminal states are: `complete`, `incomplete/cancelled`, `incomplete/error`, and `requires-action/interrupt`.

## The commit tool
- File: `src/chat-app/tools/impl/LogseqCommitChangesTool.tsx`
- Name: `logseq_commit_changes`, **type `"human"`**.
- The mutation tools (Insert/Update/Move/Delete/etc.) **apply changes to the Logseq graph immediately** and enqueue them in the `LogseqReversibleTransactionTracker` as "applied-but-uncommitted". The commit tool is the gate that either **commits** (`clear()` the tracker) or **discards** (`clear()` after revert) them.

## How the commit tool is driven (why abort behaves differently)

In `LocalAISDKChatModelAdapter.ts` `run()`:
- When the LLM emits a `tool-call` for the commit tool, the adapter yields `status: {type: "requires-action", reason: "tool-calls"}` and — because `tool.type === "human"` — does **NOT** push it to `toolCallsToExecute` (lines 118–121). So `executeFrontendTool` is never called for it by the adapter.
- The tool's result is produced entirely by the React `render` component calling `addResult(...)` after running `executeApprove` / `executeCancel`.

The abort entry point in the adapter (lines 143–148):
```ts
case "abort":
    yield { content, status: { type: "incomplete", reason: "cancelled" } };
    return;
```

## What happens on stream/run abort (the "terminated" case)

There are two sub-scenarios.

### A) Abort while the commit tool is waiting for the user to click "Review & Commit"
(the tool-call part has `result === undefined`)

1. The AI SDK stream emits an `abort` part → the adapter yields `status: incomplete/cancelled` and **returns**. The run generator ends.
2. The commit tool-call part is left with **`result === undefined`** and **`approval.resolution === undefined`**. The abort path does **not** synthesize a cancel result and does **not** touch `approval`.
3. `cancelPendingToolCallsInThread` is **NOT** invoked automatically on abort. (It is only called explicitly from `ReviewChangesDisplay.tsx` → `revertAndDiscardReviewChanges`, i.e. the "Revert and discard" button.) So nothing resolves the pending human tool-call on the abort path.
4. The reversible transaction tracker is **NOT cleared and NOT reverted**. Applied-but-uncommitted graph changes stay on the Logseq graph; the tracker state persists in the prior message's artifact.
5. The render component now sees `status?.type === "incomplete"`, so `isAwaitingResult` becomes `false` and it falls back to the generic `<ToolFallback>` UI (the "Review & Commit" button is no longer shown).

### B) Abort while the user already clicked "Review & Commit" and `reviewAndCommit` is running
(modal open, or `prepareReview` / `executeApprove` in progress)

1. The adapter still receives `abort` → yields `incomplete/cancelled` → returns.
2. **However**, `reviewAndCommit` is a React async handler, independent of the generator. It is **not** interrupted:
   - `prepareReview` calls `transactionTracker.execute()` with **no signal** (`LogseqCommitChangesTool.tsx:109`).
   - `executeApprove` is invoked as `this.executeApprove({}, {messages}, transactionTracker)` — context carries only `{messages}`, **no `abortSignal`** (lines 218, 261). So `transactionTracker.execute({signal: context?.abortSignal})` receives `signal: undefined`.
   - Therefore the commit-tool execution path is effectively **immune to the run's abort signal**; it runs to completion and calls `addResult(...)`.
3. This produces a race: `addResult` is called on a message that is already `incomplete/cancelled`. Whether LocalRuntime applies that result to a terminal message is a runtime-level edge case (not resolved by project code).
4. In practice this sub-scenario is hard to trigger from the UI, because during `requires-action` the runtime's `isRunning` is `false`, so the stop button is typically not available; a programmatic `runtime.cancelRun()` or unmount would be required.

## Contrast: explicit cancel (the "Revert and discard" path)
`revertAndDiscardReviewChanges` → `cancelPendingToolCallsInThread` → `cancelPendingToolCallsInRepository`:
- Sets `result: {success: false, error: "User canceled operation"}`, `isError: true`, and if `approval.resolution === undefined` sets `approval.resolution: "cancelled"`.
- Sets message `status: {type: "incomplete", reason: "cancelled"}`.
- Then the discard tool (`logseq_clear_uncommitted_changes`) **reverts applied commands and clears** the tracker.

So explicit cancel **resolves the tool-call cleanly and reverts**; abort does **neither** — it leaves the tool-call unresolved and leaves applied changes on the graph.

## Net effect / recovery
On abort, applied-but-uncommitted changes are **left on the graph and intact in the tracker**. They are recoverable through the existing safety nets:
- `ReviewChangesDisplay` amber indicator (GitCommitIcon + count) with **Revert** / **Revert and discard** (`src/chat-app/components/ReviewChangesDisplay.tsx`).
- The `logseq_clear_uncommitted_changes` tool.
- The branch guard `useLogseqAppliedChangesBranchGuard` (prompts to revert before branch switch / message edit).
- Reload recovery `recoverInterruptedMessages` — leaves a `requires-action` human-tool message interactive (returns `false` when an unresolved human tool-call exists), so the commit UI can resume after a reload.
