### 2.2 Final Summarized Requirements

Refactor for maintainability with these agreed decisions:

1. **ThreadStore**: replace `runSerialized` + manual lock map with `async-lock` keyed locking. Delete `loadThreadForMutation` + `isMissingFileError`; normalize missing-file semantics at the storage layer instead.
2. **Storage layer**: `LogseqPluginStorageManager.getFileContent` returns `undefined` for missing files uniformly across all backends (catch the Logseq sandbox `"file not existed"` throw there, once, close to the backend that produces it).
3. **Run lifecycle consolidation**: merge `ThreadRunLifecycle.ts`, `terminateToolTurn.ts`, and `stopThread.ts` into one cohesive `thread-run/` module with clear file-level documentation. Keep `withRoundtripPersistence` as the (documented) registration point.

5. **recoverInterruptedMessages**: rename to `recoverInterruptedMessagesDuringThreadLoad.ts`, add doc comments, and align its terminal state with stop/terminate (synthetic error results via the shared termination transform, not just a status flip).
6. **ReviewChangesDisplay.tsx**: split selectors / actions / component.
7. Thread switching: no behavior change; add a short doc note explaining why background runs are safe.
8. Update `docusaurus/docs/chat/stop-tool-result-race.md` to match the simplified design.

### 3.2 Key facts confirmed during investigation

- **Why `trackThreadRun` exists**: assistant-ui LocalRuntime derives public `isRunning` from last message status. During frontend-tool execution the message is `requires-action` → `isRunning === false` even though the adapter generator is still alive. Stop needs an independent signal to know it must `cancelRun()` + await `runEnd`. The mechanism is required; only its organization/documentation is bad.
- **Why `loadThreadForMutation` exists**: commit c6d32387 made `updateThread` load-before-write; new threads have no file; the sandbox backend throws `"file not existed"` while other backends return `undefined`. 813cdccd patched it locally in ThreadStore instead of at the storage boundary.
- **Parallel tool calls on stop**: `terminateToolTurn` already writes the error result into **every** unresolved tool-call part of the target message → parallel calls already show as user-terminated. Nothing to change; this is the least-code option the user asked for.
- **Concurrent stop calls are naturally idempotent** without `pendingStops`: a second `cancelRun()` on a settled run is a no-op; `terminateToolTurn` returns `didChange:false` when no unresolved calls remain; persistence is serialized by the per-thread store lock. The dedup map defends against races the underlying operations already tolerate.
- **Persistence merge**: Stop awaits `runEnd`, and assistant-ui appends its terminal message to history *before* emitting `runEnd`, so by persistence time the stored repo normally already contains the target message. Terminating the *stored* repo directly makes stored results win naturally; only "target ancestry missing from store" (storage lag / brand-new thread) needs a fallback.
- **Thread switching**: `RemoteThreadListThreadListRuntimeCore.switchToThread` does NOT stop the previous thread runtime; it stays alive in the hook instance manager. All project state is keyed per threadId (run counts, store locks, history adapter, `assistantRuntime.threads.getById(threadId)` in every stop caller), so background runs are already safe.
- `await-lock` stays a dependency (used by `LogseqReversibleTransactionOperationLockManager` for a single non-keyed lock — appropriate there, leave it).
- `stopThread` callers: `useStopThread` hook → `ComposerAction` (no options) and `LogseqCommitChangesTool` (defer-commit, with target); `ReviewChangesDisplay` actions call `stopThread` directly (no target).
- `StopThreadResult.kind` is only consumed by tests; production code reads `didStop` and `persistenceFailed`.
- `getReviewChangesCommandCount` is exported but only used by its own test.

## 4. Solution

### Step 1 — Normalize missing-file semantics in the storage layer

**File: `src/logseq/LogseqPluginStorageManager/LogseqPluginStorageManager.ts`**

Change `getFileContent` to return `string | undefined` uniformly:

```ts
/**
 * Returns the file content, or undefined when the file does not exist.
 * Logseq's sandbox storage backend throws "file not existed" for missing
 * files while the in-memory and localStorage backends return undefined;
 * this method normalizes both to undefined so callers never need
 * backend-specific error matching.
 */
static async getFileContent(group: string, fileName: string): Promise<string | undefined> {
    LogseqPluginStorageManager.validateOperation(group, fileName);
    try {
        return await LogseqPluginStorageManager.store.getItem(`${group}/${fileName}`);
    } catch (error) {
        if (isSandboxMissingFileError(error)) return undefined;
        throw error;
    }
}

// module-private; the ONLY place in the codebase that matches this string
function isSandboxMissingFileError(error: unknown): boolean {
    return error instanceof Error && error.message.toLowerCase().includes("file not existed");
}
```

Existing consumers (`JustBashAdapterFS`, `SkillFileStore`, `AnyDocParseResultStore`, `ToolResultStore`) already handle `undefined` (e.g. `JustBashAdapterFS` checks `content === undefined`), so this is strictly a bug-fix-generalization, not a breaking change. Verify each consumer briefly during implementation.

### Step 2 — ThreadStore: async-lock + single load path

`pnpm add async-lock && pnpm add -D @types/async-lock`

**File: `src/core/stores/thread-store/ThreadStore.ts`** — rewrite:

```ts
import AsyncLock from "async-lock";

export class ThreadStore {
    static groupName = "thread";
    /** Keyed per-thread lock: mutations of the same thread are serialized,
     *  different threads update concurrently. Non-reentrant: updaters must
     *  not invoke another ThreadStore mutation of the same thread. */
    private static readonly lock = new AsyncLock();

    /**
     * Returns the parsed thread, or null when no thread file exists.
     * Throws on storage failures and corrupt (unparseable) thread data so
     * that a later save cannot silently overwrite recoverable content.
     */
    static async loadThread(threadId: string): Promise<ThreadFileData | null> {
        const content = await LogseqPluginStorageManager.getFileContent(
            ThreadStore.groupName, threadId
        );
        if (content === undefined) return null;
        try {
            return JSON.parse(content) as ThreadFileData;
        } catch (error) {
            throw new Error(`Failed to parse thread data: ${threadId}`, {cause: error});
        }
    }

    static async updateThread<TResult>(threadId, updater): Promise<TResult> {
        return ThreadStore.lock.acquire(threadId, async () => {
            const currentThread = await ThreadStore.loadThread(threadId);
            const update = await updater(currentThread);
            if (update.type === "skip") return update.result;
            await LogseqPluginStorageManager.saveFile(
                ThreadStore.groupName, threadId, JSON.stringify(update.threadData));
            return update.result;
        });
    }

    static async deleteThread(threadId: string): Promise<void> {
        await ThreadStore.lock.acquire(threadId, async () => {
            try {
                await LogseqPluginStorageManager.deleteFile(ThreadStore.groupName, threadId);
            } catch {}
        });
    }
    // listThreads: keep, but reuse loadThread-style per-file parse-warn behavior (unchanged logic)
}
```

Deletions: `runSerialized`, `ThreadLockEntry`, `threadLocks` map, `loadThreadForMutation`, `isMissingFileError`, `loadRawThread` (dead code, zero callers), the `AwaitLock` import.

Behavior change (intentional, safer): `loadThread` no longer swallows arbitrary storage errors into `null`. Callers checked:
- `LocalThreadListAdapter.fetch` — throws either way; fine.
- `LocalThreadHistoryAdapter.load` — a real storage failure now propagates instead of silently rendering an empty thread; correct.

`listThreads` keeps its per-file try/parse-warn loop (a corrupt file should not break the whole list).

#### 3c. `stopThreadRun.ts` (rewritten, ~120 lines vs 252)

Public API:

```ts
export interface StopThreadRunResult {
    didStop: boolean;
    persistenceFailed?: boolean;
}

/**
 * Stops the active run of a thread and/or terminates its pending tool turn.
 * Safe to call concurrently and when nothing is running (idempotent):
 * cancelRun on a settled run is a no-op, terminateToolTurn skips resolved
 * calls, and persistence is serialized by ThreadStore's per-thread lock.
 */
export async function stopThreadRun(options: {
    threadId: string;
    runtime: ThreadRuntime;
    errorMessage?: string;   // defaults to USER_TERMINATED_OPERATION
}): Promise<StopThreadRunResult>
```

Removed vs today:
- `pendingStops` map + JSON `signature` comparison + shared-promise dedup (idempotency documented instead — see doc comment above).
- `target` option (all callers use the active assistant message; commit-defer passes only a custom `errorMessage` — see Step 5). Internally still `getActiveAssistantMessageTarget(runtime.export())`.
- `kind` result field (tests-only consumer).
- `mergeTargetAncestry` / `mergeTerminatedMessageItem` (see persistence below).

Flow (same proven lifecycle semantics, kept, documented):

```ts
async function stopThreadRun(options): Promise<StopThreadRunResult> {
    const {threadId, runtime} = options;
    const errorMessage = options.errorMessage ?? USER_TERMINATED_OPERATION;

    // Tracked-run signal is authoritative; public isRunning misses
    // frontend-tool execution (see ThreadRunTracker).
    const wasRunning = isThreadRunActive(threadId) || runtime.getState().isRunning;
    if (wasRunning) await cancelActiveRunAndAwaitRunEnd(runtime, threadId);

    const target = getActiveAssistantMessageTarget(runtime.export());
    if (!target) return {didStop: wasRunning};

    const terminated = terminateToolTurn(runtime.export(), {target, errorMessage});
    if (!terminated.didChange) return {didStop: wasRunning};

    runtime.import(terminated.repository);
    try {
        await persistTerminatedToolTurn({threadId, target, errorMessage,
            terminatedRepository: terminated.repository});
    } catch (error) {
        logger.error("Failed to persist terminated chat state", error);
        return {didStop: true, persistenceFailed: true};
    }
    return {didStop: true};
}
```

`cancelActiveRunAndAwaitRunEnd`: keep today's implementation (subscribe `runEnd` before `cancelRun`, re-check tracker to close the subscribe/settle race, 10s timeout) — this is the essential race fix from the doc — but add comments citing the doc for each step.

Simplified persistence:

```ts
async function persistTerminatedToolTurn({threadId, target, errorMessage, terminatedRepository}) {
    await ThreadStore.updateThread(threadId, (threadData) => {
        const stored = threadData?.exportedMessageRepository ?? {headId: null, messages: []};

        // Normal case: runEnd already appended the target to storage, so
        // terminating the STORED repo applies cancellation while stored
        // results (possibly newer than our runtime snapshot) win naturally.
        // Fallback: storage lagged (thread init incomplete / append pending);
        // insert the target's ancestry from the terminated runtime export,
        // parent-before-child, without touching unrelated stored branches.
        const repository = terminateToolTurn(
            ensureTargetAncestry(stored, terminatedRepository, target.messageId),
            {target, errorMessage}
        ).repository;

        // build-or-update ThreadFileData exactly as today (create record with
        // pkg.version metadata when threadData is null), save.
    });
}
```

`ensureTargetAncestry(stored, runtimeRepo, targetMessageId)` (~25 lines): walk parent chain of `targetMessageId` in `runtimeRepo`; append the items missing from `stored` (parent-before-child); if target itself was missing, set `headId` to `targetMessageId` unless stored `headId` already points into a branch containing the target. **No field-level content merging** — if the stored target message exists, the stored copy is used as-is and only `terminateToolTurn` mutates it. This drops the "preserve newer successful result over cancellation at field level" behavior for the exotic runtime-vs-store divergence case (user-approved), while the common cases keep identical outcomes.

Note: since termination now happens on the stored repo, the runtime `import` above and the persisted state may differ in exotic cases — acceptable per user decision; next load reconciles from storage.

### Step 4 — `recoverInterruptedMessagesDuringThreadLoad.ts`

Rename `src/chat-app/runtime/recoverInterruptedMessages.ts` → `src/chat-app/runtime/thread-run/recoverInterruptedMessagesDuringThreadLoad.ts` (it is part of the same termination concept — co-locate it).

```ts
/**
 * Repairs assistant messages that were interrupted by an app reload/crash so
 * a freshly loaded thread is never stuck in a phantom "running" state.
 *
 * A persisted message can be `running` (plugin closed mid-stream) or
 * `requires-action` with all automatic tools settled (the continuation
 * roundtrip never persisted). Neither run will ever resume, so we apply the
 * same terminal state the Stop button produces via terminateToolTurn:
 * synthetic error results on unresolved tool calls + incomplete/cancelled.
 *
 * Messages legitimately waiting for HUMAN input (unresolved approval or a
 * declared human tool) are left untouched — they are actionable, not stuck.
 */

    repository: ExportedMessageRepository,
    humanToolNames: readonly string[]
): ExportedMessageRepository
```
