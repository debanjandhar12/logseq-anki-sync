## 2. Final Requirement After Discussion With User

### 2.1 Clarification Q&A

- **Durable OAuth storage:** Store the SDK's opaque `AuthStorage` entries inside the corresponding `OAuthProviderConfig`. Do not add a separate hidden token setting and do not use browser `localStorage`/`sessionStorage` for durable credentials.
- **Existing credentials/config migration:** None. The plugin is unreleased. Delete the old credential format; canonical configs missing UUID/name or containing old OAuth `apiKey` data may fail validation and require local settings reset.
- **Modal cancellation:** A successful device login, logout, or refresh performed while editing remains in SDK memory storage until Save. Cancel discards it and leaves persisted provider data unchanged.
- **Provider types:** Keep the persisted `codex-subscription` type for now. OAuth infrastructure and UI are generic so Qwen/xAI can be added later without rewriting the flow.
- **Identity and display:** Every provider has immutable `uuid`; UUID is the sole identity used by selection, resolution, OAuth `accountKey`, storage, editor correlation, and caches. Rename provider `id` to unique editable `name`, which is display-only.
- **Name uniqueness:** Require case-insensitively unique provider names so selector groups and editor rows remain distinguishable.
- **UUID generation:** Use `v4` from the existing `uuid` package, not `crypto.randomUUID()` or a Logseq UUID API. The default provider receives a fixed UUID literal.
- **OAuth AI SDK factory:** Keep the short `createOpenAI` + `createAuthenticatedFetch` setup in `getLLMModel.ts`. Extract a factory only if actual implementation becomes materially larger or multiple call sites cannot safely share a small exported helper.
- **OAuth provider registry:** Do not introduce one for a single provider. Keep explicit `CODEX_SUBSCRIPTION` branches in existing provider flow functions. Add shared metadata/transport abstraction only when Qwen/xAI are actually implemented and repetition justifies it.
- **Runtime client cache:** Retain `OAuthClientCache`; sharing one durable `AuthClient` per UUID is required for the SDK's in-process concurrent-refresh deduplication.
- **Draft-session abstraction:** Do not add standalone `OAuthDraftSession.ts`. Own all memory storage, draft clients, intents, device-flow state, commit data, and cleanup inside `useProviderConfigOAuth`.
- **Model factory signature:** Keep the current `createLLMModel({config, rawModelId})` signature. Runtime model creation resolves its durable client from UUID. Modal Test handles its Codex branch with the staged client rather than injecting it into `createLLMModel`.

### 2.2 Final Summarized Requirements

1. Replace `openai-oauth-ai-provider` with pinned `@ai-oauth-sdk/browser`, retaining only device-code OAuth.
2. Delete the old credential codec, old-package token stores/session manager, Vite shim, optimizer exclusions, package, and obsolete tests.
3. Add only concrete reusable OAuth infrastructure under `src/core/ai-sdk/oauth/`: provider-config-backed SDK storage and a durable client cache. Keep Codex branches in existing provider functions; avoid a premature registry/session/factory hierarchy.
4. Model provider configs as a strict union: all have UUID/name/type/base URL/models; API-key providers have `apiKey`; OAuth providers instead have SDK-owned opaque `oauthStorage`.
5. Use UUID everywhere identity is needed. Persist model selections as `providerUuid////modelId`; users see provider name/model only.
6. Use a UUID-scoped `AuthStorage` adapter over `OAuthProviderConfig.oauthStorage`; use SDK `memoryStorage()` for modal drafts.
7. Use `createAuthenticatedFetch` with the existing AI SDK OpenAI provider for runtime chat/title generation and Test; use it through SDK helpers for native tools/model discovery. Use `fetchCodexModels` for Codex discovery.
8. Remove the API-key field entirely from OAuth UI and persisted OAuth configs.
9. Split all major `ProviderConfigModal.tsx` behavior into cohesive hooks, not only OAuth behavior.
10. Do not modify Docusaurus.

## 3. Existing System

### 3.1 Current paths and coupling

- `src/core/ai-sdk/codex/CodexCredentialCodec.ts` encodes old-package token objects into `ProviderConfig.apiKey`.
- `CodexProviderTokenStore.ts` rewrites the provider-config setting when tokens refresh; `InMemoryCodexTokenStore.ts` stages modal credentials.
- `CodexSessionManager.ts` creates/caches old auth, AI provider, and catalog clients and selects durable versus draft stores.
- `getLLMModel.ts`, `getLLMProviderTools.ts`, `fetchProviderModels.ts`, and `testProviderConfig.ts` branch through that session manager.
- `CodexSignInSection.tsx` owns device-login state and returns encoded credentials into the 790-line `ProviderConfigModal.tsx`.
- `selectedModelId.ts` currently encodes editable provider `id`; `resolveLLMSelection.ts` finds configs by `id`; `getLLMModelList.ts` and `ModelSelector.tsx` overload `providerConfigId` as both group identity and visible heading.

### 3.2 Why `ProviderConfigRepository` was introduced

The repository is more than a settings accessor. Since the current design stores rotating credentials in the encoded provider array, refresh and modal metadata saves can race. It supplies a lock, read/modify/write transactions, stale-refresh checks, modal-refresh preservation, credential events, and selected-model reconciliation.

The rewrite removes old-package and Codex-specific repository responsibilities, but storing SDK records inside `OAuthProviderConfig` still requires a generic aggregate transaction: every SDK refresh must find the config by UUID and rewrite only its opaque storage without losing other configs or a simultaneous modal Save. Retain a smaller `ProviderConfigStore`/simplified repository for this cause; do not keep token codecs, Codex token types, or credential listeners.

### 3.3 New SDK facts

- `AuthStorage` is generic `get/set/delete/keys?`; the SDK owns serialized values and uses keys such as `tokens:openai:<accountKey>`.
- `AuthClient.deviceLogin({signal, onCode})` performs the provider-specific device flow and writes its result through the supplied storage.
- `createAuthenticatedFetch(client)` refreshes before expiry, deduplicates refresh in one client, applies provider headers/query/body transforms, and retries one replayable 401.
- Codex uses `createOpenAI({apiKey: placeholder, baseURL: client.provider.apiBaseUrl, fetch: createAuthenticatedFetch(client)}).responses(modelId)`.
- The general Responses API is stateful-capable, but the Codex subscription backend operates statelessly. The AI SDK constructs the Responses request/conversation input; the OAuth SDK's OpenAI descriptor then normalizes the outgoing body by forcing `store: false`, requesting `reasoning.encrypted_content`, supplying reasoning defaults, removing server-side item IDs/`item_reference` entries, and removing unsupported output-token fields. Do not reproduce these transformations in application code.
- `fetchCodexModels(client)` replaces the old catalog client.
- Durable browser adapters do not fit the chosen graph/plugin persistence. SDK `memoryStorage()` is appropriate for draft sessions.

### 3.4 Constraints

- Access settings through `LogseqSettingAccessor`, never direct `logseq.settings`.
- Continue using the installed `globalThis.fetch`/`LogseqHttpProxy`; use `WindowParentBridge` only to open device verification URLs.
- Use the centralized logger and never log/render token values, opaque OAuth storage, raw OAuth responses, authorization codes, device secrets, or API keys.
- No migration or Docusaurus work.

- `vite.config.ts`: remove `openAIOAuthBrowserPlugin` import/invocation and old-package `optimizeDeps.exclude`. Retain unrelated Buffer/process polyfills.
- Delete `vite-plugins/openAIOAuthBrowserPlugin/**` and its test.
- Delete `src/core/ai-sdk/codex/{CodexCredentialCodec,CodexProviderTokenStore,InMemoryCodexTokenStore,CodexSessionManager}.ts` and old codec tests.

### 4.2 Canonical provider types and schema

In `src/core/ai-sdk/types.ts`, use a strict discriminated union:

```ts
interface ProviderConfigBase {
    uuid: string;
    name: string;
    baseUrl: string;
    models: ProviderModelConfig[];
}

type ApiKeyProviderConfig = ProviderConfigBase & {
    type: OPENAI | OPENAI_COMPATIBLE | GOOGLE;
    apiKey: string;
};

type OAuthProviderConfig = ProviderConfigBase & {
    type: CODEX_SUBSCRIPTION;
    oauthStorage: Record<string, string>;
};
```

- Add `isOAuthProviderConfig`/`isApiKeyProviderConfig` type guards.
- In `providerConfigSchema.ts`, build strict per-variant schemas and a discriminated union. API-key variants reject `oauthStorage`; OAuth rejects `apiKey`. Validate `oauthStorage` only as string-to-string because values belong to the SDK.
- Validate UUID format and uniqueness. Validate trimmed, nonblank, case-insensitively unique names; preserve user casing for display. Remove lowercase-ID and `////`-in-ID rules.
- Keep fixed Codex URL and existing URL/model uniqueness rules. Signed-out OAuth (empty storage) may have no enabled model; authenticated OAuth needs an enabled model before Save/runtime use.
- `providerConfigCodec.ts` remains strict: no UUID/name/credential migration.
- `settings.ts`: replace default `id` with `name`, add a fixed UUID literal, and do not add `oauthTokenStorageSetting`.
- Modal Add calls `uuidv4()` from `uuid`; provider type switching preserves UUID/name.

Type-switch construction must not spread incompatible variants:

- API key -> OAuth: preserve UUID/name; fixed OAuth URL; no API key; empty `oauthStorage`; clear models.
- OAuth -> API key: preserve UUID/name; remove OAuth storage; empty API key; provider default URL; clear models.
- API key -> API key: preserve UUID/name; reset key/URL/models as currently.
- Future OAuth -> different OAuth provider: preserve config UUID but clear old issuer credentials and require login unless definitions explicitly share an issuer namespace.

### 4.5 Provider-config-backed `AuthStorage`

Add `ProviderConfigSettingOAuthStorage.ts`, clearly identifying where data lives. Each instance is bound to a provider UUID:

```ts
get(key): read latest configs -> find OAuth config by UUID -> oauthStorage[key] ?? null
keys(): return Object.keys(config.oauthStorage)
set(key, value): transaction -> find same UUID/type -> set only oauthStorage[key]
delete(key): transaction -> find same UUID/type -> delete only oauthStorage[key]
```

- Runtime `get` reads current settings, ensuring refreshed records from other clients can be observed when the SDK rereads storage.
- `set/delete` use the same module-level lock as metadata Save, reread inside the lock, validate/encode the full array, and update only `providerConfigSetting`.
- Missing/deleted/type-changed UUID and malformed settings yield generic errors; never include keys/values/tokens in errors/logs.
- The adapter does not parse `TokenSet`; it preserves SDK strings verbatim.

Simplify `ProviderConfigRepository.ts` into a generic aggregate store (rename file/symbol to `ProviderConfigStore` if call-site clarity improves):

- Keep `read()`.
- Add one private/public transaction primitive that locks, rereads, transforms configs, reconciles selection, and writes.
- Remove `OpenAIOAuthTokens`, codec imports, `CodexCredentialIntent`, `updateCodexCredentials`, credential listeners, `saveFromModal`, and duplicate write logic.
- Both UUID-scoped AuthStorage mutations and modal Save use this exact lock/transaction. This is essential because SDK refresh rewrites the provider array.

### 4.6 Runtime OAuth client cache (required, not persistence)

Add a focused `OAuthClientCache.ts`:

- Cache one durable Codex `AuthClient` by provider-config UUID (or UUID plus `ProviderId.OpenAI` if the cache key type is prepared for future providers).
- Create it with `ProviderConfigSettingOAuthStorage(config.uuid)`.
- Reuse it so concurrent requests for one provider share SDK refresh deduplication.
- `get`, `invalidate(uuid)`, `remove(uuid)`, and test-only/full `clear` are sufficient.
- Name/display edits do not invalidate it. Successful explicit token commit/logout, OAuth type change, and deletion do.
- It owns no settings or token logic and does not subscribe to repository events.

### 4.8 Draft OAuth lifecycle inside `useProviderConfigOAuth`

Do not add `OAuthDraftSession.ts`. Implement the following entirely inside `useProviderConfigOAuth`, using refs/state plus small private hook helpers. For each OAuth config opened in the modal:

1. Copy `config.oauthStorage` into SDK `memoryStorage(new Map(Object.entries(...)))`.
2. Create a Codex draft `AuthClient` with `ProviderId.OpenAI`, `publicClientIds.openai`, the same UUID as `accountKey`, and memory storage.
3. Retain a deep copy of baseline storage and track `intent: unchanged | replace | clear`.
4. Determine local signed-in state via SDK token methods without calling `getAccessToken` on modal open; opening the modal must not trigger network refresh.
5. Device login calls `client.deviceLogin({signal, onCode})`; it writes only to memory and marks `replace`.
6. Draft logout calls local `client.logout()` and marks `clear`.
7. Fetch Models/Test use this draft client. Any automatic refresh changes memory only and is detected by comparing current memory keys/values to baseline.

Draft save mutations are keyed by config UUID:

```ts
type OAuthDraftMutation =
    | {kind: "replace"; uuid: string; oauthStorage: Record<string, string>}
    | {kind: "clear"; uuid: string}
    | {
          kind: "compare-and-set";
          uuid: string;
          baseline: Record<string, string>;
          oauthStorage: Record<string, string>;
      };
```

Under the provider-store lock, modal Save rereads latest configs and creates final configs by UUID:

- `replace`: use memory storage; explicit sign-in wins over runtime refresh.
- `clear`: use empty storage; explicit logout wins.
- `compare-and-set`: use refreshed draft storage only if latest durable storage still equals baseline; otherwise preserve the newer runtime value.
- unchanged/no memory change: preserve latest durable storage, never stale modal storage.
- new signed-out OAuth: empty storage.
- deleted OAuth/OAuth-to-API-key: final config naturally omits its OAuth storage.

Then reconcile `selectedModelId` by UUID and perform one `updatePluginSettings({providerConfigSetting, selectedModelId})`. On failure, keep drafts/modal open for retry. On success, invalidate affected cached clients, dispose drafts, and close.

The hook owns a `Map<uuid, OAuthDraft>` containing client, memory storage, baseline storage, explicit intent, and current device-login attempt state. It exposes only view state, actions, draft client lookup for Fetch/Test, save mutations, dirty/busy state, and disposal; no component receives token records.

Cancel/unmount aborts active login and drops the hook-owned memory stores without durable writes. Auth-only changes count as unsaved, so successful login/logout/refresh still triggers the discard confirmation.

### 4.10 Edge cases and error behavior

- Missing/malformed/duplicate UUID or old `id` fails through safe load validation; never generate transient UUIDs while decoding.
- UUID never changes on name edit, type switch, reorder, Save, or model edit.
- Duplicate names produce field validation without exposing UUID.
- Signed-out OAuth may save with no model; after draft sign-in, Save requires one enabled model.
- Runtime refresh and modal Save use the same lock. An unchanged modal never overwrites a newer runtime refresh.
- If durable storage disappears externally while an unchanged modal is open, Save does not recreate it.
- Explicit saved login/logout wins over a concurrent runtime refresh.
- Failed settings Save does not destroy drafts or invalidate clients.
- Unknown opaque SDK keys within retained OAuth configs are preserved. App code never prunes or interprets them.
- Provider deletion removes credentials because the whole config disappears; no orphan token setting exists.
- Safe errors may include provider/operation/status but not storage JSON, response bodies, tokens, codes, secrets, or API keys.
