## 3. Existing System

### Commit review and initialization

Commit `2293b932e9f0a44e6443a52807787636c0da9c73` adds optional `chatModelAdapter` injection through `App`, `ThreadBoundLocalAISDKRuntimeProvider`, and `useThreadBoundLocalAISDKChat`. It adds a language-model factory argument to `runLocalAISDKChatModel` and replaces the scenario's broad model mock with an injected adapter fixture.

Production flow:

```text
initAIChat sidebar renderer / OpenAIChatCommand modal fallback
  -> React.createElement(App)
  -> ThreadBoundLocalAISDKRuntimeProvider(undefined adapter)
  -> useThreadBoundLocalAISDKChat(undefined)
  -> LocalAISDKChatModelAdapter
  -> persistence wrapper and LocalRuntime
```

- `src/core/chat-interop/initAIChat.ts:32` and `src/core/chat-interop/commands/OpenAIChatCommand.ts:30` render `App` without an adapter.
- `src/chat-app/runtime/useThreadBoundLocalAISDKChat.ts:19-21` defaults its argument to `LocalAISDKChatModelAdapter`. Explicit `undefined` activates a JavaScript default parameter; no caller change is required.
- The factory argument in `runLocalAISDKChatModel` defaults to `createLLMModel`, preserving normal model creation.
- No demonstrated production regression requiring an initialization change was found.
- Coverage limitation: the injected scenario no longer tests the default adapter path. This is not itself a runtime bug, and adding a production-composition test is outside this agreed narrow change.

### Browser scenario

- `tests/scenario/ai-chat-modal/showAIChatModal.e2e.test.tsx` mounts `showAIChatModal` with an injected deterministic chat adapter, sends a create-page request, and checks two streamed model calls plus the follow-up response.

- `tests/helpers/mountLauncher.tsx` creates the launcher environment and internally finds the generated modal container by ID prefix. It also exports recursive `findInShadowTree` and `getTextContentInShadowTree`; only this scenario uses them.
- `Composer.tsx` exposes a native textarea named `Message input`; `ComposerAction.tsx` exposes a button named `Send message`. No production accessibility changes are needed for these locators.

These are Vitest APIs, not Vite selector APIs.

### Title-generation gap

The fixture injects only the chat runner's language-model factory. After the first completed run, assistant-ui's thread lifecycle can call:

```text
LocalThreadListAdapter.generateTitle
  -> core/title-generator/generateTitle
  -> getLLMModel
  -> configured real provider / generateText
```

Thus the new fixture does not isolate title generation. Actual provider access depends on settings and available user text; failures are caught and fall back, but unintended requests and nondeterministic background work remain possible.

`tests/src/chat-app/runtime/LocalThreadListAdapter.test.ts:8-12` already demonstrates the narrow hoisted `generateTitle` module mock pattern. Use the same boundary in the scenario, retaining the real adapter's title persistence and stream implementation.

## 4. Solution

### A. Migrate scenario selectors and actions

Modify `tests/scenario/ai-chat-modal/showAIChatModal.e2e.test.tsx`:

1. Add named `page` import from `vitest/browser`.
2. Import only `mountLauncher` from the mounting helper.
   Remove the direct `App` import and import `createChatApp` alongside `test` from `./fixture`. Mount with `createChatApp(model.chatModelAdapter)` so the fixture owns the production app import as well as mock registration.
3. Replace textarea lookup, prototype setter, and synthetic event with:

```tsx
await page.getByRole("textbox", {name: "Message input", exact: true})
    .fill(`Create a page named ${pageName}`);
await page.getByRole("button", {name: "Send message", exact: true}).click();
```

4. Preserve trace annotations and the existing `try/finally` unmount.
5. Replace the exact-one intermediate wait with polling for `languageModel.doStreamCalls.length >= 1`. The browser action can return after the tool follow-up has already started, so exact-one polling can miss a transient state.
6. Separately poll `languageModel.doStreamCalls.length` to equal `2`, retaining the final tool-roundtrip invariant.
7. Replace the combined text-content boolean poll with:

```tsx
await expect.element(page.getByText("Page created", {exact: true})).toBeVisible();
```

8. Remove the unnecessary `mockTurn` alias and explicit missing-element errors. Locator actions and assertions supply retrying, contextual errors. Keep strict matching; do not hide duplicate matches with `.first()` or use test IDs/classes as a shortcut.

The launcher resets the document and mounts one modal, so page-level role/text locators are appropriately scoped. The internal generated-ID lookup is setup plumbing, not a user interaction, and remains unchanged.

### B. Fixture-owned title-generation isolation

Modify `tests/scenario/ai-chat-modal/fixture.tsx`. Add `vi` to its Vitest import and register the mock here, not in the scenario:

```ts
const mocks = vi.hoisted(() => ({generateTitle: vi.fn()}));

vi.mock("../../../src/core/title-generator/generateTitle", () => ({
    generateTitle: mocks.generateTitle
}));
```

- Inside the existing `model` fixture, before `await use(...)`, reset the title mock and configure a deterministic resolved title such as `Deterministic scenario title`. The consumed model fixture guarantees setup before the test body; a separate automatic fixture is unnecessary.
- Move the static `App` import from the scenario into this fixture module. Vitest 5 hoists mock registration before imports in the module containing `vi.mock` and wraps its imports to prepare queued browser mocks. A mock in an imported fixture must not be expected to retroactively replace a module already loaded by a scenario's direct `App` import.
  Title generation is not invoked on mounting: it runs after the first completed message run. The import arrangement addresses module loading/binding timing only. Keeping separate static imports may appear to work under some loading orders, but is not a reliable mock-registration guarantee.
- Export `createChatApp(chatModelAdapter: ChatModelAdapter)` from the fixture, returning `<App chatModelAdapter={chatModelAdapter} />`. This establishes a clear fixture-owned import/composition boundary without changing production APIs.
- Keep the fixture's injected chat adapter behavior unchanged. Do not restore a broad `getLLMModel` mock or add production dependency props.
- Add `waitForTitleGeneration: () => Promise<void>` to `ModelFixture` and its supplied value. Implement it with `vi.waitFor` checking `mocks.generateTitle.mock.calls.length > 0`, throwing a descriptive pending error when no call exists. Expose this semantic helper instead of exposing the mock.
- After the two-call and visible-response assertions, the scenario calls `await model.waitForTitleGeneration()`. This verifies that the real runtime exercised the isolated title lifecycle before teardown without putting mock details in the scenario. Remove `vi` from the scenario import once its old `vi.waitFor` has also been replaced by `expect.poll`.
- Do not require exactly one title invocation: repetition is an implementation detail, whereas avoiding real title-model access is the isolation requirement.
- The mock remains configured for the module lifetime; do not reset it during unmount while asynchronous title work could still reach it. Reset/configure at the beginning of each model-fixture invocation. Do not use `resetModules` or `restoreAllMocks` as teardown for this mock. Retain the existing non-concurrent scenario execution.
- Title-generator internals and fallback behavior remain covered by their existing dedicated tests. This scenario validates composition, not real title inference.
