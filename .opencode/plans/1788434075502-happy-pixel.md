## 2. Final Requirement After Discussion With User

### 2.1 Clarification Q&A

1. **How should validation be reorganized?**
   - Answer: Create a `validation/` subfolder within `ProviderConfigModal`.
2. **Where should `toPersistedProviderConfigs` and `getProviderConfigsSnapshot` move?**
   - Answer: Move them to separate utilities because neither is validation.
3. **Should this refactor also extract the modal's large inline JSX sections?**
   - Answer: No. Focus on validation only in this change.
4. **Should action preflight continue duplicating save validation?**
   - Answer: No. Share semantic validators while preserving action-specific behavior and messages.
5. **Should validation and utility files be split by exported method name?**
   - Answer: Yes. Use one primary exported method per file for validation, mapping, and snapshot logic.

### 2.2 Final Summarized Requirements

- Reorganize modal-specific validation under `src/ui/pages/ProviderConfigModal/validation/`, with one primary exported method per file and matching method/file names.
- Separate validation, persistence mapping/normalization, and dirty-state snapshot responsibilities.
- Make save validation and fetch/test preflight validation reuse the same field-level rules.
- Preserve their distinct purposes:
  - Save validation returns all structured, field-addressable issues for highlighting and focus.
  - Action preflight returns the first concise prerequisite message and can conditionally require an enabled model.
- Keep OAuth sign-in state validation UI-local and callback-driven; do not push modal state into core validation or Zod schemas.
- Preserve the existing modal UI and do not modify `JinaWebToolsWarning.tsx` or `OAuthSignInSection.tsx`.
- Preserve the public exports currently available from the `ProviderConfigModal` barrel.

## 3. Existing System

### 3.1 Modal composition and data flow

`src/ui/pages/ProviderConfigModal/ProviderConfigModal.tsx` is a 633-line composition root. It delegates state and effects to:

- `useProviderConfigDrafts`: loads editable configs, tracks active config/issues, and mutates drafts.
- `useProviderConfigOAuth`: manages draft OAuth clients, sign-in state, storage mutations, and dirty state.
- `useProviderConfigActions`: fetches models and tests connections.
- `useProviderConfigPersistence`: validates, maps, and saves all configurations.

The current change intentionally leaves the rendered sidebar, provider fields, and model editor inline.

### 3.2 Current validation layers

There are three valid but partially overlapping layers:

1. `src/core/ai-sdk/provider-config/validateProviderConfig.ts`
   - Runtime primitives and connection checks.
   - `validateProviderBaseUrl` is the authoritative URL parser/normalizer and rejects malformed/non-HTTP URLs, credentials, queries, and fragments.
2. `src/core/ai-sdk/provider-config/providerConfigSchema.ts`
   - Zod validation at the persisted-data boundary.
   - Protects decoding/storage independently of the UI.
3. `src/ui/pages/ProviderConfigModal/providerConfigValidation.ts`
   - Form/save validation tied to `editorKey`, UI fields, model indexes, and live OAuth sign-in state.

The UI layer cannot simply be replaced by the Zod schema because it needs draft-only metadata, actionable field focus, and an injected OAuth status callback.

### 3.3 Mixed responsibilities in `providerConfigValidation.ts`

The file currently contains:

- `validateProviderConfigs`: actual form/save validation.
- `toPersistedProviderConfigs`: draft-to-domain mapping and normalization.
- `getProviderConfigsSnapshot`: serialization for dirty-state comparison.

Only the first responsibility is validation. This naming and placement obscures the dependency boundaries.

### 3.4 Why `useProviderConfigActions` validates separately

The separate preflight has a legitimate UX purpose:

- Fetch Models needs a valid URL and authentication, but does not require an existing enabled model.
- Test needs the same prerequisites plus an enabled nonblank model.
- Each action stops at one short message rather than generating all form issues or changing validation highlighting.

However, its inline `validateAction` duplicates URL, API-key/OAuth, and enabled-model rules. The URL implementation is also subtly weaker than save/core validation because it currently permits query strings and fragments. The purpose should remain separate, but the semantic checks should be shared.

### 3.5 Tests and compatibility

- Existing coverage is in `tests/src/ui/pages/ProviderConfigModal/providerConfigValidation.test.ts`.
- The modal barrel re-exports validation, mapping, snapshot, and modal types.
- Repository searches found no production deep imports of `providerConfigValidation.ts` beyond files in this module; tests use that deep path.
- `JinaWebToolsWarning.tsx` and `OAuthSignInSection.tsx` are already suitably isolated and remain unchanged.

## 4. Solution

### 4.1 Create method-named shared UI field validators

Add one file per shared rule:

- `src/ui/pages/ProviderConfigModal/validation/validateProviderConfigBaseUrl.ts`
- `src/ui/pages/ProviderConfigModal/validation/validateProviderConfigAuthentication.ts`
- `src/ui/pages/ProviderConfigModal/validation/validateProviderConfigEnabledModel.ts`

Each file has one primary export matching its filename:

```ts
validateProviderConfigBaseUrl(baseUrl)
// -> {valid: true, normalizedBaseUrl} | {valid: false, reason: "invalid-base-url"}

validateProviderConfigAuthentication(config, isOAuthSignedIn)
// -> {valid: true} | {valid: false, reason: "api-key-required" | "oauth-sign-in-required"}

validateProviderConfigEnabledModel(config)
// -> {valid: true} | {valid: false, reason: "enabled-model-required"}
```

Implementation details:

- Base URL validation must call core `validateProviderBaseUrl`, catch its exception, and expose the normalized URL on success.
- Authentication validation must use `isOAuthProviderConfig`:
  - API-key providers require `apiKey.trim()`.
  - OAuth providers require the injected `isOAuthSignedIn(config)` result.
- Enabled-model validation requires `model.enabled && model.id.trim()`.
- Return semantic reason codes, not toasts or `ProviderConfigValidationIssue` objects. This allows each consumer to map the same rule to its own UX.
- Keep these helpers UI-local because live OAuth sign-in state is modal state, not a core persisted-domain concern.
- Keep each validator's result/reason type beside its method unless another file needs to import that type; export only the types required to type consumers.

### 4.2 Move comprehensive save validation into the folder

Add `src/ui/pages/ProviderConfigModal/validation/validateProviderConfigs.ts` and move `validateProviderConfigs` into it.

Preserve its existing signature, issue ordering, messages, `editorKey`, `field`, and `modelIndex` behavior. Refactor only the overlapping checks to call the shared validators:

- Base URL result maps to the existing `baseUrl` issue. Use its normalized value to enforce `DEFAULT_CODEX_BASE_URL` for OAuth configs.
- Authentication reason maps to either the existing `apiKey` or `authentication` issue.
- Enabled-model reason maps to the existing non-indexed `models` issue.

Keep aggregate and form-addressing rules in this file:

- At least one configuration.
- Required and case-insensitively unique names.
- Supported provider type.
- Fixed Codex URL.
- Blank and duplicate model IDs, including model indexes.

Do not replace this validator with Zod parsing. The core schema remains an independent persistence safety boundary.

### 4.3 Add action-specific validation using shared rules

Add `src/ui/pages/ProviderConfigModal/validation/getProviderConfigActionValidationMessage.ts` with a single primary pure export matching the filename:

```ts
getProviderConfigActionValidationMessage(config, {
  isOAuthSignedIn,
  requireEnabledModel,
}): string | null
```

Apply checks in the current precedence order:

1. Base URL.
2. Authentication/API key.
3. Enabled model only when requested.

Map semantic failures to the current concise messages:

- Invalid URL: `Enter a valid Base URL first.`
- Missing API key: `Enter an API key first.`
- Missing OAuth sign-in: `Sign in first.`
- Missing enabled model: `Enable at least one model first.`

This function must not call comprehensive save validation or select an issue from its array; doing that would couple action UX to save validation order and irrelevant fields such as configuration name.

Update `src/ui/pages/ProviderConfigModal/useProviderConfigActions.ts`:

- Remove the inline `validateAction` callback.
- Use the pure action validator with `requireEnabledModel: false` for Fetch Models and `true` for Test.
- Preserve all loading state, notifications, OAuth client access/change capture, model merging, and error handling.
- Update React callback dependencies to include the inputs used by the imported validation call.

Intentional behavior alignment: action preflight will now reject URL query strings and fragments immediately, matching core/save validation, instead of allowing an operation that cannot later be persisted or accepted by runtime validation.

### 4.4 Add a validation barrel

Add `src/ui/pages/ProviderConfigModal/validation/index.ts` and export the two consumer-facing APIs:

- `validateProviderConfigs`
- `getProviderConfigActionValidationMessage` (and its options type, if exported)

Keep low-level field validators out of the barrel unless production code outside the validation folder needs them. Validation modules and focused tests can import their method-named files directly. This limits the modal module's public validation surface.

### 4.5 Move persistence mapping to a method-named file

Add `src/ui/pages/ProviderConfigModal/toPersistedProviderConfigs.ts` and move the method there without changing its behavior:

- Strip `editorKey`.
- Trim names, API keys, and model IDs.
- Normalize URLs through core `validateProviderBaseUrl`.
- Preserve OAuth storage and the provider discriminated-union shape.

Update `useProviderConfigPersistence.ts` to import save validation from `./validation` and mapping from `./toPersistedProviderConfigs`. Preserve validation-before-mapping order because the mapper may throw on an invalid URL.

### 4.6 Move dirty-state serialization to a method-named file

Add `src/ui/pages/ProviderConfigModal/getProviderConfigsSnapshot.ts` and move the method there unchanged.

Update direct imports in:

- `src/ui/pages/ProviderConfigModal/ProviderConfigModal.tsx`
- `src/ui/pages/ProviderConfigModal/useProviderConfigDrafts.ts`

The snapshot must strip only `editorKey` and retain raw draft whitespace, credentials, model state, and OAuth storage. It must not use the persistence mapper, because normalization could make a real draft edit appear unchanged.

### 4.7 Update exports and remove the mixed module

Update `src/ui/pages/ProviderConfigModal/index.ts` so its existing symbols remain available from the module barrel, but originate from their focused modules:

- `validateProviderConfigs` from `./validation`
- `toPersistedProviderConfigs` from `./toPersistedProviderConfigs`
- `getProviderConfigsSnapshot` from `./getProviderConfigsSnapshot`

Delete `src/ui/pages/ProviderConfigModal/providerConfigValidation.ts` after all repository imports and tests are migrated. No compatibility shim is needed for this internal deep path unless implementation-time search discovers an undocumented consumer.

### 4.8 Dependency direction and unchanged areas

Maintain this direction:

```text
core URL validator/types/constants
  -> method-named modal field validators
     -> save validation -> persistence hook
     -> action validation -> actions hook

modal types -> toPersistedProviderConfigs -> persistence hook
modal types -> getProviderConfigsSnapshot -> drafts hook/modal
```

Do not modify:

- `JinaWebToolsWarning.tsx`
- `OAuthSignInSection.tsx`
- OAuth lifecycle/storage behavior
- Core Zod schemas or repository validation
- Modal JSX structure or styling
- Save focus/highlight behavior
