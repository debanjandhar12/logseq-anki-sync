## 1. User Requirement

After adding several e2e test cases in 14e4bdfb, I think several of the unit cases are not required anymore since the e2e cases cover them. Can you check and delete those case / test file?

## 2. Final Requirement After Discussion With User

### Clarification Q&A

- Question: "I found overlap in chat UI, branching, attachments, and tool execution. Should I remove unit cases when the e2e tests verify the same user-visible behavior, while keeping unit-only edge cases, error paths, race conditions, and exact internal contracts?"
- Answer: **Broader removal** — "Also remove happy-path unit checks where e2e exercises the code without verifying every internal assertion."

### Final Summarized Requirements

- Remove normal-flow unit coverage superseded by the scenarios in `14e4bdfb`, including checks whose internal details are exercised but not explicitly asserted by e2e.
- Preserve distinct failure, cancellation, concurrency, malformed-input, fallback, and recovery coverage.
- Recommended scope: **58 expanded cases removed, two test files deleted, 27 surviving files modified**. Additionally simplify one mixed success/error case without removing its error coverage.
- Do not change production code, existing e2e cases, test configuration, shared helpers, or documentation. Do not touch pre-existing `.vitest` changes or resurrect helper tests deleted after the cited commit.

## 3. Existing System

### Coverage and execution

- `14e4bdfb` introduced seven `tests/scenario/ai-chat-modal/*.e2e.test.tsx` files with **54 expanded scenarios**. Many other changes in that commit merely rename existing integration tests into the e2e project; they are not newly authored coverage.
- Current inspected HEAD is `7e32f4e`, after helper-test cleanup. Source and relevant tests are clean; existing unrelated changes affect `.vitest` artifacts.
- Scenario fixtures mount the actual AI chat modal, assistant-ui runtime, `runLocalAISDKChatModel`, tool registry/executor, history adapters, and transaction commands.
- The LLM is a scripted model; title generation is deterministic; thread storage uses real `ThreadStore` logic backed by an isolated `InMemoryStore`. Graph mutation, rollback, and review use a real Logseq DB graph through the HTTP proxy.
- `vite.config.ts` selects jsdom for `unit` and headless Playwright Chromium for `e2e`. File parallelism is enabled. `tests/setup.ts` initializes the proxy/storage; some legacy tests skip without Logseq, whereas scenario fixtures require a live DB graph.
- `package.json` provides `test:unit`, `test:e2e`, and Biome `check:fix`; supported Node is `>=22.12 <23`.

### Relevant data flow

- Sending/editing/refreshing: UI -> assistant-ui runtime -> real AI SDK adapter -> scripted provider -> tool execution/continuation -> history adapter -> persisted message repository.
- Mutations: registered Logseq tool -> transaction tracker -> actual reversible command -> live graph. Tool artifacts serialize tracker state alongside public results.
- Branch switching/review: applied-change guard -> confirmation/revert -> tracker artifact persistence; successful commits lock the committed prefix, while no-change commits do not.
- Therefore normal rendering, persistence, attachment classification, commit lifecycle, and sequential execution are covered across real integrations, rather than solely through mocked unit boundaries.

- Mixed non-text/multipart edit extraction, thread subscription rebinding/cleanup and same-mounted-component start/stop, explicit null/undefined tracker inputs and tracker-only fallback.

- Commit execution failure, equal snapshots despite retained commands, clear/revert failures, read-only summaries, pending-run termination and synthetic-discard ordering.

- All unrelated transaction/command/provider/parser/export/prompt suites.
