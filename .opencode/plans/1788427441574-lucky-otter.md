# Automatic Web Tool Selection

## 1. User Requirement

Currently, the way web search tool is setup is a mess. Earlier, there could be only one provider. Now, multiple provider config can exist. This made web search tool setup confusing for user. We need to fix this.
First, in setting, we will mark Jina.ai api as optional. We will remove the select box (webToolsProvider).
Next, in ProviderConfigModal:
For providers other than codex, google and openai, we will display a warning box if Jina ai api key is not provided:
> The web_search tool will be disabled unless jina ai api key is provided.
(use groupName for the tool name)

The actual logic will be modified such that we will add the tool if jina ai api key is provided.

I think this will be more user friendly. If you can think of better ways, suggest.

## 2. Final Requirement After Discussion With User

### 2.1 Clarification Q&A

- Q: After removing `webToolsProvider`, should tool selection be automatic: OpenAI/Codex use native `web_search`, Google uses native `google_search` plus `url_context`, and unsupported providers use Jina only when its key exists?
  - A: Yes, use that automatic matrix.
- Q: What does “use groupName for the tool name” mean, given that no web-tool `groupName` exists?
  - A: This meant the canonical tool-name variable on `WebSearchTool`; in the current code that symbol is `WebSearchTool.NAME`.
- Q: Should the old persisted `webToolsProvider` setting be migrated or removed from stored settings?
  - A: No. Ignore it; migration is unnecessary because this plugin version has not been released.

### 2.2 Final Summarized Requirements

- Remove the `webToolsProvider` setting and `WebToolsProviderEnum`; any stale value is ignored without migration.
- Keep `jinaApiKey` as an always-visible, optional global setting and explain when it is used.
- Select web tools automatically per request from the selected model's provider configuration:
  - OpenAI: native `web_search`.
  - Codex Subscription: OAuth-backed native `web_search`.
  - Google: native `google_search` and `url_context`.
  - Every other/future non-native provider: Jina `web_search` and `web_page_get` only when `jinaApiKey.trim()` is non-empty.
- In `ProviderConfigModal`, show a non-blocking warning for the active draft when its provider lacks native web tools and the Jina key is blank. Build the displayed tool name from `WebSearchTool.NAME`, not another string literal.
- Ensure changing the selected provider or Jina key affects the next request without rebuilding/remounting the chat registry.
- Update tests and provider documentation.

## 3. Existing System

- `src/settings.ts` defines `PluginSettings.webToolsProvider`, renders a three-choice selector, labels the Jina key mandatory, and dynamically hides that key unless Jina is selected.
- `src/core/ai-sdk/types.ts` defines `WebToolsProviderEnum` using user-facing strings as persisted values.
- `src/core/ai-sdk/getLLMProviderTools.ts` already creates the correct native tools for OpenAI, Codex, and Google, but only behind the global `MODEL_NATIVE` selection. OpenAI Compatible returns no native tools.
- `src/chat-app/tools/ToolRegistry.ts` currently registers Jina's `WebSearchTool` and `WebPageGetTool` only when the global selector equals Jina. `ChatToolRegistryProvider` memoizes this registry for the mounted chat lifetime, so settings-driven registration can become stale.
- `src/chat-app/runtime/LocalChatModelAdapter/runLocalAISDKChatModel.ts` resolves the exact selected provider configuration on every request, merges Assistant UI frontend tool definitions with provider-native tools, and later plans frontend execution from the original unfiltered definitions.
- The Jina and OpenAI/Codex tools share the public name `web_search`. Provider tools currently win merge collisions, but stale frontend definitions can still be exposed or planned incorrectly.
- `WebSearchTool.NAME` and `WebPageGetTool.NAME` are the canonical frontend tool-name constants. Both Jina executors currently accept whitespace-only keys and use untrimmed key values.
- `ProviderConfigModal` uses discriminated `ProviderTypeEnum` drafts. Its active draft can differ from the provider selected by chat, so the draft may inform the modal warning but must never drive runtime tools.
- There is no generic alert component. Existing modal styling supports an inline `role="alert"` box with amber border/background/text classes.
- Existing tests cover native tool factories and basic registry behavior, but do not cover this automatic matrix, Jina key gating, or the modal warning.

## 4. Solution

### 4.1 Simplify plugin settings

Modify `src/settings.ts`:

- Remove `PluginSettings.webToolsProvider` and the `WebToolsProviderEnum` import.
- Delete the `webToolsProvider` schema entry.
- Keep `webToolsHeading` and `jinaApiKey`, changing the title to indicate “Optional” and the description to explain that Jina enables web tools for providers without native web support.
- Remove `applySettingsVisibility`, its initial call, and its settings listener so the key is always visible.
- Preserve the independent debug listener and CSS hiding internal `providerConfigSetting` storage.

Modify `src/core/ai-sdk/types.ts`:

- Remove `WebToolsProviderEnum` entirely. No migration or settings cleanup is added.

### 4.2 Make native tools unconditional for supported providers

Modify `getLLMProviderTools` in `src/core/ai-sdk/getLLMProviderTools.ts`:

- Remove its `webToolsProvider` gate and enum import.
- Continue accepting an already resolved selection, with the current persisted-selection fallback for direct callers.
- Preserve existing provider client construction and credentials:
  - OpenAI returns native `web_search`.
  - Codex returns OAuth-authenticated native `web_search`.
  - Google returns native `google_search` and `url_context`.
  - All other provider types return `{}`.

This decision remains based on `resolvedSelection.config.type`, so duplicate model IDs across configurations and multiple provider configs remain correct.

### 4.3 Centralize Jina eligibility and filter at request time

Add `src/chat-app/tools/providerWebToolsPolicy.ts` as the single policy boundary. It will:

- Identify native providers (`OPENAI`, `GOOGLE`, `CODEX_SUBSCRIPTION`). Any other current or future provider type is treated as non-native.
- Normalize key availability with `jinaApiKey?.trim()`.
- Filter only the Jina definitions named by `WebSearchTool.NAME` and `WebPageGetTool.NAME`; all unrelated frontend tools pass through unchanged.
- Retain Jina definitions only for a non-native provider with a usable key.
- Expose the small predicates needed by the modal warning so UI and runtime cannot drift.

Modify `src/chat-app/tools/ToolRegistry.ts`:

- Remove settings and enum dependencies.
- Always register `WebSearchTool` and `WebPageGetTool` as stable Assistant UI catalog entries. This keeps renderer/metadata support for historical tool calls.
- Do not interpret catalog registration as runtime availability; availability is enforced by the request policy.

`ChatToolRegistryProvider.tsx` needs no settings subscription or rebuild. Its static memoization becomes intentional because eligibility is no longer captured there.

Modify `runLocalAISDKChatModel` in `src/chat-app/runtime/LocalChatModelAdapter/runLocalAISDKChatModel.ts`:

1. Resolve the selected provider as it does now.
2. Read the latest `jinaApiKey` through `LogseqSettingAccessor` for that request.
3. Filter `context.tools` through the shared policy using the resolved provider type and current key.
4. Build the model tool set from those effective frontend definitions plus `getLLMProviderTools(resolvedSelection)`.
5. Pass the same effective frontend definitions to `planFrontendToolCalls`, rather than the original `context.tools`.

Using the same map for AI SDK conversion and frontend planning prevents an unavailable tool from either being advertised or executed. Native providers never receive Jina tools, eliminating `web_search` collisions instead of relying on merge order.

### 4.4 Normalize Jina credentials at execution

Modify:

- `src/chat-app/tools/impl/WebSearchTool.tsx`
- `src/chat-app/tools/impl/WebPageGetTool.tsx`

In both executors, trim `jinaApiKey` before checking it and before building the Bearer header. Undefined, empty, and whitespace-only values are all absent. Preserve endpoints, request parameters, abort signals, response shapes, and existing HTTP/network error behavior. Update the missing-key message to refer to the visible Jina AI API Key setting rather than the nonexistent `JINA_API_KEY` setting name.

### 4.5 Add the provider-modal warning

Add a focused `src/ui/pages/ProviderConfigModal/JinaWebToolsWarning.tsx` and render it from `ProviderConfigModal.tsx` near the provider/API-key controls, before model configuration.

- Inputs: active draft provider type and current Jina key.
- Use the shared provider predicate and trimmed-key predicate.
- Render nothing for OpenAI, Google, or Codex, regardless of Jina key.
- For every other provider, render only when the key is absent.
- Use a compact amber box with `role="alert"`; it is informational and must not enter validation or block Save.
- Construct the requested text with the canonical constant:

```tsx
`The ${WebSearchTool.NAME} tool will be disabled unless jina ai api key is provided.`
```

Read settings through `LogseqSettingAccessor`, not direct `logseq.settings`. Subscribe with `registerSettingsChangeListener` and clean up on unmount so an already-open modal reflects an external key change. Provider-type changes update immediately from the active draft.

The modal uses only its active draft for warning presentation. Runtime continues using the persisted provider selected by the chat request; unsaved/modal-inactive drafts cannot alter chat behavior.

### 4.6 Update documentation

Update `docusaurus/docs/providers/provider-configurations.md` to replace global selector instructions with the automatic matrix, explain that the Jina key is optional and global, and state that non-native providers have no web tools when the key is absent. Document both Jina tools and clarify that request-time selected provider configuration controls behavior.
