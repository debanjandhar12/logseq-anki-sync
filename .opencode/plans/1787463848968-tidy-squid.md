# Invalid Frontmatter Markers in SkillEditorModal

## 1. User Requirement

In SkillEditorModal, could we add a marker for invalid frontmatter similar to invalid mustache variables?

## 2. Final Requirement After Discussion With User

### 2.1 Clarification Q&A

- **Q:** Should the frontmatter marker match the existing Mustache behavior: an inline red squiggle, lint-gutter icon, and hover message in CodeMirror?
  **A:** Match Mustache.
- **Q:** Which frontmatter problems should receive markers: all save-blocking issues or YAML syntax only?
  **A:** Whichever is easier to code and easier to maintain.
- **Resolution:** Mark all per-file frontmatter failures already enforced by skill parsing. A shared structured validator keeps live linting and save-time parsing consistent and is less likely to drift than a separate YAML-syntax-only validator.

### 2.2 Final Summarized Requirements

- Show invalid skill frontmatter through the same CodeMirror UX as invalid Mustache variables: red inline range, lint-gutter marker, and hover diagnostic.
- Diagnose malformed or missing frontmatter, missing/empty required `name` and `description`, and non-boolean values for the three supported boolean fields.
- Continue accepting unknown frontmatter fields.
- Keep filename validity and duplicate skill-name checks at save time because they are not frontmatter parsing concerns and duplicate names require cross-file context.
- Allow Mustache and frontmatter diagnostics to coexist, while keeping the existing Mustache-first save validation order.
- Reuse one authoritative set of parsing rules and install only one editor lint gutter.
- Do not add a file-list badge or custom diagnostic styling.

## 3. Existing System

- `src/ui/pages/SkillEditorModal/SkillEditorModal.tsx` renders `LogseqCodeEditor` with the static extensions returned by `createSkillEditorExtensions()`. No component-state change is needed for document-local linting.
- `src/ui/pages/SkillEditorModal/createSkillEditorExtensions.ts` composes YAML-frontmatter Markdown support, frontmatter/Mustache/Markdown completion, and `createMustacheLintExtensions(validateMustacheTemplate)`.
- `src/ui/components/LogseqCodeEditor/extensions/mustache.ts` adapts `{from, to, message}` issues into CodeMirror error diagnostics and also installs `lintGutter()`. CodeMirror supplies the current squiggle, gutter icon, and hover UI; there is no project-specific lint CSS.
- `src/ui/components/LogseqCodeEditor/extensions/yamlFrontmatter.ts` supplies YAML language support, completion, and `getFrontmatterRange()`, but no validation.
- `src/core/skill-parser/parseSkillFile.ts` is the current save/storage authority. It uses `gray-matter`, requires non-empty string `name` and `description`, checks three optional boolean fields, accepts unknown keys, and throws plain errors without diagnostic ranges.
- `src/ui/pages/SkillEditorModal/utils/validateSkillFiles.ts` first rejects Mustache issues across files, then calls `parseSkillFile()`, validates derived filenames, and detects duplicate names. This order and issue taxonomy should remain unchanged.
- `gray-matter` parses YAML with `js-yaml`; YAML exceptions can expose a parser-local `mark.position`. This must be mapped to the original CodeMirror document without normalizing LF/CRLF and must have a bounded fallback.
- Current tests cover parser rules, frontmatter completion, and save validation, but not frontmatter lint diagnostics. The expected skill-authoring documentation source is absent, so this focused editor behavior does not have a viable existing documentation page to update.

## 4. Solution

### 4.1 Introduce structured, authoritative skill-file validation

Add `src/core/skill-parser/validateSkillFileContent.ts` as a focused module containing the diagnostic types, frontmatter boundary/range helpers, YAML parsing, and metadata validation. Keep `parseSkillFile.ts` focused on its existing parse-or-throw API while sharing the new validation logic across the parser and editor. The new module will export a diagnostic issue type and validator such as:

```ts
interface SkillFileValidationIssue {
    from: number;
    to: number;
    message: string;
}

type SkillFileValidationResult =
    | {valid: true; skillFile: SkillFileData; issues: readonly []}
    | {valid: false; skillFile: null; issues: readonly SkillFileValidationIssue[]};
```

Export `validateSkillFileContent(content)` from the new module. Modify `src/core/skill-parser/parseSkillFile.ts` to call it as a compatibility wrapper that returns the valid `SkillFileData` or throws the first issue message. This preserves existing callers and messages while avoiding diagnostic/range responsibilities in the parser entry-point file.

Validation flow:

1. Detect the frontmatter body and its absolute source start while preserving the original string offsets and LF/CRLF endings.
2. If no opening frontmatter exists, return a structure issue marking the first line (or `{0, 0}` for an empty document).
3. Parse with the same `gray-matter` implementation used today. On YAML errors, use a structurally narrowed `reason` and `mark.position` when available; map the local YAML offset into the document and mark its logical line. Clamp every range to `0 <= from <= to <= content.length`; fall back to the opening delimiter/first frontmatter line when parser location data is absent or invalid.
4. After successful YAML parsing, apply the existing metadata rules in their existing deterministic order: `name`, `description`, `built-in-skill`, `built-in-skill-user-controllable`, then `disable-model-invocation`.
5. For a present invalid field, mark its top-level declaration line. For a missing required field, mark the opening delimiter because no field token exists. Use a conservative top-level key locator and a bounded delimiter fallback rather than attempting fragile token-level YAML reconstruction.
6. Preserve trimmed returned `name`/`description`, optional booleans, original `content`, accepted unknown fields, and existing public error text.

Collect all semantic metadata issues for the editor, but have `parseSkillFile()` throw only the first so save behavior remains fail-fast. A YAML parse failure returns one syntax issue because semantic data is not trustworthy in that state.

Do not broaden validity beyond the existing parser contract as part of this marker feature. In particular, avoid making an otherwise parser-accepted missing closing delimiter a new compatibility-breaking save rule unless `gray-matter` already fails on its contents; its resulting parse issue will still be marked. Tests should characterize this behavior.

### 4.2 Separate lint sources from the shared gutter

Refactor `src/ui/components/LogseqCodeEditor/extensions/mustache.ts` so its lint adapter returns only the Mustache `linter(...)` extension (for example, rename it to `createMustacheLinter`) and retains the current 300 ms delay, error severity, source label, ranges, and messages. Remove `lintGutter()` ownership from this source-specific helper.

Extend `src/ui/components/LogseqCodeEditor/extensions/yamlFrontmatter.ts` with a structurally typed frontmatter issue interface and `createFrontmatterLinter(validate, delay?)`. It will read the complete CodeMirror document, map returned issues to `severity: "error"` and `source: "Frontmatter"`, and return only a `linter(...)` extension. Keep this generic editor module independent from the skill parser by injecting the validator callback.

Update `src/ui/components/LogseqCodeEditor/extensions/index.ts` exports for the renamed Mustache factory and new frontmatter linter/type. Verify there are no other consumers before removing the old factory export; if a consumer is discovered during implementation, retain a compatibility wrapper while ensuring SkillEditorModal does not install a second gutter.

### 4.3 Compose both diagnostic sources in SkillEditorModal

Modify `src/ui/pages/SkillEditorModal/createSkillEditorExtensions.ts` to:

- import `validateSkillFileContent` from its dedicated skill-parser module, both source-specific linters, and `lintGutter`;
- adapt `validateSkillFileContent(source).issues` for the frontmatter linter;
- install the Mustache linter and frontmatter linter independently so both issue sets can appear in the same document;
- install exactly one editor-wide `lintGutter()` after the two linters, with a short comment explaining that the gutter is shared.

No changes are required in `SkillEditorModal.tsx`, its file-list state, or CSS. Built-in read-only files use the same extensions and can display diagnostics without becoming editable.

### 4.4 Preserve save validation behavior

Keep `src/ui/pages/SkillEditorModal/utils/validateSkillFiles.ts` structurally unchanged. Its existing `parseSkillFile()` call will use the shared validator automatically. Preserve:

- Mustache-first save rejection;
- frontmatter failures as `parse-error`;
- derived filename and duplicate-name checks after successful parsing;
- selection/toast behavior in `SkillEditorModal.tsx`.

Live linting may show both Mustache and frontmatter errors simultaneously even though save reports the first Mustache issue. That is intentional: editor diagnostics help fix all visible local problems, while save compatibility remains unchanged.

### 4.5 Add focused tests

Add `tests/src/core/skill-parser/validateSkillFileContent.test.ts` for structured validation and diagnostic-range behavior, while expanding `parseSkillFile.test.ts` only for parse-or-throw compatibility:

- valid LF and CRLF frontmatter;
- missing frontmatter and empty input;
- malformed YAML and duplicate keys with useful, bounded ranges;
- missing, empty, and non-string `name`/`description`;
- invalid values for each optional boolean field;
- multiple semantic issues in the validator and deterministic first-error behavior in `parseSkillFile()`;
- accepted unknown fields;
- field-line positioning, parser-location fallback, non-ASCII text, and LF/CRLF offset safety;
- current missing-closing-delimiter behavior, ensuring the lint feature does not silently introduce a new save contract.

Extend `tests/src/ui/components/LogseqCodeEditor/extensions/mustache.test.ts` and `yamlFrontmatter.test.ts` (or add one narrowly scoped lint-composition test beside them) to verify diagnostic adaptation: source labels, error severity, messages, and ranges. Add an `EditorView` integration assertion where practical that production Skill Editor extensions expose both diagnostic types and render exactly one lint gutter. Use a zero delay or CodeMirror's explicit lint trigger to avoid timer-dependent tests.

Expand `tests/src/ui/pages/SkillEditorModal/validateSkillFiles.test.ts` with regressions that malformed YAML/metadata remains a `parse-error`, unknown fields remain valid, and Mustache still wins when both issue types exist.
