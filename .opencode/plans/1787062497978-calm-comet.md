# Vite 8.2.1 Upgrade and Build Performance Plan

## 1. User Requirement

I need you to upgrade the current vite version to ^8.2.1. Check dependency impact and vite plugins impact.
Aditionally, vite build is taking a lot of time. This is likely due to wasm building this. Any way to reduce this time / fix it?
Note: I want wasm as well after build is done.

## 2. Final Requirement After Discussion With User

### 2.1 Clarification Q&A

1. **How should build speed be optimized while preserving the emitted WASM asset?**
   - Answer: Keep release behavior unchanged. Do not introduce a separate fast build or remove release functionality.
2. **Are production source maps required in packaged releases?**
   - Answer: Yes. Keep source maps enabled for every production build.
3. **May the root project and CI be standardized on Node 22?**
   - Answer: Yes. Standardize on Node 22; Vite 8 requires Node 20.19+ or 22.12+, and existing AI SDK dependencies already require Node 22.
4. **Should the standalone `docusaurus/vite.config.ts` be included?**
   - Answer: No. Limit this work to the root plugin build; the Docusaurus config is not used by its current webpack-based build.

### 2.2 Final Summarized Requirements

- Upgrade the root plugin build from Vite `^7.3.3` to `^8.2.1` and regenerate the pnpm lockfile.
- Upgrade or align Vite-coupled dependencies and plugins so their declared peer ranges support Vite 8.
- Adapt custom Vite plugins to Vite 8/Rolldown behavior and test the high-risk plugin paths.
- Preserve the current production contract: minified JavaScript/CSS, production source maps, relative URLs, and a standalone emitted AnyDoc WASM file in `dist` and release archives.
- Improve build time without compiling, removing, inlining, or omitting WASM and without weakening release diagnostics.
- Standardize the root/plugin development and CI runtime on Node 22.12 or newer within Node 22.
- Do not migrate the unrelated Docusaurus Vite config, remove unrelated dependencies, or perform broad application code splitting in this upgrade.

## 3. Existing System

### 3.1 Build and dependency state

- `package.json` uses Vite `^7.3.3`; `pnpm-lock.yaml` resolves the root to 7.3.3 and also contains a Vitest-owned Vite 7 installation.
- Vite-coupled packages are currently inconsistent:
  - `@vitejs/plugin-react ^4.5.1` declares support only through older Vite majors.
  - `vite-plugin-node-polyfills 0.8.2` declares support only through Vite 4.
  - `vitest ^4.0.18` does not support Vite 8, while `@vitest/browser` and `@vitest/ui` are still on mismatched 3.x releases.
  - `@tailwindcss/vite 4.3.2` already declares Vite 5-8 compatibility.
  - Direct `esbuild ^0.27.3` is compatible with Vite 8's optional peer range and remains required by `bundleJSStringPlugin` even after Vite itself moves to Oxc.
- Vite 8.2.1 requires Node `^20.19.0 || >=22.12.0`. The repository does not declare an engine/version file; plugin workflows currently use Node 20 and 22 inconsistently.
- `vite.config.ts` keeps `base: "./"`, `target: "esnext"`, `sourcemap: true`, `minify: "esbuild"`, and `emptyOutDir: true`.
- Vite 8 replaces Rollup/esbuild internals with Rolldown/Oxc. Explicit esbuild minification remains temporarily supported but is deprecated; Oxc is the supported default minifier.

### 3.2 WASM data flow and actual cost

- `src/core/anydoc/AnyDocPdfParser.ts` imports the package glue and imports `anydoc_wasm_bg.wasm?url`.
- `@firecrawl/anydoc-wasm` ships a precompiled 6,485,379-byte WASM binary. The repository has no Rust, Cargo, `wasm-pack`, or `wasm-opt` build step.
- The current package WASM and `dist/assets/anydoc_wasm_bg-*.wasm` are byte-identical. Vite only reads, hashes, names, and copies the binary; it does not compile or transform it.
- Runtime initialization is lazy and shared by `AnyDocPdfParser`; this behavior is already unit-tested and is separate from production build duration.
- Current output is approximately 8.97 MB of minified JavaScript, a 23.25 MB source map containing 1,415 sources, 6.49 MB of WASM, and 106 KB of CSS. The source map does not embed the WASM.
- The more plausible build costs are transforming/minifying one large JavaScript graph, generating/writing the large required source map, gzip size reporting, and custom transforms. WASM hashing/copying is comparatively small and must remain.

### 3.3 Plugin impact

- `inlineSkillFilePlugin` converts `.md?inlineSkill` content into JavaScript from its `load` hook. Vite 8 auto-detects module type from the original extension, so both successful return paths must explicitly return `moduleType: "js"`.
- `staticFileSyncTransformPlugin` is invoked broadly, then Babel-parses matching modules, makes three AST traversals, and generates a map. Vite 8/Rolldown supports hook filters that can reject unrelated IDs/code before crossing into the JavaScript hook; the three visitors can also be combined without changing output semantics.
- `bundleJSStringPlugin` directly uses an esbuild context. It currently has no repository consumer, but it must remain compatible and is the reason `esbuild` cannot be removed.
- `logseqDevPlugin`, `rewriteDistReqToRootPlugin`, and `@vitejs/plugin-react` are development-only. Their middleware, module graph, HMR, and React Refresh behavior requires a Logseq development smoke test after the upgrade.
- React/Floating UI bridge plugins and node polyfills use supported plugin concepts, but Rolldown resolution/CommonJS changes require production runtime validation. In particular, validate `just-bash` and browser Node polyfills.
- Vite 8 also changes CommonJS default import handling, package-field resolution, JavaScript transforms, and default CSS minification. Do not enable legacy compatibility preemptively; diagnose and address a concrete dependency if one fails.

### 3.4 Verification constraints

- Existing unit tests mock the AnyDoc package/URL, so they verify lazy runtime initialization but not actual Vite asset emission.
- `tsconfig.json` excludes `vite.config.ts` and `vite-plugins/**`; a successful config load/build and focused plugin tests are necessary in addition to `tsc --noEmit`.
- Release packaging in `.github/workflows/publish.yml` moves all of `dist` into the ZIP, so emitted WASM and maps should be verified both in `dist` and in the packaged layout.
- Some full tests use a running Logseq API at `127.0.0.1:12315`.

## 4. Solution

### 4.1 Establish an evidence-based performance and artifact baseline

Before modifying dependencies or configuration:

1. Run at least three clean `pnpm build` measurements and record median wall time, Node/pnpm versions, peak memory when available, and output inventory/sizes.
2. Record hashes for diagnostics, treating byte equality as a requirement only for the precompiled WASM. Rolldown/Oxc will legitimately change JS, CSS, and map hashes.
3. Record the current WASM source/output SHA-256 equality, `dist/index.html` relative references, JavaScript WASM URL reference, source-map size/structure, and compressed-size-reporting time.

This distinguishes actual gains from cache warmth and prevents attributing the existing delay to nonexistent WASM compilation.

### 4.2 Upgrade and align the Vite toolchain

Modify `package.json` and regenerate `pnpm-lock.yaml`:

- Set `vite` to `^8.2.1`.
- Upgrade `@vitejs/plugin-react` to `^6.0.5`, the Vite-8-native Rolldown/Oxc release.
- Upgrade `vite-plugin-node-polyfills` to `^0.28.0`, whose peer range includes Vite 8.
- Align `vitest`, `@vitest/ui`, and `@vitest/browser` to the same concrete Vite-8-compatible 4.1.x patch (use `4.1.11` if it remains the current mutually published patch at implementation time). Avoid mixed 3.x/4.x copies.
- Retain `@tailwindcss/vite 4.3.2`, `esbuild ^0.27.3`, Sass, and TypeScript unless installation/build output reveals a concrete incompatibility. Direct esbuild is application tooling, not a stale transitive Vite dependency.
- Inspect the regenerated lockfile to confirm all peer snapshots resolve against Vite 8, no Vitest 3.x packages remain, and no unintended second root Vite major is installed.

Do not update `docusaurus/package.json`, `docusaurus/pnpm-lock.yaml`, or `docusaurus/vite.config.ts`.

### 4.3 Declare and align the Node runtime

- Add `engines.node: ">=22.12 <23"` to root `package.json`.
- Add root `mise.toml` selecting Node 22.
- Keep `.github/workflows/test.yml` on Node 22 and change `.github/workflows/publish.yml` from Node 20 to Node 22. Leave the Docusaurus workflow unchanged because it is a separate dependency/build scope.
- Use a frozen root lockfile install in plugin CI once the regenerated lockfile is committed, so Vite/plugin peer resolution is reproducible.
- Align the root test and publish workflows on pnpm 10 because pnpm 9 rejects the regenerated pnpm-10 lockfile's workspace override metadata in frozen mode.

### 4.4 Migrate custom plugins for Vite 8

#### `vite-plugins/inlineSkillFilePlugin.ts`

- Add `moduleType: "js"` to both successful `load` results. Preserve `map: null`, include expansion, missing-root behavior, and missing-include warning/empty substitution.
- Validate the inline-skill loader through the production build after adding Vite 8's required module type.

#### `vite-plugins/staticFileSyncTransformPlugin.ts`

- Express the existing extension and `readFileSync` guards as a Vite 8/Rolldown transform hook filter so unrelated modules are rejected before invoking the JavaScript handler.
- Combine the three Babel traversals into one visitor while preserving operation order where replacements depend on earlier static values. Keep source-map generation because production maps are required.
- Preserve the existing transform semantics while adding Rolldown's native hook filter, then validate through the production build.

#### Other plugins

- Retain `bundleJSStringPlugin` and direct esbuild. Add a focused synthetic `.js?string` plugin test if upgraded types/build do not otherwise exercise its esbuild context, including environment substitutions and emitted bundled-string syntax.
- Do not remove dormant plugins or enable Vite's legacy CommonJS interop as part of the migration. Resolve only demonstrated build/runtime regressions at their source.
- Validate development-only `logseqDevPlugin`, `rewriteDistReqToRootPlugin`, React Refresh, module graph handling, and bridge plugins through dev smoke testing.

### 4.5 Optimize the production build without changing its contract

Modify `vite.config.ts`:

- Keep `sourcemap: true`, `target: "esnext"`, `emptyOutDir: true`, and `base: "./"`.
- Replace deprecated `minify: "esbuild"` with explicit `minify: "oxc"`. This retains minification while using Vite 8's supported, faster native minifier. Keep direct esbuild solely for `bundleJSStringPlugin`.
- Keep `build.reportCompressedSize: true` as requested. Vite will continue reporting gzip sizes even though this adds build time.
- Keep Vite's default asset inline limit. The 6.49 MB AnyDoc binary is well above that limit and remains a standalone emitted asset.
- Retain Vite's native `?url` asset path. Do not move WASM into JavaScript/public assets, base64 encode it, run `wasm-opt`, or add a Rust compilation step.

These changes target measured overhead while maintaining one normal release-quality build. The required source map remains the irreducible major cost unless the product requirement changes later.

### 4.6 Add production artifact verification

- Verify the production artifacts directly after building; do not add a permanent verification script.
- Resolve the installed AnyDoc WASM source, locate exactly one emitted `dist/assets/anydoc_wasm_bg-*.wasm`, and assert byte/hash equality.
- Assert the emitted WASM is referenced by generated JavaScript through a relative asset URL and is not represented as a data URI/inlined payload.
- Parse `dist/index.html` to ensure JS/CSS references remain relative for Logseq's packaged/file loading.
- Parse emitted source-map JSON and assert version 3, nonempty `sources`, `mappings`, and expected `sourcesContent`; verify the JS has a valid `sourceMappingURL` and release artifacts do not expose absolute workspace paths.
- Reproduce or inspect the publish ZIP layout and confirm the WASM and source map remain under `dist/assets`.

### 4.7 Document the supported build environment

- Update `INTERNAL.md` with the Node 22.12+ prerequisite, pnpm build command, the fact that AnyDoc WASM is precompiled and copied as a standalone hashed asset, and the artifact verification command.
- Avoid broad edits to the stale product-facing README or Docusaurus during this toolchain migration.

## 5. Verification

### 5.1 Dependency and static checks

1. Regenerate dependencies with pnpm 10, then run `pnpm install --frozen-lockfile` in the same pnpm major used by both root workflows.
2. Inspect `pnpm list vite vitest @vitest/ui @vitest/browser @vitejs/plugin-react vite-plugin-node-polyfills` and lockfile peer snapshots for Vite 8 and synchronized Vitest versions.
3. Run `npx tsc --noEmit`.
4. Run focused plugin tests, then `pnpm test --run --reporter=dot --silent` (with the Logseq API test environment when required).
5. Run `pnpm run check:fix <each modified source/config/test/script file> --reporter=summary`, followed by a non-writing Biome check if needed.

### 5.2 Build correctness and performance

1. Run at least three clean and three warm `pnpm build` measurements under the same environment as the baseline; compare medians and peak memory.
2. If feasible, run one updated-build control with compressed-size reporting temporarily enabled to separate Vite/Rolldown/Oxc gains from skipped terminal gzip reporting.
3. Compare the source and emitted WASM hashes after every final production build.
4. Confirm production output remains minified, includes external source maps, contains a standalone byte-identical WASM asset, and has only relative deployable references.
5. Compare artifact inventory and sizes, not generated JS/CSS hash equality.

### 5.3 Runtime smoke tests

1. Run `pnpm dev` and load the plugin in Logseq Desktop; verify startup, HMR/reload, React Refresh, chat UI rendering, and Shadow DOM/Floating UI overlays.
2. Load the production `dist` in Logseq Desktop and verify plugin startup and core chat behavior.
3. Exercise a node-polyfilled path, especially `just-bash`, to catch Rolldown/CommonJS/polyfill regressions.
4. Parse a small PDF to prove the emitted WASM URL loads through `LogseqHttpProxy`, initializes once, and produces markdown; repeat to verify reuse.
5. Visually inspect representative styled UI to catch Oxc/Lightning CSS output regressions.
6. Reproduce the publish packaging step and inspect the ZIP for `dist/index.html`, minified JS/CSS, source maps, and the standalone WASM asset.

If production behavior fails, diagnose CommonJS/module resolution, bridge aliases, or polyfills individually. Use Vite's legacy CommonJS interop only as a temporary diagnostic, not as the default migration solution.
