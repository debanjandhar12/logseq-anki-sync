# Solution

Recommended vocabulary:

- `temporary Logseq changes`: umbrella state before a commit, covering queued and applied reversible graph mutations.
- `commit changes` / `make changes permanent`: finalization action and explanatory copy.
- `discard temporary changes`: user-facing destructive action.
- `revert temporary changes`: technical undo operation and revert-failure errors.
- `applied temporary changes`: precise branch-guard wording because that guard only operates on mutations already applied to Logseq.
- `queued change commands`: developer-facing diagnostics for tracker commands that have not been applied.

Do not use `pending`, `staged`, or `uncommitted` as the general graph-change state. They are ambiguous or Git-specific. Keep `pending tool calls` for unresolved assistant-runtime protocol calls only.

Proposed source renames:

- `PendingLogseqChangesDisplay` -> `TemporaryLogseqChangesDisplay`, including its file, props, summary helpers, state variables, toolbar import, and targeted test.
- `LogseqClearChangesTool` -> `LogseqClearTemporaryChangesTool`, including its file, args/result types, registry import, barrel export, and direct caller.
- `useLogseqUncommittedChangesBranchGuard` -> `useLogseqTemporaryChangesBranchGuard`; rename its predicate to express that it checks applied temporary graph mutations.

Preserve low-level tracker APIs such as `clear()`, `revert()`, and `revertAppliedCommands()` because they describe specific technical operations, not the product lifecycle.

Rename the serialized tool name from `logseq_clear_changes` to `logseq_clear_temporary_changes`. It is stored in persisted thread messages and is a model/runtime dispatch key, so implementation must include an explicit compatibility migration or normalization strategy for old messages/tool calls.
