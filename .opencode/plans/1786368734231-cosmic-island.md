# Continue-later and generic required-action stop plan

## 1. User Requirement

Currently in CommitTool / AIChangesReviewModalComponent, there is a button to reject changes. However, there is no button to cancel and continue with changes. We need to introduce that feature. Keep the button as ghost and to left side of footer.

When the tool is terminated (by click the stop button),it should behave same as cancel and continue with changes. Aditionally, currently, it seems like the stop button is disabled when we need to review changes: `disabled={requiresActionState}` at `ComposerAction.tsx:58`. This needs to be changed to not be disabled. When it is click, the current tool call should go for abort.

Additional requirement:

I wanted the stop button changes to be generic. For other tool calls that get terminated by the stop button, they should return success false with User terminated the operation.

Review feedback:

I don't like this change at all. First, the success false and user terminated should be generic (I.e. for non human tools which are running) as well. Also, I do not think composer is the right place for this change. Also I do not like your terminatePendingToolCallAndRetainChanges and cancelPendingToolCallsInThread

## 2. Final Requirement After Discussion With User

### 2.1 Clarification Q&A

- Q: Should header Close/Escape abort CommitTool or retain their current behavior?
  - A: Retain current behavior. Header Close/Escape only close the modal; the tool remains in `requires-action` and can be reviewed again.
- Q: What should the new footer action be called?
  - A: **Continue (Commit Later)**.
- Q: Should **Continue (Commit Later)** resume the model after recording a tool result?
  - A: No. End the current assistant turn, retain changes, and wait for a new user message.
- Q: Should composer stop resume the model after recording termination?
  - A: No. End the current assistant turn, retain changes, and wait for a new user message.
- Q: Should the generic `ModalFooter` be extended for the new layout?
  - A: No. Duplicate/specialize the footer for this review modal; do not modify the generic component.
- Q: Must the changes-review modal react to composer stop?
  - A: No. The user cannot interact with the composer stop button while the modal is open.
- Q: Which pending actions should the generic stop behavior cover?
  - A: Every non-running `requires-action` assistant turn, including human tools and approval-gated tools. Cancel every unresolved tool call in that turn.
- Q: Where should generic cancellation be owned?
  - A: Use a project runtime controller rather than patching assistant-ui. Keep orchestration out of `ComposerAction` and remove the current `terminatePendingToolCallAndRetainChanges` / `cancelPendingToolCallsInThread` design.
- Q: Must an active Logseq mutation tool's newly produced tracker artifact be journaled across the narrow post-abort settlement race?
  - A: Choose the lower-code, more maintainable option. Preserve existing artifacts and persisted tracker state, but do not add an adapter settlement journal.

### 2.2 Final Summarized Requirements

- Add a ghost **Continue (Commit Later)** button at the far-left side of the AI changes review footer, using a review-specific footer rather than changing generic `ModalFooter`.
- Clicking it must retain queued uncommitted changes and terminally end the exact pending `logseq_commit_changes` turn without resuming the model.
- Store this tool-call result/message: `success: false` and `error: "Changes not committed. User will commit later. Do not call this tool immediately again without feedback from user"`.
- Keep Commit and destructive Discard unchanged.
- Keep header Close/Escape as defer: close the modal, add no result, and leave CommitTool in `requires-action`.
- Use one project runtime stop controller for active model/tool runs and settled `requires-action` turns. Every unresolved visible tool call in the stopped assistant message receives `success: false` with exact error `"User terminated the operation"`; the message becomes `incomplete/cancelled` and the model does not continue.
- Keep stop orchestration, repository traversal, tool names, and persistence out of `ComposerAction`; expose them through a small `useStopThread` hook.
- Preserve all existing tool artifacts, including already-persisted Logseq reversible trackers. Do not add special CommitTool tracker rewrite logic to generic stop.
- Do not add external abort handling to the review modal. Stop and **Continue (Commit Later)** are separate entry points that share terminal pending-tool cancellation semantics but use their respective messages.

## 3. Existing System

### 3.1 Commit review

- `src/chat-app/tools/impl/LogseqCommitChangesTool.tsx` defines human tool `logseq_commit_changes`. LocalRuntime settles the assistant turn in `requires-action` while that call has no result.
- `reviewAndCommit` locates the latest `LogseqReversibleTransactionTracker`, temporarily executes commands to print the changed graph, reverts them, persists the tracker artifact, and opens `showAIChangesReviewModal`.
- Current modal values are `true` for Commit, `false` for Discard, and `null` for header Close/Escape. The `null` branch returns without `addResult`, so the tool correctly remains in `requires-action`.
- Commit runs `executeApprove`, applies and clears queued commands, then calls `addResult`. Discard runs `executeCancel`, clears queued commands, then calls `addResult`.
- After diff preparation succeeds and the modal is shown, queued changes are already reverted and retained in the tracker. **Continue (Commit Later)** can therefore persist the tracker and terminally patch the pending tool turn without a separate review abort session.

### 3.2 Why a project runtime stop controller is required

- `src/chat-app/components/ComposerAction.tsx` displays stop for `requires-action` but disables it with `disabled={requiresActionState}`.
- `ComposerPrimitive.Cancel` delegates to `runtime.cancelRun()`. Assistant-ui passes an abort signal during an active LocalRuntime roundtrip, but the roundtrip has already ended and its controller has been cleared once an unresolved human tool settles in `requires-action`. There is no active run signal to abort at this point.
- Calling renderer `addResult` would resolve the human tool through LocalRuntime's normal path and can resume the model. Both clarified actions must instead end the current turn and wait for new user feedback.
- During active frontend-tool execution, assistant-ui aborts the shared signal and marks the message `incomplete/cancelled`, but discards adapter yields after abort. Therefore `executeFrontendTool` cannot reliably publish the exact generic result by itself.
- For a settled human/approval action there is no active abort controller, so `runtime.cancelRun()` alone has no effect.
- The controller must therefore orchestrate both cases: await active `runEnd` when needed, then perform one terminal repository transition that fills unresolved tool results without calling `addResult`.
- `ThreadRuntime.unstable_on("runEnd")` provides an event boundary after active LocalRuntime cancellation and its normal history append have settled.

### 3.3 Artifacts, persistence, and identities

- `src/chat-app/tools/transaction/getLastLogseqReversibleTransactionTracker.ts` returns the tracker plus the earlier mutation tool part's `{messageId, toolCallId}` artifact location.
- A terminal tool-turn mutation must spread existing message parts and only add cancellation result/approval fields, thereby preserving tracker and unrelated artifacts byte-for-byte.
- Active tool cancellation is cooperative. The selected maintainable scope does not add an execution-settlement journal for a result/artifact produced after abort but rejected by LocalRuntime; already accepted/persisted artifacts remain preserved.

### 3.4 Modal/footer behavior

- `src/ui/pages/AIChangesReviewModal.tsx` currently uses generic `ModalFooter` for Commit and Discard.
- `src/ui/modals/core/ModalFooter.tsx` uses `sm:flex-row-reverse`, but it must remain unchanged per review feedback.
- `src/ui/modals/hooks/useModal.ts` returns `null` from `handleCancel`; this already provides the required header Close/Escape defer behavior and requires no modification.
- `src/ui/launchers/showAIChangesReviewModal.ts` returns `Promise<boolean | null>` and needs only a result-type update for the additional footer outcome. It does not need an abort signal.

### 3.5 Tests and documentation

- Relevant tests exist in `tests/src/chat-app/tools/impl/LogseqCommitChangesTool.test.ts`, `tests/src/chat-app/runtime/cancelPendingToolCallsInThread.test.ts`, and `tests/src/ui/pages/AIChangesReviewModal.test.ts`.
- There is no current `ComposerAction` test.
- No matching end-user documentation was found under `docusaurus/`; no documentation update is required for this targeted behavior.

## 4. Solution

### 4.1 Add a review-specific footer and explicit modal result

Modify `src/ui/pages/AIChangesReviewModal.tsx`:

- Define/export a result type such as:

```ts
type AIChangesReviewResult = "commit" | "discard" | "continue-later" | null;
```

- Keep `null` deliberately: `useModal.handleCancel`, header Close, and Escape continue to resolve `null`, and `reviewAndCommit` continues to treat it as defer without adding a tool result.
- Add a local review-specific footer component (or a narrowly named colocated component) by duplicating the relevant generic footer/button markup. Do not modify or reuse `ModalFooter` for this three-zone layout.
- Lay out **Continue (Commit Later)** as a `LogseqButton color="ghost"` at the far left on desktop, with destructive Discard and primary Commit grouped on the right. Preserve sensible full-width stacking on narrow screens.
- Route buttons to `"continue-later"`, `"discard"`, and `"commit"` respectively.
- Preserve the existing Commit shortcut behavior, destructive Discard styling, outside-click disablement, and close handling.

Modify `src/ui/launchers/showAIChangesReviewModal.ts`:

- Return `Promise<AIChangesReviewResult>` and otherwise keep the launcher unchanged.
- Do not add an `AbortSignal` or external modal-abort listener.

Do not modify:

- `src/ui/modals/core/ModalFooter.tsx`
- `src/ui/modals/hooks/useModal.ts`

### 4.2 Replace current cancellation helpers with a pure terminal transition

Add `src/chat-app/runtime/terminateToolTurn.ts` and remove `src/chat-app/runtime/cancelPendingToolCallsInThread.ts` after migrating its existing `ReviewChangesDisplay` caller.

- Define a pure repository mutation with target `{messageId, toolCallId?, toolName?}` and configurable error text. An exact tool target is used by Continue Later; generic stop captures the current assistant message and can anchor by message ID.
- Validate that:
  1. the message is on the active branch;
  2. it is an assistant message in `running`, `requires-action`, or terminal `incomplete/cancelled` state appropriate to the stop phase;
  3. it still contains at least one unresolved tool call;
  4. when exact IDs are supplied, that unresolved call matches.
- A stale/mismatched target is a no-op and never falls back to another turn.
- Set the matched call to:

```ts
result: {success: false, error: suppliedErrorMessage},
isError: true
```

- Set unresolved approval metadata to cancelled and mark the message `{type: "incomplete", reason: "cancelled"}`.
- Cancel every unresolved sibling in the same turn; preserve existing results, artifacts, text/reasoning, other messages, and inactive branches.
- Return `{repository, didChange}` without importing, saving, logging, or knowing about CommitTool.

### 4.3 Add one runtime-level stop controller and hook

Add `src/chat-app/runtime/stopThread.ts`:

- Expose `stopThread({threadId, runtime, target?, errorMessage?})`, defaulting to `"User terminated the operation"`.
- Capture the active-branch assistant message before the first await so cancellation can never drift to a newer turn.
- If `runtime.getState().isRunning`:
  1. subscribe to `runtime.unstable_on("runEnd")` before cancellation;
  2. call `runtime.cancelRun()` to abort model/provider/frontend-tool work through assistant-ui's signal;
  3. await `runEnd`, then unsubscribe;
  4. re-export the settled repository and apply `terminateToolTurn` to the captured message, allowing its now-`incomplete/cancelled` state.
- If the thread is settled in `requires-action`, apply `terminateToolTurn` immediately without calling `cancelRun`.
- Import the changed repository and persist that same authoritative repository to `ThreadStore`; do not independently transform a potentially stale stored copy.
- Serialize duplicate/in-flight stop requests per thread/message identity so double clicks do not race imports/saves.
- Never call `addToolResult`, `addResult`, approval response APIs, or start a run.
- If no visible unresolved tool call exists (for example, stopping plain text generation), still use `runtime.cancelRun`; no synthetic tool result is needed.
- On persistence failure, leave the live runtime terminal, log centrally, and notify the user that cancellation history could not be saved.

Add `src/chat-app/hooks/useStopThread.ts`:

- Own `useAssistantRuntime`, local/remote thread ID resolution, runtime lookup, duplicate-interaction state, logging, and notification policy.
- Return `{stop, isStopping}`. `stop` accepts an optional exact target/custom message for Continue Later.
- Keep all repository, persistence, active/settled branching, and tool semantics out of UI components.

Delete `src/chat-app/runtime/terminatePendingToolCallAndRetainChanges.ts`; its tracker rewrite is unnecessary because the terminal mutation preserves artifacts and Commit review already persists the reverted tracker before showing the modal.

### 4.4 Handle Continue (Commit Later) through the shared stop hook

Modify `src/chat-app/tools/impl/LogseqCommitChangesTool.tsx`:

- Call `useStopThread` at render scope and read only the renderer's exact `{messageId, toolCallId, toolName}` target.
- Replace boolean branching after `showAIChangesReviewModal` with an explicit switch:

```ts
switch (reviewResult) {
    case null:
        // Header close/Escape: leave requires-action unchanged.
        return;
    case "discard":
        addResult(await this.executeCancel(transactionTracker));
        return;
    case "commit":
        addResult(await this.executeApprove({}, {messages}, transactionTracker));
        return;
    case "continue-later":
        // Persist retained tracker, then terminally cancel exact CommitTool call.
        return;
}
```

- In `"continue-later"`:
  1. do not call `executeCancel`, `tracker.clear()`, or `addResult`;
  2. call shared `stop` with the exact commit identity and error text `Changes not committed. User will commit later. Do not call this tool immediately again without feedback from user`;
  3. rely on the already-persisted reverted tracker artifact and artifact-preserving terminal mutation;
  4. leave the assistant message terminally `incomplete/cancelled`, allowing a new user message.
- Handle stop/persistence errors without falling into the outer normal tool error path, so no late `addResult` resumes the model.
- Preserve all existing diff generation, Commit, Discard, no-change, error, and header-close behavior.

No modal abort listener is needed: **Continue (Commit Later)** is handled after review preparation/reversion, and composer controls are inaccessible while the modal is open.

### 4.5 Reduce ComposerAction to presentation and one hook call

Modify `src/chat-app/components/ComposerAction.tsx`:

- Use `useStopThread()` and render one project-owned stop button for both `thread.isRunning` and non-running `requires-action` states.
- Clicking it only calls `stop()`; the component must not import CommitTool, `ThreadStore`, tracker helpers, repository mutation functions, or runtime cancellation implementation modules.
- Disable only while `isStopping` is true. Settled `requires-action` stop remains enabled generically for human and approval-gated tools.
- Preserve the existing icon, classes, ARIA label, model selector, running cancel behavior, and idle Send behavior.
- Update the component's upstream-change comment to describe delegation to the project stop hook.

After the repository patch changes the last message to `incomplete/cancelled`, existing predicates naturally restore Send and keyboard submission. No `Composer.tsx` change is required.

### 4.6 Migrate ReviewChangesDisplay

Modify `src/chat-app/components/ReviewChangesDisplay.tsx` so its destructive discard flow uses `stopThread`/the shared stop operation before executing `LogseqClearUncommittedChangesTool`, rather than the removed cancellation helper and polling function. Its confirmation and discard semantics remain unchanged.

Manual validation in Logseq:

1. Produce uncommitted graph changes and open review. Confirm **Continue (Commit Later)** is ghost-styled at far left, with Commit and Discard grouped on the right.
2. Press header Close and Escape in separate runs. Confirm the modal closes but CommitTool remains in `requires-action`, the composer remains blocked, and review can be reopened.
3. Click **Continue (Commit Later)**. Confirm the modal closes, queued changes remain available, the tool part records the required not-committed message, the assistant turn ends without another model response, and the composer accepts a new user message.
4. Enter CommitTool review but do not open the modal; click composer stop. Confirm queued changes remain, every unresolved tool part in the turn records `User terminated the operation`, no model response resumes, and the composer accepts a new message.
5. Verify Commit still applies/clears changes and Discard still clears them.
6. Stop during an active non-human tool. Confirm its abort signal fires, the terminal tool result is exactly `success:false / User terminated the operation`, the message is `incomplete/cancelled`, and the model does not resume.
7. Trigger a non-CommitTool human or approval required action and click stop. Confirm all unresolved calls in that turn receive `User terminated the operation`, approval metadata is cancelled where present, the model does not resume, and no Logseq tracker is required.
