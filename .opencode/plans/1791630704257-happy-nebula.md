## 3. Existing System

### 3.1 Test harness

- `vite.config.ts` defines the `e2e` project as `tests/**/*.e2e.test.{ts,tsx}`, run headless in Chromium through Playwright at 1280×720. It has `expect.poll` with a 10s timeout and file parallelism enabled. Tests within a file are not run concurrently.
- `tests/setup.ts` imports `@logseq/libs`, calls `setupLogseqProxy()` to proxy calls over HTTP to `LOGSEQ_API_SERVER`, defaulting to `http://127.0.0.1:12315`, and calls `LogseqPluginStorageManager.init()` in `beforeAll`. It also sets `globalThis.isLogseqAvailable` and `globalThis.isLogseqCurrentIsDBGraph`.
- `tests/helpers/aiChatScenarioFixture.ts` contains:
  - a hoisted `vi.mock` of `src/core/title-generator/generateTitle`;
  - the `model` fixture with `chatModelAdapter`, `respondWith(turns)`, and `waitForTitleGeneration()`. That wait reports only that generation started.
- `tests/helpers/mockLanguageModel.ts`: `createMultiTurnMockLanguageModel` supports one text part or one tool call per `doStream`. Streams are created eagerly, and exhausting the script returns `undefined`.
- `tests/helpers/createChatApp.tsx` imports `App` dynamically so that mocks are registered first.
- `tests/helpers/mountLauncher.tsx` calls `UI._resetForTesting()`, starts the launcher, and waits for `[id^="modal-"]`. Its returned `result` promise resolves only when the modal closes.

### 3.2 App and runtime

- Component tree: `App` → `ShadowWrapper`, an open shadow root → `ChatToolRegistryProvider` → `ThreadBoundLocalAISDKRuntimeProvider`, using `useRemoteThreadListRuntime` with `LocalThreadListAdapter` and a per-thread `useLocalRuntime` with `LocalThreadHistoryAdapter` and `withRoundtripPersistence(adapter)` → `AppContent` → `AuiProvider` → `ThreadWrapper`.
- `App` accepts only `onClose` and `chatModelAdapter`, with no children. The app always starts on a **new thread**.
- After a tool result, the runtime continues automatically. **The follow-up text is appended to the same assistant message.**
- `executeFrontendToolPlan` runs tools in a sequential `for … of` loop. Each invocation gets fresh `context.messages`, which include earlier results and artifacts.
- `ToolRegistry.build()` binds `execute` through `getDefinition()` during mount. Spies must therefore be installed **before mounting**.
- Standalone tool UIs are registered by assistant-ui `Tools` **only when a renderer exists**. `groupMessagePart` in `AssistantMessage.tsx` groups reasoning and non-standalone tools under `group-chainOfThought`.
- `LogseqCommitChangesTool` has `type = "human"` and `display = "standalone"` and supplies a custom render. `LogseqClearUncommittedChangesTool` has neither `display` nor `render`, so **it currently renders inside reasoning**.

### 3.3 Persistence and branching

- `ThreadStore` provides `updateThread(id, updater)`, `loadThread`, `listThreads`, and `deleteThread`. `listThreads` is sorted by `custom.updatedAt` in descending order. The backend is `LogseqPluginStorageManager.store`, which can be replaced with `new InMemoryStore(ns)`.
- `ExportedMessageRepository.fromBranchableArray(items, {headId})` builds a repository. On import, `resetHead` removes descendants of the head, so **`headId` must be a leaf**.
- Branch switching does not persist the head. The head is persisted only on append.
- `useLogseqAppliedChangesBranchGuard` finds the latest tracker on the selected branch. If that tracker has applied graph mutations, the guard shows `showConfirmModal(msg, {confirmText: "Revert & Switch"})`. On confirmation, it reverts all applied commands, persists the artifact, and continues. Its consumers are `BranchPicker`, `EditComposer` (changed text only), and `AssistantActionBar` (`Refresh`).
- `committedTurnBoundary.ts` treats only `logseq_commit_changes` with `result.success === true && outcome === "committed"` as a boundary. The boundary extends through the next user message. Edit, Refresh, and branch controls before it are disabled.
- The commit review flow (`prepareReview`) executes, records the after state, **reverts**, records the before state, and then opens the modal. Approval executes again and clears the tracker. Rejection clears the tracker and returns an error result. Deferral calls `stop()`, and `Close` leaves the tool pending.

## 4. Solution

### 4.0 Key design decisions (requested items a–e)

| Item | Decision |
|---|---|
| (a) Load thread / thread list | Seed `ThreadFileData` into an isolated `InMemoryStore` with `threadBuilders` and `storage.seedThread`, before mounting. Open it through the real UI with `driver.openThread(title)` → `"Thread history"` → row trigger. Use the same approach for every static-history, menu, and navigation test, including assistant ActionBarMore absence, user-message more absence, and the thread-row More menu. |
| (b) Add attachment | Use the public `new AddAttachmentCommand(uuid).execute()`, imported directly from its file rather than the barrel, which eagerly imports `App`. Then wait for the pill and for `probe.getComposer().attachments`. Seeded sent messages use `createLogseqAttachmentFromUuid(uuid)` plus `status: {type: "complete"}`. Entities are real and created through `logseqEntities`. |
| (c) Model fixture changes | Replace the eager mock with a scripted model built from steps, segments, named gates, multiple tool calls per step, reasoning, abort-aware streams, and an explicit exhaustion error. Add a deferred title fixture, isolated storage, a probe, explicit `chat.mount()`, and ordered teardown. |
| (d) Commit confirmation | Use `driver.reviewAndCommit()`, which drives the real review modal. Do not call tool methods directly. Branch-guard dialogs are answered explicitly with `driver.confirmModal("revert-and-switch" | "cancel")`; helpers never auto-confirm. |
| (e) Sequential execution | Use a passthrough `vi.spyOn(LogseqCreatePageTool.prototype, "execute")` installed before mounting. It records `start`/`end` events and snapshots `context.messages`. Gate call #1 before invoking the original. While held, assert that call #2 has not entered. After release, assert the order `start:P, end:P, start:Q, end:Q`, max in-flight = 1, and that Q's `messagesAtStart` already contains P's result and artifact. |
| Mock tool results? | No, per the user's decision. Real tools are used everywhere, with unique temporary names and owned cleanup. |
| Cancel and unchanged-edit placement | Put both in **user-message-ui**, because they create no branch and start no run. A separate graph-aware variant, "unchanged edit bypasses guard with applied changes", goes in advanced-branching. |

### 4.1 Shared infrastructure (new and modified test helpers)

#### 4.1.1 `tests/helpers/chatScenario/gates.ts`

```ts
export interface ScenarioGate { readonly name: string; readonly isOpen: boolean; readonly arrivalCount: number;
  open(): void; wait(signal?: AbortSignal): Promise<void>; waitForArrival(count?: number): Promise<void>; }
export interface ScenarioGates { define(name: string): ScenarioGate; get(name: string): ScenarioGate;
  open(name: string): void; wait(name: string, signal?: AbortSignal): Promise<void>; dispose(reason?: unknown): void; }
export function createScenarioGates(): ScenarioGates;
export function createAbortError(message?: string): DOMException; // name "AbortError"
```

- `define` rejects duplicate names, and `get`/`wait` reject unknown names.
- `open` is idempotent and sticky.
- `wait` increments `arrivalCount`, rejects if the signal is already aborted, and removes its listeners on every path.
- `dispose` **rejects** pending waits. It never resolves them, so teardown cannot trigger graph mutations.

#### 4.1.2 `tests/helpers/mockLanguageModel.ts` (rewrite, keeping backward compatibility)

```ts
export interface ScriptToolCall { toolCallId: string; toolName: string; input: Record<string, unknown>; }
export type ScriptChunk = string | {type: "wait"; gate: string};
export type ScriptSegment =
  | {type: "text"; chunks: readonly ScriptChunk[]}
  | {type: "reasoning"; chunks: readonly ScriptChunk[]}
  | {type: "tool-calls"; calls: readonly ScriptToolCall[]}
  | {type: "wait"; gate: string};
export interface ScriptStep { name?: string; waitFor?: string; segments: readonly ScriptSegment[];
  finishReason?: LanguageModelV4FinishReason["unified"]; }
export type ScriptedLanguageModel = MockLanguageModelV4 & {
  readonly diagnostics: {consumedSteps: number; activeStreams: number; failures: readonly Error[]};
  waitForCallCount(n: number): Promise<void>; assertHealthy(): void; dispose(reason?: unknown): Promise<void>; };
export function createScriptedLanguageModel(steps: readonly ScriptStep[], opts: {gates: ScenarioGates}): ScriptedLanguageModel;
// builders
export function text(value: string | readonly ScriptChunk[]): ScriptStep;            // one step, finish "stop"
export function toolCall(call: ScriptToolCall): ScriptStep;                           // finish "tool-calls"
export function toolCalls(calls: readonly ScriptToolCall[]): ScriptStep;              // same response, many calls
export function step(segments: readonly ScriptSegment[], o?: Omit<ScriptStep,"segments">): ScriptStep;
export function textSegment(v: string | readonly ScriptChunk[]): ScriptSegment;
export function reasoningSegment(v: string | readonly ScriptChunk[]): ScriptSegment;
export function waitForGate(gate: string): ScriptSegment;
// compat
export type MockLanguageModelTurn = ...; export function createMultiTurnMockLanguageModel(turns): MockLanguageModelV4; // translates to steps
```

Implementation:

- Use `new MockLanguageModelV4({doStream: async (options) => …})`. **Build the stream inside `doStream`.**
- Compile each step into emissions, all using deterministic IDs such as `step-${i}-text-${j}`:
  - optional `waitFor`;
  - for text and reasoning: `text-start`/`reasoning-start`, then a `*-delta` per string chunk, with gate waits between chunks, then `*-end`;
  - for tools: `{type: "tool-call", toolCallId, toolName, input: JSON.stringify(input)}` in order;
  - `finish`: `{type: "finish", finishReason: {unified, raw: undefined}, usage}`. The default `unified` value is `"tool-calls"` when the step contains calls and `"stop"` otherwise.
- The `ReadableStream` producer combines `options.abortSignal` with an internal shutdown controller. Aborting rejects the pending gate wait and errors the stream with `AbortError`. Check cancellation before every enqueue, and never enqueue after cancellation.
- If `steps[next]` is undefined, record and throw `Error("Scripted language model exhausted: call N, configured M")`. The adapter converts that into an error bubble, so the fixture calls `assertHealthy()` during teardown so the test fails.
- Validate at construction: tool-call IDs are unique, referenced gates are defined (auto-define them in the fixture's gate registry), and `toolCalls([])` is rejected.

#### 4.1.4 `tests/helpers/chatScenario/threadBuilders.ts`


- `buildRepository` validates IDs are unique, parents exist, parents precede children, there are no cycles, and the head exists **and is a leaf**. It then calls `ExportedMessageRepository.fromBranchableArray`.

- `buildBranchedThread` topology, with insertion order defining sibling numbering and default head `a1-original`:

```text
u0 -> a0 -> u1-original -> a1-original | a1-refreshed
          -> u1-edited   -> a1-edited
```

  The user picker on `u1` shows `1 / 2`, and the assistant picker on `a1` shows `1 / 2`.
- Never seed tool results, tracker artifacts, or commit outcomes.

### 4.5 Edge cases and pitfalls to honour

- Each script step corresponds to one `doStream` call. A tool follow-up adds a step but not a UI message.
- Hover a non-last user message before using Edit. After clicking Edit, the original user locator becomes stale, so use the edit wrapper.
- Reasoning auto-opens while streaming and collapses afterwards. Expand it explicitly.
- `"Copy"` also appears in code headers, so always scope it.
- Do not wait for idle before `"Review & Commit"`. Use `allowRequiresAction`.
- Review preparation temporarily reverts the graph while the modal is open.
- Never open gates during teardown. Dispose them so pending waits are rejected.
- Never use `getByText(title)` unscoped in history, because the shimmer duplicates the title.
- Restore the viewport in `finally`.
- Use `expect.poll` and gates rather than sleeps.
- Live-graph uniqueness: every name includes `crypto.randomUUID()`.
