# OpenCode CLI integration plan

## Recommendation

Implement this as a **desktop-only, capability-gated local OpenCode ACP backend**, behind a narrow privileged host bridge. Do **not** use `HarnessAgent` for the local-CLI option and do not import `@mcpc-tech/acp-ai-provider` into the renderer.

This is the least misleading and most maintainable direction for the requested product behavior:

- The official `@ai-sdk/harness-opencode` adapter does not connect to an already-running/local OpenCode CLI. It installs and starts OpenCode inside a network sandbox.
- `HarnessAgent` and the OpenCode harness require Node 22+, real process/filesystem APIs, and an exposed WebSocket port. They are not browser-renderer packages and cannot be returned as an AI SDK `LanguageModel` from `getLLMModel()`.
- `createJustBashSandbox` cannot host OpenCode: it exposes no ports and its `getPortUrl()` always throws. A custom sandbox is structurally possible, but implementing process, filesystem, lifecycle, restricted-session, and exposed-port semantics in this renderer would amount to building a local sandbox platform.
- `@mcpc-tech/acp-ai-provider` launches `opencode acp` over stdio and therefore matches “local OpenCode CLI,” but its published/current implementation targets AI SDK v6/`LanguageModelV3`, needs Node process/socket APIs, and its dynamic custom-tool MCP proxy is experimental. It should not be installed directly into this AI SDK v7 renderer.
- A small app-owned ACP/host bridge keeps the current Assistant UI `LocalRuntime`, branch model, and browser-executed Logseq tools intact without pretending a stateful CLI agent is a stateless AI SDK model.

Treat the first stage as a required feasibility spike. If Logseq cannot provide a stable privileged process + streaming boundary, stop and use an authenticated localhost companion process; do not try to solve it with browser polyfills or the buffered `LogseqHttpProxy`.

## Confirmed API behavior

- OpenCode ACP uses `opencode acp` over JSON-RPC/NDJSON stdio. It does **not** require an API URL or fixed port.
- The official Harness OpenCode adapter takes an optional bridge **port**, defaulting to the first port exposed by its sandbox. It does not take a user API URL; the sandbox resolves the reachable WebSocket URL.
- Current OpenCode Harness built-ins are exactly: `read`, `write`, `edit`, `bash`, `glob`, `grep`, `ls`, `webfetch`, `skill`, `todowrite`, and `agent`.
- Harness `activeTools` is an allow-list over built-ins plus custom tools and cannot be combined with `inactiveTools`. OpenCode enforces disabled built-ins through auto-rejection.
- For this ACP design, implement the equivalent deny-by-default policy in the bridge/OpenCode session configuration rather than exposing a fake `activeTools` option.
- The existing app web tools are `web_search` and `web_page_get` when Jina is enabled. OpenCode has `webfetch`, but no verified built-in named `websearch`.

## Phase 1 — runtime feasibility spike (release gate)

1. **Verify the actual root/privileged signal**
   - Inspect `logseq.App.getInfo()` in supported desktop Logseq versions and confirm the field the product calls “root access.” The public `AppInfo` type only guarantees `version` and `supportDb`; do not hard-code an undocumented field without observing it.
   - Also inspect `logseq.baseInfo.iir` (“installed in dot root”) and determine whether that is the intended root-access signal.
   - Keep `LogseqAppInfoFetcher.checkHostAccess()` separate: same-origin access to `window.parent` is necessary for current host integrations but does not prove subprocess or streaming capability.
   - Define one capability result covering root eligibility, privileged bridge availability, process spawning, incremental streaming, and the reason for failure.

2. **Locate or add the privileged execution boundary**
   - Prove that production Logseq desktop can invoke `opencode --version` without bundling `node:child_process`, `node:net`, or ACP code into the Vite renderer.
   - Prefer a supported Logseq host/root API. If none exists, use a small authenticated localhost companion service instead of undocumented Electron renderer access.
   - Spawn the configured executable directly with argument arrays and `shell: false`; never expose generic shell execution to renderer/model input.

3. **Prove ACP lifecycle and streaming**
   - Start `opencode acp`, create one session, send one prompt, forward incremental text/reasoning events, cancel the turn, and cleanly terminate all owned resources.
   - Verify cleanup on normal completion, startup error, abort, renderer reload, and plugin unload.
   - Verify two independent sessions and serialized turns within one session.

4. **Prove tools and permissions**
   - Verify behaviorally that all OpenCode native built-ins can be denied.
   - Verify whether `webfetch` can be enabled alone.
   - Prove one existing browser tool can be advertised to OpenCode, pause the turn, execute through the renderer, submit its result, and continue the same ACP turn. If this is not reliable, custom-tools support is a blocker because it is central to this app.
   - Never accept ACP/provider behavior that automatically chooses the first permission option; permission requests must deny by default or be surfaced explicitly.

5. **Go/no-go criteria**
   - Proceed only if incremental streaming, cancellation, custom-tool continuation, native-tool denial, branch/session isolation, and process cleanup all work without Node-only code entering the renderer bundle.
   - Pin/probe a supported OpenCode CLI version range.

## Phase 2 — settings and capability integration

### `src/logseq/LogseqAppInfoFetcher.ts`

- Add an asynchronous, structured OpenCode capability probe based on the verified `App.getInfo()`/root signal plus feature detection of the privileged bridge.
- Preserve `checkHostAccess()` semantics for existing callers.
- Handle missing/malformed app info, web Logseq, cross-origin parent access, unsupported Logseq versions, and unavailable process/stream APIs with explicit failure reasons.

### `src/core/ai-sdk/types.ts`

- Add `ProviderEnum.OPEN_CODE_CLI = "OpenCode CLI"` while preserving all existing stored enum values.
- Add a provider classification helper so code can exhaustively distinguish normal AI SDK language models from the OpenCode agent backend.

### `src/settings.ts`

- Resolve the root/capability result before building the settings schema.
- Include `OpenCode CLI` in `llmProvider.enumChoices` only when the verified root/capability gate is satisfied. CSS hiding alone is not sufficient because stale settings remain possible.
- Add `openCodeCLIPath?: string` only if the spike shows PATH discovery is unreliable. Prefer default command discovery (`opencode`) and make an override optional.
- For OpenCode selection:
  - hide `llmAPIUrl`;
  - hide `llmAPIKey`;
  - hide `llmAPIModel` unless the ACP spike verifies a useful model override;
  - show the optional CLI path override;
  - keep global instructions and web-tool settings visible.
- Do not add an API URL or user-facing port setting. ACP uses stdio; any companion-service or internal loopback port should be ephemeral and owned by the bridge.
- Reject a stale OpenCode selection when capability is absent and show an actionable desktop/root-access message.
- Reject `WebToolsProviderEnum.MODEL_NATIVE` for OpenCode because it is specific to OpenAI/Google AI SDK provider tools. Allow Jina or Disabled.
- On CLI-path/provider changes, invalidate sessions and stop the plugin-owned OpenCode process lazily/safely.

## Phase 3 — privileged ACP service and renderer bridge

### New privileged host module (location determined by the spike)

Implement the Node-side process owner outside the Vite renderer graph:

- probe the executable and version;
- start `opencode acp` over stdin/stdout/stderr;
- parse NDJSON safely across arbitrary chunk boundaries;
- correlate request, session, tool-call, permission, and cancellation IDs;
- enforce startup/request/idle/shutdown timeouts;
- serialize turns per session while allowing independent sessions to run concurrently;
- terminate only processes it owns;
- redact prompts, graph paths, environment values, and tokens from ordinary logs;
- expose no arbitrary command-execution primitive.

If a companion service is required, bind only to loopback, use an ephemeral port and per-launch capability token, and authenticate every stream/control request.

### New `src/core/open-code/OpenCodeHostBridge.ts`

Add a browser-safe typed client with narrow operations:

- `getCapabilities()` / `probeExecutable()`;
- `createSession()`;
- `sendPrompt()` with streaming events;
- `submitToolResult()` / `submitPermissionResult()`;
- `abort()`;
- `disposeSession()` / `disposeAll()`.

Use the verified host event channel or `MessagePort`; do not route streaming through `src/logseq/LogseqHttpProxy.ts`, whose host proxy buffers responses.

### New `src/core/open-code/OpenCodeToolPolicy.ts`

Centralize a deny-by-default policy:

- always disable `read`, `write`, `edit`, `bash`, `glob`, `grep`, `ls`, `skill`, `todowrite`, and `agent`;
- enable OpenCode `webfetch` only when web tooling is enabled **and** the spike confirms it can be isolated safely;
- keep Jina `web_search` and `web_page_get` as existing renderer tools when Jina is selected;
- reject unknown/new native tools by default rather than implicitly enabling them.

If the official Harness is evaluated in a future server-side architecture, the corresponding configuration would be `activeTools: [...customToolNames, ...(webEnabled ? ["webfetch"] : [])]`.

### New `src/core/open-code/OpenCodeSessionRegistry.ts`

- Map stable thread **and branch lineage** to ACP session IDs; do not key only by thread ID.
- Create a fresh session for an alternate/edited branch unless a verified ACP session-fork operation exists.
- Track process generation so a restarted process cannot reuse stale sessions.
- Serialize same-session requests, handle abort races idempotently, bound registry size, and dispose idle/deleted-thread sessions.
- Start with in-memory session mapping; persist opaque OpenCode sessions only after restart/resume behavior is proven.

## Phase 4 — preserve Assistant UI LocalRuntime and custom tools

### New `src/chat-app/runtime/LocalChatModelAdapter/LocalOpenCodeChatModelAdapter.ts`

Implement a second `ChatModelAdapter` rather than replacing Assistant UI’s LocalRuntime:

- accept the current selected branch, `unstable_getMessage()`, system instructions, call settings, browser tool definitions, and abort signal;
- create/resolve the branch-specific OpenCode session;
- translate ACP text, reasoning, source, tool, finish, cancellation, and error events into the current `ChatModelRunResult` shape;
- yield only current-step content so LocalRuntime does not duplicate previous roundtrips;
- preserve `requires-action` semantics for browser/human tools;
- execute non-human renderer tools through the existing `executeFrontendTool()` path, then submit results to the same unfinished ACP turn;
- retain custom tool names so existing ToolRegistry UIs continue to work;
- reject any unapproved native tool event even if OpenCode emits it unexpectedly.

Extract small protocol-neutral helpers from `LocalAISDKChatModelAdapter.ts` only after regression tests protect its existing branch and tool behavior.

### `src/chat-app/runtime/useThreadBoundLocalAISDKChat.ts` (or a small adapter dispatcher)

- Select `LocalOpenCodeChatModelAdapter` for `OPEN_CODE_CLI` and the current `LocalAISDKChatModelAdapter` for existing providers.
- Keep `useLocalRuntime`, `LocalThreadHistoryAdapter`, attachment handling, max steps, human-tool names, and roundtrip persistence unchanged.
- Ensure a settings change recreates or safely switches the backend and disposes OpenCode sessions.

### `src/chat-app/tools/ToolRegistry.ts`

- Preserve all current renderer tool definitions and custom UIs.
- Ensure registry recreation on relevant web/content settings changes so Jina tools do not remain stale.
- Do not expose OpenCode built-ins as normal app tools.

## Phase 5 — clarify AI SDK factory boundaries

### `src/core/ai-sdk/getLLMModel.ts`

- Keep this function as an AI SDK `LanguageModel` factory for OpenAI, OpenAI-compatible, and Google.
- Add an explicit OpenCode guard with a clear internal error: OpenCode is handled by the OpenCode chat adapter and must not be passed to `streamText()`.
- Add an explicit AI SDK language-model return type; optionally rename later to `getAISDKLanguageModel()`.
- Do not return a union of `LanguageModel`, `HarnessAgent`, ACP client, or session. `HarnessAgent` is not compatible with the current `streamText({ model })` call and requires explicit stateful sessions.

### `src/core/ai-sdk/getLLMProviderTools.ts`

- Return no provider-defined model tools for OpenCode.
- Preserve current OpenAI `web_search` and Google `google_search`/`url_context` behavior.
- Keep Jina tools in the renderer ToolRegistry.

### `src/index.ts` and `src/logseq/LogseqAppListeners.ts`

- Initialize only the browser-safe bridge/capability state; start OpenCode lazily on first use.
- Register unload cleanup for all plugin-owned sessions/processes.
- Ensure cleanup listeners may be asynchronous and awaited where Logseq supports it.

## Verification

### Unit tests

- Capability parsing: missing/throwing/malformed `App.getInfo()`, root false, host inaccessible, process bridge absent, streaming absent, and supported desktop.
- Settings: OpenCode choice omitted without capability; URL/key/model/CLI-path visibility for every provider; stale selection rejection; model-native web search rejection.
- Tool policy: exact allow/deny output for Disabled and Jina, unknown built-ins denied, and no shell/filesystem/agent tools enabled.
- Session registry: same branch reuse, alternate/edit branch isolation, same-session serialization, independent concurrency, abort cleanup, process-restart invalidation, and eviction.
- OpenCode adapter: streamed text/reasoning, partial content on errors, abort, browser tool call/result continuation, human tools, rejected native tool calls, and no content duplication across roundtrips.
- Add regression coverage for existing `LocalAISDKChatModelAdapter`: full selected-branch conversion, current assistant tool-result inclusion, frontend/provider tool merge, provider-executed tools, and current-step-only yields.

### Host integration tests

- Use a fake ACP executable to test version probing, path-with-spaces, missing/non-executable path, readiness, split/malformed NDJSON, stderr, early exit, timeout, cancellation, double disposal, concurrent sessions, and plugin-unload cleanup.
- Add opt-in tests against an installed supported OpenCode CLI for session continuation, custom browser-tool roundtrip, tool denial, isolated `webfetch`, cancellation, and two branch sessions.

### Build/runtime checks

- Run `pnpm test`, `pnpm check`, and `pnpm build`.
- Inspect/fail the production renderer build if it contains Node process/socket imports, HarnessAgent, or ACP subprocess implementation code.
- Test packaged Logseq desktop on each supported OS and verify the option is absent in Logseq web/non-root mode.
- Confirm API URL/key/model settings never reach bridge requests or logs.
- Confirm no OpenCode/Node/helper process remains after completion, abort, provider change, plugin reload, or Logseq shutdown.

## Deferred alternatives

Do not implement these in the first version:

- **Official HarnessAgent/OpenCode:** reconsider only if the product accepts sandboxed OpenCode rather than the user’s local CLI and has a Node 22 server/main-process plus a real network sandbox. A custom sandbox is possible but is substantially more code and operational responsibility than ACP.
- **`createJustBashSandbox`:** not viable for OpenCode because it cannot expose the required bridge port, regardless of browser compatibility concerns.
- **`@mcpc-tech/acp-ai-provider`:** reconsider after an official AI SDK v7 release and demonstrated stable custom/client-tool continuation. Until then, reuse ACP as the protocol behind the app-owned bridge, not the incompatible `LanguageModelV3` provider.
- **`ai-sdk-provider-opencode-sdk`:** remains unsuitable because it cannot provide this app’s custom tool implementations.
