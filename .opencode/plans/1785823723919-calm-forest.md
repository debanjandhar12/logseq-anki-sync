# Review Changes Lifecycle And Revert Choices

## User Requirement

The discard temporary changes button in TemporaryLogseqChangesDisplay, clears both tracker and reverts the changes.
Instead, we should give users the option to revert the temporary changes only or do both.

The message should be intuitive. I am thinking we can use  showSelectionModal to confirm from user after they click the button

## Final Requirement After Discussion With User

### Clarification Q&A

1. What should each option do after the user clicks "Discard temporary changes"?
   - Answer: Offer "Revert changes only" (preserve the tracker) and "Revert and clear tracker" (the current behavior).
2. What should the UI do if reverting fails partway through?
   - Answer: Keep the current behavior. The tracker is cleared and the existing warning is reported, even if the user selected preservation.
3. Which user-facing lifecycle term should replace temporary-change terminology?
   - Answer: Use `Review changes`.
4. How should users choose between retaining and discarding reverted changes?
   - Answer: Show two compact, vertically stacked buttons in the existing popover rather than opening a selection modal.
5. When should an active thread be stopped for each direct action?
   - Answer: `Revert and keep for review` must not stop the thread. `Revert and discard` must stop it immediately before showing a confirmation dialog, so the messages cannot change while the user is deciding.

### Final Summarized Requirements

- Use `Review changes` as the product and chat-domain name for reversible AI-driven Logseq changes. The three user-facing lifecycle states are `Applied changes` (currently reflected in the graph), `Review changes ready to apply` (retained but not currently reflected in the graph), and `Committed changes`.
- Show two compact, vertically stacked actions in the review-changes popover:
  - Revert applied review changes while retaining them for review or a later commit.
  - Revert applied review changes and discard them.
- `Revert and discard` requires an existing `showConfirmModal` confirmation. Stop an active thread before opening it; if the user cancels confirmation, leave that stopped thread stopped and leave review changes unchanged.
- `Revert and keep for review` must not stop, cancel, or otherwise interrupt an active chat thread.
- Preserve the existing partial-revert failure behavior: clear tracking and return/display the warning.
- Persist the selected outcome as the newest tracker artifact in the thread so future operations use accurate tracker state.

## Solution

### Adopt review-change terminology

- Rename `TemporaryLogseqChangesDisplay` to `ReviewChangesDisplay` (and rename its file/imports/tests) because it presents the product-level review lifecycle rather than raw Logseq or transaction mechanics.
- Rename `LogseqClearTemporaryChangesTool` to `LogseqClearUncommittedChangesTool` as the implementation used exclusively for the `Revert and discard` action, including its file, public tool ID, registry entry, barrel export, call sites, descriptions, warnings, tests, and persisted tool-call compatibility handling where required.
- Rename chat-domain display and branch-guard names that use `TemporaryLogseqChanges` to corresponding review/applied-change names where they model this product lifecycle. Use `AppliedChanges` for behavior that requires graph mutations to be currently applied. Do not rename generic tracker-artifact and lookup names: they serialize and retrieve the reusable `LogseqReversibleTransactionTracker` implementation rather than a product-specific state.
- Replace product-facing copy such as `Temporary Logseq changes` and `Temporary commands` with `Review changes`, `Applied changes`, `Review changes ready to apply`, and `Committed changes` according to the actual applied/retained/final state.
- Keep generic core types such as `LogseqReversibleTransactionTracker`, `BaseReversibleCommand`, and `revertAppliedCommands()` unchanged. They are reusable implementation terminology and do not expose user-facing workflow concepts.
- Update discard-tool, commit-tool, user prompt guidance, branch-change UI copy, and relevant test names/assertions as part of the same terminology change, avoiding stale `temporary` wording in the active product lifecycle.

### Add direct review-change actions to the display

Modify the renamed display, currently `src/chat-app/components/TemporaryLogseqChangesDisplay.tsx`.

- Replace the current single full-width destructive button with two vertically stacked compact buttons below the counts. Both use `size="sm"`, occupy the popover width, share `isClearing` as their disabled state, and show a concise icon/label.
- Use a non-destructive/secondary-style action labelled `Revert and keep for review` for the direct tracker-revert branch.
- Use the destructive action labelled `Revert and discard` for the renamed clear-uncommitted tool branch.
- Give each button a dedicated click handler or pass an explicit named action to a shared handler. Do not use selection indexes or introduce `showSelectionModal`.
- Use `showConfirmModal` from the existing UI launcher only for the destructive discard action. The confirmation copy must explain that applied changes will be reverted and the retained review changes will be permanently discarded; use explicit confirm and cancel button labels.
- The keep-for-review button must directly run its tracker-revert path without stopping a running thread or cancelling pending tool calls.
- For **Revert and discard**, call `LogseqClearUncommittedChangesTool` with its existing `{}` arguments. Preserve its result/artifact in the appended synthetic tool-call message exactly as today.
- For **Revert and keep for review**, retrieve the latest `LogseqReversibleTransactionTracker` from `runtime.getState().messages`, call `revertAppliedCommands()` only when it has applied graph mutations, and leave its commands intact. Append a synthetic tool-call message containing `createLogseqReversibleTransactionTrackerArtifact(tracker)` so the newest persisted artifact represents retained changes with zero applied commands.
- Implement the keep-for-review error path locally with the same safety semantics as the discard tool: when direct reversion throws, log the error, clear the tracker, show the existing warning, and append a response/artifact that states review changes were discarded. This prevents a partially reverted transaction from being retained as reviewable state.
- Use distinct tool-call names/arguments for the direct keep-for-review history entry so the chat transcript represents the action accurately, instead of falsely recording a discard-tool invocation. Define this local history-only action identifier in the display module unless an existing suitable tool protocol is found during implementation.

#### Display state and copy

Keep the display visible whenever the located tracker contains graph mutation commands, regardless of whether they are currently applied. Derive the displayed lifecycle label from `tracker.hasAppliedGraphMutations()` in addition to the existing command/page counts:

| Tracker condition | Label | Meaning |
| --- | --- | --- |
| Has graph mutation commands and applied mutations | `Applied changes` | Changes are visible in the active Logseq graph and can be reverted. |
| Has graph mutation commands and no applied mutations | `Review changes ready to apply` | Changes are retained for a later review/commit but are not presently applied. |
| No graph mutation commands | Hide the display | There is no reviewable graph-change state. |

Use `Review changes` for the popover trigger `aria-label`, retain `Changed pages` as the factual count label, and render both direct actions beneath the summary. No modal, extra confirmation UI, selection shortcuts, or selection-cancellation state is needed.

#### Keep-for-review control flow

Implement this independently from discard because it must not interrupt the active chat thread:

1. Ignore a click while `isClearing` is true.
2. Set `isClearing` for the clicked action.
3. Read the current thread runtime messages and retrieve the latest tracker.
4. Revert only the tracker's currently applied graph mutations and append the retained-state synthetic artifact described below. Do not call `runtime.cancelRun()`, `waitForThreadRunToStop()`, or `cancelPendingToolCallsInThread()`.
5. Close the popover after success.
6. On an unexpected error, log with `LoggerCategory.CHAT_UI`, show `logseq.UI.showMsg` at error severity, leave the popover open, and reset `isClearing` in `finally`.

#### Discard control flow

Implement a dedicated discard handler so its message-stabilization guarantee is obvious:

1. Ignore a click while `isClearing` is true, then set `isClearing` immediately to prevent duplicate discard clicks.
2. Get the current thread runtime. If it is running, call `runtime.cancelRun()` immediately and await `waitForThreadRunToStop(runtime)` before opening any confirmation UI. This freezes the message list before the user decides.
3. Open `showConfirmModal` after the thread has stopped. Use message text that states the operation will revert applied changes and permanently discard review changes, with `confirmText: "Revert and discard"` and a non-destructive cancel label such as `Keep review changes`.
4. If the user rejects or closes the confirmation modal, reset `isClearing` and leave the popover and review-change state unchanged. The run intentionally remains stopped because that occurred before confirmation to stabilize the tracker/message state.
5. On confirmation, call `cancelPendingToolCallsInThread({threadId, runtime})`, then read `runtime.getState().messages` and invoke `LogseqClearUncommittedChangesTool` with its existing `{}` arguments.
6. Append the existing discard synthetic tool-call result/artifact, close the popover, and reset `isClearing` in `finally`.
7. If stopping the thread, opening the confirmation, cancelling pending tool calls, or executing discard fails, log/show the existing operation-level error. Do not execute the discard tool unless confirmation succeeded.

#### Revert and discard branch

This branch deliberately retains the current implementation rather than duplicating or modifying it:

1. Instantiate `LogseqClearUncommittedChangesTool` and execute it with `{}` and `{messages: currentMessages}`.
2. Convert its output with `ToolResponse.toResponse()`.
3. Append the current synthetic entry shape, with `toolName: LogseqClearUncommittedChangesTool.NAME`, `args: {}`, `argsText: "{}"`, the tool result/error flag, and the tool-produced artifact.
4. The tool remains responsible for reverting applied commands, clearing all command state, returning the cleared artifact, and its existing partial-revert warning behavior.

#### Revert and keep for review branch

This branch must not call `LogseqClearUncommittedChangesTool`:

1. Retrieve the latest tracker using `getLastLogseqReversibleTransactionTracker(currentMessages)`.
2. If `tracker.hasAppliedGraphMutations()` is false, do not invoke reversion. Preserve the tracker unchanged and still append a fresh artifact so this action is represented in persisted history.
3. If it is true, await `tracker.revertAppliedCommands()`. On complete success, this changes only the applied-command count; it preserves commands and changed-page metadata so the state becomes **Review changes ready to apply**.
4. Create a successful `ChatToolResponse` with `createLogseqReversibleTransactionTrackerArtifact(tracker)` and append it as a synthetic tool call. Use a file-local, history-only ID such as `logseq_revert_review_changes_keep` and truthful arguments such as `{retainForReview: true}`. It must not be registered in `ToolRegistry`, because it is not an LLM-invokable tool.
5. If `revertAppliedCommands()` throws after a partial revert, log the original error, immediately `tracker.clear()`, attempt the same error notification used by the legacy discard tool, and append a successful warning result plus an empty tracker artifact. This intentionally does not retain a mixed/partially reverted tracker state.
6. Ensure the success and failure transcript data says whether review changes were retained or had to be discarded. This makes later transcript inspection truthful while keeping user-facing copy independent of the legacy tool's wording.
