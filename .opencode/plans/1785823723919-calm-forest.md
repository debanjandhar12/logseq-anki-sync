# Uncommitted Changes Lifecycle Terminology

## User Requirement

Actually, can you write a new plan? This time, naming convention should be:
Applied -> Applied uncommited changes
Uncommited -> Not applied uncommited changes
Commited -> Commited changes

## Final Requirement After Discussion With User

### Clarification Q&A

1. Should the requested spellings be used literally in all UI and code identifiers?
   - Answer: Use standard spelling: `uncommitted` and `committed`.
2. Should the stable public discard-tool ID `logseq_clear_uncommitted_changes` be renamed?
   - Answer: No. It already uses the selected standard spelling and remains unchanged.

### Final Summarized Requirements

- Use these exact lifecycle state labels in user and model-facing copy:
  - **Applied uncommitted changes**: reversible graph changes currently exist in Logseq.
  - **Not applied uncommitted changes**: reversible commands are retained but are not currently reflected in Logseq.
  - **Committed changes**: changes have been finalized and are no longer reversible through the tracker.
- Retain action verbs as verbs: **Revert**, **Discard**, and **Commit**.
- Keep the existing public discard tool API stable, including `LogseqClearUncommittedChangesTool` and `logseq_clear_uncommitted_changes`.
- Retain the direct existing-artifact persistence path for Revert. It must not create a fake tool-call history entry and must not stop an active chat thread.
- Retain discard sequencing: stop an active thread before confirmation, then cancel pending calls and invoke the existing clear tool only after the user confirms.
- Keep generic reversible-transaction core names and persisted artifact schemas unchanged.

## Solution

### Lifecycle Model

Render lifecycle state from the existing `LogseqReversibleTransactionTracker`; do not add a persisted lifecycle enum.

| Tracker condition | User-facing lifecycle label | Required behavior |
| --- | --- | --- |
| Has graph mutation commands and `hasAppliedGraphMutations()` is true | `Applied uncommitted changes` | The graph contains reversible changes. Revert and Discard can first undo these mutations. Branch switching remains guarded. |
| Has graph mutation commands and `hasAppliedGraphMutations()` is false | `Not applied uncommitted changes` | Commands are retained in the tracker but absent from the graph. Branch switching is allowed without a revert prompt. |
| Commit completes and clears the tracker | `Committed changes` | A terminal success state/message only. The toolbar indicator is hidden because there is no longer a tracked reversible state. |

Do not use `Review changes`, `review commands`, `ready to apply`, `queued review changes`, or `permanent changes` as the primary lifecycle terms after this migration.

### Preserve Core And Tool Compatibility

Keep all generic reversible-transaction implementation and serialization names unchanged. In particular, do not rename:

- `src/core/logseq-reversible-transaction-tracker/`
- `LogseqReversibleTransactionTracker`
- `LogseqReversibleTransactionTrackerSerializer`
- `BaseReversibleCommand`
- `revertAppliedCommands()`, `clear()`, `hasAppliedGraphMutations()`, `appliedCommandCount`
- `LogseqReversibleTransactionTracker` artifact key/type
- `createLogseqReversibleTransactionTrackerArtifact`, tracker lookup helpers, and artifact patch/persistence APIs

These are reusable technical concepts and persisted data structures, not product lifecycle labels.

Keep the clear/discard tool stable:

- Keep `src/chat-app/tools/impl/LogseqClearUncommittedChangesTool.tsx`.
- Keep the class `LogseqClearUncommittedChangesTool`.
- Keep `LogseqClearUncommittedChangesTool.NAME` exactly equal to `logseq_clear_uncommitted_changes`.
- Keep the `ToolRegistry` registration, barrel export, and synthetic discard history entry on that ID.
- Do not add an alias or migration: the current ID already uses the agreed spelling, and tracker artifacts are independent of tool names.

### Update The Review-Changes Display

Modify `src/chat-app/components/ReviewChangesDisplay.tsx` without renaming the component/file. It remains a suitable UI container name; the state labels and copy carry the new lifecycle terminology.

#### State derivation and summary

- Update `ReviewChangesLifecycleLabel` and `getReviewChangesLifecycleLabel()` to return:
  - `Applied uncommitted changes` for graph mutation commands with applied mutations.
  - `Not applied uncommitted changes` for graph mutation commands with no applied mutations.
- Preserve current visibility rules: no tracker or zero graph-mutation command count returns `null` and hides the indicator.
- Preserve current command/page calculation: only graph-mutation commands count, and `changedPageCount` comes from tracker metadata.

#### Popover copy and actions

- Change the trigger `aria-label` from `Review changes` to `Uncommitted changes`.
- Change `Review commands` to `Uncommitted commands`.
- Keep `Changed pages` unchanged.
- Rename the secondary action from `Revert and keep for review` to `Revert`.
- Keep it non-destructive/secondary styled. It transitions Applied uncommitted changes to Not applied uncommitted changes while retaining commands.
- Rename the destructive action from `Revert and discard` to `Discard` or `Revert and discard`; choose `Revert and discard` if the label must make the applied-state consequence explicit. Use the same wording in the confirmation action.

#### Revert path

Keep `revertAndKeepReviewChanges()` behavior intact; rename only user/model-facing messages if the existing internal symbol remains. The path must:

1. Read the latest `findLastLogseqReversibleTransactionTracker()` result from current runtime messages.
2. Return safely if no artifact is located.
3. Call `tracker.revertAppliedCommands()` only when `hasAppliedGraphMutations()` is true.
4. Persist the updated tracker at its existing message/tool-call location through `persistLogseqReversibleTransactionTrackerArtifact()`.
5. Never append a synthetic keep/revert tool-call history entry.
6. Never call `runtime.cancelRun()`, `waitForThreadRunToStop()`, or `cancelPendingToolCallsInThread()`.
7. On a partial revert failure, clear the tracker, show an error that states uncommitted changes were discarded, then persist the cleared tracker to the existing artifact location.

Update operation/failure wording from review terminology to the new labels. Example: `Failed to revert applied uncommitted changes: <reason>. Uncommitted changes were discarded.`

#### Discard path and confirmation

Keep `revertAndDiscardReviewChanges()` runtime behavior unchanged, while replacing review terminology in its confirmation/error copy:

1. When a discard button is clicked, set busy state before any async work.
2. If the thread is running, call `runtime.cancelRun()` and await `waitForThreadRunToStop()` before opening `showConfirmModal`. This stabilizes the message/tracker state before user confirmation.
3. Show confirmation text explaining that **applied uncommitted changes** will be reverted and all uncommitted changes will be discarded. Use a confirming label matching the action, such as `Revert and discard`; use `Keep uncommitted changes` for cancel.
4. If the dialog closes or is rejected, do not mutate the tracker, cancel pending tools, invoke the clear tool, append a history entry, or close the popover. The already running thread intentionally remains stopped.
5. After confirmation only, call `cancelPendingToolCallsInThread()`, read the stabilized runtime messages, and execute `LogseqClearUncommittedChangesTool` with `{}`.
6. Preserve the real clear-tool response/artifact in the existing synthetic discard tool-call entry and close the popover after success.
