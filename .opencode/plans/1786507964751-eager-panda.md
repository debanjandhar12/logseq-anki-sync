# Preserve Terminated Tool Results Across Continuations

## 1. User Requirement

In 36115ee4, stop button was implemented. When it is clicked, tool result that "User terminated the operation" gets added. However, after continuation by user and further successful tool calls, the tool result gets removed. This results in following error:
Tool results are missing for tool calls call_00_i68vThuJalLRXwHnuyNT9690, call_01_z1lRQwy50UHMZ4Qlcz0N4135.

Investigate the issue and fix.

## 2. Final Requirement After Discussion With User

### 2.1 Clarification Q&A

- Q: Should the fix coordinate only stop/history persistence, or address the shared race in all current thread mutations?
- A: Migrate all current thread mutations to one serialized per-thread update mechanism.

### 2.2 Final Summarized Requirements

- Fix the root cause that allows later thread writes to overwrite the synthetic termination result added by Stop.
- Make every current mutation of a stored thread atomic across its complete read/modify/write operation and serialize mutations per thread.
- Preserve existing behavior for stopping, history appends, thread metadata, artifact persistence, initialization, and deletion.
- Add deterministic regression coverage proving concurrent mutations cannot remove a terminated tool result and that subsequent message/tool-call persistence remains valid.

## 3. Existing System

### Stop and model-message flow

- `src/chat-app/runtime/stopThread.ts` cancels an active assistant-ui run, transforms the latest runtime export with `terminateToolTurn`, imports the transformed repository into the live runtime, and separately persists the entire repository.
- `src/chat-app/runtime/terminateToolTurn.ts` correctly adds `{success: false, error: "User terminated the operation"}` with `isError: true` to unresolved calls and marks the assistant message `incomplete/cancelled`.
- `src/chat-app/runtime/LocalChatModelAdapter/message-conversion.ts` converts a retained error result to an AI SDK `output-error`; AI SDK then emits the required matching `tool-result`. If the result is absent, it emits an input-only tool call, and AI SDK reports missing tool results on the next request. Conversion is therefore exposing, not causing, the data loss.

### Root cause

- `LocalThreadHistoryAdapter.append`, `stopThread.persistRepository`, tracker-artifact persistence, and `LocalThreadListAdapter` metadata methods each independently load a complete thread, mutate their snapshot, and save the complete thread.
- assistant-ui inserts a continuation into the live runtime and invokes history persistence without awaiting it. Stop also imports the terminal live state before its storage write finishes. The operations can consequently overlap.
- Example lost update: stop and continuation both load the old repository; stop saves the terminated result; continuation then saves its stale snapshot plus the new message, restoring the old unresolved tool call. Later successful calls make the invalid history reach the model and trigger the reported error.
- Serializing only `saveThread` would not fix this: stale reads could still occur before the serialized saves. The lock must cover read, transformation, and write as one transaction.

### Constraints and patterns

- `ThreadStore` is the central abstraction over `LogseqPluginStorageManager`; direct thread-file mutation should remain encapsulated there.
- `await-lock` is already a dependency and is used by `LogseqReversibleTransactionOperationLockManager` for exclusive async operations.
- Serialization can protect concurrent writers within this plugin instance; it is not a distributed lock against external processes.
- Existing stop tests use a mocked runtime/store and verify immediate terminal state, but do not reproduce overlapping history persistence.

## 4. Solution

### 4.1 Add an atomic per-thread mutation API

Modify `src/core/stores/thread-store/ThreadStore.ts`:

- Correct `loadThread`'s return type to `Promise<ThreadFileData | null>`.
- Introduce a typed `ThreadStore.updateThread<TResult>(threadId, updater): Promise<TResult>` API. Use a discriminated updater result so callers explicitly choose either:
  - `save`: provide the resulting `ThreadFileData` and caller result; or
  - `skip`: perform no write and return the caller result.
- Keep the actual serialization/storage write private so application code cannot perform a new uncoordinated load/modify/save sequence.
- Maintain a per-thread `AwaitLock` entry with a holder/waiter count. Acquire it before the strict storage read and hold it through updater execution, JSON serialization, and `saveFile` completion. Release in `finally`; remove only an idle entry still mapped to the same object so failures cannot poison the queue and lock entries do not leak.
- Allow different thread IDs to update concurrently while preserving invocation order for each individual thread.
- Use a strict private mutation read:
  - absent storage supplies `null` to the updater;
  - malformed JSON or storage access errors reject without invoking the updater or overwriting data;
  - the public read path may retain its current tolerant behavior for UI consumers.
- Document that updater callbacks must not call a `ThreadStore` mutation method. The per-thread locks are deliberately non-reentrant, and nested cross-thread mutations could introduce lock-order deadlocks.
- Serialize `deleteThread` through the same per-thread lock. Preserve its current best-effort behavior (storage deletion failures are swallowed), while always releasing the lock.
- Make the raw storage save helper private/remove public `saveThread` once every caller is migrated, preventing future bypasses.

Conceptual contract:

```ts
ThreadStore.updateThread(threadId, (current) =>
    current
        ? {type: "save", threadData: {...current, title}, result: undefined}
        : {type: "skip", result: undefined}
);
```

### 4.2 Migrate repository writers

Modify `src/chat-app/runtime/LocalThreadHistoryAdapter.ts`:

- Perform message upsert, `headId` update, and `updatedAt` update inside `ThreadStore.updateThread`, using the latest repository loaded under the lock.
- Explicitly throw if the thread is absent, matching the fact that append requires an initialized thread.
- Preserve all unrelated messages, branches, metadata, and fields from the latest stored thread.

Modify `src/chat-app/runtime/stopThread.ts`:

- Replace `persistRepository`'s load/save pair with `ThreadStore.updateThread`.
- Preserve the existing whole-repository terminal snapshot, `updatedAt`, descriptive missing-thread error, live `runtime.import` ordering, and `persistenceFailed` reporting.
- Retain `pendingStops`; it deduplicates stop semantics, while `ThreadStore` independently serializes persistence.

Modify `src/chat-app/runtime/persistLogseqReversibleTransactionTrackerArtifact.ts`:

- Apply the artifact patch to the latest repository inside `updateThread`.
- Preserve the current no-op for an absent thread/repository and preserve stale-location errors without writing partial state.
- Keep the live runtime patch before durable persistence.

### 4.3 Migrate lifecycle and metadata writers

Modify `src/chat-app/runtime/LocalThreadListAdapter.ts`:

- `initialize`: atomically create only when absent; concurrent initializers must observe the first committed creation instead of overwriting it.
- `rename`, `archive`, and `unarchive`: mutate the latest thread under `updateThread` and fail explicitly if the thread is absent.
- `generateTitle`: update the latest thread under the lock and retain the existing no-op if the thread disappeared.
- `delete`: continue delegating to `ThreadStore.deleteThread`, now serialized by the store.
- Keep `list` and `fetch` as read-only point-in-time operations.

After migration, search for and eliminate every `ThreadStore.saveThread` use and any direct thread-group `saveFile`/`deleteFile` outside `ThreadStore`.

### 4.4 Add deterministic regression tests

Add `tests/src/core/stores/ThreadStore.test.ts` with a controllable storage double/deferred promises:

- Same-thread updates execute serially, and the second updater reads the first committed state.
- Different thread IDs remain concurrent.
- Reproduce the reported lost-update shape: queue a stop-style repository update and later history/metadata-style transformations, then assert the old tool call retains its termination result together with newer messages/fields.
- Verify updater and storage-write failures release the lock and do not block the next operation.
- Verify `skip`, return values, absent-thread initialization, corrupt-data rejection, and initialize/delete ordering.

Add `tests/src/chat-app/runtime/LocalThreadHistoryAdapter.test.ts`:

- Verify append upserts by message ID, sets `headId`/`updatedAt`, preserves prior terminated calls and branch data, and rejects an absent thread.
- Include a stop-result-plus-continuation scenario that asserts both the terminated old assistant message and newly appended message remain persisted.

Update `tests/src/chat-app/runtime/stopThread.test.ts`:

- Mock/exercise `ThreadStore.updateThread` instead of separate load/save methods.
- Preserve all existing stop assertions.
- Verify stop persists through the atomic updater, waits for persistence, retains live terminal state on failure, and handles an absent stored thread as `persistenceFailed`.

Update `tests/src/chat-app/runtime/persistLogseqReversibleTransactionTrackerArtifact.test.ts`:

- Verify persistence patches the repository supplied inside the atomic updater, preserves concurrently/current metadata and tool results, skips missing state, and performs no write for stale locations.

Add or update `tests/src/chat-app/runtime/LocalThreadListAdapter.test.ts`:

- Verify concurrent initialization writes once, metadata changes preserve the repository, title generation retains absent-thread behavior, and lifecycle mutations use atomic updates.

No user-facing documentation change is necessary because this is an internal durability correction with unchanged UI behavior.
