# Tool Result Size Limit

## 1. User Requirement

> I need you to implement a way to limit tool result size. First, we will need to introduce a constant in src/constant.ts called CHAT_APP_AGENT_TOOL_RESULT_MAX_CHAR = 120000
>
> When CHAT_APP_AGENT_TOOL_RESULT_MAX_CHAR is exceded, we need to call ToolResultStore and store the output there (only when exceeded, if not exceded no need to store output in ToolResultStore).
>
> Aditionally, instead of returning full result in ChatResponse, we need to keep the head and truncate the rest with the message:
> "...<removed> lines truncated...
>
> The tool call succeeded but the output was truncated. Full output saved to: <file_path>
> Use Bash tool to search and read with offset/limit to view specific sections."
> The file path will be ${JUST_BASH_USER_HOME}/${ToolResultStore.groupName}/${filename_with_ext}
>
> Read assistant ui skills and the current code to find the best location to implement these logic.

## 2. Final Requirement After Discussion With User

### Clarification Q&A

- Q: How should structured results be measured and represented when truncated?
  A: Pretty-print the complete result with `JSON.stringify(result, null, 2)`, measure JavaScript string characters, and use that readable serialization as the retained head.
- Q: Should truncation affect only model context or the assistant-ui result as well?
  A: Replace the oversized result everywhere, including assistant-ui state/UI, persisted history, and model context. The full value remains only in `ToolResultStore`.
- Q: Should the requested constant go in a new singular `src/constant.ts` or the existing constants module?
  A: Add it to existing `src/constants.ts`.
- Q: Is the 120,000-character budget for the entire returned notice or only the retained head?
  A: Keep the first 120,000 characters as the head, then append the notice; the final returned string may exceed 120,000 characters by the notice length.
- Q: What should the truncation count represent?
  A: Report the number of removed characters, changing the original `lines truncated` wording to `characters truncated`.
- Q: What happens if storing an oversized result fails?
  A: Return a tool error through the existing `executeFrontendTool()` error handling rather than claiming the output was saved or returning the oversized result.
- Q: Which tool paths are in scope?
  A: Automatically executed application tools routed through `executeFrontendTool()` only. Provider-native, human approval, synthetic, cancellation, and recovery results are out of scope.
- Q: Should error results be stored and truncated?
  A: No. Apply the policy only to successful results, matching the success wording in the notice.

### Final Summarized Requirements

- Add `CHAT_APP_AGENT_TOOL_RESULT_MAX_CHAR = 120000` to `src/constants.ts`.
- For each successful app-tool response in `executeFrontendTool()`, pretty-serialize `response.result` and compare its `.length` to the limit.
- Leave results at or below the limit unchanged and do not write them to `ToolResultStore`.
- For a result over the limit, save the complete original JSON value, replace the returned result everywhere with the first 120,000 serialized characters plus:

```text
...<removed> characters truncated...

The tool call succeeded but the output was truncated. Full output saved to: <file_path>
Use Bash tool to search and read with offset/limit to view specific sections.
```

- Build `<file_path>` from `JUST_BASH_USER_HOME`, `ToolResultStore.groupName`, and the actual generated filename including `.json`.
- Do not leak the original oversized result through assistant-ui `modelContent` or a tool-specific `toModelOutput` conversion.
- If storage fails, use the existing failed `ChatToolResponse` behavior.

## 3. Solution

### Existing Runtime Flow And Chosen Integration Point

The repository does not contain a `ChatResponse` type. Application tools return `ChatToolResponse`, which extends `assistant-stream`'s `ToolResponse`, and the runtime normalizes every automatically executed app-tool result in `executeFrontendTool()`:

1. `BaseChatTool.getDefinition()` exposes each app tool as an `assistant-stream` `Tool`.
2. `LocalAISDKChatModelAdapter` collects non-human app-tool calls and invokes `executeFrontendTool()`.
3. `executeFrontendTool()` calls `tool.execute()` and normalizes plain values or `ToolResponse` instances through `ToolResponse.toResponse(output)`.
4. The normalized `result`, `artifact`, `isError`, and optional `modelContent` are merged into the assistant-ui tool-call part.
5. That part is then rendered, persisted in thread history, and converted into the next AI SDK model request.

The limit belongs between steps 3 and 4 in `src/chat-app/runtime/LocalChatModelAdapter/tool-execution.ts`. Applying it in individual tools would duplicate policy and miss future tools. Applying it in `ChatToolResponse.success()` would be synchronous and would not have the tool call ID needed for storage. Applying it during message conversion would protect model context too late because the oversized result would already be in assistant-ui state and persisted history.

The selected scope intentionally excludes these bypass paths:

- Provider-native tool results are attached directly by `LocalAISDKChatModelAdapter` and do not pass through `executeFrontendTool()`.
- Human-tool results are submitted by assistant-ui UI callbacks.
- Synthetic, cancellation, and recovery results are generated directly and currently contain small status payloads.
- UI-only `artifact` values are not tool results and can contain transaction metadata required by existing features.

### Constants

Modify `src/constants.ts`:

- Export `CHAT_APP_AGENT_TOOL_RESULT_MAX_CHAR` beside `CHAT_APP_AGENT_MAX_STEPS`.
- Use this single value for threshold comparison and head slicing.

### Storage Filename Contract

Modify `src/core/stores/tool-results/ToolResultStore.ts`:

- Change `storeToolResult()` from `Promise<void>` to `Promise<string>`.
- Continue storing the complete original JSON value under the existing `${toolCallId}_${toolName}.json` naming convention.
- Return the generated filename after a successful save so callers use the exact storage name rather than duplicating private filename logic.
- Generate the filename once before calling `LogseqPluginStorageManager.saveFile()`, pass that value to storage, and return the same value only after the awaited save succeeds.
- Keep filename generation encapsulated in `ToolResultStore`; no unrelated sanitization or storage-format changes are included.

Why this API changes: the truncation notice must contain the exact persisted filename, but `getFileName()` is private and `storeToolResult()` currently returns no identifier. Returning the filename makes persistence the source of truth and ensures the runtime cannot claim a location until the write succeeds. The alternatives are weaker: duplicating `${toolCallId}_${toolName}.json` in the runtime creates two naming authorities, while making `getFileName()` public lets callers construct paths for files that may never have been stored. Existing callers do not depend on a `void` value, so changing the resolved value is backward-compatible for current usage.

The stored content remains the complete original value serialized by the store with compact `JSON.stringify(result)`. The readable inline head is independently generated from pretty JSON; the file does not need to match the display formatting to preserve the full data.

### Central Result Limiting

Modify `src/chat-app/runtime/LocalChatModelAdapter/tool-execution.ts`:

- Apply the policy immediately after `ToolResponse.toResponse(output)`. This is the earliest shared point with the normalized result, tool call ID, and tool name, before assistant-ui state, thread persistence, rendering, or the next model request receives the value.
- Only inspect responses where `response.isError` is false.
- Pretty-serialize the result once with `JSON.stringify(response.result, null, 2)` and compare its JavaScript `.length` to `CHAT_APP_AGENT_TOOL_RESULT_MAX_CHAR`.
- At or below the boundary, preserve all current behavior, including existing `modelContent` and `tool.toModelOutput`, and perform no storage write.
- Above the boundary, await `ToolResultStore.storeToolResult(toolCallId, toolName, response.result)` before constructing or returning the replacement.
- Construct the Bash-visible path from imported values, not hard-coded path segments: `${JUST_BASH_USER_HOME}/${ToolResultStore.groupName}/${filename}`.
- Slice the serialized result at exactly `CHAT_APP_AGENT_TOOL_RESULT_MAX_CHAR` characters.
- Compute the removed character count as `serialized.length - CHAT_APP_AGENT_TOOL_RESULT_MAX_CHAR`.
- Construct the replacement with explicit blank-line separation:

```ts
`${serializedResult.slice(0, CHAT_APP_AGENT_TOOL_RESULT_MAX_CHAR)}\n` +
    `...${removedCharacterCount} characters truncated...\n\n` +
    `The tool call succeeded but the output was truncated. Full output saved to: ${filePath}\n` +
    "Use Bash tool to search and read with offset/limit to view specific sections."
```

- Return that replacement string as `result`, retain the original `artifact`, and retain `isError: false`.
- Do not retain response-provided `modelContent` and do not invoke `tool.toModelOutput` for an oversized response. This is required because assistant-ui's message conversion uses `modelContent` as a separate model-facing representation; preserving an original large `modelContent`, or deriving one from the full result, could bypass the new limit.
- Let storage or serialization exceptions reach the existing `catch`, which converts them into `ChatToolResponse.error(...)` and preserves current tool failure semantics.
- Keep `artifact` handling unchanged because the requested limit concerns the tool result, not UI-only transaction metadata.

Implement the decision as a single branch in `executeFrontendTool()` rather than adding a general-purpose utility. The policy has one caller, and keeping it adjacent to normalized response handling makes the distinction between normal and oversized `modelContent` behavior explicit.

The resulting control flow is:

```text
execute tool
  -> normalize ToolResponse
  -> response is error: preserve current error behavior
  -> pretty result length <= 120000: preserve current result/modelContent behavior
  -> pretty result length > 120000:
       store complete original result
       -> save succeeds: return retained head + saved-path notice
       -> save fails: existing catch returns a tool error
```

Character count means JavaScript UTF-16 string length because the requirement names a character limit and the agreed comparison is `.length`; this plan does not introduce UTF-8 byte counting or token estimation. The threshold is strictly `>`: exactly 120,000 characters remain inline and are not stored.

The final replacement is intentionally longer than 120,000 characters because the agreed behavior retains a 120,000-character head and appends the notice afterward.

### Tests

Add `tests/src/chat-app/runtime/LocalChatModelAdapter/tool-execution.test.ts` with focused tests around `executeFrontendTool()` using `InMemoryStore`:

- A successful result below the limit is returned unchanged and creates no file in `ToolResultStore.groupName`.
- A successful result whose pretty serialization is exactly 120,000 characters is returned unchanged and creates no file.
- A successful result one or more characters over the limit stores the complete original result at `${toolCallId}_${toolName}.json`.
- The oversized replacement begins with exactly the first 120,000 pretty-JSON characters.
- The oversized replacement reports the exact omitted character count.
- The oversized replacement includes `/home/user/tool-results/<filename>.json` and the exact Bash offset/limit instruction.
- The persisted JSON parses back to the original structured result, proving truncation affects only the returned copy.
- An oversized response with explicit original `modelContent` returns no original `modelContent`.
- An oversized response from a tool with `toModelOutput` does not call that function.
- An oversized error result is not stored or truncated.
- A forced storage failure is converted to the existing failed tool result and does not claim a saved path.

Test setup and fixture details:

- Assign `LogseqPluginStorageManager.store` to a uniquely named `InMemoryStore` and call `InMemoryStore.clearAll()` in `beforeEach`, matching existing just-bash storage tests.
- Build exact-boundary string fixtures with JSON quote overhead included. For a JSON string, `JSON.stringify(value, null, 2).length` is `value.length + 2`, so use payload lengths derived from the exported constant rather than embedding another `120000` literal.
- Use stable `toolCallId` and `toolName` values and assert the exact expected filename, covering the changed `storeToolResult()` return contract through the runtime-generated notice.
- Read persisted content through `LogseqPluginStorageManager.getFileContent()` and parse it for equality with the original result.
- Read `LogseqPluginStorageManager.getFiles(ToolResultStore.groupName)` to prove below-limit, exact-limit, and oversized-error cases do not write files.
- Use a `vi.fn()` `toModelOutput` implementation to prove it is skipped only for oversized successful results and remains active for normal results.
- Use a one-test `vi.spyOn(LogseqPluginStorageManager, "saveFile").mockRejectedValueOnce(...)` to simulate deterministic storage failure, then restore the spy so global storage state does not leak across tests.
- Assert storage failure produces `{success: false, error: <message>}` with `isError: true`; do not assert an oversized fallback because that would violate the limit.
- Pass an inert `AbortSignal` and an empty message array to `executeFrontendTool()` so tests exercise the same public runtime function without starting the full assistant-ui runtime or requiring Logseq.

No separate `ToolResultStore.test.ts` is necessary for this feature because the runtime test verifies the store's generated filename, persisted full value, and returned saved path together. Existing just-bash tests already verify that files in `ToolResultStore.groupName` are readable at `/home/user/tool-results` and remain read-only.
