## 2. Final Requirement After Discussion With User

### 2.1 Clarification Q&A

- **Which prompt files become commands?** Only dedicated `COMMAND_*.md` files. Existing system and skill prompts remain unchanged.
- **What does a missing `user-invocable` mean?** Follow Skill Editor behavior: commands are enabled unless explicitly disabled (`user-invocable: false`).
- **When is a built-in command user-controllable?** Only when `built-in-command-user-controllable: true`; missing or false locks the enabled checkbox.
- **What context is used by native Logseq invocation routes?** A block slash command attaches its callback block. A Logseq Command Center invocation has no attachment. Both render the prompt, obey the thread flag, open chat, and do not send.
- **Was the second flashcard note intended to describe video detection?** Yes. Implement separate flashcard and video block utilities.
- **Fallback labels?** Use `Other Blocks` and `Other Pages`.
- **Can built-in invoke conditions be edited?** No. Built-in source, invoke conditions, and new-thread behavior remain read-only; only the enabled checkbox may be changed when explicitly user-controllable.
- **What happens to an existing composer draft?** Replace the entire draft: clear text and attachments before applying the selected command.
- **When do native registration edits take effect?** Newly added Command Center and slash commands take effect on the next Command Editor save, because the plugin re-runs native registration then. Removals — disable, delete, rename, reroute — require a plugin reload, because Logseq exposes no documented unregister API; until reload, the stale entry refuses to run and warns. Context-menu palettes read current storage every time they open.

- **Are command names unique?** Yes, case-insensitively. The name is also the storage filename stem and native Logseq label.
- **How are disabled commands presented?** `user-invocable: false` commands are hidden from palettes and skipped during native registration.

### 2.2 Final Summarized Requirements

1. Add a storage-backed command-file domain parallel to skills, with dedicated parsing, validation, body-only Mustache rendering, built-in initialization, and a `commands` storage group.
2. Use this frontmatter contract:
   - required `name: string`;
   - required non-empty `invoke-condition: CommandInvokeCondition[]`;
   - optional `user-invocable: boolean`, default `true`;
   - optional `command-invoke-in-new-thread: boolean`, default `true`;
   - optional `built-in-command: boolean`;
   - optional `built-in-command-user-controllable: boolean`.
3. Add an immutable built-in `Add as attachment` command with an empty body, all nine block/page context-menu leaf conditions, `command-invoke-in-new-thread: false`, and a locked-enabled state so it remains available and sorts first.
4. Replace both existing `Add to AI Chat` context items with `Invoke AI Command`. Resolve the clicked entity to exactly one context condition, open a searchable command palette, and invoke the selected matching command.
5. Invocation is composition, not a new layer. A user command is a `{name, execute()}` object whose `execute()` renders the body, then runs existing `chat-interop` commands in order — optional `NewThreadCommand`, `ClearComposerCommand`, optional `AddAttachmentCommand`, `SetComposerTextCommand` — and finally `OpenAIChatCommand` exactly once. Rendering happens before anything is enqueued so a failure cannot destroy the current draft. Nothing sends automatically.
6. Register enabled commands configured for native Command Center or block slash invocation at startup and again after each successful Command Editor save. Slash invocation attaches its block; Command Center invocation does not attach an entity.
7. Add a Command Editor settings button and Skill Editor-style modal. The editor controls `user-invocable` and `invoke-condition`, validates all command files, protects built-ins, and exposes invoke conditions through an accessible hierarchical checkbox popover.
8. Use the existing `cmdk`/shadcn command primitives and `UI.showModal`; do not import `neigebaie/shadcn-ui-tree-view` unchanged. Its animation/context-menu/hover dependencies and mouse-oriented/global-document behavior are excessive for a fixed two-level selection tree.
9. Use the installed public Logseq API `logseq.App.registerCommandPalette` (or its equivalent `registerCommand` palette form) for Command Center registration. The requested `registerSimpleCommand` method is not present in the installed `@logseq/libs` typings.
10. Own the user-facing command system in a dedicated `src/core/user-commands/` module with exactly two responsibilities: registering entry points in Logseq chrome, and producing `UserCommand` objects for whichever picker is in play. `src/core/chat-interop/` stays a thin transport of one-operation `ChatCommand`s and must not host classification, palette orchestration, native registration, or built-in command lifecycle. The word "command" already means three different things here (chat interop commands, reversible transaction commands, user commands), so module boundaries — not naming alone — keep them apart.
11. `user-commands` never calls `ChatInteropCommandQueue.enqueue` directly and defines no new `*Command` class. It composes the existing `chat-interop` command classes; `UserCommand` is an interface. Two new one-operation commands are added to `chat-interop`: `ClearComposerCommand` and `SetComposerTextCommand`.

### 4.0 Module layout and ownership

Decision: introduce `src/core/user-commands/` as the owner of the user-facing command system. Keep `src/core/command-parser/` and `src/core/stores/command-file-store/` where they already are — that mirrors the existing `skill-parser` + `stores/skill-file-store` precedent and avoids moving 13 source files and 6 test files for no behavioral gain.

Target layout:

```text

src/core/stores/command-file-store/            (unchanged) persistence under group "commands"

src/core/user-commands/

    constants.ts                               ADD_AS_ATTACHMENT_COMMAND_NAME
```

The module has exactly two responsibilities:

**(a) Registration.** Put the plugin's entry points into Logseq chrome: the `Invoke AI Command` block/page context menu items, plus one native Logseq command-palette entry and one slash command per command configured for those routes.

**(b) Production.** Given an invocation context, produce `UserCommand` objects — `{name, execute()}` — for whichever picker is in play (our palette, or a native Logseq callback). `execute()` composes existing `chat-interop` commands. It never touches `ChatInteropCommandQueue` directly.

Everything else already exists: the parser validates, the store persists, `chat-interop` transports, `useChatCommandHandler` applies.

Ownership rules, enforced by review:

- `src/core/user-commands/` may import from `chat-interop`, `command-parser`, `command-file-store`, `logseq/*`, and `ui/launchers`.
- `src/core/chat-interop/` must not import from `user-commands`, `command-parser`, or `command-file-store`. It stays usable without the command system.
- `src/ui/pages/AICommandPaletteModal/` must not import `CommandFileStore` and must not re-filter or re-sort. It receives `UserCommand[]`, renders it, and returns the selected one. Filtering/ordering rules live in `getUserCommands` so the native routes and the palette cannot diverge.
- `UserCommand` is an interface, not a class, and lives only in `user-commands`. The `*Command` **classes** remain exclusive to `chat-interop` (`ChatCommand` implementations) and to `logseq-reversible-transaction-tracker/commands` (`BaseReversibleCommand`). A reader can tell the three apart by location and by class-vs-interface.

Keep `"string-array"` command-specific unless extracting a generic frontmatter validator clearly reduces duplication without weakening skill typing. Array validation should report the relevant key/item range, not only the opening delimiter:

```ts
function validateInvokeConditions(value: unknown): CommandFileValidationIssue[] {
    if (!Array.isArray(value) || value.length === 0) {
        return [issueAtKey("invoke-condition", "invoke-condition must contain at least one value")];
    }

    const seen = new Set<string>();
    const issues: CommandFileValidationIssue[] = [];
    for (const condition of value) {
        if (
            typeof condition !== "string" ||
            !COMMAND_INVOKE_CONDITIONS.has(condition as CommandInvokeCondition)
        ) {
            issues.push(issueAtArrayValue(condition, `Unsupported invoke condition: ${String(condition)}`));
            continue;
        }
        if (seen.has(condition)) {
            issues.push(issueAtArrayValue(condition, `Duplicate invoke condition: ${condition}`));
        }
        seen.add(condition);
    }
    return issues;
}
```

### 4.2 Add the command file store — DONE

Follow the established store API so callers cannot save or retrieve a command without parser validation:

```ts
export class CommandFileStore {
    static readonly groupName = "commands";

    static getCommandFileName(command: Pick<CommandFileData, "name">): string {
        return `${command.name}.md`;
    }

    static getCommandFileNameFromContent(content: string): string {
        return this.getCommandFileName(parseCommandFile(content));
    }

    static async getCommandFile(fileName: string): Promise<CommandFileData | null> {
        try {
            const source = await LogseqPluginStorageManager.getFileContent(this.groupName, fileName);
            return parseCommandFile(source);
        } catch (error) {
            logger.warn(`Failed to load command file ${fileName}`, error);
            return null;
        }
    }

    static getCommandFileByName(name: string): Promise<CommandFileData | null> {
        return this.getCommandFile(this.getCommandFileName({name}));
    }

    static async saveCommandFile(content: string): Promise<void> {
        const fileName = this.getCommandFileNameFromContent(content);
        await LogseqPluginStorageManager.saveFile(this.groupName, fileName, content);
    }
}
```

Do not introduce Zustand solely for this domain. The editor owns unsaved state locally like Skill Editor; every short-lived context palette reloads storage when opened. This gives immediate behavior after Save without maintaining two sources of truth.

Handle external/manual storage edits deterministically:

- Log and skip malformed files while listing, including their physical filenames.
- Preserve the physical filename as each editor entry's `originalFileName`; saving a valid changed `name` performs delete-then-save rename semantics.
- Reject all logical duplicate names case-insensitively before the first storage mutation.
- Let a valid physical filename/content-name mismatch appear in the editor and repair it on Save.
- Do not silently swallow save failures. As with Skill Editor, report that the current multi-file save is non-transactional if a later operation fails.

#### 4.5.3 `createUserCommand` — the composition

`src/core/user-commands/createUserCommand.ts`:

```ts
export function createUserCommand(
    commandFile: CommandFileData,
    context: CommandInvocationContext
): UserCommand {
    return {
        name: commandFile.name,
        builtInCommand: commandFile.builtInCommand === true,
        execute: async () => {
            // Render before enqueueing anything: a template failure must not
            // destroy the user's current draft.
            const prompt = await renderCommandFileTemplate(commandFile.content);
            const attachmentUuid = "uuid" in context ? context.uuid : null;

            const steps: ChatCommand[] = [
                ...(commandFile.commandInvokeInNewThread ? [new NewThreadCommand()] : []),
                new ClearComposerCommand(),
                ...(attachmentUuid ? [new AddAttachmentCommand(attachmentUuid)] : []),
                new SetComposerTextCommand(prompt)
            ];

            // Each step command enqueues synchronously, so mapping them all at
            // once keeps the batch contiguous in the queue and prevents a second
            // invocation from interleaving between the steps.
            await Promise.all(steps.map((step) => step.execute()));

            // Reveal chat last, exactly once. Queued steps are flushed when the
            // runtime subscribes, so this also works from a cold start.
            await new OpenAIChatCommand().execute();
        }
    };
}
```

Notes on the ordering:

- `clear` after `new-thread`, never before: "replace the whole draft" applies to the destination composer, and a source-thread draft must survive a failed switch.
- `set text` after `add attachment`, so clearing cannot wipe the attachment.
- `SetComposerTextCommand("")` for `Add as attachment` is intentional, not a skipped step.
- Nothing in this path sends. There is no send/append command in `chat-interop` and none should be added for this feature.

#### 4.5.4 `getUserCommands` / `findUserCommand`

`src/core/user-commands/getUserCommands.ts` is the only place storage reads, filtering, and ordering happen, so our palette and the native routes cannot diverge:

```ts
export async function getUserCommands(
    context: CommandInvocationContext
): Promise<UserCommand[]> {
    const commandFiles = await CommandFileStore.getAllCommandFiles();
    return commandFiles
        .filter((commandFile) => commandFile.userInvocable)
        .filter((commandFile) => commandFile.invokeConditions.includes(context.condition))
        .sort((left, right) => {
            if (left.name === ADD_AS_ATTACHMENT_COMMAND_NAME) return -1;
            if (right.name === ADD_AS_ATTACHMENT_COMMAND_NAME) return 1;
            return left.name.localeCompare(right.name);
        })
        .map((commandFile) => createUserCommand(commandFile, context));
}

export async function findUserCommand(
    name: string,
    context: CommandInvocationContext
): Promise<UserCommand | null> {
    const commands = await getUserCommands(context);
    return commands.find((command) => command.name === name) ?? null;
}
```

Because both functions read storage at call time, `findUserCommand` doubles as the revalidation mechanism for native Logseq registrations: a command that was deleted, disabled, or rerouted since startup simply is not found, and the callback shows a warning instead of acting. #### 4.5.6 Queue hardening

Two real bugs in `src/core/chat-interop/queue/ChatInteropCommandQueue.ts:30-54` matter more now that one invocation is several queued items: the handler is resolved once per flush (stale if the runtime unmounts mid-await), and a handler rejection escapes the `while` loop, dropping every later item.

Resolve a handler before each item, peek rather than shift until it settles, and leave the item queued if no runtime remains:

```ts
private static async flush(): Promise<void> {
    if (this.isFlushing) return;
    this.isFlushing = true;
    try {
        while (this.pendingCommands.length > 0) {
            const handler = this.getCurrentHandler();
            if (!handler) return;

            const command = this.pendingCommands[0];
            try {
                await handler(command);
            } catch (error) {
                logger.error("Failed to execute queued chat command", error);
            } finally {
                if (this.pendingCommands[0] === command) this.pendingCommands.shift();
            }
        }
    } finally {
        this.isFlushing = false;
        if (this.pendingCommands.length > 0 && this.getCurrentHandler()) void this.flush();
    }
}
```

Add a `_resetForTesting()` static guarded to test builds rather than exposing the mutable statics.

Error reporting stays single-sourced: the palette/native callback layer reports "command unavailable" and classification failures; `useChatCommandHandler` logs runtime-application failures; the queue logs only otherwise-unhandled handler rejections to preserve progress.

Same file:

```ts
const registeredNativeKeys = new Set<string>();

export async function registerNativeUserCommands(): Promise<void> {
    const commandCenterContext: CommandCenterInvocationContext = {
        source: "command-center",
        condition: "Logseq Command Center"
    };

    for (const {name} of await getUserCommands(commandCenterContext)) {
        const key = createNativeCommandKey("command-center", name);
        if (registeredNativeKeys.has(key)) continue;
        registeredNativeKeys.add(key);

        logseq.App.registerCommandPalette(
            {key, label: name, keybinding: {mode: "global", binding: ""}},
            () => executeNativeUserCommand(name, commandCenterContext)
        );
    }

    // Slash commands need a per-invocation block UUID, so probe availability with
    // a placeholder context and resolve the real one inside the callback.
    const slashProbeContext: SlashCommandInvocationContext = {
        source: "block-slash-command",
        condition: "Block Slash Command",
        uuid: ""
    };

    for (const {name} of await getUserCommands(slashProbeContext)) {
        const key = createNativeCommandKey("slash", name);
        if (registeredNativeKeys.has(key)) continue;
        registeredNativeKeys.add(key);

        logseq.Editor.registerSlashCommand(name, async ({uuid}) => {
            if (typeof uuid !== "string" || uuid === "") {
                await logseq.UI.showMsg("Could not determine the current block.", "error");
                return;
            }
            await executeNativeUserCommand(name, {
                source: "block-slash-command",
                condition: "Block Slash Command",
                uuid
            });
        });
    }
}

async function executeNativeUserCommand(
    name: string,
    context: CommandInvocationContext
): Promise<void> {
    const command = await findUserCommand(name, context);
    if (!command) {
        await logseq.UI.showMsg(
            `"${name}" is no longer available. Reload the plugin to remove it.`,
            "warning"
        );
        return;
    }
    await command.execute();
}
```

The empty-`uuid` probe context is a small wart: `getUserCommands` needs a context to build `execute()`, but the real UUID only exists inside the callback. The probe result is used only for its names, never executed. ### 4.7 Build the command palette UI
