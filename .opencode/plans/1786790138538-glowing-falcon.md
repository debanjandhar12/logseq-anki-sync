# Persist Model Selector Choice

## 1. User Requirement

Currently, present selection of Model and varient in ModelSelector.tsx is not stored anywhere. I think it is stored in memory which gets reset after app restart? We need to store this inside settings (logseq has a update setting method). No need to add to actual setting schema but add to type and use it?

## 2. Final Requirement After Discussion With User

### 2.1 Clarification Q&A

- **Q:** When you say persist the selected “variant,” do you mean the reasoning-effort choice shown in the selector (`low`, `medium`, or `high`)?
  **A:** Reasoning effort.
- **Q:** If a saved model is no longer available after a provider or model-list change, how should selection recover?
  **A:** Use and persist the first currently available model.

### 2.2 Final Summarized Requirements

- Persist the selected model ID and reasoning effort across chat remounts and Logseq/plugin restarts.
- Store both values as optional, typed fields in `PluginSettings`, but do not expose them in Logseq's visible `settingsTemplate`.
- Read and write only through `LogseqSettingAccessor`.
- Preserve the existing defaults: first available model and `medium` effort.
- Validate stored values at runtime. If the stored model is unavailable, select and persist the first available model. If effort is missing or invalid, use and persist `medium`.
- Never send a stale model ID to the assistant runtime, including while the model list is empty or changing.

## 3. Existing System

- `src/chat-app/components/ComposerAction.tsx` gets provider-specific models from `useModelList()` and renders `ModelSelector` with uncontrolled mount-only defaults (`models[0]?.id` and `medium`). It does not provide change callbacks, so choices currently live only in React state.
- `src/chat-app/components/ModelSelector.tsx` supports controlled `value`/`effort` props and callbacks. Its internal `useControllableState` currently treats `undefined` as uncontrolled, so it cannot represent a controlled “no model available” state. `ModelSelectorModelContext` also registers any non-undefined raw ID even when that ID is absent from the current model list.
- `src/chat-app/hooks/useModelList.ts` rebuilds the model list after every settings-change event. Model IDs are provider/model-list dependent, so a provider change or custom-model removal can invalidate a stored selection.
- `src/settings.ts` owns `PluginSettings` and the visible Logseq schema. `lastWelcomeVersion` is an existing precedent for a typed setting that is intentionally omitted from the schema.
- `src/logseq/LogseqSettingAccessor.ts` provides the required `getPluginSettings()`, `updatePluginSettings(Partial<PluginSettings>)`, and settings-change listener APIs.
- The selector's “variant” is actually reasoning effort (`low`, `medium`, `high`). Its `variant="ghost"` prop is only button styling and must not be persisted.
- Vitest only discovers `*.test.ts`; React component/hook tests therefore use `createElement` and `react-dom/client`, following existing test conventions.

## 4. Solution

### 4.1 Add hidden typed settings

Modify `src/settings.ts`:

- Export a narrow `ReasoningEffort` type: `"low" | "medium" | "high"`.
- Add optional `selectedModelId?: string` and `selectedModelReasoningEffort?: ReasoningEffort` fields to `PluginSettings`.
- Do not add either field to `settingsTemplate`; they remain internal persisted state, like `lastWelcomeVersion`.

### 4.2 Centralize selection, validation, and persistence

Add `src/chat-app/hooks/usePersistedModelSelection.ts` and make it the state owner between settings, the current model list, and `ModelSelector`.

The hook will:

1. Synchronously initialize its preferred model ID and effort from `LogseqSettingAccessor.getPluginSettings()` so a remounted chat immediately restores persisted values.
2. Validate effort with a runtime type guard. Accept only `low`, `medium`, or `high`; normalize missing/invalid data to `medium`.
3. Derive the effective model synchronously from the current list:
   - return `undefined` when the list is empty;
   - retain the preferred ID when it exists in the list;
   - otherwise return the first model ID.
   This prevents even a transient render from exposing a stale stored ID.
4. Reconcile normalized defaults in an effect:
   - do not clear or overwrite the stored model while the list is empty;
   - once a non-empty list exists, update local preferred state and persist the first model if the stored/preferred ID is missing or unavailable;
   - persist `medium` when the stored effort is missing/invalid.
5. Expose model and effort callbacks for user selection. Validate model IDs against the current list and validate callback effort strings before changing state or writing settings. Keep the effort preference when switching models; the existing selector will omit it from runtime context if a future model does not support effort.
6. Optimistically update local state, then serialize settings updates through a promise-chain ref. Before each write, reread settings and omit fields already equal to the requested values. This preserves rapid A-to-B-to-C selection order and prevents the hook's own settings-change/model-list refresh from causing write loops.
7. Catch each write failure inside the queue and log it with `createLogger(LoggerCategory.CHAT_UI)` so later writes still run. Keep the current in-memory choice after a persistence failure rather than disrupting the active chat, and do not cancel already queued writes on unmount.

The hook does not need another broad settings listener: restart/remount restoration comes from the initial accessor read, provider/model-list changes already flow through `useModelList`, and optimistic state covers writes made by this selector.

### 4.3 Wire the selector as a controlled component

Modify `src/chat-app/components/ComposerAction.tsx`:

- Pass `models` to `usePersistedModelSelection`.
- Replace `defaultValue` and `defaultEffort` with controlled `value`, `effort`, `onValueChange`, and `onEffortChange` props returned by the hook.
- Update the component's project-change comment to mention Logseq-backed model and reasoning-effort persistence.

The resulting flow is:

```text
Logseq hidden settings -> persistence hook -> validated controlled selector
user choice -> optimistic hook state -> serialized LogseqSettingAccessor update
provider settings change -> useModelList refresh -> model-ID reconciliation
```

### 4.4 Make controlled empty state and runtime registration safe

Modify `src/chat-app/components/ModelSelector.tsx`:

- Change `useControllableState` to receive an explicit controlled flag instead of inferring control from `prop !== undefined`.
- In `ModelSelectorRoot`, determine control from whether each prop (`value`, `effort`, `open`) was supplied. This allows `value={undefined}` to remain controlled when no model is available, without affecting existing uncontrolled callers.
- Change `ModelSelectorModelContext` to use `selectedModel` and register `selectedModel.id` only when the ID resolves against the current model list. Register no model context for an empty list or stale ID.
- Extend the copied-component adaptation comment to document these project-specific controlled-state and stale-ID protections, as required by `src/chat-app/AGENTS.md`.

### 4.5 Add regression coverage

Add `tests/src/chat-app/hooks/usePersistedModelSelection.test.ts` using a small `createRoot`/`createElement` hook harness and mocked accessor/logger. Cover:

- restoring valid persisted model and effort;
- first-model/`medium` defaults and their persistence;
- invalid or missing effort normalization;
- unavailable stored model fallback and persistence;
- no model overwrite while the list is empty, followed by reconciliation when models arrive;
- fallback when a changed model list removes the selected ID;
- valid user model/effort updates and rejection of invalid callback values;
- idempotence after model arrays are recreated by settings refreshes;
- ordered rapid updates using deferred promises;
- failed writes are logged, local state remains usable, and subsequent queued writes still run.

Add `tests/src/chat-app/components/ModelSelector.test.ts` with focused assistant-ui registration mocks. Cover:

- controlled `value={undefined}` does not adopt the first model;
- empty lists and IDs absent from the list do not register model context;
- a valid controlled model and effort register the expected `modelName` and `reasoningEffort`.

If needed to guard the integration seam, add a small `ComposerAction` test that mocks the hook and selector and verifies controlled props/callbacks are forwarded; keep this only if the hook and selector tests do not directly cover the wiring.

No Docusaurus update is required because these are hidden implementation settings and the visible selector behavior is unchanged apart from persistence.
