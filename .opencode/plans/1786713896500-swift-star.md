# Disable Branch-Creating Actions After Commit

## 1. User Requirement

One more modification required: 
We need to disable the edit button / refresh button when already comitted artifact exists

## 2. Final Requirement After Discussion With User

### 2.1 Clarification Q&A

1. **Question:** The tracker artifact itself cannot distinguish commit from discard/no-op because all produce an empty tracker. What should count as an “already committed artifact” for disabling actions?
   **Answer:** Successful commit tool.
2. **Question:** Which message action buttons should become disabled after a successful commit exists on the selected branch?
   **Answer:** Actions before commit. Disable edit/reload on messages at or before the committed turn; later turns remain actionable.
3. **Question:** Should commits already stored before adding a typed commit outcome also disable actions when reopening old threads?
   **Answer:** New commits only. No migration is required because the plugin has not been released.

### 2.2 Final Summarized Requirements

- Persist an explicit, typed outcome in successful `logseq_commit_changes` tool results so a real commit can be distinguished from no-op success, discard, cleanup, and failure.
- On the currently selected assistant-ui branch, find the latest tool result whose outcome confirms that graph mutations were actually committed.
- Treat the user message that started that committed turn, the assistant commit message, and any assistant continuation messages before the next user message as locked.
- Disable user-message Edit and assistant-message Refresh for locked messages. Copy and branch-picker behavior are unchanged.
- Keep Edit and Refresh enabled, subject to their existing conditions, for turns after the latest commit.
- Do not migrate or infer commitment from old untyped results or human-readable result strings.

## 3. Existing System

### 3.1 Commit representation

- `src/chat-app/tools/impl/LogseqCommitChangesTool.tsx` defines `LogseqCommitChangesTool` and currently returns `ChatToolSuccessResult<{changes: string}>` for both real commits and successful no-op paths.
- A real commit executes retained commands, verifies applied graph mutations, clears the reversible tracker, and returns the text `Committed changes successfully...`.
- No-change paths also return success and an empty tracker artifact. Decline/discard and some cleanup paths can likewise leave an empty tracker artifact.
- Therefore, tracker emptiness is not a valid committed-state discriminator. A typed result field is required.

### 3.2 Current message actions

- `src/chat-app/components/UserMessage.tsx` renders `UserActionBar` imported from `src/shadcn/assistant-ui/thread.tsx`.
- The registry `UserActionBar` wraps its button in `ActionBarPrimitive.Edit`; assistant-ui currently disables it only for its intrinsic editing state.
- Repository convention requires customized assistant-ui components to be copied into `src/chat-app/components`; `src/shadcn` must remain upstream-compatible.
- `src/chat-app/components/AssistantActionBar.tsx` already owns custom Refresh behavior. It disables Refresh for reload-in-progress, running thread, disabled thread, and non-assistant roles, then applies the uncommitted-change branch guard before calling `reload()`.

### 3.3 Branch scope

- `useAuiState((state) => state.thread.messages)` is the reactive, linear message list for the selected branch. It must be used instead of scanning the complete persisted repository, which also contains sibling branches.
- Message IDs are stable identifiers and should be used to classify the action’s target; array indexes should only be derived from the current branch snapshot.

## 4. Solution

### 4.1 Add a typed commit outcome

Modify `src/chat-app/tools/impl/LogseqCommitChangesTool.tsx`:

- Export the commit result type and define successful outcomes explicitly, for example:

```ts
type LogseqCommitChangesSuccessResult = ChatToolSuccessResult<{
    changes: string;
    outcome: "committed" | "no-changes";
}>;
```

- Return `outcome: "committed"` only after commands execute, at least one graph mutation is confirmed applied, and the tracker is cleared without error.
- Return `outcome: "no-changes"` from every successful path that did not commit graph mutations:
  - no graph-mutation commands exist;
  - execution results in no applied graph mutations;
  - review finds no reviewable page changes.
- Keep declined, discarded, persistence-failed, preparation-failed, and execution-failed paths as `success: false`; they cannot create a commit boundary.
- Do not inspect the cleared tracker or parse `changes` text when detecting commits.

Update `tests/src/chat-app/tools/impl/LogseqCommitChangesTool.test.ts` to assert the typed outcome on every success path and ensure error/decline responses do not expose a committed outcome.

### 4.2 Add a current-branch committed-turn selector

Create `src/chat-app/utils/committedTurnBoundary.ts` with pure, React-independent helpers:

- `isSuccessfulLogseqCommitToolPart(part)`:
  - requires `part.type === "tool-call"`;
  - requires `part.toolName === LogseqCommitChangesTool.NAME` (or an exported shared tool-name constant if needed to avoid coupling);
  - structurally checks that `part.result` is an object with `success === true` and `outcome === "committed"`;
  - rejects pending/incomplete calls, malformed results, `"no-changes"`, failures, declines, and unrelated tools.
- `getLatestCommittedTurnBoundary(messages)`:
  - scan selected-branch messages from newest to oldest for the latest qualifying tool part;
  - after locating its assistant message, find the next user message;
  - return an exclusive message index equal to that next user message’s index, or `messages.length` if no later user turn exists.
- `isMessageInCommittedHistory(messages, messageId)`:
  - resolve the target by stable ID in the same current snapshot;
  - return true when its index is before the exclusive boundary;
  - return false when there is no commit boundary or the target is absent.

This turn-based boundary handles normal and non-alternating streams:

```text
[user A, assistant A (commit), assistant continuation, user B, assistant B]
 |---------------- locked ----------------| |--------- enabled --------|
```

The latest qualifying commit is authoritative. A later failure or no-op does not erase an earlier real commit boundary; a later real commit moves the boundary forward. Because callers pass only `state.thread.messages`, commits on inactive sibling branches do not affect the selected branch.

Add `tests/src/chat-app/utils/committedTurnBoundary.test.ts` covering no/pending/malformed/unrelated/failed/no-op/real commit results, turn boundaries, continuation messages, later turns, multiple commits, missing target IDs, non-alternating messages, and independent branch snapshots.

### 4.3 Add a committed-aware user action bar

Create `src/chat-app/components/UserActionBar.tsx` by copying the small relevant component from `src/shadcn/assistant-ui/thread.tsx` and documenting the divergence in its `Changes` comment.

- Subscribe to selected-branch messages, current message ID/role, current edit state, and existing thread running/disabled state.
- Derive `editDisabled` from existing assistant-ui-compatible conditions plus `isMessageInCommittedHistory(messages, messageId)`.
- Pass `disabled={editDisabled}` to the Edit button/primitive so the visual and accessible disabled state are preserved.
- Ensure the click path fails closed against a newly arrived commit or branch change. If retaining `ActionBarPrimitive.Edit` does not permit a fresh check, replace only its behavior with an explicit `aui.message().composer().beginEdit()` handler that rereads `aui.thread().getState()`, `aui.message().getState()`, and edit-composer state before acting.
- Preserve existing classes, tooltip, icon, `hideWhenRunning`, and `autohide="not-last"` behavior.

Modify `src/chat-app/components/UserMessage.tsx` to import this custom action bar instead of the shadcn registry implementation and extend its divergence comment. Do not modify `src/shadcn/assistant-ui/thread.tsx`.

### 4.4 Disable committed-history refresh safely

Modify `src/chat-app/components/AssistantActionBar.tsx`:

- Subscribe to selected-branch messages and current message ID.
- Add `isMessageInCommittedHistory(messages, messageId)` to `reloadDisabled`, retaining all current reload, running, thread-disabled, and role conditions.
- Keep Copy enabled; only Refresh is branch-creating and affected.
- Keep `useLogseqAppliedChangesBranchGuard` for eligible later turns because it protects applied uncommitted changes, which is independent of the committed-history lock.
- Reread current thread/message state before invoking the guard and again after the asynchronous guard resolves. Do not reload if a commit boundary arrived, the branch changed, the target ID disappeared/changed, or the thread became running/disabled while awaiting confirmation.
- Use a synchronous ref latch alongside `isReloading` to prevent rapid duplicate clicks before React commits the disabled-state render.
- Extend the component’s `Changes` comment to document committed-history locking.

### 4.5 Component regression tests

Add focused action-bar tests under `tests/src/chat-app/components/` using the project’s React/jsdom pattern and a minimal assistant-ui runtime fixture or controlled mocks:

- User Edit is disabled in the committed turn and enabled in a later turn.
- Assistant Refresh is disabled in the committed turn (including assistant continuation messages) and enabled in a later turn.
- Disabled clicks do not call `beginEdit()` or `reload()`.
- Eligible clicks retain existing behavior.
- A commit or branch change introduced after render but before action is rejected by the fresh handler check.
- A commit or branch change introduced while Refresh awaits the branch guard prevents reload afterward.
- Rapid Refresh clicks invoke at most one guard/reload flow.
- Copy remains available on a locked assistant message.
