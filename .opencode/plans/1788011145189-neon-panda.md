## 2. Final Requirement After Discussion With User

### 2.1 Clarification Q&A

1. **May the plan recommend better boundaries instead of treating every proposed path as fixed?**
   - Answer: **Recommend improvements.**
2. **How should `template-engine` be split?**
   - Answer: Move Mustache rendering/runtime context into `renderer/`; move Mustache validation and frontmatter splitting/validation into `parser/`; retain a top-level facade.
3. **Should old import paths remain as compatibility shims?**
   - Answer: **No.** Make a clean break, update all repository consumers, and remove old paths.

### 2.2 Final Summarized Requirements

The refactor is a good idea with one important correction:

| Proposal | Verdict | Final direction |
| --- | --- | --- |
| `skills` -> `skill-init` | Good | Rename as proposed; it contains initialization only. |
| Entire `user-commands` -> `user-commands-init` | Not good as proposed | Keep reusable command-domain code in `user-commands`; move only startup/reconciliation and Logseq entry-point registration to `user-commands-init`. |
| `pdf` -> `anydoc/pdf` | Good | Move PDF splitting and hashing utilities beneath AnyDoc. |
| `AnyDocPdfParser.ts` -> `AnyDocParser.ts` | Good with explicit contract | Rename the concrete implementation and singleton, but retain a PDF-specific injectable interface. |
| `parsePage` -> `parsePdfPage` | Good | Rename across implementation, tool, and tests with no alias. |
| Merge `frontmatter-parser` into split `template-engine` | Good | Create `renderer/` and `parser/`, preserve the top-level `template-engine` API facade, and remove `frontmatter-parser`. |

This is a structural refactor. Runtime behavior, persisted storage group names, virtual filesystem paths, command registration order, template diagnostics, and PDF caching semantics must remain unchanged.

## 3. Existing System

### 3.1 Initialization modules

- `src/core/skills/` contains only `initBuiltInSkillFiles.ts` and its barrel, so `skill-init` accurately describes its responsibility.
- `src/core/user-commands/` is mixed-purpose:
  - startup/integration: `initBuiltInCommandFiles.ts`, `registerCommandEntryPoints.ts`;
  - reusable domain behavior: `createUserCommand.ts`, `getEligibleCommandFiles.ts`, `classifyCommandInvocationContext.ts`, `constants.ts`, and `types.ts`.
- `src/index.ts` initializes stores, then built-in skills/commands, then registers command entry points. This ordering must remain intact.
- UI modules import `UserCommand` from the current `user-commands` barrel, confirming that the whole module is not initialization-only.

### 3.2 AnyDoc and PDF flow

- `src/chat-app/tools/impl/ParsePdfTool.tsx` is the sole production consumer of:
  - `src/core/pdf/PdfPageSplitter.ts`;
  - `src/core/pdf/getPdfSha256.ts`;
  - `src/core/anydoc/AnyDocPdfParser.ts`.
- `AnyDocPdfParser` lazily fetches and initializes AnyDoc WASM, caches one initialization promise, clears it after failure, and exposes a module-level singleton.
- `PdfMarkdownParser` is an injection boundary for `ParsePdfTool`; its current method is `parsePage` even though the accepted bytes and AnyDoc format are explicitly PDF.
- Parsed result persistence is separately owned by `AnyDocParseResultStore`; its group name (`anydoc-parse-results`), cache filenames, and Bash mount path are runtime contracts and are not source-layout concerns.

### 3.3 Template engine and frontmatter

- `template-engine` currently contains:
  - Mustache rendering (`parseTemplateString`);
  - runtime view/context creation (`MustacheView` and date/time/skill-list helpers);
  - Mustache syntax and variable validation (`validateMustacheTemplate`);
  - shared delimiter constants.
- `frontmatter-parser` contains:
  - exact frontmatter boundary extraction (`splitFrontmatter`, `FrontmatterSplit`);
  - frontmatter-aware Mustache policy validation (`validateFrontmatterTemplate`).
- `validateFrontmatterTemplate` already depends on template-engine internals, so merging its ownership removes an artificial sibling-module boundary.
- The skill and command render wrappers intentionally differ:
  - `renderSkillFileTemplate` preserves the original frontmatter prefix and renders only the body;
  - `renderCommandFileTemplate` discards frontmatter and returns only the rendered body.
  These domain policies must stay in `skill-parser` and `command-parser`.
- `splitFrontmatter` preserves source text and diagnostic offsets, including CRLF and malformed/unclosed frontmatter behavior. It must be moved, not casually rewritten.
- There is an existing dependency cycle through barrel imports:
  `template-engine/MustacheView -> SkillFileStore -> skill-parser barrel -> renderSkillFileTemplate -> template-engine`.
  The refactor must not preserve or worsen this cycle.

### 3.4 Conventions and constraints

- Folder `index.ts` files are established public facades; internal implementation files commonly use leaf imports.
- TypeScript and Vite both resolve the `src/*` alias.
- Tests mirror source layout and contain deep import mocks that must move with implementation files.
- No package dependency changes are needed.
- This is an internal plugin, so a clean import-path break is reasonable; obsolete forwarding modules would only retain confusing boundaries.

## 4. Solution

### 4.1 Rename skill initialization module

Move without semantic changes:

```text
src/core/skills/index.ts                         -> src/core/skill-init/index.ts
src/core/skills/initBuiltInSkillFiles.ts         -> src/core/skill-init/initBuiltInSkillFiles.ts
tests/src/core/skills/initBuiltInSkillFiles.test.ts
                                                  -> tests/src/core/skill-init/initBuiltInSkillFiles.test.ts
```

- Keep the `initBuiltInSkillFiles` symbol unchanged.
- Update `src/index.ts` to import from `./core/skill-init`.
- Keep `SkillFileStore.groupName === "skills"`; this is persisted data identity, not a source directory name.
- Remove the empty old directory and leave no compatibility barrel.

### 4.2 Split user-command initialization from the command domain

Do **not** rename the whole current module. Use this boundary:

```text
src/core/user-commands/
  index.ts
  classifyCommandInvocationContext.ts
  constants.ts
  createUserCommand.ts
  getEligibleCommandFiles.ts
  types.ts

src/core/user-commands-init/
  index.ts
  initBuiltInCommandFiles.ts
  registerCommandEntryPoints.ts
```

Implementation details:

- Move only `initBuiltInCommandFiles.ts` and `registerCommandEntryPoints.ts`.
- Add/update `user-commands-init/index.ts` to export `initBuiltInCommandFiles` and `registerUserCommandEntryPoints`.
- Remove those two exports from `user-commands/index.ts`; retain reusable classifiers, constants, eligibility helpers, and all `UserCommand` types there.
- Update moved registration code to import `createUserCommand`, classifiers, eligibility helpers, and types from `../user-commands` leaf modules. `user-commands` must never depend on `user-commands-init`.
- Update `src/index.ts` to import startup functions from `./core/user-commands-init` while preserving initialization order.
- Keep UI type imports in:
  - `src/ui/launchers/showAICommandPaletteModal.ts`;
  - `src/ui/pages/AICommandPaletteModal/AICommandPaletteModal.tsx`;
  pointed at `core/user-commands`.
- Move only the initialization/integration tests:
  - `initBuiltInCommandFiles.test.ts`;
  - `registerCommandEntryPoints.test.ts`;
  to `tests/src/core/user-commands-init/`.
- Keep `getEligibleCommandFiles.test.ts` under `tests/src/core/user-commands/`.
- Keep `CommandFileStore.groupName === "commands"`.

### 4.3 Consolidate PDF support beneath AnyDoc

Move:

```text
src/core/pdf/PdfPageSplitter.ts  -> src/core/anydoc/pdf/PdfPageSplitter.ts
src/core/pdf/getPdfSha256.ts      -> src/core/anydoc/pdf/getPdfSha256.ts
```

- Retain `PdfPageSplitter`, `PreparedPdfPage`, and `getPdfSha256` names and behavior.
- Add `src/core/anydoc/pdf/index.ts` only if it is used consistently as the public PDF-utility facade; otherwise retain explicit leaf imports. Do not create an unused barrel.
- Update `ParsePdfTool.tsx` imports to the new location.
- Mirror the move for tests under `tests/src/core/anydoc/pdf/`.
- Do not move or rename `AnyDocParseResultStore`, its storage group, `${pdfHash}-page-${pageNo}.md` naming, or `/home/user/anydoc-parse-results` mount.
- Remove `src/core/pdf/` after all consumers move.

### 4.4 Rename the AnyDoc concrete parser and PDF operation

Move `src/core/anydoc/AnyDocPdfParser.ts` to `src/core/anydoc/AnyDocParser.ts` and use:

```ts
export interface PdfMarkdownParser {
    parsePdfPage(pdfBytes: Uint8Array): Promise<string>;
}

export class AnyDocParser implements PdfMarkdownParser { /* unchanged lifecycle */ }

export const anyDocParser = new AnyDocParser();
```

- Rename `AnyDocPdfParser` to `AnyDocParser` and `anyDocPdfParser` to `anyDocParser` so exported symbols agree with the new module name.
- Keep `PdfMarkdownParser` PDF-specific; it is the precise injected contract used by `ParsePdfTool`, while `AnyDocParser` is the concrete AnyDoc-backed implementation.
- Rename every interface implementation, invocation, test object key, mock type reference, and assertion from `parsePage` to `parsePdfPage`.
- Preserve lazy initialization exactly:
  - no WASM fetch before the first parse;
  - concurrent calls share one initialization promise;
  - successful initialization is reused;
  - failed initialization clears the promise and permits retry;
  - non-OK fetch responses throw;
  - conversion remains `toMarkdownBytes(pdfBytes, "pdf")`.
- Move/rename `tests/src/core/anydoc/AnyDocPdfParser.test.ts` to `tests/src/core/anydoc/AnyDocParser.test.ts` and update `ParsePdfTool.test.ts`.
- Do not retain old class, singleton, or method aliases.

### 4.5 Split and merge template-engine

Use the following responsibility layout:

```text
src/core/template-engine/
  index.ts
  constants.ts
  renderer/
    index.ts
    MustacheView.ts
    parseTemplateString.ts
    getModelInvokableSkillListString.ts
    getUserPreferredDayjsFormat.ts
    getUserTimeZone.ts
  parser/
    index.ts
    splitFrontmatter.ts
    frontmatterTypes.ts
    validateFrontmatterTemplate.ts
    validateMustacheTemplate.ts
```

Responsibilities:

- `renderer/` owns Mustache expansion, case-insensitive runtime views, Logseq/date/settings context, and model-invokable skill context.
- `parser/` owns frontmatter boundary parsing and all non-rendering template validation/diagnostics, including Mustache token validation.
- `constants.ts` remains neutral because delimiters are shared by parsing and rendering.
- `template-engine/index.ts` remains the public facade and exports the current API plus merged frontmatter exports:
  `MUSTACHE_TEMPLATE_TAGS`, `MustacheView`, `MustacheTemplateView`, `parseTemplateString`, context helpers, `validateMustacheTemplate`, `MustacheTemplateIssue`, `splitFrontmatter`, `FrontmatterSplit`, and `validateFrontmatterTemplate`.
- Submodules must not import the top-level facade; use sibling/leaf imports internally to avoid barrel cycles.
- Application/UI consumers should import public features from `src/core/template-engine`. Domain implementation modules may use explicit parser/renderer leaf imports to make dependency direction clear.

Move existing files rather than changing algorithms. In particular:

- `splitFrontmatter` must preserve exact `prefix + body === source`, half-open `matterRange`, CRLF handling, closing-delimiter handling, and unclosed-frontmatter behavior.
- `validateFrontmatterTemplate` must continue masking the prefix so body diagnostics retain document-relative offsets and must continue rejecting every Mustache tag in frontmatter.
- `validateMustacheTemplate` must preserve custom `<% %>` parsing, unknown-variable validation, section recursion, delimiter-change rejection, and bounded syntax diagnostics.
- `parseTemplateString` keeps its existing public name despite acting as a renderer; renaming it would add unrelated API churn.

Delete `src/core/frontmatter-parser/` after updating consumers in:

- `src/core/skill-parser/renderSkillFileTemplate.ts`;
- `src/core/command-parser/renderCommandFileTemplate.ts`;
- `src/ui/components/LogseqCodeEditor/extensions/yamlFrontmatter.ts`;
- command and skill editor extension factories;
- command and skill save validators.

Keep the two domain render wrappers in their existing modules and preserve their differing prefix policy.

### 4.6 Make the new template dependency graph stable

- Change `SkillFileStore` to import `parseSkillFile` from its leaf implementation instead of the `skill-parser` barrel. This prevents loading `renderSkillFileTemplate` on the path from `MustacheView` back into skill parsing and breaks the current cycle.
- Apply the same leaf-import rule to `CommandFileStore`/`parseCommandFile` for consistency and to avoid a parallel future cycle.
- Keep parser/renderer interaction one-way at implementation level. The parser validation code may obtain supported variable names through a small injected provider/internal parameter, with the public facade preserving the current one-argument async validation API. This prevents pure token/frontmatter logic from acquiring Logseq/store dependencies merely by import.
- Preserve `MustacheView.getVariableNames()` caching and failed-promise reset behavior at the facade/provider boundary.

Conceptual flow:

```text
template-engine public facade
  -> renderer/MustacheView (supported runtime variables)
  -> parser validators (source + supported variable names)

renderer/MustacheView
  -> SkillFileStore
  -> skill-parser/parseSkillFile leaf

skill-parser/renderSkillFileTemplate
  -> template-engine/parser/splitFrontmatter
  -> template-engine/renderer/parseTemplateString
```

  - `tests/src/core/template-engine/parser/validateMustacheTemplate.test.ts`;

- Update deep module spies in `MustacheView.test.ts` to renderer paths.

- Add focused coverage for `parseTemplateString` if moving it reveals that its current indirect coverage is insufficient; minimally verify supplied case-insensitive views and default view creation without changing behavior.
- Retain the command- and skill-render wrapper tests as regression coverage for body-only versus prefix-preserving output.
- Perform a final source/test search for old paths and symbols. There must be no live references to:
  - `core/skills`;
  - startup exports from `core/user-commands`;
  - `core/pdf`;
  - `core/frontmatter-parser`;
