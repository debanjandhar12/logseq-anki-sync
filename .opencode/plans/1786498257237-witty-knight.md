## 2. Final Requirement After Discussion With User

### 2.1 Clarification Q&A

- **Q: Should debug JSON be compact or pretty-printed?**  
  **A:** Both sections should be compact. The full section must remain the raw stored JSON string; current persistence already writes compact JSON.
- **Q: Which reversible artifact data should be removed?**  
  **A:** Remove the entire `artifact` field from tool-call parts, not only the `LogseqReversibleTransactionTracker` member.
- **Q: Should block reconciliation preserve existing blocks recursively?**  
  **A:** Yes. Reconcile children recursively by position, preserving overlapping block UUIDs.
- **Q: How should tool arguments and results be rendered?**  
  **A:** Use `Tool Args: <compact JSON>` and `Tool Result: <compact JSON>` child blocks.
- **Q: Should persisted but empty threads also disable the actions?**  
  **A:** Yes. Disable both actions whenever the active thread has no messages.
- **Q: How should source, data, and generative-UI assistant parts be handled?**  
  **A:** Omit them along with reasoning and attachments; export only assistant text and tool-call parts.
- **Q: How should a tool call without a result be represented?**  
  **A:** Write `Tool Result: null`.
- **Q: What should replace the unclear `chatDebugJson` module name?**  
  **A:** Use `ChatDebugReportFormatter`.
- **Q: Should the two new classes be instantiated or expose static methods?**  
  **A:** Follow the project convention and use static methods.

### 2.2 Final Summarized Requirements

- Add `Export as Page` and `Copy Debug JSON` to `ThreadTopToolBarMore`; keep development-only Devtools behavior unchanged.
- Disable both chat actions when the scoped thread is new/deleted/unavailable, has no persisted remote ID, has no active-branch messages, or an action is already in progress. Use the menu primitive's real `disabled` prop and visible disabled styling.
- Copy exactly the requested two-section fenced text. Read `thread/<threadId>` as a raw string so the full section is identical to storage. Parse a copy, recursively remove the complete `artifact` property from every object whose `type` is `tool-call` (including nested tool-call messages), compactly serialize it, and use that as the first section.
- Export the currently selected assistant-ui branch to the deterministic page `_chat_export_${threadId}_${thread title}`. Prefer the active thread-list title, then the stored title, then the existing `generateTitle(threadId, messages)` fallback. Trim only outer title whitespace; do not silently rename or sanitize the specified page name.
- Represent every user message as a top-level block using its text parts joined in order. Attach subsequent assistant output to the nearest preceding user block. Each assistant text part is a separate child; each tool call is a separate child with exactly two children for compact args and result. Omit reasoning, attachments, and every other non-text/non-tool part. Treat a missing tool result as `null`.
- Create the page without a placeholder block if it is absent. Never delete/recreate an existing page. Reconcile every sibling list recursively by positional index: update differing shared blocks, remove excess trailing blocks from the end, and append missing blocks in order. Preserve the UUIDs of all shared positional blocks.
- On success, show a success notification; after page export, navigate to the exported page. On failure, log through the centralized chat logger, show an error notification, and do not copy partial debug output or navigate after a failed export.
- Implement the two export modules as PascalCase stateless utility classes: `ChatPageExporter` and `ChatDebugReportFormatter`. Their filenames must match their principal classes, and callers must use static APIs rather than importing free functions.

## 3. Existing System

### 3.1 Toolbar and active-thread state

- `src/chat-app/components/ThreadTopToolBar.tsx` already renders `ThreadTopToolBarMore`; `handleExportAsPage` is currently a `not implemented` toast and there is no debug-copy action.
- The toolbar already reads `state.thread.messages`. `state.threadListItem` also exposes `id`, `remoteId`, `title`, and `status`; statuses include `new`, `regular`, `archived`, and `deleted`.
- A newly opened assistant-ui thread is an optimistic local item (`status: "new"`, no `remoteId`) and is not persisted until initialization. Therefore `remoteId` is the correct storage/export identity, while the local ID must not enable these actions.
- `state.thread.messages` is the selected active branch. The persisted `ExportedMessageRepository.messages` may contain inactive branches, so page export must use toolbar state rather than flattening storage.
- `ThreadListItemMorePrimitive.Item` is Radix-backed and accepts `disabled`; the local menu classes need explicit `data-[disabled]` styling.

### 3.2 Thread storage and reversible artifacts

- `src/core/stores/thread-store/ThreadStore.ts` writes `JSON.stringify(threadData)` through `LogseqPluginStorageManager` under `thread/<threadId>`.
- `ThreadStore.loadThread()` parses storage and collapses missing, malformed, and backend errors to `null`; it cannot provide exact raw text or actionable failures.
- The full stored payload is `ThreadFileData`, containing metadata and an optional complete `ExportedMessageRepository` branch graph.
- Reversible Logseq state is stored in assistant `tool-call` parts' `artifact` property. Tool-call parts can themselves contain nested `messages`. Existing code creates, reads, patches, and preserves artifacts but has no artifact-free export utility.
- `src/logseq/WindowBridge.ts` is the project abstraction for the plugin sandbox window and should mediate `navigator.clipboard` access.

### 3.3 Message and page behavior

- Assistant-ui user parts include text and attachment/data types; assistant parts include text, reasoning, tools, sources, files/images, data, and generative UI. Only user text plus assistant text/tool calls are in scope.
- Existing UI grouping in `AssistantMessage.tsx` is presentation-only. The exporter must iterate original `message.content` order so sibling block order matches the transcript.
- `src/logseq/LogseqEditor.ts` currently wraps `updateBlock` but not page lookup/creation, block-tree lookup, insertion, or removal.
- Logseq provides `getPage`, `createPage`, `getPageBlocksTree`, `insertBlock`, `updateBlock`, and `removeBlock`. `createPage` and `insertBlock` may return `null`; wrapper methods must turn unexpected nulls into clear failures or refetch after page creation.
- `insertBlock(parentUuid, content, {sibling: false, end: true})` appends a child. Passing a page UUID therefore appends a root block; passing a block UUID appends a nested child.
- Deleting a root block removes its descendants. Reconciliation must not separately delete descendants of an excess parent.
- `LogseqNavigator.goToBlock(page.uuid)` is the established page/block navigation abstraction.
- There is no atomic Logseq transaction spanning recursive edits. A failed run may leave a partially reconciled export page; rerunning the positional reconciliation will converge it to the desired tree.

### 3.4 Testing and conventions

- Vitest uses jsdom and includes `*.test.ts` files. Current component-related tests favor exported pure functions and injected dependencies rather than mounting the full assistant-ui provider tree.
- Unit tests can stub `logseq`, storage, `WindowBridge`, and `LogseqEditor`; graph integration tests must use the existing Logseq API availability guards.
- Production diagnostics must use `createLogger(LoggerCategory.CHAT_UI)`, never `console.log`.
- Significant features should be documented under `docusaurus/`; this checkout currently has no `docs/` directory even though `sidebars.js` references one.

## 4. Solution

### 4.1 Add raw thread access and debug JSON transformation

**Modify `src/core/stores/thread-store/ThreadStore.ts`:**

- Add `ThreadStore.loadRawThread(threadId): Promise<string>` that calls `LogseqPluginStorageManager.getFileContent(ThreadStore.groupName, threadId)` and returns the value unchanged.
- Throw a descriptive error when storage does not return a string. Do not catch read errors in this method; callers need to report a failed copy instead of creating misleading output.
- Leave `loadThread()` behavior unchanged for compatibility with current adapters.

**Add `src/chat-app/export/ChatDebugReportFormatter.ts` (replacing the interim `chatDebugJson.ts` name):**

- Add a stateless `ChatDebugReportFormatter` class with a public static `format(rawThreadJson)` method, following project conventions such as `LogseqPageDataPrinter` and serializer classes.
- Keep recursive artifact removal as a private static implementation detail; verify it through the public formatted report rather than retaining free-function compatibility exports.
- Implement a pure recursive clone/transform over parsed JSON:
  - map arrays in order;
  - copy object keys in insertion order;
  - when an object has `type === "tool-call"`, omit its own `artifact` key entirely;
  - recursively transform every retained value, including `messages`, so nested tool calls are covered;
  - preserve `artifact` keys on non-tool objects and never mutate the parsed input.
- Implement `ChatDebugReportFormatter.format(rawThreadJson)`:
  1. `JSON.parse` the raw value (failure aborts before clipboard access);
  2. transform and compactly `JSON.stringify` the result;
  3. return exactly:

  ```text
  Chat Data without logseq reversible artifacts:
  ```
  <compact artifact-free JSON>
  ```

  Full Chat Data JSON:
  ```
  <raw stored JSON>
  ```
  ```

  Build this with newline-joined strings and fences without a language identifier. Do not add a trailing explanation or log either JSON payload.

### 4.2 Build the page-export model

**Add `src/chat-app/export/ChatPageExporter.ts` (replacing the interim `chatPageExport.ts` module):**

- Add a stateless `ChatPageExporter` class with public static `resolveTitle`, `createPageName`, `createBlockTree`, and `exportPage` methods. Keep `DesiredLogseqBlock` and `ChatPageExporterDependencies` as exported types for tests.
- Define a small neutral tree type such as `{content: string; children: DesiredLogseqBlock[]}`; keep assistant-ui types out of `LogseqEditor`.
- Implement `ChatPageExporter.createBlockTree(messages)` by walking active-branch messages in order:
  - User message: make a top-level block whose content is its text parts joined with `\n\n`; ignore its attachments and non-text parts. Keep an empty user block when it has no text so following assistant output still has its required parent.
  - Assistant message: append exported parts to the closest preceding user block. A text part becomes one child containing the exact text. A tool-call becomes `Tool Call: ${toolName}` with `Tool Args: ${compactJson(args)}` and `Tool Result: ${compactJson(result ?? null)}` children.
  - Omit reasoning, files/images, sources, data, generative UI, nested tool messages, artifacts, approval metadata, model content, timing, and all other non-text/non-tool fields.
  - Omit system messages. If an assistant message appears before any user message, throw a descriptive malformed-transcript error rather than violating the requested hierarchy.
- Implement compact tool-value serialization that preserves explicit falsey values (`false`, `0`, `""`, `null`), maps only an absent result to `null`, and throws if JSON serialization fails or returns `undefined` for a present unsupported value. This prevents `[object Object]` or misleading blocks.
- Implement `ChatPageExporter.createPageName(threadId, title)` as exactly `_chat_export_${threadId}_${title.trim()}`. Resolve title through `ChatPageExporter.resolveTitle` from active UI title, raw stored title, or `generateTitle(threadId, messages)`.

### 4.3 Extend `LogseqEditor` and reconcile the tree recursively

**Modify `src/logseq/LogseqEditor.ts`:**

- Add typed wrappers for page lookup, page creation without an initial block, page block-tree retrieval, child insertion, and block removal. Continue using the existing `updateBlock` wrapper.
- Normalize page-tree results enough to guarantee recursive code receives entities with UUIDs and nested children. Resolve UUID tuples through `getBlock(..., {includeChildren: true})`, and fail if a child cannot be resolved instead of treating it as absent.
- Make insertion fail clearly if Logseq returns `null`.

**In `ChatPageExporter.ts`, implement page acquisition and reconciliation behind `ChatPageExporter.exportPage`:**

1. Look up the exact page name.
2. If absent, create it with `{redirect: false, createFirstBlock: false}`; if creation returns `null`, refetch by exact name to handle Logseq's nullable/concurrent behavior, then fail if still absent.
3. Fetch the existing root tree once.
4. At each sibling list, compute the shared positional count:
   - for every shared index, update content only when `(current.content ?? "") !== desired.content`, then recurse into that block's children;
   - remove excess current blocks from the final index down to the desired length, allowing parent removal to delete its subtree;
   - append missing desired blocks in ascending order with `{sibling: false, end: true}`, then recursively add each new block's children.
5. Return the existing/created page UUID and exact page name. Never invoke `deletePage`, recreate an existing page, or replace shared blocks.

Record operation context (page/thread identity and positional location, but not message content) in thrown errors so toolbar logging is actionable. Stop at the first failed Logseq API call; a future rerun safely converges from the partial state.

### 4.4 Wire both actions into `ThreadTopToolBarMore`

**Modify `src/chat-app/components/ThreadTopToolBar.tsx`:**

- Read one scoped state snapshot containing active messages and `threadListItem` identity/title/status.
- Derive availability from `status` being `regular` (the active thread should not normally be archived), non-empty `remoteId`, and `messages.length > 0`. Also disable both items while either action is running. Treat `new`, `deleted`, missing state, and empty threads as disabled.
- Add a shared operation state (`"export" | "copy" | null`) to prevent double invocation and cross-action races. Each handler captures thread ID, title, and messages before awaiting so a thread/branch switch cannot mix data.
- `Copy Debug JSON` handler:
  1. raw-load the persisted thread;
  2. build the exact clipboard string through `ChatDebugReportFormatter.format(rawThreadJson)`;
  3. obtain the sandbox window through `WindowBridge.getWindow()`, validate `navigator.clipboard?.writeText`, and await the write;
  4. show a success toast only after the write resolves.
- `Export as Page` handler:
  1. raw-load/parse thread metadata only as a title fallback;
  2. resolve title/page name and build the desired tree through `ChatPageExporter` static methods before mutating Logseq;
  3. create/reconcile the deterministic page through `ChatPageExporter.exportPage` and `LogseqEditor` wrappers;
  4. navigate with `LogseqNavigator.goToBlock(pageUuid)` and show a success toast.
- Catch action failures, log them with a module-level `LoggerCategory.CHAT_UI` logger, and attempt an error toast. Catch notification failure separately so it does not overwrite the original result. Clear busy state in `finally`.
- Extend `ThreadTopToolBarMoreProps` with the copy callback and common disabled flag. Render `Copy Debug JSON` after `Export as Page`; pass `disabled` to both and add `data-[disabled]:pointer-events-none`, `data-[disabled]:cursor-not-allowed`, and `data-[disabled]:opacity-50`. Keep Devtools independent.
- Update the component's existing `Changes:` comment to record the new customized menu actions and disabled-state behavior, per `src/chat-app/AGENTS.md`.
