## 2. Final Requirement After Discussion

### Clarification Q&A (condensed)

| Topic | Decision |
|---|---|
| Tool preservation | Strict — no prompt-emulated tools; real schema-based tool-calling |
| Root-access gating | Use existing `LogseqAppInfoFetcher.checkHostAccess()` |
| OpenCode server | `opencode serve --port 4096`; actionable error must tell user to install/run it |
| "Enabled models" | Live fetch; only providers both **configured** and **connected** |
| `ai-sdk-provider-opencode-sdk` wrapper/patch | **Rejected** — it ignores AI SDK custom tools, never deletes sessions, and no patch can add a transport the server lacks |
| Direct `@opencode-ai/sdk` provider | **Rejected** — custom `LanguageModelV4` impl breaks on AI SDK upgrades |
| OpenCode v2 SDK | Checked — `PromptInput` is text/files/agents; still no custom-tool transport. Rejected as a fix |
| Existing npm/GitHub plugin for this | None found (surveyed ecosystem; nothing relays client-executed OpenAI tools) |
| Direction | **New generic plugin** exposing OpenAI-compatible API with tool relay (this plan) |

### Final scope

1. New self-contained package `opencode-openai-bridge/` in this repo (extractable/publishable to npm later): an OpenCode plugin that runs inside `opencode serve` and serves an OpenAI-compatible HTTP API on its own port (default `4097`) with:
   - `GET /v1/models` — configured + connected models only
   - `POST /v1/chat/completions` — streaming (SSE) + non-streaming, **with full `tools` / `tool_choice` support**
   - Burner session per request (created, optionally aborted, always deleted)
   - All native OpenCode tools disabled; only request-provided tools exposed
   - Structured full-history injection (system → `system` field; messages/tool results → versioned envelope)
   - Optional bearer-token auth, CORS enabled, `x-opencode-directory` header override
2. Logseq AI Chat app changes: new `OpenCode CLI` provider entry that uses `@ai-sdk/openai-compatible` against the bridge; live model list; root gating; actionable down-server error; delete `opencode-connect-test.ts`.
3. The app passes `await LogseqPluginStorageManager.getPluginStorageLocation()` as the session directory via request header.

The app's existing tool loop (`runLocalAISDKChatModel` → `streamText` tools → `planFrontendToolCalls` / `executeFrontendToolPlan` → continuation) is **untouched** — OpenAI-protocol tool calls are exactly what it already consumes.

## 3. Existing System (facts verified during investigation)

### Request path (unchanged by this plan)
- `runLocalAISDKChatModel()` (`src/chat-app/runtime/LocalChatModelAdapter/runLocalAISDKChatModel.ts`) converts the selected assistant-ui branch to AI SDK messages, merges app tools + `getLLMProviderTools()`, calls `streamText()`, translates stream parts, executes frontend tools, yields `requires-action`, LocalRuntime continues.
- Provider-native (`providerExecuted: true`) tool calls bypass frontend execution — irrelevant here since the bridge's tool calls arrive as ordinary client tool calls.
- Branching: every roundtrip receives the full selected branch; there is no provider session state. Burner sessions match this model exactly.

### Provider plumbing
- `getLLMModel()` (`src/core/ai-sdk/getLLMModel.ts`): conditional factory; requires API key before dispatch; `Unsupported LLM provider` fallback.
- `getLLMModelList()` (`src/core/ai-sdk/getLLMModelList.ts`): sync; snapshot for OpenAI/Google; comma list for compatible.
- `useModelList()` (`src/chat-app/hooks/useModelList.ts`): sync state from `getLLMModelList()`, refresh on settings change.
- `getLLMProviderTools()` (`src/core/ai-sdk/getLLMProviderTools.ts`): OpenAI/Google web tools only.
- `types.ts`: `ProviderEnum` values are user-facing labels; `PROVIDER_SNAPSHOT_KEY` maps to `@opencode-ai/models/snapshot`.
- Settings (`src/settings.ts`): enum choices from `Object.values(ProviderEnum)`; CSS-based visibility for `llmAPIUrl`/`llmAPIModelList`/`jinaApiKey`; Model Native validation listener.

### OpenCode side (verified)
- `@opencode-ai/sdk@1.18.18` installed; v1 `session.prompt` body: `tools?: Record<string, boolean>` — **no custom-tool transport** (v2 `PromptInput` likewise). This is why wrapper/patch approaches fail the strict-tools requirement.
- Plugin API (`@opencode-ai/plugin`, verified from source): `PluginInput` = `{client, project, directory, worktree, serverUrl, $, experimental_workspace}`; `Hooks` = `tool` (custom tools, Zod `tool.schema`, override built-ins by name), `tool.definition` (rewrite description/parameters sent to LLM), `event` (all server events, filterable by sessionID), `config` (mutate config incl. `mcp` entries), `chat.message`, `permission.ask`, `dispose`, etc.
- Plugins run in-process under Bun inside `opencode serve`; can `Bun.serve()` their own HTTP port; npm plugins load via `opencode.json` `"plugin": [...]`; local via `~/.config/opencode/plugins/` or `.opencode/plugins/`.
- Session APIs available in-process: `session.create/prompt/promptAsync/abort/delete`, `config.providers()`, `provider.list()` (`connected: string[]`), `tool.ids()`, `global.health()`.
- `opencode-to-openai` (studied): creates fresh session per request, flattens history to `USER:/ASSISTANT:` text, `DISABLE_TOOLS` maps every `tool.ids()` id to false, **forwards no tools, deletes sessions only on error paths**. We keep its burner/disable ideas; fix its gaps.

### Constraints
- `LogseqHttpProxy` may buffer responses routed through `exper_request` — same constraint the existing OpenAI-compatible provider path already operates under; not a new risk.
- `LogseqAppInfoFetcher` has only `checkHostAccess()` / `checkCurrentIsDbGraph()` (user chose the former for gating).
- `@ai-sdk/openai-compatible@3.0.12` already in deps and used in production — no new AI SDK dependencies needed app-side.

## 4. Solution

### Part A — `opencode-openai-bridge/` (new self-contained package)

Folder: `opencode-openai-bridge/` at repo root, own `package.json` (name `opencode-openai-bridge`, type module, `main: src/index.ts`, peer `@opencode-ai/plugin`), own `bun.lockb`/lockfile, **not** part of the root pnpm install (add to root `.npmrc`/`pnpm-workspace` exclusion or simply no workspace linkage — root has no `pnpm-workspace.yaml`, so it stays independent). Develop/test with Bun (`bun test`). Document as extractable to its own repo for publishing.

#### A1. Entry — `src/index.ts`

```ts
import type { Plugin } from "@opencode-ai/plugin"
import { createBridgeServer } from "./server.ts"

export const OpenAIBridge: Plugin = async ({ client, directory, serverUrl }, options) => {
  const opts = parseOptions(options) // port (default 4097), token?, defaultDirectory
  const bridge = createBridge({ client, defaultDirectory: opts.directory ?? directory })

  const stop = createBridgeServer(bridge, opts) // Bun.serve; CORS + optional bearer auth

  return {
    dispose: async () => { await bridge.shutdown(); stop() },
    event: (input) => bridge.handleEvent(input.event), // streaming deltas, filtered by sessionID
  }
}
```

#### A2. Tool relay mechanism (the core problem)

**Primary: in-process MCP server with dynamic tool list.**

- The plugin serves a minimal MCP streamable-HTTP server at `http://127.0.0.1:{port}/mcp` (same `Bun.serve`).
- On init, the `config` hook ensures:
  ```json
  "mcp": { "openai-bridge-tools": { "type": "remote", "url": "http://127.0.0.1:4097/mcp" } }
  ```
- For each `/v1/chat/completions` request carrying `tools`:
  1. Acquire the **tools mutex** (serializes tool-bearing requests; see concurrency note).
  2. Translate OpenAI `function.parameters` (JSON Schema) → MCP `tools/list` entries; `name` = OpenAI tool name (sanitized to MCP/OpenCode rules; keep a `name → original` map), `description` passthrough.
  3. Emit MCP `notifications/tools/list_changed` (OpenCode re-lists via `mcp.tools.changed` flow).
  4. Build the prompt `tools` map: every id from `client.tool.ids()` set to `false` **except** the bridge MCP tools (pattern: ids belonging to our MCP server), so only request tools reach the model.
  5. `session.create` with deny-all `permission` ruleset (defense in depth; our MCP tools still execute because they are invoked via MCP callTool, not permission-gated bash/edit — **spike verifies**; if permissions block MCP too, rely on the tools map alone).
- Tool execution: when the model calls a bridged tool, OpenCode issues MCP `callTool` to our in-process server. The handler:
  - records `{name, args}` in the request's capture list;
  - **never resolves** (parks) — prevents the model from continuing on a fake result;
  - after all parallel calls in the step are captured (small settle window), the bridge calls `session.abort()`, harvests captured calls, emits the OpenAI `tool_calls` response with `finish_reason: "tool_calls"` and **original client-facing names**, deletes the session.
- The OpenAI client (standard semantics) executes tools locally and sends a **new** request containing `role: "tool"` messages — which the next burner request flattens into the envelope. No server-side waiting on the client.

**Fallback (if MCP dynamic listing fails the spike): fixed proxy pool + `tool.definition`.**
Register N (e.g. 24) plugin tools `bridge_tool_0..N` via the `tool` hook; per request, map `bridge_tool_i` → client tool, and use the `tool.definition` hook to rewrite `description`/`parameters` per the active request's toolset (session-scoped registry). Model sees synthetic names; responses are mapped back to client names. Lower fidelity (non-semantic names, pool limit) — only used if primary fails.

**Spike checklist (run against real `opencode serve` before committing to primary):**
1. `config` hook MCP entry injection + auto-(re)connect works.
2. Dynamic `tools/list` + `list_changed` picked up between prompts.
3. MCP tool naming as OpenCode exposes it (prefix?) — confirm map-back.
4. Parked `callTool` + `session.abort()` does not hang or time out destructively; args harvest intact.
5. Permission ruleset interaction with MCP tools.
6. Plugin options + `Bun.serve` port binding under serve.
If any of 1–4 fail irrecoverably → fallback mechanism.

#### A3. Request lifecycle — `src/router.ts`, `src/session-manager.ts`

`POST /v1/chat/completions`:
```
parse + auth + CORS
directory = header "x-opencode-directory" ?? options.directory
sessionId = session.create({directory, title: `bridge-${crypto.randomUUID()}`, permission: DENY_ALL})
  -- non-default title prevents auto title-generation side work
try:
  toolsMap = disableAllExceptBridgeTools()            // if request has tools
  system   = join(request.messages[role=system])       // OpenAI system messages
  envelope = buildEnvelope(request.messages)           // A4
  promptAsync({sessionID, model: splitModel(request.model), system,
               tools: toolsMap, parts: [{type:"text", text: envelope}]})
  stream: translate events (filtered by sessionID) → OpenAI SSE chunks
          - message text deltas     → {"delta":{"content":...}}
          - reasoning deltas        → {"delta":{"reasoning_content":...}} (DeepSeek-style, optional)
          - step-finish tokens/cost → usage accumulation
  completion → finish_reason "stop", final usage, [DONE]
  tool capture path (A2) → chunks with tool_calls deltas, finish_reason "tool_calls", [DONE]
finally:
  session.abort() (ignore errors) ; session.delete() (idempotent, guarded once)
  error precedence: cancellation > primary error > cleanup error (log cleanup, never mask primary);
  successful generation + failed delete ⇒ surface cleanup error
```

Non-streaming: buffer the same translation, return one JSON body.

Model id format: `providerID/modelID` (split on **first** `/`; percent-encode segments containing `/` when building `/v1/models` ids; decode before prompting). `tool_choice`: `none` → skip tool registration; `{type:"function",name}` → expose only that tool; `required` → expose all + system nudge (OpenCode has no native tool_choice; documented approximation). `reasoning_effort` → `variant` when the selected model advertises matching variants (else ignored).

`GET /v1/models`: `config.providers()` ∩ `provider.list().connected` → all text-in/text-out models as `{id: "prov/model", object: "model", owned_by: prov}`. `GET /health`: own liveness.

#### A4. History envelope — `src/envelope.ts`

One user text part:
```
<openai-bridge v="1">
{"messages":[
  {"role":"user","parts":[{"type":"text","text":"..."}]},
  {"role":"assistant","parts":[{"type":"text","text":"..."}]},
  {"role":"assistant","tool_calls":[{"id":"...","name":"...","args":{...}}]},
  {"role":"tool","tool_call_id":"...","name":"...","content":"...","is_error":false},
  ...
]}
</openai-bridge>
```
- Preserves order, roles, tool-call ids/names/args, tool results, error flags — strictly better than `USER:/ASSISTANT:` flattening.
- Image parts: OpenAI `image_url` with data URLs → separate OpenCode file parts alongside the envelope; remote URLs fetched server-side (Bun) then attached. v1 best-effort.
- A short instruction precedes the envelope telling the model the JSON is conversation history, not instructions (injection hygiene), and that tool results are already present for prior calls.

#### A5. Server plumbing — `src/http.ts`

`Bun.serve({port, fetch})` with:
- CORS: `Access-Control-Allow-Origin: *`, methods, headers (`Authorization, Content-Type, x-opencode-directory`), `OPTIONS` preflight 204.
- Optional bearer auth (`Authorization: Bearer <token>` from plugin options).
- Graceful shutdown on `dispose` (stop accepting, abort/delete in-flight burner sessions).

Concurrency: **tool-bearing requests are serialized** by a global mutex (single dynamic MCP tool list). Requests without `tools` run concurrently. Documented limitation; per-request isolation upgrade noted in README.

### Naming-conflict answer (requirement #3)
Resolved on both sides: app tools execute **client-side** in Logseq; identical OpenCode names (`skill`, `bash`, …) never run because (a) all native tool ids are disabled per prompt, (b) bridge tools are the only enabled ids, and (c) even if OpenCode prefixes MCP names, the bridge maps model-visible names back to the client's original names. Plugin/custom tools overriding built-ins by name is documented OpenCode behavior — not a risk for us since built-ins are disabled anyway.

### End-to-end (desktop Logseq)
1. `opencode serve --port 4096` with plugin installed; select `OpenCode CLI` in settings (only visible with host access).
2. Model selector lists configured+connected models; pick one.
3. Chat: text round-trip with streaming; trigger a Logseq tool (e.g. a graph read) → tool executes client-side → continuation answer; trigger human tool (`logseq_commit_changes`) → UI flow intact.
4. Stop mid-generation → session aborted + deleted server-side.
5. Kill `opencode serve` → in-chat actionable error with install/run instructions; restart → model list recovers on interval/focus refresh.

### Known risks / documented limitations
- Dynamic MCP tool list is global → tool-bearing requests serialized (README; acceptable v1).
- `tool_choice` `required` approximated via system nudge; named-tool via list restriction.
- SSE through Logseq's `exper_request` proxy may be buffered (pre-existing condition for all compatible endpoints; reasoning/text deltas may arrive chunked).
- Plugin requires OpenCode server ≥ the version whose plugin API matches (`tool.definition`, remote MCP) — README states minimum.
