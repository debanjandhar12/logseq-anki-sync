# PDF-Level Parse Cache Plan

## Original User Requirement

> Currently, Pdf parse tool accepts a range parameter for what pages to parse. We need to remove that parameter. We also need to remove CHAT_APP_AGENT_ANYDOC_MAX_PAGE_PARSE.
>
> Instead, we will parse all pages of pdf when tool is called and save each page separately as we are doing now. Earlier we had limits in place since the understanding was that it is expensive operation. But in reality, it takes only around 5ms for a single page parsing. Hence, we are changing approach.
>
> Aditionally, we need to change the result text to: "Parsed pages stored in ${JUST_BASH_USER_HOME}/${new store.groupName} as: ${hash}-page-<page no>. Use bash to list / search the pages and read the relevent context."
> [Do not hardcode the parts... instead use the variables such as JUST_BASH_USER_HOME etc]
>
> Also change the save file return type from string to void if it is not required or used.
>
> Also, currently, when parse error such as Unsupported / Malformed / Encrypted / ResourceLimit / MissingPart / Io occurs in a single page, the entire tool call fails. Instead, we should make the entire tool call fail only when more than 50% of pages results in error [Please suggest what error will be appropriate here].
> The threshold should be configurable from src/contants.ts. When a page gets error (without entire tool getting marked as failed), simply store the error instead of parsed result in the store file [along with a note that parsing failed for that page].

Follow-up clarification:

> if a page is failed to parse but file exists, we will not reparse...
>
> Infact, we should avoid reparse as long as a pdf is parsed once (not page level check)

## Final Requirement

### Clarification Q&A

- Page conversion failures such as I/O or image-only/unsupported pages are written to their normal page files. Their existence prevents those pages from being parsed again.
- Incomplete parse: save each page outcome immediately. If execution stops before later pages are handled, those page files remain absent; the next invocation preserves existing success/failure files and parses only the missing pages.
- Failures that prevent writing a page file may be retried on a later invocation; this is acceptable.
- Existing cache migration: not needed because the plugin has not been released.
- PDF completion strategy: do not persist a metadata/manifest record. Determine completeness by scanning the PDF's stored page files.

### Summary

- Treat a PDF as already parsed when the storage scan contains every expected deterministic page filename for that PDF hash.
- Use one storage listing/read operation for the PDF rather than issuing an existence query for each page. When the PDF is complete, skip the entire AnyDoc page-conversion phase and never reparse stored failure pages.
- When an earlier attempt is incomplete, reuse all existing page files, including failure files, and parse only missing pages.
- Preserve the current aggregate rule: page failures are stored, and the tool call fails only when the failure ratio is strictly greater than the configured 50% threshold.
- Keep the aggregate cached result consistent by identifying stored failure notes while reading the completed PDF's page results.
- Keep parse-failure formatting and recognition in `ParsePdfTool`; they are parsing policy, not generic storage behavior.

## Proposed Solution

### `src/core/stores/anydoc-parse-result-store/AnyDocParseResultStore.ts`

- Keep deterministic page filenames and `save(...): Promise<void>`.
- Remove public `isParseFailure` and `createParseFailure`; the store should not understand AnyDoc error semantics or Markdown failure-note formatting.
- Replace per-page cache probing with one PDF-scoped retrieval API that:
  - Calls `LogseqPluginStorageManager.getFiles(groupName)` once.
  - Selects only filenames matching the exact `${pdfHash}-page-<positive integer>.md` format.
  - Loads the selected files' contents and returns page number/content pairs in page order.
- Validate the PDF hash before constructing the filename matcher so unrelated files or prefix collisions cannot be treated as pages for the PDF.

### `src/chat-app/tools/impl/ParsePdfTool.tsx`

- Define the stable parse-failure marker, failure-note formatting, and failure-note recognition locally in the tool.
- After loading, hashing, and splitting the PDF, retrieve the PDF's stored pages through the single PDF-scoped store operation.
- Build a map keyed by stored page number and compare it with all pages emitted by `PdfPageSplitter`.
- Completed PDF control flow:
  - If every expected page number has stored content, invoke `pdfMarkdownParser.parsePage` zero times.
  - Count failure-marker files from the retrieved contents.
  - Return the normal result or the same aggregate threshold error based on the current constant.
- Incomplete PDF control flow:
  - Skip every page already represented in the stored-page map, regardless of whether it contains parsed Markdown or a failure note.
  - Parse only missing pages.
  - Convert supported page-level parser errors into the local failure-note format and save them under the normal page filename.
  - Save each successful Markdown result or failure note immediately before proceeding to the next page. Do not accumulate unsaved page outcomes until the conversion loop completes.
  - If parsing is cancelled or another non-page-level failure interrupts execution, already saved page files remain durable and later invocations retry only pages without files.
  - If storing a page fails, fail the tool call immediately; because that page file is absent, a later invocation may retry it.
  - Count both stored and newly produced failure notes before applying the threshold.
- Keep storage, fetch, PDF loading/splitting, and cancellation errors as immediate tool failures; only page conversion errors participate in the page-error threshold.
- Keep the aggregate error explicit, for example: `PDF parsing failed for 3 of 5 pages (60%), exceeding the allowed 50% page-error threshold.`
- Keep the requested success text assembled from `JUST_BASH_USER_HOME`, `AnyDocParseResultStore.groupName`, and `pdfHash` rather than hardcoded path/hash values.

### `tests/src/core/stores/AnyDocParseResultStore.test.ts`

- Remove tests for store-level failure-note creation/detection.
- Add coverage that PDF-scoped retrieval returns only exact matching pages, ordered by page number, with their contents.
- Cover unrelated hashes/files and invalid PDF hashes.
- Retain coverage for deterministic filenames and the void save behavior.

### `tests/src/chat-app/tools/impl/ParsePdfTool.test.ts`

- Verify a first call parses and stores every page.
- Verify a fully stored PDF performs zero page conversions on a subsequent call.
- Verify a stored failure page is never reparsed.
- Verify an incomplete parse reuses all existing success/failure files and converts only missing pages.
- Verify an interruption after one or more pages leaves those page files stored and a later invocation resumes from the first missing page.
- Verify a page storage failure does not create that page file and allows that page to be retried later.
- Verify cached and newly generated failure notes both count toward the strict greater-than-50% threshold.
- Verify exactly 50% failures still succeeds and more than 50% returns the aggregate error.
- Verify failure notes include the page number and mapped AnyDoc error explanation.
- Keep schema and result-text assertions for the all-pages tool contract.
